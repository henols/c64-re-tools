<objective>
Make the store canonical and the Markdown memory map a generated view — and make the two
run-scoped-facts decisions concrete rather than a tension between D-24 and D-27.

**Reconciliation this plan owns (`<decisions_you_own>` #5).** D-24 makes the store canonical and the
memory map generated; D-27 keeps run-scoped facts in Markdown because the store is address-keyed
and has no shape for them. Resolution, in three parts:

1. **The provenance header is an INPUT to the renderer, not a region of its output.** It arrives as
   a JSON sidecar (`<capture>.provenance.json`) with a fixed, validated schema: capture path and
   SHA-256, `$01`, `$DD00` and the derived VIC bank, `$D018`-derived screen/charset, `$D011`/`$D016`
   mode, video standard, the live vector pair and its handler, and observed raster positions.
2. **The sidecar is hand-authored from the existing tools' output, and machine-validated.** Its
   values come from `c64-ram-capture`'s `compare.mjs digest` (the capture SHA-256) and
   `c64-program-recon`'s `derive.mjs vectors` / `vic` / `sprites` (the derived chain). It is NOT
   emitted by those scripts, because a producer under `.claude/skills/` runs in the tree CI never
   tests (`ci.yml` runs `npm test` only inside `.claude/mcp/vice`) — so the safety comes from the
   renderer validating the schema on the MCP side, where a test actually runs. A missing or
   malformed required key is a named error; the renderer never emits a `<placeholder>`.
3. **What stops a human hand-editing the generated artifact:** the rendered file opens with a
   banner naming the generator, the store path, the sidecar path and a `render_digest` over
   (sorted store query results + sidecar bytes + renderer version); and
   `vice-mcp r2000 render-memmap --check` re-renders and exits non-zero when the file on disk
   differs. That is the same discipline `resources-sync.test.ts` already applies to this repo's
   generated `.mjs`, in the one form that works in a consuming project rather than only in this
   repo (ENGINEERING_RULES.md §11).

**Second decision recorded here: the renderer embeds its layout in TypeScript rather than reading
`templates/memory-map.template.md` at runtime.** Reason, from Phase 10's D-06: `.claude/mcp/vice/*.ts`
exists as files on disk only under the Claude Code plugin route — both npm-installer routes launch
via `npx` — so a renderer resolving a path into the skills tree would silently fail to resolve for
npm-installed users. The template file becomes prose pointing at the generator (plan 11-12), and the
confidence vocabulary it defines is hardcoded in `r2000-confidence.ts`.

Purpose: criterion 1 says findings must be queryable "instead of re-deriving from Markdown prose".
That is only true by construction if the prose is generated from the queryable thing.

Output: the confidence convention, the renderer with its sidecar schema and drift mode, and the
`render-memmap` verb.
</objective>

Create `r2000-confidence.ts`:

- `CONFIDENCE_GRADES` — the five grades from the template, each with its canonical bracket token
  (`[confirmed-code]`, `[probable-code]`, `[confirmed-data]`, `[probable-data]`, `[unknown]`) and its
  human phrase. This is the ONE place the vocabulary is written down.
- `parseConfidencePrefix(comment: string): { grade, rest }` — extracts a leading bracket token.
  Behaviour on a malformed token is the point of the module: a comment beginning with a bracket
  token that is not exactly one of the five (a typo like `[confimed-code]`, wrong case, a plural, an
  underscore instead of a hyphen, extra whitespace inside the brackets) must THROW a named error
  (`R2000ConfidenceGradeError`) naming the offending token and listing the five valid ones. A comment
  with NO leading bracket at all returns `grade: null` — that is an ungraded comment, which is legal;
  what must never happen is a typo silently becoming an ungraded comment, because that is how a
  `[unknown]` row disappears from the "still unknown" query.
- `formatConfidenceComment(grade, evidence)` — the one place a graded comment is composed, so writers
  cannot invent a variant spelling.
- `searchQueryForGrade(grade)` — the literal string to pass to `r2000_search_disassembly`'s comment
  search to list every address still carrying that grade, so the "show me everything still unknown"
  query has exactly one spelling.

Header carries: WHY (r2000's block types carry classification but no confidence axis — `Code` cannot
distinguish "PC observed executing" from "reachable via a JSR, never run", and that distinction is
the memory-map template's most deliberate feature); the ONE authoritative place for the vocabulary
and the parser; and the what-NOT-to-do list — never accept a near-miss token, never add a sidecar
JSON keyed by address (a second store to keep in sync is the exact drift class criterion 1 closes),
never promote a row by editing its grade.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| a hand-authored provenance sidecar → a generated document presented as evidence | Unvalidated run-scoped facts would make a generated artifact look authoritative while carrying template placeholders |
| a human editor → a generated artifact | The drift class D-24 exists to kill; an edited generated file is a claim with no source |
| store comment text → the Confidence column | A near-miss grade token silently becoming "ungraded" removes a row from the "still unknown" query |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-11-GRADE-TYPO | Spoofing | `parseConfidencePrefix()` | mitigate | Task 1: a bracket token that is not exactly one of the five THROWS naming it; six near-miss typos pinned as failures |
| T-11-GEN-EDIT | Tampering | the rendered memory map | mitigate | Task 2/3: banner + `render_digest` over store results and sidecar bytes, plus `--check` exiting non-zero on drift; a store-side change alone must also register as drift |
| T-11-PLACEHOLDER | Spoofing | the provenance sidecar | mitigate | Task 2: `parseProvenanceHeader()` refuses `<hash>`/`<PAL/NTSC>`-shaped placeholders and reports every missing key at once |
| T-11-SKILLPATH | Denial of Service | resolving the layout from the skills tree at runtime | mitigate | Task 2: layout embedded in TypeScript; asserted by a zero-count grep for the template filename. Reason recorded (Phase 10 D-06: npm routes launch via `npx`) |
| T-11-SECOND-STORE | Tampering | a sidecar JSON keyed by address | mitigate | Task 1: explicitly rejected in the header — grades live in r2000 line comments, so there is no second address-keyed store to drift |
| T-11-SC | Tampering | npm/pip/cargo installs | accept | No package installed (phase-wide audit: no new package) |
