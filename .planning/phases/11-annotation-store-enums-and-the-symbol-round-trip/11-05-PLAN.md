<objective>
Put the annotation store on the tool surface: 17 curated `r2000_*` tools, one allow-list gate that
also recurses into batches, and a registration route that makes CLAUDE.md's interception
constraint moot by construction.

**Decision this plan owns (`<decisions_you_own>` #1 — the exact final tool list), under D-18's
rule that a tool earns its place by serving a named criterion:**

| Tool | Serves |
|---|---|
| `r2000_set_label_name` | criterion 1 (recon writes labels) |
| `r2000_set_comment` | criterion 1 (comments; carrier for D-25's confidence prefix) |
| `r2000_set_data_type` | criterion 1 (block types) |
| `r2000_add_scope` | criterion 1 (scopes) |
| `r2000_get_symbols` | criteria 1, 2, 4 (read labels back; `kind` filter) |
| `r2000_get_comments` | criteria 1, 2 (read comments back; D-25 grade queries) |
| `r2000_get_blocks` | criteria 1, 2 (read block classification back) |
| `r2000_get_cross_references` | criterion 2 (which addresses reference X) |
| `r2000_search_disassembly` | criteria 2, 3 (search labels/comments/instructions; the enum pairing passes) |
| `r2000_disassemble` | criterion 2 (render a range — measured working on a 64K project) |
| `r2000_get_binary_info` | criterion 1 (store identity/size; also the live counter-evidence to D-32) |
| `r2000_create_project_enum` | criterion 3 |
| `r2000_update_project_enum` | criterion 3 |
| `r2000_delete_project_enum` | criterion 3 (a regenerated enum set must be able to replace an old one) |
| `r2000_apply_enum_usage` | criterion 3 |
| `r2000_save_project` | all four (nothing persists without it) |
| `r2000_batch_execute` | criterion 1 (a memory map is dozens of annotations; without batching D-17's per-call spawn pays a load and a whole-file save each time) — gated per D-33 |

Excluded, each with its reason recorded in the module: the TUI-shaped tools
(`jump_to_address`, `get_disassembly_cursor`, `read_selected`, `toggle_splitter`) have no
criterion; `undo`/`redo` are useless under D-17's per-call lifecycle (history dies with the
process); `get_address_details` is D-32 (returns `OutOfRange` for **every** address on a 64K
project — `handler.rs:1894`'s `raw_data.len() as u16` wraps 65536 to 0 — and
`c64-ram-capture` produces exactly 64K, so this is every captured program; filed upstream as
issue #42); and `unpack_binary`, `read_region`, `search_memory`, `set_immediate_format` have no
criterion in this phase (`set_immediate_format` is the strongest later candidate).

**Decision this plan owns (`<decisions_you_own>` #4 — which manifest the family lands in):
NEITHER, and that is asserted, not assumed.** The reason is not preference: both manifests are
regenerated from a live host VICE server's own `tools/list` by `refresh-manifest.ts`, so a
hand-added `r2000_*` entry would be silently wiped on the next refresh — an r2000 child process is
never that host. The `vice_result_continue` precedent (`vice-proxy.ts:398-413`, registration at
`:3245`) is the established shape for a tool served entirely proxy-locally. Two consequences worth
stating: `fork-manifest-surface.test.ts`'s exact-62 gate and `stock-dispatch.test.ts`'s exact-38
dispatch-table gate both stay untouched, because this family is in neither structure; and because
`buildViceTool()` is used directly, no `r2000_*` runner can reach `forwardToVice()`, so
`rewriteArguments()` (at `vice-proxy.ts:2943` and `:1422`) is structurally unreachable and
CLAUDE.md's "derived tools must be intercepted before `forwardToVice()`" constraint is satisfied by
construction rather than by an interception. Task 3 makes that claim mechanical instead of prose.

Purpose: criterion 1's whole premise is that a later session can query these findings. Nothing
else in the phase works until this surface exists.

Output: `r2000-tools.ts`, its registration, the D-33 gate with its smuggling test, and a coverage
checker that can see `r2000_*` names in skill prose.
</objective>
