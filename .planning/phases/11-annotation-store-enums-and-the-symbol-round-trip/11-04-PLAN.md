<objective>
Become an MCP **client** for the first time, in one module, with every failure mode this
project's own history says will otherwise be reported as a success.

**Decision this plan owns (`<decisions_you_own>` #2, the module split).** The seam is
`r2000-mcp-client.ts` — spawn/protocol/correlation/failure-handling only, no knowledge of which
tools exist. Tool definitions, the curated allow-list and the D-33 batch gate live in
`r2000-tools.ts` (plan 11-05); the enum generator, renderer and confidence convention are their
own modules (plans 11-06, 11-08). Reason: CLAUDE.md's single-seam-per-concern rule, and the
concrete consequence that a client which knows tool names cannot be tested against a stub server.

**Decision this plan owns (`<decisions_you_own>` #3, `MCPClient` vs. hand-rolled), resolved by a
determinate rule rather than a preference.** RESEARCH.md recommends `@mastra/mcp`'s `MCPClient`
(already a declared dependency, zero new footprint) with a ~120-line hand-rolled
newline-delimited JSON-RPC client as the documented fallback, and names the fallback trigger as
"`MCPClient`'s heavier surface fights this phase's failure-handling discipline". Task 1 measures
that, against five properties this phase actually requires, and Task 2 implements whichever
passes all five. The properties, and why each is required here rather than nice to have:

1. An unanswered `tools/call` fails in bounded time. (`r2000_search_disassembly` on a large
   program is the one call that can be slow; a hang would take the whole plan step with it.)
2. A child that exits mid-call surfaces as a distinct error, not a timeout.
3. A spawn failure (`ENOENT`) surfaces as a distinct error naming the missing binary — the
   existing `runR2000()` message is the model.
4. The child's **exit code** is reachable after the session closes.
5. The child's **stderr** is reachable and attributable to the call.

(4) and (5) are not stylistic: RESEARCH.md's Anti-Patterns section requires that
`r2000_save_project` never be reported as persisted on the strength of its own text response
(`{"content":[{"type":"text","text":"Project saved to <path>"}]}` is a string, not a checksum),
and `r2000-verify.ts` exists in this repo because a zero exit code and an "All roundtrip
verifications passed" line were both lying. If `MCPClient`'s public API does not expose the
spawned child's exit code and stderr, it cannot satisfy the module's own success-refusal contract
and the fallback triggers. Whichever way the measurement lands, the verdict and its evidence go
in the module header.

Purpose: every `r2000_*` tool, the enum generator, the memory-map renderer and both symbol legs
all run through this one module. It is the phase's single point of failure and gets the phase's
most explicit failure handling.

Output: three fixed argv builders, the client seam, its failure-mode tests, and the closed-consumer-set
and `files[]` bookkeeping for all five new modules.
</objective>

- `saveAndVerify(projectPath, session)` — calls `r2000_save_project` and then proves persistence
  independently: re-read the project file from disk (size + mtime change is not enough — compare a
  content hash before and after, or re-open a FRESH child against the same path and re-query the
  mutated field). It returns a result that distinguishes "saved and re-read" from "the child said
  it saved". Never return the latter as success.

Failure handling, each a distinct named error class carrying the child's exit code and captured
stderr where available:
- spawn failure (`ENOENT`) → the `runR2000()`-style message naming `R2000_BIN` and
  `cargo install regenerator2000`;
- a JSON-RPC `error` object on the response → surface `code` and `message` verbatim, never
  flattened into a generic failure;
- an unanswered request → bounded by an explicit per-call timeout (default configurable via one
  named constant, not a magic number at the call site);
- a mid-call child exit → distinct from a timeout, naming the exit code and stderr;
- a non-zero exit AFTER an otherwise-successful call sequence → the whole session fails, because
  `r2000-verify.ts`'s incident is exactly a zero-exit lie in the other direction;
- a response whose `id` does not match the pending request → refuse rather than resolve.

  correlate on `id` explicitly anyway: CLAUDE.md's request-id-first demux rule is that synchrony is
