<objective>
Session A of criterion 1's two-session evidence (D-26): analyse one real program, write the
findings into the annotation store, and write down a question — not the answer — that only the
store can answer.

**Why this is two plans in two waves and not one.** Criterion 1's claim is *"a **later** session
answers a question by querying that store instead of re-deriving the findings from Markdown
prose"*. That is a claim about a session boundary and prose-blindness. A single `node --test` run
cannot sample it at all — it can only sample that the query API returns correct rows, which plan
11-05 already does. And this project has a documented, repeated failure mode of executor agents
stalling on nested headless `claude -p` invocations, so the second session must be a genuinely
separate plan in a later wave (plan 11-09), not a child process spawned from here.

**Why the answer is sealed as a hash.** "Barred from reading the earlier wave's prose" is an
instruction, and an instruction is not a mechanism. Committing the expected answer in a canonical
normalised form plus its sha256 lets plan 11-09's result be checked by comparing hashes, so the
evidence stands even if someone later doubts the separation. The canonical format is specified in
`QUESTION.md` precisely enough that two correct answers hash identically.

**Falsifiability rule this plan must satisfy** (11-VALIDATION.md's Manual-Only Verifications):
the question must be unanswerable from the `.prg`, from the `.a` source, and from the program's
name. The reliable way to achieve that is to make the answer depend on **human naming and
grading choices recorded in the store** — a label name, a confidence grade, an evidence note —
which are not derivable from bytes by any amount of analysis. A cross-reference alone is NOT
sufficient: it is recoverable from the bytes, so a question built only on xrefs is guessable by
re-deriving, which is exactly what criterion 1 says must not be necessary.

Purpose: this is the criterion the roadmap calls "the prize". Everything else in the phase is
machinery for it.

Output: a committed fixture program, a committed annotated store, a committed transcript, and a
sealed question/answer pair with a test that keeps the seal honest.
</objective>

  <action>
**Decision recorded here (`<decisions_you_own>` #6 / D-31, the fixture, for criterion 1 specifically):**
build a purpose-made subject rather than reusing `probe-illegal.prg`. Reason: `probe-illegal.prg`
is an illegal-opcode probe with no vectors, no handler and no tables, so any question about it is
either trivial or guessable — it cannot satisfy the falsifiability rule. (Plan 11-08 makes the
opposite call for the symbol round trip, where the mechanism, not the program's structure, is what
is under test.) Keep it small: assembled size under ~512 bytes, so the committed `.prg` and its
project file stay reviewable in a diff.

Write `recon-subject.a` (ACME, `!cpu 6510`, origin `$0810`) containing enough structure for recon
to have something to classify and name:
- an init routine that sets `$D011`/`$D018`/`$DD00` and installs an IRQ vector at `$0314/$0315`;
- an IRQ handler that reads `$D012`, updates a counter in zero page, and jumps through `$EA31`;
- a main loop that reads a table and calls two subroutines;
- one data table (bytes) and one address table (word pairs) — so `r2000_set_data_type` has
  distinguishable block types to record (`byte` vs `address`);
- at least one region that is genuinely ambiguous from the bytes alone (e.g. a table whose entries
  could be read as code), so a confidence grade is a real judgement rather than a formality.

Assemble it with real ACME into `recon-subject.prg`. Commit both. Record the assembled byte length
and the sha256 of the `.prg` in the SUMMARY, and put the same two values in a comment header in
`recon-subject.a`, so a regenerated `.prg` that differs is visible.
  </action>
