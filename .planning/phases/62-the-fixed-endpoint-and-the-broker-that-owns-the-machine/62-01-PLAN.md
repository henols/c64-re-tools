<objective>
Make the fixed endpoint real end to end: a broker answers a handshake ahead of its
token gate, and a client finds that broker by dialling two fixed candidates on one
fixed port with nothing on disk telling it where to look.

Purpose: this is the premise the whole milestone rests on. Every later phase
(session relay, file transfer, the skill-script seam, the deletion cutover) reaches
the broker through this dial. Proving it end to end on one thin path before
expanding is what catches an architectural dead end after one commit instead of ten.

Output: a new client-side module `src/mcp/vice/broker-endpoint.ts` that owns the
dial, the handshake and the four ranked refusals; a ninth control op dispatched
between the JSON shape guards and the token check; and a new colocated test file
exercising the whole path against a real listener.
</objective>

<assumption_delta_decision>
**Generalized identity (the noun that is now primary):** *the broker's address* —
today a single resolved dial target (`resolveControlTarget()` in
`src/mcp/vice/vice-broker-client.ts`: one host, one source, derived from the
discovery record); from this plan onward an **ordered set of dial candidates**,
each bounded by its own timeout, where the first *completed handshake* wins
(D-07, ENDPOINT-01, ENDPOINT-02).

**Decision: `add-alongside` — accepted debt, with the promote already owned.**

Rationale in one line: CONTEXT.md's phase shape is binding and says the
direct-dial path "keeps working, untouched, in parallel for the whole phase", and
the discovery record the singular resolver exists to read is only deleted by
`RM-02` in Phase 66 — promoting now would mean deleting a reader whose input still
ships.

**What forces the later promote, and who owns it.** Two requirements, both already
mapped: `RM-02` (Phase 66) deletes the discovery record and every reader of it,
which removes the singular resolver's only input; and `SEAM-01` (Phase 65) requires
that *exactly one* module owns dialling the endpoint. Either one on its own makes
the plural representation the sole survivor. Phase 66 is where the demotion lands.

**How this plan keeps the debt from silently deepening.** The plural representation
is deliberately given its **own new module** (`broker-endpoint.ts`) rather than
being grafted onto `resolveControlTarget()`, so the two models never blend into one
function with a mode flag — and Task 1's acceptance criteria assert that the new
module reads nothing from disk and imports nothing from the legacy discovery-record
client. That assertion is the contract test encoding the generalized intent: a
future phase that reintroduces the singular, record-derived assumption into the new
dial path goes red rather than landing silently.
</assumption_delta_decision>

<flagged_assumptions>
**Probe-surfaced edge left `unresolved` (never silently dropped).**

- **ENDPOINT-03 / `unclassified`** — the deterministic edge probe could not place
  this requirement in its shape taxonomy, and the fallback protocol forbids
  auto-resolving an `unclassified` row. Carried forward as an explicit assumption:
  the planner's reading is that ENDPOINT-03's edge surface *is* the four-outcome
  classification, which the explicit truths above cover (nothing listening, foreign
  listener, stale broker, version skew). If a reviewer can name a fifth
  distinguishable listener state, it is unplanned and should be raised rather than
  absorbed.

**Design assumptions this plan makes, stated rather than buried.**

- The broker's own version for the handshake reply is resolved by reading the
  package manifest from two candidate locations relative to the running module
  (beside it, then one directory up) — the same locate idiom `tool-location.mts`
  already uses for its declaration file. In a git checkout and in an npx-invoked
  package, the one-directory-up candidate is the package root. If neither candidate
  resolves, the reply carries the dev placeholder version, which a published client
  reads as a major mismatch; the refusal therefore has to name the observed version
  so that case is diagnosable rather than mystifying.
- The protocol magic string is **mirrored, not imported**, between
  `broker-control.mts` (host-bound, compiled into `resources/`) and
  `broker-endpoint.ts` (container-side, run as source). Mirroring is this project's
  standing convention across that boundary, and Task 1 pins the two literals
  together with a source-reading assertion so they cannot drift.
</flagged_assumptions>

CLIENT HALF — a NEW file `src/mcp/vice/broker-endpoint.ts`:

Container-side plain TypeScript. Give it a module header stating what it is the one
authoritative place for (dialling the fixed endpoint and classifying what answers),
and stating that it must never reach the filesystem and must never import the
legacy discovery-record client — that route is the parallel one this milestone
retires, and blending the two is the exact defect this module's separation exists

from here; this project mirrors rather than imports across that boundary).

Export `DIAL_CANDIDATES` as a frozen, ordered two-element array: the loopback
literal first, the Docker bridge alias hostname second. The order is fixed and IS
the host/container detection (the phase goal) — no code in this module may call a
container detector to decide what to dial.

Export `dialBrokerEndpoint(options)` taking a destructured options object with
`port`, `candidates`, `connectTimeoutMs`, `replyTimeoutMs` and an injectable
`connect` seam, all optional: `port` defaults to the control plane's own default
port value, `candidates` to `DIAL_CANDIDATES`. For THIS task it needs only the happy
path — open one socket per candidate using the same `settled` flag plus
`setTimeout(...).unref()` plus `once("connect")` / `once("error")` shape
`openBrokerControl()` already uses, write one handshake line per connected socket,
read one newline-delimited JSON reply, and resolve with the first candidate whose
reply carries the expected protocol magic. Destroy every socket the dial opened
before resolving, including the losing candidate's.

Return a discriminated result: on success an object carrying `ok` true plus the
winning candidate host, the port, the reply's version and its tag; on failure an
object carrying `ok` false plus the per-candidate observations. The failure ranking
and the refusal text are Task 2 and Task 3 — for this task a failure may carry raw
observations with no ranking applied.

Parse every byte from an unknown listener as untrusted input: wrap the JSON parse in
try/catch, type-check every field before use, never throw out of the dial, and never
cache a negative result. This is the same never-throw posture the existing client
header already states for this boundary.

Expand the dial from Task 1's happy path into the full D-07 shape. Write the
`<behavior>` cases as failing tests first, then make them pass.

Give EACH candidate its own independent timer pair and its own `settled` flag: a
connect timeout bounding the TCP connect, and a separate reply timeout bounding the
wait for the handshake line after a successful connect. ENDPOINT-02 is what makes
D-07 safe — a wedged listener parked on candidate 1 must not prevent candidate 2
from being tried, so the two candidate attempts are started immediately and
concurrently, never sequentially and never chained.

Do NOT stop on the first candidate to settle. Per D-07 both candidates always run
to completion, because inside a container the loopback candidate is the container's
OWN loopback in a different network namespace: candidate 1 failing is expected
rather than exceptional, and candidate 1 answering says nothing about the host.
Resolve the overall dial as soon as any candidate produces a COMPLETED handshake
(valid magic and a compatible major); otherwise wait for both to settle and resolve
not-ok.

Classify each candidate's observation into exactly one of four ranks, ascending by
informativeness. Rank 1: connect refused, or the hostname did not resolve — nothing
is listening. Rank 2: connected, but the reply timed out, was not valid JSON, or
carried no matching protocol magic — a foreign listener is squatting the port. Rank
3: connected, and the reply was an error whose code is `unauthorized` or
`bad_request` — a pre-v2.0.0 broker, whose token gate runs ahead of dispatch and so
refuses a credential-free handshake (D-06's stale-broker discriminator). Rank 4:
connected, valid magic, but an incompatible major version — a genuine broker at the
wrong version. Export `classifyHelloReply` as the named, pure classifier so the
ranking has exactly one definition that both the dial and its tests call.

On failure, report the HIGHEST rank seen across both candidates, and carry the full
per-candidate observation list alongside it so the refusal in Task 3 can name what
each candidate did. When two candidates tie on rank, order the reported observations
by the fixed candidate order, never by settle order — the output must be stable.

Also record, per candidate, whether the hostname RESOLVED — that single boolean is
what gates the rootless-container disclosure in Task 3, and it can only be observed
here at dial time. A DNS failure and a connection refusal are different observations
even though both land in rank 1.

Give every timer `.unref()` and clear it on settle, exactly as the existing client

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| unknown TCP peer → broker control plane | The handshake arm answers BEFORE the credential gate, so every byte it emits is readable by anything that can reach a bound address |
| unknown TCP listener → dialling client | The client sends a handshake to whatever answers the fixed port and parses the reply; those bytes are fully untrusted |

| T-62-01 | Spoofing | `broker-endpoint.ts` `dialBrokerEndpoint` | high | mitigate | A bare TCP accept proves nothing about who is listening; only a reply carrying the exact protocol magic AND a compatible major version counts as a completed handshake (rank 4 and below never resolve the dial) |
| T-62-02 | Information Disclosure | `broker-control.mts` handshake arm | high | mitigate | The reply's key set is fixed to exactly four fields and asserted with a sorted key-set equality test; no token, path, hostname, username or instance detail may be added without the test going red |
