<design_decision>
## The check this plan builds, and why it has that shape

The verifier asked for a mechanical, repeatable check that validates every
`file:line` citation in `docs/phase58-declaration-provenance.md` resolves to a
line whose content actually supports the claim it is cited for. No machine can
judge "supports the claim" semantically. What a machine *can* do is hold the
author to a recorded, falsifiable statement of what the cited line says.

So the document gains a **Citation ledger**: one entry per distinct citation,
each carrying the citation string and an `anchor` — the exact substring the
cited line range must contain. The guard then enforces four relations:

1. **Resolution** — every anchor is found inside its cited range in the live file.
2. **Completeness** — every citation in the body has a ledger entry.
3. **No orphans** — every ledger entry's citation appears in the body.
4. **Non-vacuity** — the ledger is never empty against a document that cites.

The anchor is *redundant by design*. It is not a second source of truth: it is
re-asserted against the cited file on every run, so it cannot drift into being
believed on its own. That redundancy is the whole mechanism — it converts an
unfalsifiable prose claim into a check that fails the build.

**Reversibility ratings** (REVERSIBILITY_GATES):

| Decision | Rating | Rationale |
|----------|--------|-----------|
| The ledger lives inside the provenance document as a fenced json block, not a sidecar file | reversible | Moving it to a sidecar is a data move plus one path change in the audit. Keeping it in the document keeps citation and anchor visible to the human reader who is the document's whole audience. |
| Anchor matching is raw substring, no normalisation | reversible | Adding normalisation later is one line, and the encoding case documents exactly what changes. |
| unp64 is recorded as a deferral rather than added as a ninth record | costly | Reversing means adding the record, extending `prerequisites.test.ts`'s required-id set and amending ROADMAP SC1 — three coupled edits. The owner already made this call in the planning session, so it is decided, not open. |

No decision here is `one-way`, so no `checkpoint:decision` is inserted and the
plan stays `autonomous: true`.

**Why the guard lives in `src/mcp/vice/`.** `phase50-findings-contract.test.ts`
is the exact precedent: a colocated structural test in `src/mcp/vice/` that
reads committed markdown elsewhere in the tree, exposes its audit as one named
exported function so the real case and the planted case run the *same* code, and
carries a "fails rather than passing vacuously" case. Mirror it.

**What this plan deliberately does not do.** `prerequisites.test.ts`'s
`assertSourcesResolve()` has the same weakness class — it strips the trailing
line part and only `existsSync`-checks the path. It is left alone: the code
reviewer independently re-opened and confirmed every citation inside
`prerequisites.json` itself, so there is no live defect there, and widening this
closure into the JSON's own source fields would grow an Executed phase past its
gap. The audit function is written with an injectable options object so a later
phase can point it at those fields without a rewrite.

**The wrong citation's origin is left on the record, uncorrected.**
`58-CONTEXT.md`'s D-05 carries the same wrong pointer; the provenance document
faithfully carried it forward. CONTEXT.md is a dated snapshot of what was known
on 2026-09-16 and GSD planning artifacts are append-only history, so it is not
edited. Named here so a future reader sees a decision rather than a missed file.
</design_decision>
