# Phase 11.1 Plan 06: Close WR-09, IN-06 and WR-12 on the Bootstrap Path Summary

**Restored bootstrapProject()'s/cmdRenderMemmap()'s never-throw contract on the two branches that broke it (unwrapped .d64 parsePrg, two unguarded writeFileSync calls), pinned it structurally with a brace-depth backward scan proven by a planted violation and a real reverted demonstration; closed IN-06 with one verb-options map and a single pre-dispatch refusal check covering all seven verbs, not just verify; and pinned WR-12's .d64 used-byte DOS convention with two hand-written literal fixtures, proven independent of the implementation by a live joint-mutation demonstration.**

## Performance

- **Duration:** ~70 min
- **Tasks:** 3/3
- **Files modified:** 3 (`r2000-cli.ts`, `r2000-cli.test.ts`, `r2000-d64.test.ts`) -- no files created

## Accomplishments

- `bootstrapProject()`'s `.d64` path no longer throws past its own documented never-throw contract: a `parsePrg()` rejection is caught and reworded entirely in the caller's vocabulary (names the `--entry` and byte count, never the word `parsePrg`).
- Both `bootstrapProject()`'s project-file write and `cmdRenderMemmap()`'s Markdown write are now guarded, so an `ENOENT`/`EACCES`/`ENOSPC` write failure returns a one-line `bootstrap:`/`render-memmap:`-prefixed message instead of throwing.
- A structural test reads `r2000-cli.ts`'s own source, strips comments and string/template-literal bodies, and asserts every `writeFileSync(` call sits inside a `try` via a backward brace-depth scan that classifies each enclosing brace by its preceding keyword -- proven non-vacuous by a synthetic planted-violation test (bare top-level call reported unguarded; try/catch-wrapped call not) and, during execution, by literally un-wrapping the real `cmdRenderMemmap()` write, confirming the scanner caught it, and reverting.
- IN-06: one frozen `VERB_OPTIONS` map plus `checkAcceptedOptions()`, wired at `runR2000Cli()`'s single pre-dispatch call site, refuses any `--flag` a verb does not accept -- closing not just `verify --out` (the finding's own named case) but the identical `verify --force` gap found while building the map, and generalising the closed-option-set posture to `bootstrap`/`export-asm`/`verify` (which previously had none) while leaving the four already-enforcing verbs' own behaviour intact.
- A mechanical test parses `--help`'s own rendered USAGE text per verb and asserts it agrees with `VERB_OPTIONS`, for all seven verbs -- catching a future USAGE/behaviour drift automatically rather than by review.
- WR-12: two hand-written, literal `.d64` final-sector fixtures (`usedByte 0x04` -> 3 payload bytes; `usedByte 0x02`, the WR-05 boundary -> 1 payload byte) pin the DOS used-byte convention independently of `writeChain()`'s own formula. Neither test calls `writeChain()` or computes a used byte from a payload length.

## Decisions Made

See `key-decisions` in the frontmatter above for the full list with rationale. The two most consequential:

- **export-asm's USAGE line was corrected to add `--entry`, a documentation-only fix.** Building `VERB_OPTIONS` from real code behaviour (not from USAGE text) surfaced that `export-asm` already forwards `--entry` to `bootstrapProject()` (required for `.d64`/raw inputs), which USAGE never documented. This is not IN-06's "accepted but silently ignored" shape (the option is genuinely used) -- it is a plain doc gap. It was fixed rather than left as a recorded-but-unfixed disagreement, because leaving it unfixed would force a choice between (a) excluding `--entry` from `export-asm`'s map entry, which would make the new pre-dispatch checker start refusing a real, working, `.d64`-input-required option, or (b) writing a map-agrees-with-USAGE test that could not mechanically pass for all seven verbs, which the plan's own acceptance criteria require. The fix is behaviour-preserving: no test needed `export-asm --entry` to be refused, and the gated criterion-3 test plus every other `export-asm` test still pass unchanged.
- **verify's `--force` is refused alongside `--out`.** IN-06 named `--out` specifically, but `parseArgs()`'s shared parser also silently parses and discards `--force` for `verify` (only `{ positional, entry }` is destructured in `cmdVerify()`) -- the identical defect shape. Closing only `--out` and leaving `--force` unfixed would have re-created AUDIT-01's own pattern (a found-but-not-fully-dispositioned defect) one plan later, so both are closed by the same `VERB_OPTIONS.verify = ["--entry"]` entry.
