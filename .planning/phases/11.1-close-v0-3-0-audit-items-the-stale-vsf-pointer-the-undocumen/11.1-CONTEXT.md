# Phase 11.1 Context — Close v0.3.0 Audit Items

**Source of truth for scope:** `.planning/v0.3.0-MILESTONE-AUDIT.md` (committed `c7dc2d2`).
Every item below is quoted from that audit and was **independently re-verified against
the working tree** during the audit itself — none is inferred from SUMMARY prose. Treat
the file:line citations as checked as of 2026-08-21, and re-check rather than trust if a
line does not match.

**This phase adds no requirements.** It closes findings against the existing 12 in-scope
`R2000-*` IDs, all of which are already `satisfied`. Nothing here re-opens a requirement.

## Why this phase exists

The audit returned `tech_debt`: 12/12 requirements satisfied, no blockers, but a set of
findings that would ship as debt. Two of them are not really debt — they are a user-facing
false claim and an undiscoverable feature set — and four more exist *because a guard
enumerated a list that stopped growing*. That last pattern is the phase's organising idea.

v0.2.0 closed exactly this way (Phases 8.1 and 8.2). The precedent is deliberate.

## The organising principle: guard-first, not fix-first

Four findings in this phase exist because a mechanical guard hard-coded a list:

- `hostpath-consumers.test.ts` enumerated 10 r2000 modules; the family grew to 14.
- `check-skill-tool-coverage.mjs` checks `r2000_*` **tool names** in prose but never CLI
  **verbs**, so three verbs reached `main` documented nowhere.

So a fix that only edits the list is the same bug deferred. **Every item below that can be
pinned by a self-deriving guard must be, and the guard must be proven non-vacuous by a
planted violation** — the discipline plans 11-01/11-02 already established in this repo.

## Items to close

### FLOW-02 — a false claim on a user-facing surface, pinned green (highest priority)

`.claude/mcp/vice/r2000-cli.ts:164` (USAGE text) and `:258` (the live `bootstrap` refusal
for `.vsf` input) both say:

> `.vsf` input is not supported … Closing that gap for real is **Phase 11's job**, not this CLI's.

Phase 11 is complete and never touched `.vsf` bootstrap — confirmed: no `.vsf` handling in
`r2000-project.ts`, `r2000-d64.ts`, `r2000-mcp-client.ts` or `r2000-symbols.ts`.
`REQUIREMENTS.md`'s own D-34-corrected `R2000-09` text says the opposite explicitly:
`.vsf` is *"**not** deferred to a later phase — no `R2000-*` requirement covers it as a
bootstrap input"*, filed as backlog at
`.planning/todos/pending/2026-08-20-vsf-as-a-bootstrap-input.md`.

`.claude/mcp/vice/r2000-cli.test.ts:237-248` pins it with `assert.match(stderr, /Phase 11/)`,
so it passes green forever while certifying a false claim.

**Decision D-11.1-01:** reword both strings to name the **backlog file**, not a phase.
Retarget the test assertion at the new wording. `.vsf` stays out of the bootstrap input
set — this phase does **not** implement `.vsf` support.

**Guard (the "won't come back" half):** add a check that fails if any shipped source string
under `.claude/mcp/vice/` points the user at a *future/other phase number* as a remediation
path. A phase number is a planning artifact; it must never appear in a user-facing
diagnostic as a promise. This is the generalisation of the defect, not just its instance.

### FLOW-01 — three CLI verbs that no playbook names

Measured: `grep -rl 'r2000 <verb>' .claude/skills/`

| Verb | Skill files naming it |
|------|----------------------|
| `bootstrap` | 1 |
| `export-asm` | 3 |
| `verify` | 1 |
| `render-memmap` | 3 |
| `gen-enums` | **0** |
| `export-lbl` | **0** |
| `import-lbl` | **0** |

Those three are the delivery path for `R2000-13`'s enum install, `R2000-14`'s export leg
and `R2000-15`'s import leg. All are built, tested and live-proven; none is reachable by
the consumer they were built for. This milestone's thesis is that the annotation store is
reachable **from a skill**.

`scripts/check-skill-tool-coverage.mjs` validates `r2000_*` MCP tool names in prose but
does not check CLI verbs at all, so nothing caught it.

**Decision D-11.1-02:** document the three verbs in the playbooks where they belong —
`gen-enums` in `c64-memory-mapping` (it consumes that skill's `memmap.json`), `export-lbl`
/`import-lbl` in `c64-program-recon` (the symbol round trip is a recon activity). Show the
round trip as one closed loop, matching how `R2000-15` was actually proven, not as two
one-way dumps.

**Guard:** extend `check-skill-tool-coverage.mjs` to parse the verb list **from
`r2000-cli.ts` itself** (not a hard-coded array) and assert every verb appears in at least
one skill file, with a non-vacuity floor on the parsed count. A verb added later with no
documentation must fail CI.

### INT-01 — the R2000-02 absence assertion stopped growing with the family

`.claude/mcp/vice/hostpath-consumers.test.ts:106-118` lists 10 modules. The production
family is 14. Uncovered: `r2000-acme-ident.ts`, `r2000-regbits-gen.ts`, `r2000-symbols.ts`,
`r2000-test-gate.ts`.

Verified: none of the four imports `hostpath.ts`/`containerpath.ts`, so `R2000-02`'s runtime
guarantee **holds today — by luck, not by the test**. `r2000-symbols.ts` implements
`R2000-14`/`R2000-15` and is the highest-value target for an accidental host-path import.

**Decision D-11.1-03:** derive the list from `readdirSync` filtered on `/^r2000-.*\.ts$/`
minus test files, so it cannot silently under-cover again. Keep a non-vacuity floor
(count >= 14) so an empty glob cannot make the test pass trivially.

### INT-02 — two file headers disagree about the spawn seam

`r2000-launch.ts:2,12-13` claims to be *"the ONE authoritative place in this repo that
spawns regenerator2000 … No other file may shell out to the `regenerator2000` binary
directly."* `r2000-mcp-client.ts:332` calls `spawn(bin, argv, …)` directly — necessarily,
since `withR2000Session()` needs a long-lived async child while `runR2000()` is blocking
`spawnSync`. `r2000-mcp-client.ts`'s own header correctly says "both spawn call sites."

`R2000-01` is **not** compromised: `r2000-mcp-client.ts:330` calls the shared
`assertNoViceFlag(argv)` before every spawn, covering both `buildMcpServerStdioArgs()` and
11-08's `argv` override (fed only by `buildImportLblArgs()`, never hand-built).

**Decision D-11.1-05:** correct `r2000-launch.ts`'s header to describe what is actually
authoritative (the `--vice` guard and the fixed argv builders), and add a guard asserting
**every** `spawn`/`spawnSync`/`execFile` call site touching the regenerator2000 binary calls
`assertNoViceFlag` first. That converts a prose promise into a checked invariant, which is
what `R2000-01` deserves.

### Phase 11 IN-02 — `regenerateAndReload()` has no production caller

Confirmed by grep across `.claude/mcp/vice/`, `.claude/skills/` and `scripts/`: zero callers
outside its own module and test. It is the **named D-29 live-discovery merge point**.
`R2000-15` is satisfied through the `export-lbl`/`import-lbl` verbs, so this is durability
debt on a convenience wrapper, not a gap.

**Decision D-11.1-06:** decide one way and record it — either give it a caller (the natural
one is the documented round-trip step FLOW-01 is adding) or mark it library-only in its own
header so a future phase does not assume it is wired. Do not leave it ambiguous.
