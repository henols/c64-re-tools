<objective>
Build the committed on-disk form of a per-fixture annotation store: a general
JSON export and a general importer (D-02), with the derived/authored
provenance split carried per row (D-03).

No general store-JSON round trip exists today — `anno_import_ghidra_export` is
Ghidra-shaped and writes cross-references only (RESEARCH.md §5, VERIFIED). This
is the second and last deliberately-new module in this phase; everything else
is a modification of existing code.

Purpose: D-01 gives every fixture its own store, and D-02 says the committed
form is a diffable JSON export plus a committed importer — because a binary
SQLite file cannot show a purpose-comment change in a diff, which is exactly
what D-03's split provenance exists to make visible. Every later plan in this
phase writes its artifact through this module.

Output: `anno-store-export.ts` (the schema, the exporter, the importer and the
three provenance comment-prefix constants) and its round-trip test.
</objective>

  <name>Task 1: Freeze the export schema — a ONE-WAY decision</name>
  <decision>
D-02 is rated **one-way** in 45-CONTEXT.md: the export becomes the committed
on-disk format every later phase's fixture artifacts are written in, and
changing it afterwards means migrating every committed artifact. This
checkpoint exists so that shape is chosen deliberately, once, in front of the
owner — not discovered later as a migration.

Present, concretely, before writing any code:

1. **The row classes the document carries** and their order in the file:
   `ranges`, `labels`, `comments`, `projectEnums`, `enumUsage`, `xrefs`,
   `execObservations` — each an array, each sorted by a stated stable key
   (address, then endInclusive, then name), so two exports of the same store
   are byte-identical.
2. **Where the provenance tag lives (D-03):** proposed as a per-row
   `"provenance": "derived" | "authored"` field on every `ranges` and
   `comments` row — row level, not table level, because one fixture's comment
   table mixes authored purpose comments with derived decline comments
   (RESEARCH.md §5). The alternative considered and rejected: a table-level
   tag, which cannot express that mix.
3. **The three comment-text conventions** that ride the one existing
   `anno_set_comment` API, proposed as exported constants:
   `DECLINE_COMMENT_PREFIX = "DECLINED:"` (criterion 4 — what is unknown and
   why), `DISAGREEMENT_ACCEPTED_COMMENT_PREFIX = "DISAGREEMENT-ACCEPTED:"`
   (criterion 2 — reviewed and accepted, a different fact from "could not be
   determined"), and `AUTHORED_PROVENANCE_COMMENT_PREFIX = "PROVENANCE:
   authored"` (D-10's per-range authored marker). One API, three
   distinguishable greppable prefixes — never a second mechanism and never a
   schema column.
4. **`STORE_EXPORT_SCHEMA_VERSION`**, and the statement that a document
   carrying an unknown version is REFUSED by name rather than best-effort
   imported.
5. **The one forward consumer:** Phase 46's `BUILD-05` reads D-10's per-range
   provenance markers. The field is being designed for it now.

Ask the owner to confirm or amend items 2 and 3 specifically — they are the
two the rest of the phase cannot change cheaply.
  </decision>
  <options>
    - **Confirm as proposed** (recommended): row-level provenance tag, three comment prefixes, versioned document, stable sort order.
    - **Amend the provenance granularity**: table-level instead of row-level — cheaper to write, but it cannot express a comment table that mixes authored purpose comments with derived decline comments, which every fixture in this phase will have.
    - **Amend the decline recording**: a dedicated store table/column instead of a comment convention — structurally queryable, but it is a schema change, it contradicts the roadmap's "match that convention rather than inventing a second one", and REQUIREMENTS.md's out-of-scope reasoning about a store table for a derived query applies.
  </options>
  <default>Confirm as proposed.</default>
  <resume-signal>Type "confirm" to freeze the schema as proposed, or name the amendment to item 2 (provenance granularity) or item 3 (the three comment prefixes)</resume-signal>

after those plans run means rewriting nine committed artifacts and every gate
