<objective>
Derive the verdict from the seven recorded values by applying the committed rules
in written order, record it as machine-readable frontmatter with every value cited
to the line it came from, and bind it to the four downstream phases so their scope
is selected by this record rather than chosen later.

Purpose: this is the fourth pre-committed gate in this project's history and the
first three all fired — one returned `degrade` and the milestone shipped smaller
and correct, one returned `no-go` and five of eleven plans were deliberately never
dispatched, one returned `degrade` with the one available override explicitly
declined. The precedent is not decorative: gates here fire, and are obeyed. This
plan's job is to apply the rule, not to negotiate with it.

Output: the completed verdict document, the four downstream phases bound through
their roadmap entries, and a state pointer.

**Execution note:** this plan delivers `.planning/STATE.md` and `.planning/ROADMAP.md`
content, so it takes the stock per-plan carve-out `USE_WORKTREES_FOR_PLAN=false` —
worktree executors may not touch either file and the commit strips them.

**Reversibility note:** the `one-way` rating on Task 1 carries `39-CONTEXT.md`'s own
ratings forward rather than re-deriving them. No `checkpoint:decision` precedes it
because the door it names — the pre-commitment and the no-abstention property that
make the verdict trustworthy — was chosen by the owner at `/gsd-discuss-phase` and
confirmed again at `39-01` Task 1, before any measurement existed. Gating it a
second time here, with the numbers already visible, would invite exactly the
after-the-fact renegotiation the pre-commitment exists to forbid.
</objective>

why — so a reader re-derives the verdict mechanically rather than taking it on
trust. Quote the fired rule's full text verbatim from the rules file.

**Narrowing.** If the fired rule carries a pre-mapped narrowing, reproduce that
narrowing's committed text verbatim and note that it was written before the
measurement existed. If the fired rule's narrowing is authored at verdict time,
author it now against the evidence and **label it explicitly** as authored at

explicit override: record it as such, name what it overrides and why, and state
plainly that an override weakens the pre-commitment it departs from. Do not edit

**Every triggered narrowing, not only the fired rule's.** The rules file's
`## Narrowings are not scoped to the fired rule` subsection is binding here: both
pre-mapped narrowings apply whenever their **own** input carries its triggering
value, independently of which rule id fired, because the antecedents are
conditioned and only the first one in reading order is recorded. So check both
inputs' transcribed values directly and state every narrowing whose triggering
value was recorded — a verdict reached through the disconnect rule still carries the
hit-count narrowing if that input reads `breaks`. Listing only the fired rule's
narrowing would silently discard a measured finding.
