<objective>
Measure the two experiments about **what happens when a client goes away**: whether
a halt held by an abruptly killed text client is ever released, and whether the
text-monitor server serves one client or more than one.

Purpose: the first is the experiment the ROADMAP flags as one that "may itself
discover required mechanism". The binary side's rule is that closing the connection
IS the release; the text channel has no known analogue, and only the broker outlives
a killed client. `D-10` therefore pre-mapped the narrowing before this measurement
existed: a machine left permanently halted is a **missing mechanism**, not proof of
incompatibility, and the outcome points at the broker-lease shape rather than away
from coexistence. The second is the milestone's other blocking UNVERIFIED item, and
its trap is documented: a second connection to a single-client server sits
unserviced with no reply and no end-of-file, which is indistinguishable from a
wedge under a short budget.

Output: a kill victim, two probe scripts and two evidence files, each carrying one
gate input at column 0.

**Serialization note:** this plan runs in its own wave because every probe refuses
to start when any other emulator process is alive — a real constraint from `D-16`
and Phase 33's recorded five-orphan incident, not a file conflict.

**Reversibility note:** the `one-way` ratings on this plan's tasks carry
`39-CONTEXT.md`'s own ratings forward rather than re-deriving them. No
`checkpoint:decision` precedes them because the owner already chose each of those
doors at `/gsd-discuss-phase` — re-asking a decision already recorded produces
checkpoint fatigue, not a gate. The phase's one genuinely unasked door, the rule
text and its ordering, is gated at `39-01` Task 1.
</objective>

Write two scripts. The victim must be a **separate process**, not a socket the
probe closes itself: a clean application-level teardown exercises a release path a
killed process cannot run, and that distinction is the whole experiment.

**`textmon-kill-victim.mjs` — the victim.** A tiny script taking the text port as
its only argument. It imports the throwaway client, connects, awaits the banner,
issues a halting command, awaits the prompt, prints a single ready line to stdout
so the parent knows the halt is established, and then blocks forever with no
cleanup handler of any kind — no exit handler, no signal handler, no socket
teardown. Its header states why: any cleanup path would make the measurement about
that path rather than about what the emulator does when a client vanishes.

**`disconnect-recovery-probe.mjs` — the measurement.** Import the shared harness
and the throwaway client, same three-part header. Sequence:

  1. Refusal check, spawn the stock baseline binary by absolute path with both ports
     bound, record the binary and its version.
  2. Connect the binary channel with retry, ping until ready, arm a non-stopping
     exec checkpoint at the IRQ frame anchor, and confirm from a bracket that its
     hit count is advancing. This is the liveness instrument for the whole
     experiment; if it is not advancing before the victim starts, the run is void.
  3. Spawn the victim as a child process, passing it the text port. Wait for its
     ready line with a bounded budget. If the ready line never arrives, the halt was
     never established and the outcome is `not-taken` with that reason.
  4. Confirm the halt from the binary side: a hit-count bracket that now shows zero
     advance where the pre-victim bracket showed a positive one. Record both.
  5. Terminate the victim with an uncatchable kill signal and confirm the process is
     gone. Record the exact signal used and the observed exit status.
  6. **Poll for recovery across the full 60-second budget with no further action**:
     read the checkpoint's hit count at a stated interval and record the whole
     series with timestamps. `recovers` requires the series to start advancing on
     its own. Do not send anything on either channel during this window — a single
     probe command would make the measurement about that command.
  7. If the budget expires with no advance, record `leaves-halted`, then run the
     **separate** follow-up observation the schema asks for: open a fresh text
     connection, send the exit command, and record whether the machine resumes. That
     result is recorded as prose and as part of the transcript, and it is the
     mechanism the committed narrowing names — but it does not change the outcome
     line, because the frozen rule defines recovery as happening with no further
     action.
  8. Write a short section stating which verdict the shipped wedge-triage playbook
     would currently reach for the end state this experiment produced, and whether
     that verdict would recommend a destructive recycle of a healthy instance. This
     is an observation for the verdict document to carry forward; the playbook is
     not modified by this phase.
  9. Repeat the whole sequence twice and record both runs.
 10. Reap all children — including the victim if it somehow survived — then append
     the transcript and the outcome line.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| the probe process → a directly spawned emulator (D-12) | The probe reaches the emulator by `execve` rather than through the broker, so none of the broker's guards apply: no single-client enforcement, no port allocation, no crash supervision, no pre-kill incident capture |
| a dead client's held halt → the emulator's run state | The binary side's release is the connection closing; whether the text channel has any analogue is unknown, and a halt with no owner and no release path is a machine nothing can restart |
| an unserviced second connection → a wedge diagnosis | A connection accepted and then left silent is documented as indistinguishable from a genuine hang; an under-budgeted probe would record the wrong answer confidently |
