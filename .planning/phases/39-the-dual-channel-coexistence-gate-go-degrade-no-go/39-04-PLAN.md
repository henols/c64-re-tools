<objective>
Measure the two experiments about **halt crossing between the channels**:
whether one channel's halt is visible to the other, and whether a halt taken on
one channel can be read and released from the other.

Purpose: these are the two inputs that decide whether a serialization authority
can *observe* what it needs to serialize. `FOREIGN_HALT_VISIBILITY: invisible`
means a future authority has no signal to react to and must own every halt
prospectively rather than detect one; `CROSS_CHANNEL_RESUME: corrupts` means the
two channels cannot even cooperate on releasing a halt, which narrows the shape
sharply. Both feed `degrade` rules whose narrowing is authored at verdict time
against the evidence, so what the evidence *says* — not only which enumerated
value it produces — is the deliverable.

Output: two probe scripts and two evidence files, each carrying one gate input at
column 0.

**Serialization note:** this plan runs in its own wave rather than beside the other
measuring plans because every probe refuses to start when any other emulator
process is alive. That refusal is deliberate (`D-16`, and Phase 33's recorded
five-orphan incident), so concurrent live plans would refuse each other rather than
parallelise. The wave numbering reflects a real constraint, not a file conflict.

**Reversibility note:** the `one-way` ratings on this plan's tasks carry
`39-CONTEXT.md`'s own ratings forward rather than re-deriving them. No
`checkpoint:decision` precedes them because the owner already chose each of those
doors at `/gsd-discuss-phase` — re-asking a decision already recorded produces
checkpoint fatigue, not a gate. The phase's one genuinely unasked door, the rule
text and its ordering, is gated at `39-01` Task 1.
</objective>

channels. Read the text-side monotonic cycle counter and record it. Issue a halting
command on the text channel and await its prompt, so the machine is halted by the
text monitor. Then, over the **binary** channel: read the CPU registers and record
them, and read a small memory window with side effects off, confirming both
succeed while the machine is halted by the other channel. Then send the binary
monitor's resume opcode. Then wait at least one second and read the text-side cycle
counter again. The resume is confirmed only if that counter advanced — a monitor
accepting a resume command is not evidence the machine ran, and this is the one
independent liveness signal available across the two channels.

mechanism on the binary channel to take a halt the binary client owns (an exec
checkpoint with stop-on-hit on at the IRQ frame anchor, waited on by its own hit

read the cycle counter and one register view, confirming both succeed. Then send
the text monitor's exit command to release the halt. Then confirm from the
**binary** channel that the machine is running again, by a non-stopping
checkpoint's hit count advancing across a bracket.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| the probe process → a directly spawned emulator (D-12) | The probe reaches the emulator by `execve` rather than through the broker, so none of the broker's guards apply: no single-client enforcement, no port allocation, no crash supervision, no pre-kill incident capture |
| an unsolicited broadcast-id frame → a pending binary request | Two of the five unsolicited message types share a response type with a legitimate command reply, so a demux that keyed on response type instead of request id would resolve a pending request with an event |
| a foreign halt → the binary client's model of who stopped the machine | This is the experiment: whether a halt the binary client did not cause is distinguishable from one it did |
