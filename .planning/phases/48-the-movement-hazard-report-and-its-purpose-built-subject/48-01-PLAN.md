## Planner decisions recorded for this phase

These bind every plan in Phase 48. They are decisions, not preferences, and a plan that
contradicts one has failed the phase. D-48-A, D-48-B and D-48-C are owner decisions taken
this session; D48-D through D48-H are the planner's, recorded here rather than left implicit.

**D-48-A — hazard class 3 "page-alignment dependence" means VIC-II HARDWARE alignment.**
Sprite shape data on 64-byte boundaries (the sprite pointers at `$07f8`-`$07ff` store
`address / 64`); the character set on a 2K boundary within the current 16K VIC-II bank.
Chosen because it composes with the sprite/charset/level/music tables criterion 1 already
requires the subject to carry, and because a deliberate mis-alignment fails VISIBLY on
screen with no error signal — the negative control is observable rather than notional. The
code/timing page-crossing reading (a table page-aligned so an indexed access never crosses a
page, costing a cycle) is explicitly NOT this phase's class 3; it is documented in the
fixture design document as a real, separate, deliberately-out-of-scope hazard so a later
reader sees it was considered and excluded, not missed. Implemented by plans 48-02 (subject),
48-03 (detector) and 48-04 (design document).

**D-48-B — the hazard report defines its OWN small, explicitly-scoped detection-strength
vocabulary, and records the departure in its own header.** Verified at source: the existing
five-grade confidence vocabulary is a bracket-token prefix inside an annotation LINE COMMENT
answering "what does this ADDRESS classify as" (code vs data). The analysis module family's
"never define a second confidence vocabulary" rule is written against that axis.
Hazard-detection strength is a different axis — "how sure is this specific static signal" —
so a separate, differently-spelled vocabulary is correct, NOT a rule violation. Binding
constraints on it: the three tokens are `observed-corroborated`, `static-shape-matched` and
`static-signature-only`; none of them may be stored as a bracket-token comment prefix; none
may add a second address-keyed sidecar store; and the module's own header must record this
as a deliberate, reasoned departure in the WHY-THIS-EXISTS style this codebase uses, stating
the two axes and why one vocabulary cannot answer both. Implemented by this plan, task 2.

**D-48-C — indirect-indexed self-modification is a PLANTED variant whose recorded MISS
demonstrates the limit, not a detector to solve.** A store through a runtime-computed
zero-page pointer into the code range is planted deliberately in the subject (plan 48-04),
the class-2 detector misses it by construction, and that miss is recorded in the cross-check
table (plan 48-05) and named in the report's own emitted limits (this plan, task 2). A
demonstrated, recorded limit is worth more here than an attempted pointer-range analysis
with no existing primitive in this codebase.

**D48-D — the new read-only report verb DOES get a CLI entry, and the precedent is the
observed-execution disagreement query, not the exclusion verbs.** MEASURED this session:
the exclusion/inclusion verb pair has zero entries in `anno-cli.ts` (three registration
sites, not four) because an exclusion is a small bounded piece of session state, not a
filesystem artefact — that is the OPPOSITE case to this one. The disagreement query, the
one existing read-only computed query over already-fetched store data, DOES carry a CLI verb
(`evid-disagreements`, four registration sites including the verb floor and a skill
mention), for the stated reason that a CLI route runs the query against a real store rather
than only exposing it as an MCP answer. The hazard report is that same shape, and criterion
5's cross-check runs it over three committed stores, so it takes the same four sites.

**D48-E — the report's region disposition has exactly THREE inhabitants and no boolean
anywhere.** `hazard-reported`, `no-signal` and `unclassified`. `no-signal` means "the
detectors ran over this region and matched nothing" and is NEVER a safety claim;
`unclassified` means "the detectors could not decide" and is reachable from four real
causes (the region's bytes do not decode, the region lies outside the loaded image, the
region's store block class is itself undefined, or a detector declined on the region). There
is no `clean` field, no `dirty` field, no `hasHazards` boolean and no single verdict
anywhere in the returned shape. Plan 48-03 owns the test that refuses a boolean shape.

**D48-F — the module is PURE and receives plain data.** Every input arrives as an argument:
`bytes`, `origin`, `symbols`, `comments`, `ranges`, `xrefs` and optional
`execObservations`. The module calls `decode()` and `scanIndirectDispatch()` (both pure) and
nothing else that touches the outside world. It never takes a store handle, never resolves a
path, never reads a file. The callers (`anno-cli.ts`, `anno-tools.ts`) do all fetching, the
same split the disagreement query already ships.

**D48-G — runtime execution evidence STRENGTHENS, never suppresses.** An
`execObservations` row that covers a finding's anchor address raises that finding's strength
token to `observed-corroborated`. No observation, or no observations at all, changes nothing
about whether the finding exists. There is no code path in which an observation removes,
downgrades or silences a finding, and no path in which "never observed" contributes to any
count that a reader could take as evidence of safety.

**D48-H — planning vocabulary never enters `src/**`.** Product files must be readable by
someone who has only the product. No requirement id, decision id, gap id, phase number, plan
number, `.planning/` path or roadmap cross-reference may appear in any file this phase adds
or edits under `src/` — in prose, in a comment, or in a string literal. Write the REASON, not
the pointer. The single structural exception is `anno-register.ts`'s `requirements` array,
which is a DATA field its own enforcing test demands be populated; that array carries
`["BUILD-04"]` and nothing else in that file cites an id.
