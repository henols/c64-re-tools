<objective>
Run every detector against programs this phase did not write, record what each one found,
missed and wrongly flagged, and commit the result — including the rows that say a class has
no independent positive example at all.

Purpose: this phase ships the fixture and the detector together, which is the failure mode
where the fixture gets written to match the detector. Everything else in the phase is
downstream of one control: do the detectors work on programs nobody here shaped for them?
Four committed fixtures answer that, authored between five and twelve days before this phase
opened, for questions about disassembler vendoring, analyser volatile-I/O carving,
mid-instruction label export and phantom labels inside a character set. None of them has ever
seen a hazard detector. Their independence is the whole value.
Output: a three-outcome comparator, declared expectations read from each fixture's own bytes,
the strengthen-never-suppress proof, and a committed cross-check record.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| the declared expectations → the cross-check's conclusions | The expectations are the only control a detector did not influence; if they drift toward detector output, every conclusion downstream is circular. |
| the committed record → a reader deciding how much to trust each detector | The consequential boundary: the record is what a later reader acts on. |
| runtime observation rows → the finding set | Asserted to be a one-way strengthening boundary. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-48-07 | Spoofing (evidence) | the expectation table | high | mitigate | An expectation quietly edited to match a detector run turns the control into a mirror. Mitigated by deriving every positive expectation from the fixture's own committed source with the derivation recorded in a comment beside it, by a module-side doc comment stating the rule, and by the record-consistency test that forces a class's no-positive-example statement and its expectation rows to move together. |
| T-48-04 | Repudiation (false assurance) | `CROSS-CHECK.md` | high | mitigate | An all-zero false-positive column reads as a strong result even when it only means the detectors never fire.
