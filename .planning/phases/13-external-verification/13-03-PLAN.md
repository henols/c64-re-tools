**A1 — `-remotemonitoraddress` spelling and binding.** The flag spelling is
already confirmed present on both builds' `--help`, so what remains is whether
the port actually binds. The probe takes the text-monitor host and port as input
(default `127.0.0.1:6510`), opens a plain TCP connection to it with the existing
bounded connect helper, reads whatever the peer sends within a short bounded
window, and reports whether the connection was accepted and whether any banner
bytes arrived. `CONFIRMED` requires an accepted connection; note that an accepted
connection with no banner is still a bound listener and should be recorded as
such rather than downgraded. Close the socket in a `finally`.

**A2 — `ADVANCE_INSTRUCTIONS` step-over semantics.** Build a deterministic
subject in RAM rather than stepping over a KERNAL routine with side effects: use
`MEM_SET` to write, at a scratch address, a `JSR` to a second scratch address
followed by a distinguishable filler byte, and at that second address a single
`RTS`. `JSR` is a three-byte instruction, so the address immediately after it is
the `JSR` address plus 3. Discover the program-counter register's id by sending
`REGISTERS_AVAILABLE` and matching the returned name — do not hardcode a
register id. Set the PC to the `JSR` address with `REGISTERS_SET`, send
`ADVANCE_INSTRUCTIONS` with the step-over byte set and a count of 1, then read
the PC back with `REGISTERS_GET`. `CONFIRMED` means the PC equals the `JSR`
address plus exactly 3 — not merely a value greater than the `JSR` address, and
not the subroutine's own address. A PC equal to the subroutine address means the
step-over byte behaved like a plain single step, which is `CONTRADICTED`. Record
the machine's stop state and how it was reached, because register writes only
stick with the machine stopped; if the machine cannot be brought to a reliable
stop without arming a checkpoint on a hot address, record `INCONCLUSIVE` rather
than working around it. Restore the scratch bytes and the PC in a `finally`.

**A3 — `JOYPORT_SET` bit mapping.** Drive the five bits one at a time, in the
fixed recorded order up, down, left, right, fire — never two at once, so a
collision between adjacent bits cannot be read as a single-bit pass. For each
bit: read both CIA1 port bytes at `$DC00` and `$DC01` with `MEM_GET` and
side-effects suppressed to establish a baseline, send `JOYPORT_SET` with that
one bit set, read both bytes again, and record the delta per byte per bit. Read
*both* ports every time — on a real C64 joystick 2 reads at `$DC00` and
joystick 1 at `$DC01`, so reading both is also what answers which wire `port`
value maps to which physical port, which the assumption does not state. Real
joystick lines are active-LOW, so a driven direction is expected to *clear* a
bit, not set one: state the observed polarity explicitly rather than assuming
it. Derive the observed mapping from the deltas and compare it to the assumed
`up=0x01, down=0x02, left=0x04, right=0x08, fire=0x10`. If no single-bit write
produces any observable delta in either port byte — which the keyboard-matrix
multiplexing on port B can cause — record `INCONCLUSIVE` with the raw before/after
bytes, not `CONFIRMED`. Release the joystick (value 0) in a `finally`.

**A5 — `AUTOSTART` `fileIndex` with the run flag clear.** Build a scratch disk
image with at least two distinct programs on it so index 0 and index 1 are
distinguishable, using the `c1541` tool available on this host, writing into a
temporary directory. For each of `fileIndex` 0 and 1: establish an observable
baseline before the send — write a recognisable sentinel byte pattern into the
BASIC program area with `MEM_SET` and read back the BASIC pointer bytes in zero
page — then send `AUTOSTART` with the run flag clear and that index and the
image's absolute host path, wait a bounded moment, and read the same regions
back. Record, per index, whether the sentinel survived, whether the zero-page
pointers moved, and therefore whether any program was loaded or partially
loaded. Also record whether the machine reset as a side effect, since
`AUTOSTART` is a machine-restarting opcode. `CONFIRMED` means the run-flag-clear
call left the program area and pointers untouched at both indices, matching the
approximation the disk-attach handler advertises; any observable load at either
index is `CONTRADICTED`. Delete the scratch image and directory in a `finally`.

Two hard scope fences, both recorded in the mode's own header comment:

- A4 is out of scope. No probe in this file may arm a non-stopping checkpoint,
  and none may arm any checkpoint on a hot or frequently-executed address. The
  reason is that a non-stopping checkpoint's hit frame is emitted synchronously
  from inside the emulator's CPU loop and can stall the emulator thread.
- If a probe shows that an *advertised tool contract* is wrong — for example
  that a documented step-over semantic on the MCP surface is false — record the
  finding and stop. Do not redesign the contract here; plan 13-05 files the todo
  (D-13-04's escape hatch). The trigger is a behavioural-contract change, not a
  file count.

Because several probes touch machine state in one live session, run the
checkpoint-free probes in an order that does not depend on a clean checkpoint
slate, and if any probe needs a known-clean machine, relaunch the emulator
rather than assuming the previous probe cleaned up.
