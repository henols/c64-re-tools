<design_facts>
These are MEASURED or CODE-CITED. Do not re-derive them, and do not treat any of them
as an open question.

1. **The dot refusal binds the ABSOLUTIZED literal path argument, not the physical
   storage location.** `ProjectLocator` calls `java.io.File.getAbsolutePath()` and
   never `getCanonicalPath()` (javap, 12.1.3). So: a relative location is absolutized
   against cwd and refused; a bare `.` segment is caught; a SYMLINK is not resolved and
   is accepted. Run C in the note drove a full import PLUS analysis through a symlinked
   handle -- `REPORT: Analysis succeeded`, 2.1M of program database physically under
   `.c64-re-tools/`.

2. **The location must stay INSIDE the bind-mounted workspace.** `containerPath()`
   THROWS on a host path matching no known host root (`containerpath.ts:141`, reached
   from `host-tool-client.ts:320`). A `/tmp` or XDG-cache handle makes `ghidra.analyze`
   fail on EVERY container-route call. The owner's "tmp folder" idea is refuted by this
   project's own code, not by preference.

3. **The link target MUST be the RELATIVE string.** The CONTAINER itself traverses the
   handle: `ghidra-run.ts:241` reads the run log at the translated path. An absolute
   HOST target names a path that does not exist inside the container, so every run-log
   read would ENOENT. This is the unrecorded third condition that made `/tmp` look
   plausible for so long, and it is the real reason requirement R2 says the broker
   creates the link.

4. **The chosen location is `<repoRoot>/c64-re-tools` -> symlink -> `.c64-re-tools`**,
   with the runs root at `join(handle, "runs", "ghidra")` -- structurally parallel to
   the existing `runs/oracle` (`host-tool.mts:2934`). One link whose name differs from
   the root by a single character reads as an ALIAS, not a third root, and generalises
   to any future dot-refusing host tool at zero code cost.

5. **git ignores a symlink only WITHOUT a trailing slash.** MEASURED in a throwaway
   repo at plan time: with `/c64-re-tools/` the symlink shows as `?? c64-re-tools`;
   with `/c64-re-tools` it is ignored (`git check-ignore -v` attributes it to that
   line). Git does not treat a symlink-to-directory as a directory. Get this wrong and
   every consumer's `git status` goes permanently noisy.

6. **`install-resources.ts` and `repo-root.ts`'s `toolsDir()` are NOT involved.** The
   former is container-side and no longer owns `tools/` (`installTargetDir()` returns
   `.c64-re-tools/bin`); the latter is unreachable from a host-bound `.mts` module by
   the documented module-cycle rule. Join the segments directly here, exactly as
   `host-tool.mts:2930-2934` already documents for `runs/oracle`.
</design_facts>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| filesystem -> `ensureGhidraRunsHandle()` | Whatever already sits at the handle path is untrusted input: it may be a user's own directory, a stale artifact, or a redirect planted by anything with write access to the workspace |
| host -> container (bind mount) | The container resolves the same symlink against its own mount root; the target string crosses this boundary and is interpreted on the far side |
| caller -> `resolveGhidraProject()` | `repoRoot` and `runId` are caller-supplied and reach the filesystem |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-40-08-01 | Tampering | `ensureGhidraRunsHandle()` handle verification | high | mitigate | `readlinkSync()` must equal `GHIDRA_RUNS_HANDLE_TARGET` by exact string comparison; any other target, any non-link, refuses by name and is NEVER repaired, replaced, or unlinked. A redirected handle cannot be laundered into success. Task 1 tests 4, 5, 6, 7 |
| T-40-08-02 | Tampering | `resolveGhidraProject()` reservation `mkdirSync` | high | mitigate | The handle precondition runs BEFORE the reuse check and before `mkdirSync`, so recursive mkdir can never materialise a real directory tree at an unverified handle path.
