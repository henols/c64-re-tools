<objective>
Give the monitor claim a channel axis, so the text socket is owned explicitly
rather than implicitly, and a second MCP process is refused by name instead of
vanishing into a state the wire cannot distinguish from a hang.

Purpose: Phase 39 MEASURED `TEXT_SECOND_CONNECT_OBSERVATION: accepted-then-silent`
— stock's text monitor accepts a second connection and then never answers it,
with no reply and no EOF. Fact 5 states the consequence directly: a second text
connection must be handled by explicit policy (refuse or queue), because it
cannot be diagnosed automatically as a wedge from protocol signal alone. D-14
extends the working `monitor_claim` mechanism rather than building one.

Output: `InstanceRecord.monitorClients` — a per-channel holder map replacing the
single field — threaded through the control op, the client and both connect
paths, plus the invariant test that keeps the generalization from being quietly
reverted.
</objective>

`broker-state.mts`:

- Export `MONITOR_CHANNELS` as `Object.freeze(["binary", "text"] as const)` and
  `MonitorChannel` as its member type. Comment that `channel-lock.ts` declares
  the same two-value contract independently, on purpose: this module is
  host-bound and compiled to `resources/*.mjs`, so a container-side `.ts` module
  cannot import it at runtime — the shared thing is the contract, not the
  declaration.
- Replace `monitorClient?: { grantId; claimedAt; pid }` with
  `monitorClients: Partial<Record<MonitorChannel, { grantId: string; claimedAt: number; pid: number | null }>>`.
  Make it NON-optional and default it to `{}` at every record-construction site

  map rather than an absent field — an absent field is what let the single-holder
  reading survive by omission. `pid` keeps its existing convention: the emulator
  child process's pid at claim time, not the connecting client's, which this
  broker cannot observe over TCP.
- Widen `clearMonitorClient(record: InstanceRecord, channel?: MonitorChannel)`:
  with a channel, clear that one entry; with no channel, clear every entry. Keep
  it the ONE place clearing happens, and state in its doc comment which callers
  pass a channel (an explicit `monitor_release`) and which do not (recycle,
  release, process exit — where the whole record's ownership is going away).
- Rewrite the MONITOR-OWNERSHIP DECISION banner. It currently hands the
  discriminator to a future numbered phase and asserts that nothing dials the
  text-monitor port; both statements are false as of this phase. The replacement
  states: the holder map is keyed by channel; both channels may be claimed
  simultaneously by the same grant; the map is bookkeeping for SOCKET OWNERSHIP
  only and no halting path consults it, because cross-channel halt serialization
  is the container-side in-process mutex's job; and the text-monitor port is
  dialed. Do not hand any remaining work to a numbered phase in this comment —

`broker-control.mts`:

`vice-broker.mts`:

- `handleMonitorClaim(requestId, targetId, channel, state)` reads
  `instance.monitorClients[channel]`. No entry: record the holder and answer
  `ok: true`. Same grant already holding that channel: idempotent `ok: true`,

  named channel, only when `targetId` is that channel's current holder; a
