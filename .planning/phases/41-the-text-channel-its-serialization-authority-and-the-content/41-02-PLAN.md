<objective>
Build the serialization authority Phase 39's verdict selected, and route both
channels' halting operations through it.

Purpose: Phase 39 MEASURED that a text command halts the machine exactly as a
binary one does (the stopwatch advanced only across an `x`), and that ANY
binary-channel command re-halts a running CPU. Two channels therefore need one
discipline, not a free side-channel. The `go` verdict (rule `R15`) selected an
in-process async mutex with no narrowing — so this is the plain primitive, built
fresh: there is no async mutex anywhere in this tree, and the only prior
single-flight queue died with the retired analyser and was explicitly not
extracted.

Output: `channel-lock.ts` — the ONE place the mutex, its FIFO queue, its holder
record and its refusal text live — plus its integration at the binary side's
existing single adapter seam and the text side's own.
</objective>

Implementation notes that are requirements, not suggestions: the queue is a
plain array used strictly FIFO (`push` to enqueue, `shift` to wake); the
grant-on-free path and the enqueue path are both reached through one internal
function so there is no second admission path; a waiter whose timeout fires is
removed from the queue by identity, so a later `release()` never wakes a waiter
that has already been rejected; and `release()` hands the lock to the next
waiter synchronously rather than through a `setTimeout`, so arrival order is not
perturbed by timer scheduling.
