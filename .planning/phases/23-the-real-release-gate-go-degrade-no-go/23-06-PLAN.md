<objective>
Turn criterion 1's cracker/game separation from an argument into a measurement, using the
fact that the operator supplied **two independently-cracked releases of one title**.

Purpose: 23-CONTEXT.md's `<specifics>` recorded that the separation "is not available via
provenance diffing on a single image, since `c64-provenance-diff` is N-way", and left the
researcher to propose how cracker-authored bytes are held out or to state what measuring
everything resident costs. The two-release answer supersedes that: the N-way diff needs
exactly two independently-cracked releases of one title, and it now has them. The
unadjudicated third bucket in the criterion-1 model is **not** discarded — it still covers
bytes provenance diffing cannot classify — it now sits alongside the hold-out rather than
substituting for it, and both the with-cracker-bytes and without-cracker-bytes numbers are
printed because the difference is itself evidence about how far a naive measurement would
have been distorted.

This plan is a vertical slice: align → diff → coalesce → classify → record the hold-out and
its availability. It runs entirely offline over files the capture plan already wrote and
never touches the emulator.

Output: `PROV_HOLDOUT` and the cracker-patch range set criterion 1 subtracts.
</objective>

Run the provenance pipeline in its documented order against the scratch registry, and
record every step verbatim.

Export `C64RE_DATA_DIR` to the phase's `evidence/capture` directory and `C64RE_REGISTRY` to
the `RELEASES.json` inside it, so the toolkit resolves release ids against the scratch
registry rather than looking for a `recovery/` tree this repository does not have.

**Step 1 — prove the offset.** Run `anchor-search` with the canonical release as the
reference. It locates long distinctive byte runs and derives a single global offset per
release, and it **refuses a majority vote**: every usable anchor must agree or there is no
offset. Paste its real output. If it reports success, record the per-release offsets and
write `PROV_ANCHOR_OK: true`. If it reports failure, write `PROV_ANCHOR_OK: false` and stop
the pipeline there — do not pick the majority, do not widen the tolerance, and do not
re-capture in the hope of a better alignment. The tool's own troubleshooting entry is
explicit that a disagreement means the images are not the same fully-loaded state or one
capture is bad, and forcing an offset manufactures false patch verdicts wholesale. Note
that this verb writes to the registry.

**Step 2 — the diff.** Run the `diff` verb with `--json` and paste the tally. Record the
distribution across the five kinds and the three verdicts, and the coalesced differing
ranges with the gap tolerance used, stated explicitly rather than left at whatever the
default is.

**Step 3 — patch counting.** Run `count-patches`, which counts addresses that are both
`CRACKER-PATCH` and `game`-kind. Paste its output. Record `PROV_RELEASES:` (the number of
releases the diff had) and `PROV_CRACKER_PATCH_BYTES:` (the total byte count across all
`CRACKER-PATCH` ranges, not only the game-kind intersection — criterion 1 holds out
cracker-authored bytes wherever they sit, since a loader or cracktro byte contaminates the
denominator exactly as a trainer byte does).

**The independence caveat, stated beside the numbers.** The skill's own premise is that the
two cracks are independent; two releases sharing an ancestor classify nothing, and a
`count-patches` result of zero is not evidence that no cracker change exists, because the
diff cannot see a change both releases carry. Write that in the file next to the count, not
in a footnote. Record the operator's stated basis for believing the two releases are
independently cracked, or record that no basis was stated — that is a fact about the corpus
and belongs in the verdict's accepted limits.

Nothing in this task contacts the emulator, and neither dxa nor Ghidra is invoked.
