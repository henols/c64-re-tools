<objective>
Establish what the dropped `analyzer.rs` work actually did, function by function, and give
every capability exactly one disposition — replaced, accepted as lost with its cost, or
lost and blocking.

Purpose: criterion 4 exists so that dropping the external analyser is a measured decision rather
than an inference from one 279-byte fixture. This plan is the one criterion that needs no
corpus and no instrument — it reads 1,506 lines of Rust offline from the cargo registry —
which is why it runs in wave 2 in parallel with corpus acquisition rather than waiting.

Output: `C4_UNREPLACED_CAPABILITIES`, rule R8's only input, plus the full audit table.
</objective>

**The capability table.** One row per top-level entry point, each row carrying: the
function name, the source line it is declared on, one sentence of what it does derived
from the code and its doc comment, and exactly one disposition string from
`replaced-by:<what>`, `lost-accepted:<cost>`, `lost-blocking:<what it breaks>`. Start from
the eight the researcher enumerated — `analyze` (line 20), `analyze_instruction` (285),
`promote_return_labels` (372), `update_usage` (419), `follow_indirect_jumps` (445),
`guess_scope_end` (546), `flow_analyze` (581), and the `AnalysisResult` shape (8) — but
**check each against the source rather than accepting the mapping**, and add any entry
point the researcher's grep missed.

Three rows carry known weight and must be argued rather than asserted:

- `follow_indirect_jumps` **directly overlaps criterion 2**. On a `JMP ($xxxx)` it checks
  whether the target block is already typed as an address block inside the binary and, if
  so, reads the 16-bit pointer and registers a jump-target label plus a cross-reference.
  Ghidra's `COMPUTED_JUMP` covers the constant case; the anno version needs the block
  already typed, so it is not obviously stronger. This is criterion 4's most load-bearing
  row and its disposition must state the comparison in both directions.
- `promote_return_labels` promotes branch, jump and subroutine label types to a return type
  when the target's first byte is `RTS` or `RTI`, mirroring IDA's `locret_` convention. No
  Ghidra equivalent surfaced during the pivot. If none is found here either, this is a
  candidate `lost-accepted:` with a cosmetic label-quality cost — say so plainly rather
  than inventing a replacement.
- The split-pointer table handling in `BlockType`'s `LoHiAddress` / `HiLoAddress` pair walk
  is answered by Ghidra with the `CONCAT11` idiom in the decompiler — a **different shape
  of answer** to the same question. The audit must state whether that shape is sufficient
  for a per-range typing model (`STORE-01`'s concern) or not, and if it is a partial
  replacement it is written `replaced-by:` **with an explicit shape-mismatch note naming
  what is lost**, per this plan's flagged assumption.

**The vocabulary accounting.** Two further tables: the eleven `LabelType` variants used
(`AbsoluteAddress`, `Branch`, `ExternalJump`, `Field`, `Jump`, `Pointer`, `Return`,
`ZeroPageAbsoluteAddress`, `ZeroPageField`, `ZeroPagePointer`, and any twelfth found) and
the seven `BlockType` variants (`Code`, `Address`, `DataWord`, `LoHiAddress`,
`HiLoAddress`, `LoHiWord`, `HiLoWord`). Each variant is a concrete fact anno records, and
each gets its own disposition — the replacement either records the same fact or drops it.
The zero-page-specific triple and the `Field` versus `Pointer` distinction drive the typed
label prefixes `STORE-05` names as worth stealing, so their dispositions matter beyond
bookkeeping.

**Evidence discipline for a `replaced-by:` claim.** A disposition of `replaced-by:` is only
written where this project has *observed* the replacement producing the fact — the pivot's
own `ghidra3.txt` reference dump is the available observation, and the reference kinds it
carries are `READ`, `WRITE`, `READ_WRITE`, `DATA`, `CONDITIONAL_JUMP`,
`UNCONDITIONAL_JUMP`, `UNCONDITIONAL_CALL`, `COMPUTED_JUMP`. Where the replacement is only
plausible from a feature list, the disposition is `lost-accepted:` or `lost-blocking:` with
the uncertainty stated in the cost. A capability whose replacement lives in the annotation
store rather than in either engine is written `replaced-by: store-side (<requirement id>)`
and named as a Phase 25 dependency rather than as an engine capability.

**Scope boundary.** The audit is scoped to `analyzer.rs`. Where reading it reveals a
capability that actually lives in `exporter/` or `state/`, record it in a
`## Scope observations for Phase 25` section rather than widening the audit — widening here
would grow the gate, and criterion 4 names `analyzer.rs` specifically.
