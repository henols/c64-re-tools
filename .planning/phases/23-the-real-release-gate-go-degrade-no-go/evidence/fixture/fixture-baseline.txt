Reading those two extracts together:

  $0869-$086b  The source (report line 64) emits `jsr print`, an instruction:
               `print` pops its own return address, walks the inline string, and
               returns PAST it, so control really does arrive at $0869 and this
               really is executed code. dxa emitted `.byt $20,$71,$08` for it
               (listing line 60) -- it had already lost the thread inside the
               first inline string at $0863 and never recovered before the
               second call. Under SCHEMA.md section 4 these are three bytes of
               C that dxa typed as data, i.e. three FALSE POSITIVES.

  $08a6        The operand cell of `lda #$00` at smc_target (report line 108).
               `sta smc_target+1` at $08a2 writes into it at runtime (report
               line 106, and the source comment says so: "writes INTO a Code
               block"). dxa typed $08a5-$08a6 as one instruction, i.e. code.
               Whether this cell is "code" or "data" is a definitional choice,
               not an observation.

Recorded in this plan's own evidence file, per evidence/README.md convention 8

**RC-1. Assumption A1 -- the fixture's 141-code / 138-data partition is NOT
source-derivable, and this plan is the first to check.**

23-RESEARCH.md logs the 141/138 partition as assumption A1. Re-deriving it byte
by byte from `fixture.a` via acme's own report gives **145 code / 131 data /
3 assembler-pad**, or 145/134 with the pad counted as data. It does not give
141/138 under any padding treatment. The published partition classifies four
more bytes as data than the source does.

Those four bytes are identified above: `$0869-$086b`, the second `jsr print`
opcode that dxa mis-typed as data, and `$08a6`, the self-modified operand cell.
Reclassifying exactly those four from code to data reproduces **all four**
published figures simultaneously and exactly -- 141/138, 72.46% (100/138),
0 false positives, 27.54% (38/138) -- as `RECON_*` above shows.

**That reconstruction was FITTED, and is recorded as a hypothesis, not as a
derivation.** The four addresses were chosen because they make the numbers
agree; the fact that they are also semantically meaningful (an inline-parameter
blob boundary and an SMC operand cell) is corroboration, not proof. What is
proven is the negative: the published partition cannot be recovered from the
source alone, so A1 was an assumption and remains one.

**Why this matters to D-11, which is the whole reason the fixture is here.**
The pivot's partition is *more generous to dxa than the source is*, in the one
place that decides the headline "0 false positives" claim. Three bytes dxa got
wrong -- it typed a live JSR as data -- are counted as data in the published
ground truth, so they score as a success instead of as three false positives.
The corpus measurement in 23-06/23-07 derives its `C` and `D` sets from the
pre-committed VICE runtime inventory (D-05/D-06, SCHEMA.md section 4), which has
no equivalent hand-adjustment step. **A side-by-side that prints the corpus's
inventory-derived numbers beside the pivot's published 72.46% / 0-FP is
therefore NOT apples-to-apples.** The apples-to-apples fixture figures are the
source-derived ones on the outcome lines below: 72.39% recovery, 3 false
positives, 27.61% false negatives. D-11 should print those, and may print the
pivot's published figures beside them only with this correction attached.

**RC-2. The pivot's published dxa command line uses `-a enabled`, not `-a dump`.**

The pivot evidence README records the run as
`dxa -U -p all-nmos6502 -t detect-all -a enabled fixture.prg`, and its `dxa.out`
carries address+text lines with no byte columns. 23-02-PLAN.md's action text
calls `-U -p all-nmos6502 -t detect-all -a dump` "the pivot's own published
command line"; the `-a dump` part is not the pivot's, it is this phase's, and
SCHEMA.md section 6 requires it because the byte columns are what make counts
READ rather than inferred from mnemonic lengths. dxa's classification is
identical under both (179 code / 100 data either way -- the pivot's own dxa.out
shows the same `.byt $20,$71,$08` at $0869). The substitution is correct and
changes no number; only the attribution in the plan text is wrong.

**RC-3. dxa's "alpha software" self-description is in INSTALL, not the man page.**

23-02-PLAN.md attributes it to `dxa.1`. `grep -i alpha dxa.1` exits 1 with no
output; the statement is at INSTALL:15, "Please keep in mind this is still
considered \"alpha\" software and there may be bugs, which is why it is not part
of the official xa distribution yet." The claim holds; the citation does not.
Recorded in evidence/tools/instrument-provenance.txt as well.

Per SCHEMA.md's preamble: a measuring plan that needs a name or a value the
pre-commitment does not declare records that as an ACCEPTED LIMIT in its own
evidence file. It does not invent a name and it does not edit SCHEMA.md. Four

     unsatisfiable without contradicting the pre-commitment, and is not

     23-02-PLAN.md expects `pass` / `fail`. SCHEMA.md wins: `no` is written.

     section 3 fixes the percentage shape as `<decimal> (<numerator>/<denominator>)`

     `FIXTURE_DATA_RECOVERY_PCT` at end-of-line after two decimals. SCHEMA.md
