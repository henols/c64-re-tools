## 2. Parse before booting — the corpus is untrusted input

The corpus arrives from outside the project and is about to be executed in an
emulator. `d64-parse.mjs` reads the bytes directly and answers what is on the
disk without booting anything. It reports a `chain_error` instead of hanging on a
directory chain that leaves the image or loops, and sets `suspicious` /
`suspicious_reasons` on an entry whose block count is 0, whose first track/sector
falls outside the image, or which points into a track the BAM reports entirely
free — the signature of an entry claiming a file never written to disk.

This addresses threat T-23-01 (Denial of Service — malicious or corrupt .d64).
Whatever it reports is recorded here as a fact about the corpus and is NOT
worked around. Per threat T-23-04, every string recovered below is evidence text
only: no directory string is ever interpolated into a path or a shell command.

## 4. The independence claim, at the confidence the evidence supports

  INDEPENDENCE: no-shared-ancestor-indicator-found   (stated as prose here; the outcome line itself is in ## Outcome lines below)

Stated at that strength deliberately, and NOT as "proven independent".

What the evidence above does support: the two images are not the same artifact
and are not a re-labelled copy of one another. They differ in sha256, in disk
header name, in disk id, in directory entry name, and — the substantive part —
in physical layout. The payload starts at track 17 on one disk and track 1 on the
other, runs to a different block count (178 vs 186), and occupies disjoint track
ranges (9-18 vs 1-9 plus 18). Two releases derived from a common cracked master by
re-writing the same file would not relocate the payload across the disk and change
its length.

What it does NOT support, and what must not be read into it: that the *game code
inside* the two payloads has no shared ancestor. A directory and BAM comparison
speaks to how each disk was written, not to what the depacked bytes are. Two
crackers working from the same original tape or cartridge dump will legitimately
produce near-identical game bytes with entirely different disk layouts — that is
the expected case, not a defect, and it is the whole reason the provenance diff
in 23-06/23-07 anchors before it diffs.

The claim recorded here is therefore the negative one it is entitled to be: a
search for a shared-ancestor indicator was made against the evidence available
before booting, and none was found. Should the provenance diff later find the two
payloads byte-identical outside the loader, THAT is the fact that would retire
this claim, and it is measured downstream rather than assumed here.

## 5. The scratch release registry

`dump-artifacts.mjs write-set` resolves its `--release` id through `releases.mjs`,
which reads a registry file. There is no `RELEASES.json` anywhere in this
repository (23-RESEARCH.md § Pitfall 6), so `write-set` would refuse with a
known-id list. The toolkit is pointed at a scratch registry inside the evidence
tree instead of one being created in `recovery/`:

  export C64RE_DATA_DIR=<phase>/evidence/capture
  export C64RE_REGISTRY="$C64RE_DATA_DIR/RELEASES.json"
  export C64RE_DISKS_ROOT=/home/henrik/dev/henrik/git/bruce_lee

`C64RE_DISKS_ROOT` is set because `disk_image` is resolved relative to
`disksRoot()`, which defaults to this repository's own root; the images live in a
different repository entirely and must not be copied into this one.

THIS REGISTRY IS SCRATCH STATE FOR ONE PROBE. It is not the `recovery/` tree a
consuming project would have, it is not a fixture, and nothing outside phase 23
reads it. It exists so that one toolkit entry point can resolve two ids.

It follows the release-centric shape c64-ram-capture/SKILL.md § Release registry
shape documents: `canonical` is a boolean on exactly one of N entries, never a
privileged singular image. `dumps` is present as an array on every entry even
while empty — an absent key throws `TypeError` in `releases.mjs list`, which
reads `r.dumps.length` with no guard.
