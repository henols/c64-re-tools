## 0. The instrument

`evidence/vsf-ram-extract.mjs`, added alongside this transcript. It reads a VICE `.vsf`
snapshot file and never contacts the emulator. Difference classification follows
`compare.mjs`'s published rule and does not reimplement it beyond the stated popcount
split: exactly one differing bit is drift (passes), two or more bits is divergence (fails).

A `.vsf` is `"VICE Snapshot File\x1a"` (19 bytes) + 2 version bytes + a 16-byte machine
name, then modules; each module is a 16-byte NUL-padded name, 1 major, 1 minor, and a
4-byte little-endian size covering the whole module including its 22-byte header. The
`C64MEM` module body is 4 bytes of port/PLA state followed by exactly 65536 bytes of RAM.

## 1. The extraction is correct — cross-checked against 23-03's own hand-transcribed hex

Before trusting any number derived from a snapshot, the snapshot route was checked against
the independent hex 23-03 transcribed out of the same instant via `vice_memory_read`.

$ node vsf-ram-extract.mjs ~/.config/vice/mcp_snapshots/danish_r2_handoff.vsf --write-bin /tmp/v.bin
SNAPSHOT_A: /home/henrik/.config/vice/mcp_snapshots/danish_r2_handoff.vsf
SNAPSHOT_A_SIZE: 65536
SNAPSHOT_A_SHA256: 626db182bb13fdf5197840854738663a4a74eeeec19145058faf8cb3f6a3851b
WROTE_BIN: /tmp/v.bin

$ node -e '<compare /tmp/v.bin against $PROBE_DIR/capture-work/danish-run2/c*.hex>'
XCHECK_C0000: 8192 bytes, differences=2 at $0000,$0001
XCHECK_C2000: 8192 bytes, differences=0
XCHECK_C4000: 8192 bytes, differences=0
XCHECK_C6000: 8187 bytes, differences=1679 (transcript ODD-LENGTH: corrupt) first=$7871

Two 8 KB chunks are **byte-identical**. `$0000-$1FFF` differs at exactly two addresses,
`$0000` and `$0001`, which is expected and not an error: those hold the underlying RAM
bytes in a snapshot, while a CPU-view `vice_memory_read` returns the 6510 processor-port
registers layered over them. `$6000-$7FFF` agrees to `$7871` and is shifted thereafter —
that chunk's transcript has an odd hex length, independently localising the ten dropped
characters 23-03 reported to `$7871`.

XCHECK_VERDICT: pass — the snapshot route reproduces the transcript everywhere the
transcript is itself intact, and the only systematic difference is the documented
two-byte port overlay.

## 3. What it establishes

The two `danish` runs are **not equivalent**, and they are not equivalent for a reason that
has nothing to do with how the bytes were read out. Both sides of this comparison came from
snapshot files; there is no transcription anywhere in it. 23-03 had already separated the
two causes and this measurement isolates the surviving one:

- Hex-transcription unreliability is **removed** here — § 1 proves the route.
- The runs still diverge at 201 multi-bit addresses, because the fork's stopping exec
  checkpoint is not frame-exact: it reports the hit but pauses roughly a frame later at a
  wall-clock-determined instruction, and these two runs landed on different frames
  (`hit_count` 1 and 2). `saeger`'s two runs, which both landed on `hit_count` 1, diverged
  at exactly one byte — `$00F6`, the KERNAL keyboard-decode-table pointer — which is the
  contrast that identifies frame index as the dominant term rather than intra-frame
  position.

A frame-exact stop is therefore the single remaining gate on rule R1's "secure a corpus
first" branch.
