## 1. Working copies of the corpus, inside the mounted workspace

## 2b. VOIDED identification run 2 — the broker died with the session (~12:55 UTC)

Recorded here, beside the § 2 epoch-drift void and in the same shape, because the
two are the same kind of fact about the same run of work. It is out of chronological
order deliberately: it happened AFTER everything in § 3 - § 7 below was observed, and
placing it beside § 2 keeps both voids where a reader looking for "what was voided"
will find them together, rather than buried under the observations they void.

What happened: the VICE broker was, at that time, a child of the Claude Code process
tree. When the executor's session was torn down at ~12:55 UTC the broker died with it,
taking the emulator instance with it. This is not any of the four states
`vice-wedge-triage` triages — the machine was not paused, not checkpoint-trapped, not
wedged and not respawned-under-us. The process that owned it simply ceased to exist.
There was no error frame to quote, because there was no surviving client to receive
one; the death is inferred from the session teardown and from the fact that the
subsequent session found a different broker pid.

The scope of the void, stated plainly:

- **Every observation in § 3 - § 7 was taken on the machine that died.** Under
  `c64-ram-capture` § *Prove the machine did not change under you*, an observation
  whose machine identity cannot be carried forward does not carry forward. All of it
  is void as *measurement*.
- **No capture artifact existed to rename.** No `.bin`, `.state.json`, `.map.json` or
  `.capture.json` had been written at any point on that machine — the run never
  reached `write-set`. The template's voiding rule (rename each artifact to
  `<name>.VOID-<UTC timestamp>`, keep it on disk) therefore has nothing to act on,
  and the void is recorded here instead. That substitution is the rule's own
  instruction for the artifact-less case and is not a weakening of it.
- **`$HOME/.cache/c64-re-tools/phase23/capture-data/` and `capture-work/` hold no
  capture files** — only two transient screenshots from the § 4 keypress step. Nothing
  in either directory is reusable evidence. The capture work below starts from zero.

What survives the void, and why that is not a contradiction: § 5 - § 6's conclusion
that `$1BC2` is the head of the game's own frame loop is a **claim about the game
image**, not a measurement of a machine. A void invalidates numbers read off a machine
that can no longer be shown to be the same machine; it does not invalidate a reading of
a disassembly that any fresh machine will reproduce from the same disk bytes. The
distinction is made honest by re-verifying it rather than asserting it: **every capture
run below disassembles `$1BC2` on its own fresh machine, per release, and pastes the
result**, so the handoff address the captures actually break at is proven on the machine
that took them. What § 5 - § 6 is relied on for is only *where to look* — and the D-06
prohibition it satisfies (the address came from emulator observation, never from dxa or
Ghidra) is a property of how it was found, which a later machine's death cannot undo.

The cause has been removed rather than worked around. The broker now runs as a systemd
**user** unit, outside the Claude Code process tree, so a session teardown no longer
takes the emulator with it:

$ systemctl --user is-active vice-broker
active

$ mcp vice_ping
{"status":"ok","version":"3.10","machine":"C64SC","execution":"paused"}

Backend on the fresh machine is unchanged and still satisfies Task 3's
`<precondition>`: fork, /usr/local/bin/x64sc, VICE 3.10.

## 5. Naming the handoff address by disassembly, not by guess

$ mcp vice_disassemble {"address":"$1C20","count":30}

$1C23: 20 C3 29    JSR $29C3
$1C26: 20 84 31    JSR $3184

$1BD7: AD 05 01    LDA $0105
$1BDA: 10 03       BPL $1BDF

$1BEE: 20 BC 40    JSR $40BC

$1BC2 sets the per-frame counter $48 = 3, runs the game's subsystem calls, then $1C32-$1C34
waits for the IRQ to drain $48 to zero and $1C36 jumps unconditionally back to $1BC2.
**$1BC2 is the head of the game's own main frame loop.**

## 6. The handoff address, and why it is this one

CAPTURE_HANDOFF_PC for both releases is **$1BC2**, and the capture instant is defined as
**the FIRST execution of $1BC2 after a cold autostart**.

Why this address and not another:

- It is game code, not loader or intro code. At the intro the CPU is in $0800-$0CFF and the
  game image is not yet resident; $1BC2 cannot execute until the second load has completed
  and control has been transferred. Its first execution is therefore, by construction, on
  the game side of the loader handoff.
- It is the *head* of the frame loop, so its first execution is the first game frame — the
  earliest point at which "control has reached the game" is observably true, and the point
  at which the least timing-dependent state has accumulated. That is what makes two runs
  comparable: nothing animated has advanced, no input has been consumed.
- It was found by disassembling the running machine ($1C36's unconditional `JMP $1BC2`
  closing the loop, $1BC4's frame-counter reload opening it), not by pattern-matching a
  database or by asking a disassembler under test. **No fact used to judge dxa or Ghidra is
  produced by dxa or Ghidra** (plan prohibition; D-06).

Both releases are cracks of the same title, so the same game image and the same $1BC2 head
are expected in both; the capture runs below confirm that per release rather than assuming
it.

## 7. Accepted limit — WarpMode could not be set, so every run is real-time

$ mcp vice_machine_config_set {"resources":"{\"WarpMode\":1}"}
vice: the host VICE MCP server ... rejected this call: Missing or invalid 'resources' object.
Expected: { "resources": { "ResourceName": value, ... } }

The `vice_machine_config_set` tool declares `resources` as a JSON **string** in its own
schema while the host server requires a JSON **object**, so the call cannot be satisfied
from this surface. Recorded as an observation about the tool, not worked around: no shell
invocation of `x64sc` was attempted (plan prohibition), and none of the three power-cycling
resources (MachineVideoStandard, VICIIModel, MachinePowerFrequency) was set at any point.
Consequence: every load below ran at real speed, ~95 s to the intro and ~40 s more to the
title menu.
