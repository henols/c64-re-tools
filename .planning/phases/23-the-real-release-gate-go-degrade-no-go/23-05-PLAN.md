<objective>
Commit what the corpus actually contains, before anything measures it: every `$01` write
with its program point and value, every dispatch site with how many distinct targets it was
observed taking, the bytes proven to be code, the bytes proven to be data, and the window
those facts are scoped to.

Purpose: D-05 makes the inventory a pre-commitment, so "not exercised" becomes an earned
corpus property rather than a post-hoc excuse. D-02 makes VICE the way the code of interest is
reached at all — navigating to the region under study in the running emulator rather than
analysing whatever the file statically happens to contain — and D-06 makes the inventory
VICE-observed only, which closes the circularity trap — if either engine under test enumerated the sites, criterion 2
would degrade to "Ghidra resolved the dispatch that Ghidra found", and criterion 3 would
inherit the same defect. This plan is a vertical slice: arm → observe → bound → transcribe
→ commit, with no engine involved at any point.

Output: the four inventory files and the `INV_*` outcome lines every later criterion reads.
</objective>

  <context>
    Three parameters become one-way the moment the first watchpoint is armed.

    1. **The `$01` hit ceiling**, declared before the run, with the saturation stop condition:
       stop early when no new distinct program counter appears in K consecutive hits. Proposed:
       ceiling 2000 hits, K = 200. A raster interrupt that banks twice per frame produces roughly
       100 stops per emulated second and each stop is several MCP round trips, so an unbounded run
       is not affordable; 2000 hits is roughly 20 emulated seconds of a hard-banking title, which
       is past the title screen and into play.
    2. **The site-discovery route**, which must be engine-free: byte-pattern search over the
       resident window followed by disassembly at each hit to confirm alignment — `$6C` for
       `jmp (abs)`, the `48 48 60` `pha`/`pha`/`rts` shape for an RTS-trick dispatch, and `$4C`
       whose operand bytes are also a store target for a self-modified `jmp abs`.
    3. **The "computed" definition**: a site is computed iff, across the observed run, the value
       it dispatches through takes two or more distinct values at the same program address. One
       target across many hits is the easy case, recorded as the easy case.

    Alternatives rejected: using the in-house decoder to *find* candidates, which edges toward
    being an oracle even though it is not an engine under test; full executed-byte coverage via
    instruction history, which needs `CPUHISTORY_GET` (VICE ≥ 3.10, and exposed as an MCP tool on
    neither manifest); and non-stopping trace checkpoints, which the stock backend auto-disables
    above 20 hits per second — turning the instrument off mid-run silently — and which on either
    backend emit one frame per hit synchronously from inside the CPU loop over the blocking
    monitor socket.

    Cost of being wrong: a ceiling set too low records `not-exercised` for a construct the corpus
    does contain, firing a `degrade` narrowing that was not earned. Raising it afterwards is
    exactly the move the pre-commitment forbids.

**The `$01` timeline.** Write `INV_HIT_CEILING:` and the saturation constant into
`evidence/inventory/bank-timeline.txt` first, then arm a write watchpoint on `$0001`. Loop:
run, poll the checkpoint's hit count until it increments — poll on hit count, never on
paused state, which is the documented `vice-sync.ts` invariant and the fix for a real
earlier bug — then read the program counter from the registers, read the new value at
`$0001`, read the cycle stopwatch for ordering, and record the triple. Stop when the
ceiling is reached or when no new distinct program counter has appeared in K consecutive
hits. Record which of the two ended the run on `INV_TERMINATION:` — `saturation` or
`ceiling` — because a ceiling stop and a saturation stop mean different things about how
completely the corpus was surveyed.

Order the timeline by non-decreasing cycle, keeping equal-cycle hits in observation order.
If the stopwatch is observed non-monotonic, say so in the file and order by observation
index instead, recording the substitution — this plan's flagged assumption covers exactly
that case. Emit `INV_BANK_WRITE_SITES:` (the count of distinct program counters that wrote
`$01`) and `INV_BANK_VALUES:` (the distinct values observed, comma-separated in `$xx`
form).

When done, disarm: delete the checkpoint, then call the checkpoint list and accept only its
enumeration as proof that none remain — a delete call's own word is never the proof — and
resume the machine exactly once.

**Dispatch-site enumeration.** Write `evidence/inventory/dispatch-sites.txt`. Search the
resident window for each construct byte pattern with the memory-search tool and confirm
every hit's alignment by disassembling at that address; paste both transcripts. Then, for
each confirmed site, place an execution checkpoint and, on each hit, read the value the
site dispatches through — for a `jmp (abs)` that is the two pointer bytes at the indirect
address plus the index register the preceding load used; for an RTS-trick site it is the
two bytes pushed. Record one `INV_DISPATCH_SITE:` line per site carrying the address, the
construct kind from `jmp-indirect` / `rts-trick` / `self-modified-jmp`, the count of
distinct targets observed, and the hit count. Sort ascending by address. Emit
`INV_DISPATCH_SITES:` as the total count.

**Reject nothing.** If a construct is not present in the corpus, record that as a fact with
the search transcript that found nothing — do not widen the search until something turns
up, and do not substitute a different release. A dispatch site observed taking exactly one
target across many hits is written as the easy case, in those words, and is not a computed
site; that distinction is the whole reason criterion 2 exists, since the pivot fixture used
an immediate index and silently re-testing the easy case would reproduce the defect this
phase removes.

**Cost control.** A raster interrupt that banks twice per frame produces roughly 100 stops
per emulated second and each stop is several round trips. Stay inside the declared ceiling.
Prefer stopping checkpoints over non-stopping trace checkpoints. If the emulator stops
responding, work the wedge-triage decision tree before concluding anything and record the
triage outcome; do not open a second monitor connection to diagnose a slow run, because the
stock binary monitor services exactly one client and a second connection is
indistinguishable from a hang.

Turn the observations into the three sets criterion 1's ratios are computed over, and
commit the aggregate inventory.

**Certain code, set `C`.** Every byte the processor was observed executing, plus every JSR
call site and every call target. Sample the program counter across the run — batched
execution steps, or a run-until with a cycle budget followed by a register read — and at
each sample take the backtrace, which returns the JSR return addresses on the stack; each
return address minus the length of the `jsr` instruction is a call site and therefore code,
and its target is a routine entry. That is roughly two tool calls per sample and yields
several certain-code addresses each time. The set only has to *bound* false positives from
below; it does not have to enumerate all code, and the file says so plainly so a reader does
not mistake incompleteness for a claim.

**Certain data, set `D`.** The VIC's DMA-fetched regions, which are data whether or not any
instruction references them: the 1000-byte screen matrix at the screen base, the eight
sprite pointers at screen base plus `$3F8`, the charset or bitmap at the charset base, and
the sprite bitmaps those pointers name. Take these from the pointers the capture already
derived rather than hand-decoding `$DD00`, `$D018` and `$D011` — the `$DD00` bits are
inverted and that is the classic error. Cross-check them independently with `vicderive.mjs`
and record both results; a disagreement between the two is a finding and is written up.

**The overlap.** Compute the size of the intersection of `C` and `D` and emit it on
`INV_CODE_DATA_OVERLAP:`. This is a **finding, not an error** — self-modifying code and
jump tables legitimately produce bytes that are both executed and DMA-fetched — and those
bytes enter neither ratio. State that in the file.

**The window `W`.** Apply the derivation rule committed in 23-01: the union of the ranges
the loader was observed writing and the ranges observed executing, minus `$0000-$01FF`,
minus `$D000-$DFFF`, minus any range the capture shows as neither loader-written nor
executed. Emit it as an explicit comma-separated list of `$xxxx-$yyyy` ranges on
`INV_WINDOW:` and its byte count on `INV_WINDOW_BYTES:`. Never express it as a percentage of
the image. Show the derivation step by step so a reader recomputes the range list rather
than trusting it.

**Commit the aggregate.** Write `evidence/inventory/runtime-inventory.txt` carrying
`INV_SOURCE: vice-runtime-observation` — the D-06 assertion, and the file states in prose
that no dxa or Ghidra output informed any fact in this inventory — then `INV_WINDOW`,
`INV_WINDOW_BYTES`, `INV_DISPATCH_SITES`, `INV_BANK_WRITE_SITES`, `INV_BANK_VALUES`,
`INV_HIT_CEILING`, `INV_TERMINATION`, `INV_CERTAIN_CODE_BYTES`, `INV_CERTAIN_DATA_BYTES`,
`INV_CODE_DATA_OVERLAP` and `INV_ADJUDICATED_FRACTION` (the certain-set total over the
window byte count, computed as an exact ratio and displayed rounded half-up to two decimal
places, with the raw counts printed beside it).

Close with a `## Pre-declared corpus properties` section listing, in prose, every construct
the corpus was searched for and does **not** contain, with the transcript reference for
each. That section is what earns a later `not-exercised`: it is a fact about the corpus,
recorded ahead of the measurements, rather than an excuse offered after them.

This plan's commit must land before any `criterion1`, `criterion2` or `criterion3` evidence
commit. Verify with `git log` before finishing, and record the check.
