<objective>
Collect every outcome line into one durable document, walk them through the rule committed
before any of them existed, and record the verdict as machine-readable frontmatter.

Purpose: criterion 5 is what makes the gate structural rather than skippable, and D-10 fixes
the form the verdict takes — machine-readable frontmatter in a durable findings document
mirroring `docs/phase9-external-analyser-probe-findings.md`, with the body reproducing the
full rule and walking the actual outcome values through it. Phase 9's
precedent is the stated bar — the rule fired, `degrade` was honoured rather than overridden,
and the milestone shipped smaller and correct. The document must let a reader re-derive the
verdict from the evidence rather than take it on trust, which is why the rule is reproduced
verbatim and every earlier rule's non-firing is shown.

Output: `docs/phase23-real-release-gate-findings.md`, the artifact Phase 24's planner reads
as a precondition.

carries YAML frontmatter unlike the two frontmatter-less probe documents in `docs/`, because
criterion 5 requires a machine-readable verdict Phase 24's planner reads as a gate and a
prose sentence buried in the body is not that.

**The `## Verdict` section, first in the body.** State the verdict and the fired rule. Then
show the derivation: the input value that made the rule fire, and — one clause per rule —
why every earlier rule did **not** fire, citing each earlier rule's input value. That is the
re-derive-don't-trust property and it is exactly what made Phase 9's criterion 5 checkable.

which side the observed value fell on, so an exactly-at-threshold value is unambiguous.

Then reproduce **the entire decision rule verbatim**, as a blockquote, from
`evidence/DECISION-RULE.md`, so the document is self-contained and does not depend on a plan
file surviving. Include the never-a-gate declarations, so a later reader cannot mistake a
non-zero `C4_LOST_ACCEPTED` or a large `C3_DIVERGENT_SITES` for a failure.

merged. Where the fired rule carries a pre-mapped narrowing — rules R6 and R7 do — reproduce
that narrowing as written in 23-01 rather than re-authoring it, and name the requirement ids
it acts on. Where the fired rule does not carry one — R3, R4, R5, R8 — author the narrowing

`no-go`, name what the milestone becomes instead.

**If an outcome value fits the rule badly**, do not reinterpret the rule. Write a
`### Override` subsection naming exactly what was overridden, the rule text it departs from,
the evidence that motivated it, and the acknowledgement that an override weakens the
pre-commitment it exists to provide. That is the one permitted escape and it is loud.
