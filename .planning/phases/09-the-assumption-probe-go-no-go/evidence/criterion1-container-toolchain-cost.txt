## Dockerfile.single (verbatim, final/corrected)

# Single-stage probe: what "just cargo install it in the devcontainer" costs forever.
# Resolved base tag: rust:1.90-slim (rustc 1.90.0). NOTE: rust:1.88-slim (rustc 1.88.0)
# was tried first per plan 09-01's evidence but failed with a real compile error --
# quantette@0.6.0 requires rustc 1.90, safe_arch@1.2.0 and wide@1.6.1 require rustc
# 1.89 -- so the actual floor is higher than plan 09-01 recorded. See this evidence
# file's RESEARCH CORRECTIONS section.
# Deliberately unoptimised -- no apt-get, no cache mounts -- the point is to measure
# the naive route's cost, not to minimise it.
FROM rust:1.90-slim
RUN cargo install regenerator2000
ENTRYPOINT ["regenerator2000"]

## Dockerfile.multi (verbatim, final/corrected)

# Multi-stage probe: what the shipped devcontainer image would actually need.
# Builder base: rust:1.90-slim (rustc 1.90.0, same real floor as Dockerfile.single --
# rust:1.88-slim failed here too; see Dockerfile.single's header note and this
# evidence file's RESEARCH CORRECTIONS section).
# Runtime base: node:22-slim (Node v22.23.2), because regenerator2000 runs on the MCP
# proxy's side of the container boundary per D-R4, and the runtime must satisfy
# .claude/mcp/vice/package.json's engines.node floor (>=22.18.0) -- v22.23.2 clears it.
FROM rust:1.90-slim AS builder
RUN cargo install regenerator2000 --root /out

FROM node:22-slim
COPY --from=builder /out/bin/regenerator2000 /usr/local/bin/regenerator2000
ENTRYPOINT ["regenerator2000"]

## Runtime verification (the multi-stage image must actually run the binary it ships)

First attempt (`rust:1.90-slim` builder, Debian 13 "trixie") -- a **real, distinct
finding**, not a version mismatch:

$ docker run --rm r2000-probe-multi --version
regenerator2000: /lib/x86_64-linux-gnu/libc.so.6: version `GLIBC_2.38' not found (required by regenerator2000)
regenerator2000: /lib/x86_64-linux-gnu/libc.so.6: version `GLIBC_2.39' not found (required by regenerator2000)

$ docker run --rm rust:1.90-slim cat /etc/os-release
PRETTY_NAME="Debian GNU/Linux 13 (trixie)"

$ docker run --rm node:22-slim cat /etc/os-release
PRETTY_NAME="Debian GNU/Linux 12 (bookworm)"

Confirmed the root cause directly: the two base images are built against different
Debian releases with incompatible glibc generations, so a binary compiled in the
trixie-based builder cannot run against the bookworm-based runtime's libc, regardless
of anything Rust- or regenerator2000-specific. Corrected `Dockerfile.multi`'s builder
to `rust:1.90-slim-bookworm` (Debian 12, matching `node:22-slim`), rebuilt (the timed
build above is already the corrected version), and re-verified:

$ docker run --rm r2000-probe-multi --version
regenerator2000 0.9.20

R2000_VERSION_IN_IMAGE matches plan 09-01's host `INSTALLED_VERSION` exactly
(`regenerator2000 0.9.20`) -- no install-reproducibility mismatch to report for the
version itself. The mismatch that *did* occur was structural (Debian release / glibc
generation across build stages), not a version drift, and is recorded as its own
finding below.

## Baseline note

This repo has no existing devcontainer image of any kind -- there is nothing to diff
these numbers against. `SINGLE_STAGE_BYTES` (1,256,576,420 bytes, ~1.26GB) and
`MULTI_STAGE_BYTES` (250,820,636 bytes, ~251MB) are **absolute image sizes**, not
deltas from a "before" state. The ~5x difference between them (1.26GB vs 251MB) is
the actual, measured cost of carrying `rustc`/`cargo`/`~/.cargo/registry` in the final
image forever (single-stage) versus discarding the builder and shipping only the
compiled binary (multi-stage) -- this is the number Phase 10's `R2000-03` needs, and
it is not a delta against any pre-existing baseline because none exists.

## RESEARCH CORRECTIONS

1. **The real rustc floor for regenerator2000 0.9.20 is >= 1.90, not >= 1.88.** Plan
   09-01 established rustc >= 1.88 from the crate's own committed `Cargo.lock` pins
   (`ratatui 0.30.0`, `image 0.25.10`, `vergen 9.1.0`, `icu_properties 2.2.0`) but did
   not attempt an actual compile against that floor. This plan did: `rust:1.88-slim`
   (rustc 1.88.0) resolves fine and satisfies those four pins, but fails a real
   `cargo install regenerator2000` outright with `rustc 1.88.0 is not supported by the
   following packages: quantette@0.6.0 requires rustc 1.90, safe_arch@1.2.0 requires
   rustc 1.89, wide@1.6.1 requires rustc 1.89`. `rust:1.90-slim` (rustc 1.90.0) builds
   cleanly. Phase 10's `R2000-03` should document the floor as **rustc >= 1.90**, not
   1.88 or 1.85.
2. **A multi-stage build across `rust:*-slim` and `node:*-slim` needs matching Debian
   releases, or it ships a broken binary.** `rust:1.90-slim` is built on Debian 13
   "trixie"; `node:22-slim` is built on Debian 12 "bookworm". A binary compiled in the
   former and copied into the latter fails immediately with
   `GLIBC_2.38'/'GLIBC_2.39' not found` -- confirmed directly via `/etc/os-release` in
   both base images. `rust:1.90-slim-bookworm` (Debian 12, matching `node:22-slim`)
   fixes it. **This is a new finding 09-RESEARCH.md's Code Examples section did not
   anticipate** (its skeleton used unqualified `rust:1.85-slim` and `node:24-slim`
   with no Debian-release pairing note) and Phase 10's `R2000-03`/any real devcontainer
   Dockerfile must pin matching Debian releases across stages, or statically link
   (e.g. musl target) to sidestep the glibc coupling entirely.
3. **`docker images <repo1> <repo2>` (two positional arguments) is rejected by this
   host's docker (29.7.2): "requires at most 1 argument".** 09-RESEARCH.md's Code
   Examples section did not show the human-readable listing command at all (only
   `docker image inspect --format`), so this is a new, minor CLI-surface note rather
   than a contradiction -- recorded here since plan 09-02's own task text sketched the
   two-positional-argument form. `docker images --filter reference=<name>` per image
   is the working equivalent on this docker version.
