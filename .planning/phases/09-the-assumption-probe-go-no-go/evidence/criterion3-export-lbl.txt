        let mut export_list = Vec::new();

        Ok(format!("Labels exported to {path:?}"))

VERDICT: ".start" is an AUTO-GENERATED artifact -- no human ever typed the name "start";
it is produced by the "Import Context Setup" modal's Confirm handler (the exact modal
09-03 discovered and dismissed with Enter, with the "[X] Disassemble from Entry Point
Address" checkbox checked, confirmed in 09-03's transcript) -- but it is internally
classified LabelKind::User, by deliberate tool design: the dialog calls
`create_set_user_label_command`, the IDENTICAL constructor function a genuine
`r2000_set_label_name` MCP call uses (compare mcp/handler.rs's r2000_set_label_name
handler, which calls the same `create_set_user_label_command`, with a caller-supplied
name/address instead of the hardcoded "start"/entry_addr). There is no separate
"auto"/"synthetic" label kind involved -- the tool deliberately treats "name the entry
point" as equivalent to a user action, indistinguishably from a real `r2000_set_label_name`
call, at the data-model level. This is NOT the empty-export trap the inherited findings
warned about (that trap is TRUE auto-analysis artifacts like the cross-reference names
"f_C021"/"zpp_C0"/"zpa_0F" visible in this same fixture's disassembly, none of which
appear in the exported .lbl file above -- confirming those really are excluded by the
LabelKind::User filter, unlike "start").

The exported file therefore carries ONE genuinely human-initiated label
(.probe_user_label, from this task's own r2000_set_label_name MCP call) and ONE
tool-synthesized-but-User-kind label (.start, from the Import Context dialog). Both
exercise the identical export code path and format, so both are valid evidence for the
format question this criterion asks -- but only .probe_user_label answers "did a real
user annotation survive the round trip", which is why Task 1 did not stop at Route A's
observation of ".start" alone and went on to Route B.
