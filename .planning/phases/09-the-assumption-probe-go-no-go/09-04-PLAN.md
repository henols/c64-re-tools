<objective>
Answer criterion 3(2) (`R2000-16`(2)): does `--export_asm --assembler acme` output
**reassemble** under this project's `!cpu 6510` illegal-opcode expectations?

Purpose: this is the assumption Phase 10's criterion 4 rests on — the deletion of
`acme-build`'s `disasm` verb, its `## Disassembly` caveat section, and its `toacme`
prerequisite is only earned if regenerator2000's output survives a real assembler.

**Use the tool's own gate.** `--verify` already exports, shells out to a real
`acme --cpu 6510 --format cbm`, diffs the assembled bytes against the original, and reports
which assemblers actually ran (skipping ones not on PATH without failing the whole check).
Re-implementing that is an anti-pattern named in both `09-RESEARCH.md` and
`09-VALIDATION.md`, and a hand-built gate's result would be **less** trustworthy, not more.

**Pitfall 3 is the trap here.** `run_assembler`'s ACME branch only adds `--cpu 6510` when
`state.settings.use_illegal_opcodes` is true — a runtime setting, not something the CLI flags
set directly. Whether the analyzer flips it for a binary containing illegal opcodes was never
verified. **A pass recorded under `use_illegal_opcodes = false`, on a run that emitted no
illegal opcode, proves nothing about the assumption as this milestone needs it proven.** So
this plan determines and records which mode was exercised before scoring anything.

Output: `evidence/criterion3-reassembly.txt` with an `ILLEGAL_OPCODE_MODE:` line and a
`REASSEMBLY:` outcome line, plus the exported `.a` kept for inspection.
</objective>
