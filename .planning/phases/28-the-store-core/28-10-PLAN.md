<objective>
Close the ROOT of verification gap 1 by deciding what IDENTIFIES a snapshot, and
proving that identity end-to-end on one thin vertical slice before anything else
is touched.

`28-VERIFICATION.md` names three reproduced destructive defects (CR-01, CR-02,
CR-03) and its own closure guidance says they are one missing idea, not three
bugs: *"A closure plan that fixes them one at a time will keep finding the
fourth. One that decides what identifies a snapshot — which store, keyed on the
store file; which revision, derived from the handle rather than stored; and who
may judge an unclaimed file, which is nobody who cannot have created it — closes
all three."*

This plan settles the first two halves of that sentence — **which store** and
**which revision** — and closes CR-01 and CR-03. The third half (**who may
judge**) is 28-11, which depends on this one because it sweeps the directory
this plan renames.

Purpose: `revertTo` currently returns a *different store's* annotations with no
error, and one `mv` of the project directory plus one write silently deletes the
whole revert history. Both are reproduced against committed code. The phase goal
promises state that is *"durable across a `SIGKILL`, revertible, and reachable
through exactly one persistence seam"*; durability and the single seam are
VERIFIED, **revertible is not**, and this is where it fails.

Output: a snapshot whose location is a pure function of the store handle —
`<dir>/<store-filename>.snapshots/r<revision>.db` — with the `anno_snapshot.path`
column dropped so there is no second, persisted, absolute truth left to disagree
with it; a `SCHEMA_VERSION` bump that makes a store written by the current code
refuse by name; and three tests that would each have caught one of the reproduced
defects.
</objective>

<design_the_property_not_the_repro>
The verification recorded the failure pattern this plan must not repeat: *"in
both cases the plan closed the specific reproduction the prior verification
happened to write, and the underlying property stayed false one step to the side
of it."* So the property, and the adjacent cases it must make unreachable:

**The property.** A snapshot's location is a total function of `(handle,
revision)` and of nothing else. Nothing about a snapshot is persisted except its
revision number. Therefore:

- **The adjacent case to CR-01** — "a third store, or a store created later, or a
  store in a subdirectory, reaching into this store's ring." Unreachable by
  construction: the ring directory name is `basename(handle.path) +
  SNAPSHOT_DIR_SUFFIX`, and two distinct store files in one directory have
  distinct basenames by definition of a filesystem. There is no per-directory
  ring left in the code for a second store to find. This is a *structural*
  impossibility, not an untested case — which is why the fix is a rename of the
  location rather than an ownership predicate layered over the old location. The
  per-revision ownership predicate 28-07 added could never see CR-01 precisely
  because it tried to be the second kind of fix.
- **The adjacent case to CR-03** — "any OTHER way the recorded location can stop
  matching the real one": a bind mount seen from two namespaces (this repo's
  entire architecture is built around that boundary), a symlinked ancestor, a
  container/host path pair, a case-insensitive filesystem, a `realpath` that
  changes between two opens. All of these are the same shape: two absolute
  strings for one file. Dropping the column removes the *primitive* — there is no
  persisted absolute string left, so there is nothing for a second namespace to
  disagree with. Storing a *relative* filename instead (the other option the
  remedy offers) would leave one persisted field that a future edit could go back
  to reading absolutely; dropping it leaves nothing to misread.
- **The residual, stated rather than closed.** Renaming the STORE FILE itself
  (`mv proj.annostore other.annostore`) re-points the ring name, so the old ring
  becomes unreachable. It is **not deleted** — the sweep only ever reads
  `snapshotDirFor(handle)`, so it cannot see a ring it does not name — and
  `retainedRevisions()` honestly reports `[]`. That is an under-claim, which
  28-07 P2 covers in its second direction, and it is accepted here because the
  alternative (guessing which ring a renamed store used to own) is CR-01 again
  with a new cause. State this in the `snapshotDirFor` doc comment.
</design_the_property_not_the_repro>

<assumption_delta_decision>
`gsd-tools query assumption-delta scan 28` returned `detected: true` with
`pluralization` and `chosen` signals. Answering it properly rather than
perfunctorily, because CR-01 *is* the missed promotion this checkpoint exists to
catch:

- **The noun that is now primary:** *the store file's own snapshot ring*
  (`<store-filename>.snapshots`). The old primary was *the directory's snapshot
  ring* (`<dir>/snapshots`), which silently assumed one store per directory.
- **Decision: `promote`.** The general representation (one ring per store FILE)
  becomes the primary and only representation; the specific one (one ring per
  DIRECTORY) is removed, not kept alongside. `add-alongside` — supporting both
  layouts, or falling back to `<dir>/snapshots` when the new one is absent — is
  *exactly* CR-01 with an extra branch: two identities for one thing, and
  whichever the sweep sees first wins. The reason `promote` is safe here is that
  the ambiguity is not resolvable after the fact, so a compatibility branch could
  only ever guess.
- **What would force a later promote if we had chosen `add-alongside`:** the
  first user with two stores in one directory — which is the reproduced case.
- **The contract test encoding the generalized intent:** the two-stores-in-one-
  directory revert test in task 3 goes red the instant a future phase reintroduces
  a per-directory ring, because both stores' rings would collide again.
</assumption_delta_decision>
