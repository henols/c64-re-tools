<objective>
Close the three verifier-routed WARNINGs that live in and around `revertTo` —
WR-22, WR-24 and WR-18 — in one serialised pass over `anno-store.ts`.

Purpose: none of the three is a blocker and the verifier says so plainly for each,
but all three are on the revert path, all three are in the one function this
phase's blockers keep arriving in, and two of them are recorded as incomplete
fixes IN THEIR OWN TERMS from round 4. WR-18 is the residual of WR-16's fix: 28-17
added `rollbackFailed` to report the one state its handler cannot fix, and nothing
reads it, so `revertTo` can hand back a connection still inside the sweep's
transaction — CR-07's exact reported symptom re-created on the revert path.
WR-22 turns a plain argument error into a corruption-flavoured refusal, which the
module's own doc comment forbids, and Phase 29 puts that argument on a transport
whose validator is `validate: (value) => ({ value })`. WR-24 is a
same-function neighbour of the round's blocker: two attempts at the same revision
share a staging path, and three unguarded cleanups can delete each other's
in-flight copy.

**Why this is a separate wave from 28-19.** Every prior round of this phase found
that concurrent edits to `anno-store.ts` are how the next blocker arrives — see
the wave 12 and wave 15 dependency notes in `ROADMAP.md`. 28-19 rewrites
`retype()`; this plan rewrites `revertTo`, `pruneSnapshots` and
`runWriteSequence`. They are different functions in the same file, which is
exactly the situation those notes describe, so they are serialised rather than
parallelised.

**Scope fence.** The round-5 verification routes exactly five WARNINGs to this
round. Three of them are here. WR-06 (no bound on `baseRevision`) is NOT routed
and must not be widened into: the review's WR-22 sketch suggests reusing the new
validator for `baseRevision` too, and that suggestion is deliberately declined
here and recorded as declined. WR-03, WR-05, WR-07, WR-09, WR-10, WR-11's leak
half, IN-01..IN-05 are all carried forward untouched.

Output: an argument error that reads like one, a staging file no second attempt
can collide with, and a reported rollback failure that something in production
actually reads.
</objective>

<assumption_delta_decision>
The detector fires `detected: true` on four recycled ROADMAP signals, none of
them introduced by this round.

**The one real delta this plan settles** is an `optional` transition:
`reconcileSnapshotRing`'s `rollbackFailed` was, in practice, an optional fact —
present on every result and read by nobody, which is the same thing as optional.
It becomes REQUIRED: two production call sites must answer it.

**Noun now primary:** the HANDLE's transaction state, rather than the sweep's
return value. The sweep reports; the handle carries. That is the promotion, and
it is what lets the fact survive the boundary between the call that produced it
and the call that must act on it — without violating 28-11 P5, which forbids the
producing call from reporting it as a failure.

**Decision: `promote`.** The alternative considered and rejected was
`add-alongside`: widening `AnnoWriteResult` with a second field beside `changed`.
Rejected because `AnnoWriteResult`'s own doc comment states that `changed` is the
ONLY signal distinguishing a no-op from a real edit, and because every write entry
point in the module returns that shape, so the change would ripple through every
result assertion in the suite for a state no caller can act on at that moment
anyway. The handle is where the consequence lives, so the handle is where the
fact belongs.

**What would force a later change:** a second connection-level fact needing the
same treatment. One boolean on the handle is a fact; three would be a state
machine, and at that point the field should become a named state rather than a
flag.
</assumption_delta_decision>
