<objective>
Close **CR-02**, the fourth in-scope item — which `28-VERIFICATION.md`'s
frontmatter `gaps:` list omits and its body carries twice, as *Gaps Summary*
item 3 and as a **Blocker**: *"VERIFIED REAL, blocks the goal's 'revertible'
clause"*, reproduced verbatim including the reviewer's own output line
`revertTo(1) gave revision 2 with 2 row(s) -- expected revision 1 with 1 row`.
The omission is a defect in the report, not permission to drop the item.

Cause: the `rmSync` and the `vacuum into` at `anno-store.ts:498-499` run **before**
`begin immediate`, outside any lock, with no check that the target path is
already owned by a committed pointer row. A stale-revision loser therefore
overwrites a winner's committed snapshot bytes; the loser's *write* is then
correctly refused — STORE-05 holds and was verified — leaving a pointer row that
describes the wrong revision and a `revertTo` that **silently succeeds with the
wrong state**. Silent-wrong-answer severity, and because `vacuum into` is a full
database copy the window scales with store size rather than being a microsecond
race.

This is the third route into the invariant plan 28-07 named: *the snapshot ring
had no ownership discipline between its files and its pointer rows.* 28-07 gave
the ring one definition of "retained" and one half-state resolver. This plan
gives it one **owner per published file**: the writer that commits the pointer
row, and nobody else.

Folded in rather than deferred, because the verifier put them in the same class
as gap 1's raw `ENOENT` — *"same family-escape class"*: **WR-04** (`new
DatabaseSync` and the fresh-store DDL outside every `try`; bare `Error` escapes,
connection leaks) and **WR-11** (`currentRevision` undefined on exactly the
CAS-failure path). Gap 1's own `missing:` list already required converting a
family escape into a named `AnnoStoreError`, so this work is inside the gap.

Output: `stageSnapshot` / `publishSnapshot` / `discardSnapshot` as the three named
transitions of one staging path; a CAS refusal that carries both numbers; an
`openStore` with no family escape; and the third absent test scenario — a
concurrent snapshot write — driven through the production staging code with its
planting observed red.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Two concurrent store writers | The module supports them by design (`{ timeout: 5_000 }`, a cross-process CAS proof). This is the boundary CR-02 crosses: a writer that will be refused acting on a file another writer owns. |
| MCP transport → `openStore` | The store path arrives unvalidated (`vice-proxy.ts`'s validator is `(value) => ({ value })`). A directory, a missing parent, or a path with no write permission are all reachable inputs. |
| `anno-store.ts` → the `snapshots/` directory | Two naming conventions now share it: published `r<revision>.db` and transient `r<revision>.<pid>.<uuid>.tmp`. Plan 28-07's sweep matches only the first. |
