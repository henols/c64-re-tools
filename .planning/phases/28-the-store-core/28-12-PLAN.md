**dangling** symlink and lets a store file be created outside the workspace root.

<design_the_property_not_the_repro>
The verification named the failure pattern this plan must not repeat: *"Gap 3's
remedy handles live symlinks and not dangling ones — a strictly easier plant."*
So state the property and the adjacent cases.

**The property.** `realpathOfNearestExisting` must stop at the first path
**entry** — the thing `lstat` sees — and must never step past a name that exists
in a directory. `existsSync` answers a different question ("does this path
resolve to something?") and the two answers differ for exactly one input class:
a name whose entry exists but whose target does not. That class is symlinks, and
it is the whole of CR-04.

**The adjacent cases, and why the new walk makes them unreachable rather than
merely untested:**

- *A chain of dangling links* (`a → b → c`, none of which exist). The old walk
  stepped past all of them; the new one stops at `a`, hops to `b`, stops at `b`,
  hops to `c`. Each hop re-enters the same loop, so a chain is the same case
  repeated rather than a new one.
- *A link that becomes live between two walks*, or *a link whose last hop lands
  on a live entry*. After a hop the loop re-tests with `pathEntryExists`, and a
  live entry falls through to `realpathSync`, which resolves the remaining chain
  itself. There is no arm that treats "live" and "dangling" differently after the
  hop, so there is no third state to get wrong.
- *A symlink cycle* (`a → b`, `b → a`). Unreachable as a hang because the hop
  count is bounded by `MAX_SYMLINK_HOPS`; exceeding it refuses inside the family.
  This is the case the old code could not even reach and the naive fix would loop
  on forever, so it is pinned by its own test rather than argued.
- *A dangling link pointing INSIDE the root.* Followed, and the store lands at the
  link's target inside the root. This is the over-refusal control in its dangling
  form, and it is what distinguishes this fix from the blanket "refuse every
  symlink" fix that would pass every refusal test and prove nothing.
- *A relative link target* (`ln -s ../outside x`). Handled by resolving the target
  against `dirname(current)` rather than against the process cwd — which is the
  one detail a naive `readlinkSync` fix gets wrong, and which the dangling-leaf
  test plants deliberately in its relative form.

**The residual, STATED and not closed.** The confinement decision and the file
creation are two separate filesystem operations. A link planted between them
redirects the write, and nothing at this layer can close that: `node:sqlite`'s
`DatabaseSync` constructor takes a path, not a file descriptor, so there is no
`O_NOFOLLOW`/`openat` route to making the check and the open one operation. The
CR-04 todo names this case ("links whose target appears between the check and the
open") as part of the test surface; the honest disposition is a recorded limit,
carried as a `verification: backstop` truth, never a claim that it is handled. The
prohibition against claiming an untested residual closed is carried in
`must_haves` for the same reason.
</design_the_property_not_the_repro>
