<objective>
Close CR-09, this round's one blocker: `retype()`'s split-and-preserve writes a
split-table row with an ODD byte count — a shape `setDataType` refuses at its own
entry point and `resolveSplitTargets()` cannot decode. Fold in IN-06, which lives
on the same two lines, and WR-08, which is the same function's other unpinned
behaviour.

Purpose: the store is the one component whose job is to make silent
un-documenting impossible, and its own remainder writer is the only unvalidated
writer in the module. Two ordinary calls — type a table, then correct one byte
inside it — leave a region annotated with a type no reader can act on, reported
as `changed: true` with an empty `contradictedComments` and no diagnostic. That
falsifies ROADMAP criterion 3's stated purpose (*"Silently un-documenting a
previously annotated region is the exact failure the store exists to prevent"*)
and blocks STORE-01 and STORE-03. It is not deferrable: Phase 29 puts
`set_data_type` and `list_ranges` on an agent-driven tool path where, per
`anno-types.ts`'s own header, the proxy's `validate: (value) => ({ value })`
means arguments arrive unvalidated, and Phase 30 reads these rows to emit ACME
source.

**This is the TRACER of round 5.** It is the one end-to-end slice — caller ->
`setDataType` -> `retype` -> disk -> `listRanges` -> `assertRangeShape` /
`resolveSplitTargets` — and it is verified end-to-end before any of the round's
expansion plans run. Plans 28-20, 28-21 and 28-22 all rewrite or read
`anno-store.ts`, and five rounds of evidence in this phase say concurrent edits
to that one file are how the next blocker arrives; so this plan runs alone in its
wave and the round expands outward from the proven slice.

**What this plan does NOT claim.** It does not close criterion 1: the vocabulary
is 12 members, the four split layouts are first-class, and the
differing-resolved-target-set control with its collapse planting were green in
the verifier's own 169/169 run. The verifier issued that correction explicitly
and it must not be re-broken here. What is FALSE is criterion 3's stated purpose,
and STORE-01's and STORE-03's clauses that depend on it.

Output: a store that cannot write a shape it would refuse, a named refusal that
says which table and which boundary, the `bank` column surviving a split, the
collapse decision on the record, and the class-level invariant that would have
caught this in round 1.
</objective>

<assumption_delta_decision>
The detector fires `detected: true` with four signals, all of them recycled
ROADMAP prose from earlier rounds (`second` in criterion 2's independent oracle,
`another` in criterion 5's second OS process, `alongside` in round 4's narrative,
`chosen` in the spike note). None of them is a new pluralization introduced by
this round.

**The one real assumption delta this plan settles** is a `chosen` transition, not
a pluralization: the remainder's data type stops being DERIVED (whatever the
overlapped row happened to carry, propagated unconditionally) and becomes
CHECKED — a value the store must be able to justify before it writes it.

**Noun now primary:** the REMAINDER, as a range the store is about to write on
its own initiative, rather than as a fragment of a row it already accepted.

**Decision: `promote`.** The rule that governs a caller's range is promoted to
govern the store's own writes, and the "a remainder is exempt because it came
from a row we already accepted" reading is demoted to what it always was — an
accident of the implementation. The promotion is enforced by asking
`assertRangeShape` itself rather than by a second even-count test, so there is
exactly one definition of a legal range shape in the repo.

**What would force a later change:** a shape rule that is legal for a caller's
range but genuinely illegal for a remainder, or vice versa. The round-trip
invariant in task 3 is what would surface it, as a failing re-acceptance
assertion naming the row.
</assumption_delta_decision>
