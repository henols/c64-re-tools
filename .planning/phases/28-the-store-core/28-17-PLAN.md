<objective>
Close the two round-4 warnings that sit inside `anno-store.ts` and the one that
sits inside its test file: WR-13, which manufactures CR-08's input from an
ordinary crash; WR-16, which reports a rollback as fact after swallowing that

`ok` for a precondition they could not build.

Purpose: WR-13 is why CR-08's input is not hypothetical. `stageSnapshot`
(`anno-store.ts:1009-1015`) runs `vacuum into` and returns with no `fsync`;
`publishSnapshot` (`:1047-1049`) is a bare `renameSync` with no file and no
directory `fsync` — while the pointer row that names that image is inserted
inside the write transaction and committed by SQLite, which DOES fsync. The two
halves of a revision's record therefore have different durability, so a host
crash can leave a durable row naming a file whose bytes never reached disk. The
module already owns `fsyncPath()` (`:322-329`) and already uses it correctly on
the revert path; the publish path is the one place it is missing.

Output: the publish path made as durable as the row that claims it, three
handlers that report what happened instead of what was intended, and two
controls that skip visibly instead of passing vacuously.

`anno-store.ts`. Waves 12 and 13 of this phase carry the same note and it has
earned its place: three rounds of evidence say concurrent edits to
`anno-store.ts` are how the next blocker arrives. This plan is serialised strictly
after 28-16 for that reason, and for a second: task 2's rewritten commit-failure
message must be checked against the commit-count control that is still word-based

| Boundary | Description |
|----------|-------------|
