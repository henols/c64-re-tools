<objective>
Close the last third of verification gap 1: **who may judge an unclaimed
snapshot file.** Plan 28-10 settled which store owns a ring and how a revision's
file is located; this plan settles the one remaining question, which
`28-VERIFICATION.md` states as *"who may judge an unclaimed file, which is
nobody who cannot have created it"* — and folds in the three warnings that live
inside the exact code being rewritten.

CR-02, reproduced: `reconcileSnapshotRing` runs on every accepted write and
decides ownership from **this connection's committed view only**. A concurrent
writer's snapshot is a filesystem fact (the rename) before it is a transactional
one (the pointer row), so for the width of that window the file looks unowned and
the sweep deletes it. The destroyed revision then becomes permanently
unrevertible — *"manufacturing the exact orphan state trap 10 declares
unsurvivable"*, and doing it from the reconciliation that exists to prevent it.

Purpose: this is the one of the three ring defects that is a *regression
introduced by the previous gap-closure round*. 28-07 P1 is recorded **violated**
against it. Leaving it open would ship, behind a Phase 29 MCP tool family, a
store that silently loses a revision under ordinary write contention.

Output: a sweep that decides under the same write lock a publication is already
ordered by — so a published-but-uncommitted file is unobservable to it by
construction rather than by timing — that commits its row deletes before it
unlinks anything, and that reports when it declined to judge; plus guarded
versions of the three unguarded regions (WR-01, WR-02, WR-04) that sit inside the
same code.
</objective>

<design_the_property_not_the_repro>
**The remedy chosen, and why the other offered one is refused.** Gap 1's remedy 2
offers two routes. This plan takes the second — **serialise under `begin
immediate`** — and refuses the first, on the record.

A grace bound is a guess about how long a writer can sit between its rename and
its commit. It has a tuned constant, it is wrong for a writer that is paged out
or stopped at a debugger, and the next reproduction of this defect would arrive
as a request to raise the constant. That is precisely the "closed the specific
reproduction, the property stayed false one step to the side" pattern the
verification named. The prohibition against it is carried in `must_haves` so the
next verification can rule on it.

**The exclusion is exact, and it is exact by derivation rather than by testing.**
A writer can publish a snapshot only *after* winning the compare-and-swap, and
the compare-and-swap runs inside `begin immediate` — so a writer that is
published-but-uncommitted **holds the store's write lock**. A sweep that takes
`begin immediate` before it reads anything therefore cannot run at all while any
writer is inside that window: either the sweep gets the lock first (and no
publication can begin until it releases it), or the writer has it (and the sweep
waits, after which the pointer row is committed and visible). The window and the
lock are the same interval. Nothing is timed and no constant is tuned.

**The adjacent (fourth) case, and why the design makes it unreachable.** Ask what
else could put a file into this store's ring that the sweep would see as
unowned:

- *A writer in another OS process.* Same store file, same SQLite write lock —
  the exclusion is cross-process, which is the level SQLite's lock operates at
  and the level this module already relies on for its cross-process CAS proof.
- *A writer that publishes without winning the CAS.* Not reachable: 28-08 made
  `publishSnapshot` the only rename site and put it between the won CAS and the
  pointer insert; `anno-seam.test.ts` bounds the seam-private exports so no
  shipped module can stage from outside.
- *A neighbouring store publishing into this ring.* Made structurally impossible
  by 28-10 — distinct store files have distinct ring directories.
- *A staging `.tmp` mid-`vacuum`.* Invisible to the sweep by the deliberate
  anchoring of `SNAPSHOT_FILE_PATTERN` on `r<digits>.db`, which 28-08 documented
  as a contract between the two functions. Unchanged here.
- *The sweep interrupted between its own row delete and its own unlink.* This is
  the one genuinely new hazard the transaction introduces, and it is closed by
  ordering rather than left: the sweep commits its row deletes and only then
  unlinks, so an interruption leaves extra files — the harmless direction trap 10
  already argues for — and never a row aimed at a deleted file.

That enumeration is closed: the only way a file reaches `<store>.snapshots/rN.db`
is `publishSnapshot`, and `publishSnapshot` is reachable only from behind the
lock the sweep now takes. **The judge cannot see a file it could not have
created, because while it is judging, nobody else can create one.**

**The honest residual, in BOTH of its directions.** A sweep that cannot take the
lock within the connection's five-second `busy_timeout` **declines**: it returns
`{ droppedRows: [], droppedFiles: [], deferred: true }` and changes nothing.

*First direction — ring size.* The ring may temporarily exceed
`MAX_SNAPSHOT_REVISIONS` files until the next accepted write sweeps successfully.
That is the extra-files direction, which trap 10's own premise calls harmless and
reconcilable by revision number, and it is reported rather than silent. Declining
is required by 28-07 P2 read in its second direction: a sweep that guesses when
it cannot know would be publishing a judgement it cannot support.

*Second direction — LATENCY, and this one is new caller-visible behaviour rather
than a bounded-ness claim.* Before this change the sweep took no write lock at
all and could not block. After it, under contention, **every accepted write can
block for up to the full five-second `busy_timeout` inside
`reconcileSnapshotRing`** before it proceeds. That is a real cost on a path
Phase 29 exposes as an MCP tool, and it is stated here rather than discovered
later.

The second five seconds is refused rather than accepted. `pruneSnapshots` runs
the sweep first and then issues its OWN autocommit `delete from anno_snapshot`
statements for the doomed set; those are writes, so under the same contention
they would block a second `busy_timeout` and then throw `SQLITE_BUSY` — which
task 2's WR-02 wrap would swallow, making the worst case ~10 s of silent added
latency for work that is guaranteed to be redone. **Decision: `pruneSnapshots`
returns early when the sweep reports `deferred: true`.** Two reasons, and the
second is the load-bearing one:

1. It bounds the added latency at ONE `busy_timeout` rather than two, and removes
   a swallowed failure that would otherwise happen on every contended write.
2. The doomed set would be computed over a ring the sweep just declined to
   reconcile. Acting on it is exactly the shape 28-07 P2 forbids — publishing a
   bound the store cannot support — and it is the same reasoning that makes the
   sweep decline in the first place. A prune that presses on where its own sweep
   abstained is the sweep's guess with an extra step.

The cost of the early return is that the ring stays un-pruned for one more write.
That is the same extra-files direction as the first residual, already accepted,
already reconcilable by revision number, and now reached by one route instead of
two.
</design_the_property_not_the_repro>

**Structure, in this order:**

1. Take the store's write lock with `handle.db.exec("begin immediate")` inside a
   `try`. On failure — the only expected one is `SQLITE_BUSY` after the
   connection's five-second `busy_timeout`, which means another writer holds the
   lock — return `{ droppedRows: [], droppedFiles: [], deferred: true }` and do
   nothing else. Do not throw, and do not partially sweep.
2. With the lock held, read `retainedRevisions(handle)` (unchanged — it is still
   THE one predicate, and this function still must not re-decide with a second
   `existsSync`), read the pointer rows, and read the directory listing from
   `snapshotDirFor(handle)`. Compute the full drop set for BOTH directions before
   changing anything: the orphan row revisions, and the orphan file paths.
3. Delete the orphan pointer rows.
4. Commit through `commitTransaction(handle.db)`. **It must be
   `commitTransaction`, never `handle.db.exec` of the bare word:**
   `anno-seam.test.ts` asserts the module contains exactly ONE commit statement,
   because the durability proof's planted violation must have a single site. A
   second literal would split that planting and let half of it survive.
