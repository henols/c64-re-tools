<objective>
Discharge `STORE-04` the way the requirement insists — with **one** combined
planted-violation test rather than two — and close the three file-level and
process-level failures the store owns rather than SQLite: a corrupt file read as
an empty one, another process's annotations discarded, and a revert history that
grows without bound.

Purpose: two separate tests, one for durability and one for revert, both stay
green over an in-memory journal that satisfies neither claim. Combining them
means one planted violation — removing the single `COMMIT` — fails both halves,
which was observed during research (`readBackByValue=false`,
`revertReturnsPriorValue=false`). The mechanism that makes it one test is that
the snapshot pointer row is inserted in the same transaction as the mutation, so
removing the commit destroys the durability claim and the revert claim
simultaneously.

Output: the mutator child process in three modes, the one combined test with its
planted counterpart, the four corrupt-file refusals with the tail residual
stated, the cross-process stale-revision refusal observed across two real OS
processes, and a bounded snapshot ring.
</objective>

- **C-2 (HIGH) — the store owns its refusal, and the tail case stays a stated
  residual.** `ROADMAP.md` criterion 4's "a store file truncated between kill and
  reopen is refused, never returned partial" is only half true of SQLite. The
  zero-length case is the dangerous one, because "no annotations" and "your
  annotations are gone" become indistinguishable. Plan `28-01` implemented the
  refusal; this plan proves it on four shapes and **states** the residual: a tail

- **C-3 — the default `delete` journal mode is the one to stay on, and it is
  pinned by a test.** Measured: `delete` and WAL are equally durable across
  `SIGKILL` (four sequences each), `delete` is single-file at rest and leaves
  only a transient `<db>-journal` after an unclean kill which the next open rolls
  back and deletes, and WAL is the only mode with persistent `-wal`/`-shm`
  sidecars. `journal_mode` is a **persistent database property** and `pragma`
  statements are not transactional, so one stray set anywhere is inherited by
  every later connection — which is why the mode is asserted rather than left to
  convention.

**In `anno-store.ts`, add the bounded snapshot ring.**

Export `oldestRetainedRevision(handle): number` — the smallest revision still
present in `anno_snapshot` — and `pruneSnapshots(handle): void`, which deletes
snapshot files and their `anno_snapshot` pointer rows for every revision older
than `currentRevision(handle) - MAX_SNAPSHOT_REVISIONS`. Call `pruneSnapshots`
from the end of the write path, **after the commit and outside the
transaction**. Comment the reason and the chosen failure direction: a filesystem
unlink is not transactional, so pruning inside the transaction would make a
rollback leave the pointer row pointing at a deleted file; pruning after the
commit means a kill between the commit and the prune leaves **extra** files,
never a missing one the revert path still points at. Delete the file first and
the pointer row second, for the same reason — a pointer row with no file is the
failure that matters, and the opposite order cannot produce it.

Unlink with a swallowed error (the file may already be gone after a previous
interrupted prune) but never swallow the pointer-row delete's failure.

**Make `revertTo` refuse past the bound by name.** When the requested revision
has no `anno_snapshot` row, throw `AnnoStoreError` whose message carries the
requested revision, `oldestRetainedRevision()` and `currentRevision()`. It must
not fall back to the nearest available snapshot: returning a different revision
than the one asked for is a silent substitution of the caller's intent, and the
caller cannot tell it happened.

**Add one entry to the header's `WHAT NOT TO DO` list:** never prune inside the
write transaction, and never let a revert fall back to the nearest available
revision. Cite `STORE-04`; no phase number in an assignment shape and none in any
literal.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| the store file on disk → `openStore` | The file may have been truncated, replaced, partially written or produced by something else entirely. SQLite refuses only some of those shapes, so this is a boundary the store must police itself. |
| a second OS process → the same store file | SQLite's locking arbitrates writes but not intent: two processes can both commit, and the later one can erase the earlier one's meaning without erasing its bytes. |
| the write transaction → the filesystem | Snapshot creation and snapshot pruning are filesystem operations that are not part of the transaction, so the ordering around the commit decides which failure a kill produces. |
