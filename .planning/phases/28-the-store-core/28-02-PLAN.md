<objective>
Prove `STORE-03` the way the requirement demands it be proven: a
narrowest-range-wins lookup that is exact at every one of the 65,536 addresses,
cross-validated against a second, independently written implementation with zero
disagreements, with the tie-break, both range ends and the `$FFFF` boundary each
pinned separately.

Purpose: the exhaustive loop can be green while any of the four pins is wrong. A
fixture with no range touching `$0000` or `$FFFF` makes both oracles agree on
`NO_ROW` there, so the boundary pin is not implied by the agreement. The
tie-break pin needs deliberately overlapping rows, which the store's write path
is designed to prevent from ever existing — that is precisely why
`anno-index.ts` is a pure module taking rows as an argument, and this plan is
where that design choice pays.

Output: `anno-index.test.ts`, holding the cross-validation, the four pins, the
non-degeneracy assertions that keep the agreement from being vacuous, and the
purity assertions that keep the index from becoming a second truth.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| caller-supplied address → `resolveAt` | An address arrives from an unvalidated MCP argument (`vice-proxy.ts:3230`) and is used directly as a typed-array index. This is the only boundary this plan's subject touches; the module has no filesystem, no SQL and no network. |
| caller-supplied row set → `buildPaintIndex` | Row spans arrive from the store and, in the tests, from a fixture. A span whose ends are outside the address space would drive the paint loop past the array. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-28-oob | Tampering / Denial of service | `resolveAt(index, address)` and `buildPaintIndex`'s paint loop | medium | mitigate | `resolveAt` refuses an address outside `ADDRESS_MIN..ADDRESS_MAX` with `AnnoAddressError` carrying the offending value, pinned by Task 2's Pin 1 against both 0x10000 and -1. `buildPaintIndex` clamps nothing and instead relies on `assertRangeShape` having already refused an out-of-range row at the store's entry; the pin asserts the returned array's length is exactly `PAINT_INDEX_SIZE` so a write past the end would be visible. Note that a JavaScript typed array silently ignores an out-of-bounds write rather than throwing, which is why the refusal is at the read side and the length is asserted at the build side. |
