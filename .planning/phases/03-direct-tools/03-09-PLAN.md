<objective>
Ship Family C on the stock backend: `vice_execution_pause`, `vice_execution_run`,
`vice_execution_step`, and the new stock-only `vice_execution_until_return`.

Planner decision recorded here (CONTEXT.md's open item 1): `EXECUTE_UNTIL_RETURN`
(0x73) surfaces as a stock-only tool named **`vice_execution_until_return`**.
Reason: the fork has no tool for this operation (`vice_execution_step`'s `stepOver`
is a different operation — it steps *over* a call rather than running out of the
current one), Phase 2's D-07 permits stock-only manifest entries, and the chosen
name follows the existing `vice_execution_*` convention while reading as the
operation rather than as a value — `vice_execution_return` could be misread as
"return from the tool". Phase 8's parity harness needs no new naming rule; the tool
is simply absent from the fork manifest.

Purpose: this is phase success criterion 3. Idempotence is the load-bearing part —
a duplicate resume after an event race genuinely restarts a machine the agent
thought it had paused, which is why D-08 short-circuits rather than relying on the
commands being harmless.

Output: `stock-execution.ts` and `stock-execution.test.ts`. No dispatch or manifest
edits — plans 03-12 and 03-13 own those.
</objective>

best-effort ordering nicety, **not** a guarantee: if the event has not arrived the

never asserts a state the wire did not report.

`export const handleExecutionPause: StockSessionHandler`
- No arguments; refuse an unexpected argument key by naming it.
- Read `runStateFor(session.client)`.
  - `"stopped"` → **send nothing** and answer ok with
    `{ requested: "pause", sent: false, alreadyStopped: true }` plus a short note
    that the machine was already halted so no command was issued (D-08's
    already-stopped marker).
  - `"running"` or `"unknown"` → send `CommandType.Ping` with no body. While the
    state is `"unknown"` the command IS sent — there is nothing to short-circuit
    against — and a comment must say so, because "unknown means do nothing" is the
    tempting wrong reading.
- After the reply, `await settleEvents()`, then answer through `stockAnswer()` with
  `{ requested: "pause", sent: true, alreadyStopped: false, stateBefore }`.
- Wire errors through `convertWireError("vice_execution_pause", err)`.

A shared private helper `function refuseIfUnknown(state: RunState, toolName: string): StockErrorResult | null`
implements D-07's gate once for both tools: when `state === "unknown"` it returns a
refusal whose text states that the derived run state is unknown because nothing on
the wire has reported a `STOPPED` or `RESUMED` transition on this connection yet,
that stepping a machine whose state is unknown could either step a halted CPU or
race a running one, and that the agent should call `vice_execution_pause` or
`vice_execution_run` first to establish a known state. It must also say that this
gate applies **only** to the execution tools — memory, register and checkpoint tools
run freely while the state is unknown (D-07) — so an agent reading the refusal does
not conclude the whole backend is unusable.

`export const handleExecutionStep: StockSessionHandler`
- Arguments: `count` (optional, `parseByteCount({ max: 0xffff })`, default 1) and
  `stepOver` (optional boolean, default `false`) — the fork's exact names.
- Read `runStateFor(session.client)`; return `refuseIfUnknown(...)` when it is
  `"unknown"`, recording **zero** sends.
- Send `CommandType.AdvanceInstructions` with
  `advanceInstructionsBody({ stepOver, count })`.
- After the reply, `await settleEvents()`, then answer through `stockAnswer()` with
  `{ requested: "step", count, stepOver, stateBefore }` and, when the reply or a
  settled `REGISTER_INFO`/`STOPPED` event exposes a program counter, `programCounter`.
  When no program counter is available, omit the key rather than reporting `0`.
- A comment must record that `stepOver: true`'s runtime semantic is `[ASSUMED]`
  (RESEARCH.md A2 — never probed against a real `JSR`) and point at

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| agent/LLM → execution-control tool calls | a retry or a duplicate call can change whether the emulated machine is running |
| container MCP server → binary-monitor socket | `EXIT` (0xaa) resumes the machine; `PING` (0x81) halts it |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-3-06 | Tampering (unrequested state change) | `handleExecutionRun` | mitigate | `CommandType.Exit` has exactly one call site in the whole module (grep-gated to 1), reached only from the tool whose entire purpose is the agent's explicit resume request. D-08's short-circuit means a duplicate resume after an event race sends nothing rather than restarting a machine the agent believed paused — asserted by a two-call, one-send test |
| T-3-06b | Tampering | `handleExecutionPause` idempotence | mitigate | Pause short-circuits when the derived state is already `"stopped"`, so an agent retry cannot issue a second halt; the answer's `alreadyStopped` marker makes the no-op visible rather than indistinguishable from a fresh halt |
| T-3-02 | Tampering (integrity of the debugging session) | the `"unknown"` gate | mitigate | Stepping a machine whose state is unknown could step a halted CPU or race a running one, producing a program counter the agent would trust; D-07's refusal blocks it and names the action that establishes a known state. The gate deliberately does not extend to memory/register/checkpoint tools, and the refusal says so |
| T-3-02b | Tampering | `stepOver: true` semantics | accept | The body layout is `[CITED]` but the runtime step-over behaviour is `[ASSUMED]` (A2) and cannot be validated offline. Labelled in the source and filed as probe debt rather than silently trusted |
| T-3-05 | Information Disclosure | this module | accept | No path arguments and no filesystem access |
</threat_model>
