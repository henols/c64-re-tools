<objective>
Ship the register half of Family A on the stock backend: `vice_registers_get`,
`vice_registers_set` and the new stock-only `vice_registers_available`, plus the
per-session register catalog both value tools need.

Planner decision recorded here (CONTEXT.md's open item 2): `REGISTERS_AVAILABLE`
(0x83) surfaces as its own **stock-only tool named `vice_registers_available`**,
not as an extra field on `vice_registers_get`'s answer. Reason: enumeration and
value-reading are different operations with different callers, a fork-parity-minded
caller expects `vice_registers_get` to keep returning values only, and Phase 2's
D-07 already permits stock-only manifest entries. The name follows the existing
`vice_registers_*` / `vice_memory_*` convention so Phase 8's parity harness needs no
new naming rule.

Purpose: `REGISTERS_SET`'s wire body needs a numeric register id, while the fork's
`vice_registers_set` takes a name. Register ids are enumerated by the wire itself
and are not guaranteed identical across VICE builds, so reading them beats
hardcoding a guess.

Output: `stock-registers.ts` and `stock-registers.test.ts`. No dispatch or manifest
edits — plans 03-12 and 03-13 own those.
</objective>

Add the two value handlers to `stock-registers.ts`.

`export const handleRegistersGet: StockSessionHandler`
- Takes no required arguments (matching the fork). Refuse an unexpected argument
  key by naming it.
- Fetch `registerCatalogFor(session)`, then send `CommandType.RegistersGet` with
  `memspaceBody({ memspace: 0x00 })`.
- Refuse a reply whose type is not `"registers"` naming the observed type.
- Render the reply's `{ id, value }` pairs into names through `catalog.byId`. An id
  the catalog does not know is reported as `{ id, name: null, value }` rather than
  dropped — a silently omitted register is a wrong answer.
- Answer through `stockAnswer()` with
  `registers: Record<string, number>` (name → value, for the ids the catalog knows)
  plus `unknownIds: Array<{ id: number; value: number }>` (empty in the normal
  case) and `memspace: "main"`. This is a stock-native shape per D-01; the parity
  doc already records that stock answers do not reproduce the fork's shape.
- Note in a comment that the flag bits the fork's `register` argument enumerates
  (`N|V|B|D|I|Z|C`) are not separate wire registers — they live in the processor
  status register the catalog reports (typically `FL`). Report the status register's
  value as a number; do not synthesise per-bit fields in Phase 3, and say so rather
  than leaving the omission unexplained.

`export const handleRegistersSet: StockSessionHandler`
- Arguments: `register` (required string) and `value` (required number), the fork's
  exact names and types (D-03).
- Uppercase and trim `register`, then resolve through `catalog.byName`. An unknown
  name refuses with a message **listing the names the catalog actually returned** —
  never a generic "invalid register".
- If `register` names one of the individual flag bits (`N`, `V`, `B`, `D`, `I`, `Z`,
  `C`) and the catalog has no register of that name, refuse with a message stating
  that the binary monitor exposes the whole status register rather than individual
  flag bits, and naming the status register the catalog does report plus the bit
  position the caller asked for. This is an explanatory refusal, not a silent
  read-modify-write.
- Range-check `value` against the resolved register's declared `size`: `0..0xff`
  for size 1, `0..0xffff` for size 2. Refuse out of range naming the register, its
  size and the range.
- Send `CommandType.RegistersSet` with
  `registersSetBody({ memspace: 0x00, items: [{ id, value }] })`.
- Refuse a reply whose type is not `"registers"`; read the register's value back
  out of that same reply (VICE answers `REGISTERS_SET` with a full `RegisterInfo`
  dump) and report both the requested and the observed value, so a write the
  emulator silently clamped is visible rather than assumed.
- Answer through `stockAnswer()` with `register` (the resolved wire name), `id`,
  `requestedValue`, `observedValue`, and `memspace: "main"`.

Add test cases: `register: "a"` resolves case-insensitively and the encoded body's

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| agent/LLM → `register`/`value` arguments | an untrusted name and value become a CPU register write on the emulated machine |
| container MCP server → binary-monitor socket | `REGISTERS_SET` can redirect execution by writing `PC` |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-3-01 | Tampering | `handleRegistersSet`'s `value` range check | mitigate | The value is bounded by the register's own wire-declared `size` (1 byte → `0..0xff`, 2 bytes → `0..0xffff`) before any body is built, so an over-wide value cannot be truncated into a different value silently; the answer reports the emulator's read-back value alongside the requested one so a clamp is visible |
| T-3-01b | Tampering | register-name resolution | mitigate | Names resolve only through the emulator's own `REGISTERS_AVAILABLE` enumeration; an unknown name refuses and lists the available names, and a flag-bit name gets an explanatory refusal rather than a silent read-modify-write of the status register |
| T-3-02 | Tampering (integrity of a debugging session) | `handleRegistersGet`'s unknown ids | mitigate | An id the catalog does not know is reported in an `unknownIds` array rather than dropped, so a partial register dump cannot be mistaken for a complete one |
| T-3-06 | Tampering (unrequested state change) | this module | mitigate | Grep-gated to zero `CommandType.Exit` references (D-05) |
</threat_model>
