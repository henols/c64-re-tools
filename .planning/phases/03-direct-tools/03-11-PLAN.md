tree. Three-part header comment; WHAT-NOT-TO-DO must name: never write a second

Exports:
- `export const PETSCII_RETURN = 0x0d;`
- `export class StockPetsciiError extends ViceError`
- `export function asciiToPetscii(text: string, { upper = true }: { upper?: boolean } = {}): Buffer`

The mapping, byte by byte, matching VICE's own `charset_p_topetscii()` behaviour
(cite that function name in the doc comment as the source of the case-swap rule):
- `0x0a` (LF) and `0x0d` (CR) → `PETSCII_RETURN` (`0x0d`). This is what the fork's
  own "Use \n for Return" description promises.
- `0x20`-`0x40` → unchanged (space, digits, `!"#$%&'()*+,-./`, `:;<=>?@`)
- `0x41`-`0x5a` (ASCII `A`-`Z`) → `byte | 0x80` (`0xc1`-`0xda`) when `upper` is
  `true`; unchanged when `upper` is `false`
- `0x5b`-`0x60` → unchanged
- `0x61`-`0x7a` (ASCII `a`-`z`) → `byte - 0x20` (`0x41`-`0x5a`) when `upper` is
  `true`; unchanged when `upper` is `false`
- `0x7b`-`0x7e` → unchanged
- **every other input byte refuses** — `0x00`-`0x09`, `0x0b`, `0x0c`,
  `0x0e`-`0x1f`, `0x7f`, and anything `>= 0x80` — throwing a `StockPetsciiError`
  whose message names the offending character, its zero-based index in the input
  string, its hex code, and states that PETSCII control codes must be sent through
  `vice_keyboard_petscii` as explicit bytes if they are genuinely wanted.

Also: refuse a non-string input; refuse an empty string; refuse a string whose
converted length exceeds 255 bytes, naming the limit (`KEYBOARD_FEED`'s length
field is a `uint8`). Refuse any code unit above `0xff` (i.e. any non-Latin-1
character) with the same named-index message — never a lossy `charCodeAt & 0xff`.

Note in the doc comment that `upper: false` is a deliberate pass-through of the
ASCII byte, mirroring the fork's `petscii_upper: false` ("raw PETSCII") semantics,
and that the case-swap in `upper: true` is what makes uppercase ASCII display as
uppercase on the C64 in both the unshifted and the mixed-case charset.

Create `.claude/mcp/vice/stock-petscii.test.ts` with an **exhaustive** test, not a
spot-check (Pitfall 3's explicit requirement — a test file with fewer than ten
assertions for this table is the warning sign):
- a loop over **every** input code point `0x00`-`0xff`, asserting for each one
  either the exact expected output byte or that the call throws, computed from an
  independent expectation table written out in the test file rather than by calling
  the implementation
- explicit named cases: `asciiToPetscii("A")` is `Buffer.from([0xc1])`;
  `asciiToPetscii("a")` is `Buffer.from([0x41])`; `asciiToPetscii("A", { upper: false })`
  is `Buffer.from([0x41])`; `asciiToPetscii("\n")` is `Buffer.from([0x0d])`;
  `asciiToPetscii("LOAD\"*\",8,1\n")` produces the expected 12-byte sequence written
  out literally
- refusal cases: `asciiToPetscii("")`; `asciiToPetscii("ab")` throws naming
  index 1 and `0x93`; `asciiToPetscii("é")` throws; `asciiToPetscii("\t")` throws;
  `asciiToPetscii("x".repeat(256))` throws naming 255
- a boundary sweep asserting the four range edges explicitly: `0x40`, `0x41`,
  `0x5a`, `0x5b`, `0x60`, `0x61`, `0x7a`, `0x7b`

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| agent/LLM → `text` / `data` / `direction` arguments | an untrusted string becomes bytes in the emulated machine's keyboard buffer, and untrusted direction names become joystick switch states |
| container MCP server → binary-monitor socket | `KEYBOARD_FEED` injects into the buffer BASIC/KERNAL will execute; `JOYPORT_SET` drives input the running program reads |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-3-01 | Tampering | `asciiToPetscii()`'s unmapped-byte refusal | mitigate | Every byte the table does not map is refused with its index and hex code named — including PETSCII control codes such as `0x93` (clear screen) and the colour codes — so an LLM-supplied string cannot silently corrupt the debugged program's display or emit control sequences the caller never reasoned about. Explicit control bytes remain reachable, but only through `vice_keyboard_petscii`, where the caller states them one at a time |
| T-3-01b | Tampering | `handleKeyboardPetscii`'s `data` validation | mitigate | Every element is checked to be an integer in `0..0xff` with the offending index named, the array length is capped at 255 to match the `uint8` wire field, and a non-Latin-1 code unit is refused rather than truncated with `charCodeAt & 0xff` |
| T-3-02 | Tampering (integrity of the debugging session) | `JOYPORT_BITS` | mitigate | The assumed bit mapping is a single named constant labelled `[ASSUMED]` with its probe debt filed, and every answer reports the composed `value` plus its decoded `valueBits` — so a wrong mapping is diagnosable from the answer rather than only from unexplained emulator behaviour. Contradictory pairs (`up`+`down`, `left`+`right`, `center`+anything) are refused, because a composed value asserting two opposite switches is a state no real joystick produces and would be silently accepted by the wire |
| T-3-06 | Tampering (unrequested state change) | this module | mitigate | Grep-gated to zero `CommandType.Exit` references, and `vice_joystick_tap` is deliberately not implemented because its duration semantics would require exactly that resume (D-05). No sleep-based approximation is permitted |
| T-3-05 | Information Disclosure | this module | accept | No path arguments and no filesystem access |
