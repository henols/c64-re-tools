<objective>
Build the typed condition AST, the one canonical emitter, and the two input paths
that funnel into it (D-09). This is the piece that makes phase success criterion
2 true: a silently-always-false condition must be structurally unreachable, not
merely discouraged.

Purpose: VICE's condition parser has three independent traps that each produce a
condition that is always false with no diagnostic over the socket — no operator
precedence (`mon_parse.y:168`, so `RL == $64 && CY == $14` parses as
`(((RL==$64) && CY) == $14)`), bare integer literals are hex (`monitor.c:1597`,
so `RL == 100` means line 256), and the pseudo-registers are `RL`/`CY` not
`LIN`/`CYC` (which lex as `BANKNAME` and error with `0x8f`). String
concatenation at a call site is exactly how all three ship. A typed AST plus one
emitter removes the class of bug.

Output: `stock-condition.ts` and `stock-condition.test.ts`. No handlers, no
dispatch entries — plan 03-08 consumes this module.
</objective>

Types:
- `export type ConditionRegister = "A" | "X" | "Y" | "SP" | "PC" | "FL";`
- `export type ConditionPseudo = "RL" | "CY";` (raster line / cycle within line)
- `export type ConditionOperand =`
  `| { kind: "register"; name: ConditionRegister }`
  `| { kind: "pseudo"; name: ConditionPseudo }`
  `| { kind: "literal"; value: number };`
- `export type ConditionOp = "==" | "!=" | "<" | ">" | "<=" | ">=";`
- `export type ConditionNode =`
  `| { kind: "comparison"; left: ConditionOperand; op: ConditionOp; right: ConditionOperand }`
  `| { kind: "and"; left: ConditionNode; right: ConditionNode }`
  `| { kind: "or"; left: ConditionNode; right: ConditionNode };`
- `export class StockConditionError extends ViceError` (imported from `./vice.ts`)

`export function emitCondition(node: ConditionNode): string` — the ONE function
in the tree that ever produces condition wire text. Rules, all structural:
- A `comparison` emits `(<left> <op> <right>)` — always its own parentheses.
- An `and`/`or` emits `(<left> && <right>)` / `(<left> || <right>)` — always its
  own parentheses too. So the worked example
  `{ kind: "and", left: { kind: "comparison", left: { kind: "pseudo", name: "RL" }, op: "==", right: { kind: "literal", value: 0x64 } }, right: { kind: "comparison", left: { kind: "pseudo", name: "CY" }, op: "==", right: { kind: "literal", value: 0x14 } } }`
  emits **exactly** `((RL == $64) && (CY == $14))`. Because VICE has no operator
  precedence at all, over-parenthesising is the only safe emission and there is
  no "minimal parens" mode.
- A `literal` emits `$` followed by lowercase hex digits, zero-padded to 2 digits
  when the value is `<= 0xff` and to 4 digits when it is `<= 0xffff`. Never a
  bare decimal, never `0x`, never uppercase hex digits — one deterministic form.
- A `register`/`pseudo` emits its name verbatim in uppercase; the type already
  forbids any other spelling.
- Operands and operators are separated by exactly one space.

Validation inside `emitCondition()` (it is the last gate before the wire, so it
re-checks rather than trusting its caller):
- a `literal` outside `0..0xffff`, non-integer, or NaN → refuse
- an `RL` comparison whose literal exceeds `0x138` (312 PAL raster lines) or a
  `CY` comparison whose literal exceeds `0x3f` (63 cycles per line) → refuse,
  naming the range and the standard. Cite that bare `RL == 100` means line 256
  under VICE's hex-by-default rule as the reason the range check matters.
- an unrecognised `kind` → refuse via an exhaustive switch with a `never`-typed
  default (the `parseResponse()` discipline), never a silent fall-through

Also export `export function conditionFromJson(value: unknown): ConditionNode` —
the structured-object input path (D-09's second form). It narrows an untrusted
parsed-JSON value into the AST with a private `isPlainObject()` (declared locally
per the established convention, `vice.ts:310-316`), refusing with a message that
names the offending path (e.g. `condition.left.op`) on: a missing or unknown
`kind`, an unknown operator string, a lowercase register or pseudo name (name the
uppercase form required), `LIN`/`CYC` (name `RL`/`CY` as the replacement), a
literal that is a string rather than a number, and a nesting depth over 8.

Add `export function parseConditionString(expr: string): ConditionNode` to
`stock-condition.ts` — D-09's fork-compatible input path. It parses into the SAME
AST Task 1 defined and returns it; it never emits text itself, so
`emitCondition()` remains the only producer of wire text.

Accepted input, deliberately narrow:
- a single comparison, with or without surrounding parentheses:
  `A == $42`, `(PC == $c000)`, `SP <= $ff`, `RL == $64`
- a conjunction/disjunction where **every comparison is individually
  parenthesised**: `(RL == $64) && (CY == $14)`, `(A == $42) || (X == $01)`,
  and the same with outer parentheses present
- operand forms: an uppercase register name from `ConditionRegister`, an
  uppercase pseudo name from `ConditionPseudo`, or a `$hex` / `0x` literal
- arbitrary internal whitespace around operators and parentheses; leading and
  trailing whitespace trimmed
- operators `==`, `!=`, `<`, `>`, `<=`, `>=`

Refusals — each throwing `StockConditionError` with a message that names the
offending token AND the correct form, never a bare "syntax error":
1. `LIN` or `CYC` anywhere → message names `RL` / `CY` as the required
   pseudo-registers and states that `LIN`/`CYC` lex as a bank name and fail at
   runtime with error `0x8f` and no socket diagnostic.
2. a lowercase or mixed-case register/pseudo name (`a`, `pc`, `rl`) → message
   names the uppercase spelling required.
3. a **bare decimal literal** (`RL == 100`, `A == 42`) → message states that
   VICE's condition lexer reads bare integer literals as hex, so the author's
   intent cannot be recovered, and that `$64` or `0x64` must be written
   explicitly. This is a refusal, never a guess.
4. a multi-comparison expression where any comparison is **not** parenthesised
   (`RL == $64 && CY == $14`) → message states that the condition grammar has no
   operator precedence, shows what that input would actually parse as, and gives
   the parenthesised form to use instead.
5. a value out of range for its operand (delegated: build the AST then let
   `emitCondition()`'s range checks fire, or check inline — either way the
   message must be the same one Task 1 produces).
6. an empty or whitespace-only string, an unknown operator, unbalanced
   parentheses, more than 8 comparisons, or any token the grammar above does not
   cover → refuse naming the token.

Do not implement a general expression parser: the accepted grammar above is the
whole surface, and anything outside it refuses. The doc comment must say that
widening this grammar is Phase 6's GAIN-06 decision, not a maintenance liberty.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| agent/LLM → `condition` argument | an untrusted string or JSON object crosses here and becomes a breakpoint predicate the agent will then trust |
| container MCP server → binary-monitor socket | condition text reaching VICE's own lexer, which reports syntax problems only as error code `0x8f` with no diagnostic |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-3-02 | Tampering (integrity of the debugging session) | `emitCondition()` / `parseConditionString()` | mitigate | The emitter parenthesises every comparison and every boolean node and emits `$hex` literals only, so the no-precedence and hex-by-default traps are unreachable by construction; the string parser refuses `LIN`/`CYC`, lowercase names, bare decimals and unparenthesised conjunctions with a message naming the correct form. Golden tests assert exact emitted strings, not regex matches |
| T-3-02b | Tampering | out-of-range `RL`/`CY` literals | mitigate | `RL > 0x138` and `CY > 0x3f` are refused, so a condition that can never be true because the raster value is out of range cannot be armed and mistaken for a working breakpoint |
| T-3-04 | Denial of Service | condition nesting depth | mitigate | Depth capped at 8 and comparison count capped at 8 in both input paths, so a pathological nested object cannot produce an expression that blows the 255-byte wire limit or the parser stack |
</threat_model>
