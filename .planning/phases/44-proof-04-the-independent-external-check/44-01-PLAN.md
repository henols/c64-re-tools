## THE DERIVATION RULE -- FIXED AT PLAN TIME, BEFORE ANY MEASUREMENT

This block is normative. `evidence/SCHEMA.md` restates it; neither may drift
from the other, and neither may be amended after a run without recording both
readings (see this plan's second prohibition).

**Fixed inputs.** Binary `/usr/bin/x64sc`, resolved by absolute path -- genuine
unpatched stock, VICE 3.9; the fork at `/usr/local/bin/x64sc` shadows a bare
`x64sc` on `$PATH` and is never launched here. Release
`.planning/phases/23-the-real-release-gate-go-degrade-no-go/evidence/corpus/danish.d64`,
sha256 `1a9d294e07f9593ba59d878423d157bacfe6c6902d3a52ef6ac96512a15fb6c5`.
Entry `BRUCE LEE   (DC)`, sha256
`331fe97e73f8c77624242b4da3029efcb9199ffa184d6cd95220a60311efdaf4`, 45074
bytes, entrypoint `$0819`. Argv from `buildProbeArgs()` including
`STOCK_DETERMINISM_FLAGS` unmodified, so seed `4242`. The same release and the
same entry `PROOF-01` measured -- not a different corpus.

**Positive class and tier.** The positive class is `code` and the tier is
`runtime-observed`, both read from `reconcileObservedExecution()`'s own return
fields, never asserted by the driver. A false positive is one address the
byte-derived tier classified `data` and the emulator was observed executing.

**Verdict, per run.**

- `not-exercised` iff ANY of: a required input is absent or digests differently
  (the corpus, `/usr/bin/x64sc`, a resolvable dxa binary); `preflight()`
  refuses (the `vice-broker` unit is not `inactive`, or another `x64sc` is
  alive); the emulator never reached the anchor stop at all
  (`ORACLE_DEPTH_REACHED` is `0`); `parseAccessMap()` refused
  (`ORACLE_PARSE_REFUSAL` is not `none`); or `PROOF04_DENOMINATOR` is `0`.
  `not-exercised` is **NOT a pass**. It forbids any false-positive claim, and
  the record states what was searched and at what depth -- the outcome Phase 38
  recorded for `PROOF-02` rather than smoothing over.
- `unresolved` iff the run reached the anchor stop and the join ran, but
  `PROOF04_BLOCK_ADDRESSES_OBSERVED` is `0` -- no address the block table
  covers was observed executing. The answer is stated as
  `0 of <PROOF04_DENOMINATOR>` with the denominator named. This is a
  **shortfall**, explicitly not a clean bill of health, and the covered
  addresses are not thereby data.
- `resolved` iff the run reached the anchor stop, the join ran, and
  `PROOF04_BLOCK_ADDRESSES_OBSERVED` is at least `1`. `PROOF04_FALSE_POSITIVES`
  is the count; `PROOF04_DENOMINATOR` is its denominator.

**Phase verdict.** `PROOF04_PHASE_VERDICT` is `resolved` iff at least one
recorded run is `resolved`; `unresolved` iff no run is `resolved` and at least
one reached the join; `not-exercised` iff no run reached the join.

**Depth label, per run.** `frame-exact-region` iff `ORACLE_DEPTH_REACHED` is 50
or below; `narrowed` above it. Under `narrowed` the record states beside itself
that `EVID-06`'s `no-perturbation` verdict licenses claims only at anchor hit
depths of 50 or below, that `S3` is measured frame-exact and byte-identical to
hit 50 and diverging from hit 75 because `AUTOSTART`'s power cycle does not
reset the absolute emulated clock, and that any comparison against v0.8.0's
frame-exact captures is therefore narrowed rather than assumed. A run reaching
fewer hits than its target does not change its verdict -- it narrows the depth
claim, and `ORACLE_DEPTH_REACHED` is what the record states.

**Absence.** `PROOF04_BLOCK_COVERED_NEVER_OBSERVED` is a count against
`PROOF04_DENOMINATOR` and nothing else. No branch of this rule converts it, or
any part of it, into a class.

## RECORDED PLANNER DECISIONS (no CONTEXT.md exists for this phase)

`44-RESEARCH.md` left three open questions with a recommendation on each, and
this plan resolves each explicitly rather than implicitly. Two further
decisions were forced by facts found while planning.

- **D-P1 -- in-memory subject classification, not store-backed.** The subject
  `BlockEntry[]` is built directly from dxa's own map and written to a JSON
  artifact; no `.annostore` file is created or read anywhere in this phase.
  Rationale: `blockClassAt` already accepts a bare
  `{ start_address, end_address, type }` with no store involvement, and
  `evid-reconcile.ts` never opens a store -- so the store adds a shared
  resource the independence argument would then have to reason about, in
  exchange for a reviewability this phase does not need. The store-backed route
  (`anno_evid_ingest` plus `vice-mcp anno evid-disagreements --store`) already
  has committed Phase 43 unit tests; re-exercising it here buys nothing for
  `PROOF-04`'s question. Reversible: adding the store route later changes no
  published contract.
- **D-P2 -- two runs, one licensed and one explicitly narrowed.** Research
  flagged that a hit-50-only run may report zero disagreements for want of
  coverage rather than for want of false positives. Since dxa classified only
  67 of 45072 covered addresses as code, coverage is the whole question. Plan
  44-02 therefore takes BOTH: one run at anchor depth 50, inside `EVID-06`'s
  licensed region, and one deeper run labelled `narrowed` with the boundary
  stated beside it -- which Success Criterion 3's own text licenses. Neither
  replaces the other.
- **D-P3 -- `saeger.d64` is not taken.** Phase 38 declined it as optional
  strengthening; this phase declines it for the same reason and adds one: a
  second release doubles the live surface without changing whether `PROOF-01`'s
  count is computable, which is the reversal condition being closed.
- **D-P4 -- artifacts travel as name plus sha256, not as committed bytes.** The
  two producer JSON artifacts and every log land under
  `$HOME/.cache/c64-re-tools/phase44/`, outside the checkout and never in the
  system temp directory (a 16 GB RAM tmpfs whose aging is disabled on this
  host). Their digests are recorded as outcome lines. This is Phase 38's
  evidence README convention unchanged.
- **D-P5 -- the independence test lives in the phase's own `evidence/`
  directory, not in `src/mcp/vice/`.** A test in the shipped tree that reads a
  `.planning/phases/**` path becomes one more consumer that breaks when the
  milestone archives the phase directory -- a cost this project has already
  measured at twelve-plus consumers. Colocated with the two scripts it checks,
  the test and its subjects move together. It is therefore not picked up by
  `npm run test:automated`'s cwd-scoped glob and is run explicitly by this
  plan's own verify gate, which is where its result is recorded.
- **D-P6 -- Ghidra strengthening and `chis` cross-confirmation are not taken.**
  Research marks both optional. dxa alone supplied `PROOF-01`'s classification,
  so dxa alone is the subject whose count is being made computable; adding a
  second static classifier would change what is being measured.
