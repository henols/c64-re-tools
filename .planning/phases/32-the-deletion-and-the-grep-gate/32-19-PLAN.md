<objective>
GAP CLOSURE, round 2. **The restore-on-signal invariant — the one item the verifier routed to
a human, decided rather than carried.**

The verification frontmatter carries this under `behavior_unverified_items` and again under
`human_verification`. It is not scored as a gap, and the brief is explicit that it may either
be planned or recorded as debt — but not left unaddressed. This plan LANDS it, because the
cost is now near zero and it will never be lower: the harness is already being edited in this
round, and the one thing the attempt needed turns out to already exist.

**What plan 32-14 measured, and why it could not finish.** It drove ten attempts, five per
signal, against a scratch root, using an observable rather than a timer — polling the target
file every 2 ms until the planted bytes appeared, then signalling. All ten landed inside the
window. None ran the handler. The measured cause: `main()` and everything it calls are wholly
synchronous — no `await`, no `async`, no `.then(`, every subprocess a `spawnSync` and every
git call an `execFileSync` — so Node cannot dispatch a JavaScript signal handler while that
stack is running. The signal is queued, the stack unwinds, `finally { revert }` and
`finally { restoreAll }` run, and the process exits 0 with the queued callback undelivered.
Its own words: the verifier's four attempts did not miss a narrow window; there is no window.

Landing it needs either an in-process driver or an injected `await`. **This plan takes the
first and refuses the second.** Injecting an `await` into the plant window would change the
instrument's runtime behaviour in order to test it, which is the shape of defect this whole
phase exists against.

**And the thing that makes the driver cheap already exists.** `scripts/audit-mutation-harness.mjs`
already ends with an `IS_ENTRY_POINT` guard — the same idiom `scripts/check-guard-fates.mjs`
uses — so importing the module registers its four process handlers WITHOUT running `main()`.
A driver that imports the module, plants into a scratch root, and then awaits a timer has: the
real handlers registered, a real plant on disk, and an event loop that is turning. The window
is created outside the harness. The harness stays synchronous, unchanged, and un-widened.

**The second thing this settles.** `WR-03` doubts the `restored` latch — whether the exit
handler's `restoreAll()` after the signal handler's is genuinely a no-op or a second write.
Plan 32-14 expected to exercise it by construction and could not, because the handler never
ran. It stays "unsettled rather than resolved" in the verifier's words. A latch that looks
idempotent because both writes produce identical bytes is indistinguishable from a real no-op
unless something changes between the calls — so the second driver mutates the restored file by
hand between the two `restoreAll()` calls and asserts the hand-written bytes survive.

Implements **D-04** (the harness is a committed, re-runnable instrument), **D-13** (broker
state is an asserted, recorded precondition of every recorded figure), **D-15** (the evidence
artifact carries raw commands, raw output, broker state and the commit measured), **D-16** (no
new CI step and nothing added to either `package.json` `scripts` block) and **D-17** (the
harness stays a phase instrument rather than a CI job — see the truth above for why a
restore-machinery contract test does not contradict it).

Purpose: broken-windows entry 33 closes with an observation rather than an argument, and
verifier truth 13 stops being present-but-unverified.

Output: three exported symbols; two in-process drivers; a spawned test for both signals and
for the latch; and an evidence file carrying the full attempt log either way.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| test process → live working tree | A driver plants real mutations on disk and is then killed by a signal. A failed restore leaves a mutated file behind. |
| module import → process handlers | Importing the harness registers four process-level handlers, one of which calls `process.exit(130)`. Importing it into the wrong process would change that process's signal behaviour. |
| exported surface → future consumer | Three new exports are a contract. A wider surface than needed invites a consumer that depends on internals. |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-32-34 | Denial of service | a driver killed mid-plant | high | mitigate | The test deliberately kills a process with a mutation on disk. A failed restore would void every later harness run — the tree-cleanliness check treats a dirty tree as void evidence — and could be committed by accident. Mitigated by planting only inside a gitignored scratch root under the repository root, by capturing the target's bytes before planting, by asserting Buffer-level byte identity and porcelain identity after every attempt, and by removing the scratch root and killing any surviving child in a cleanup hook that runs even when an assertion fails. |
| T-32-35 | Tampering | importing the harness into the test runner's process | high | mitigate | Importing the module registers a SIGINT handler that calls `process.exit(130)`; doing that inside the test runner would change how the whole suite responds to an interrupt.
