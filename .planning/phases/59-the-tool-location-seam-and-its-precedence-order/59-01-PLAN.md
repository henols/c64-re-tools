## Decisions this plan records, beyond CONTEXT.md's eleven

`59-CONTEXT.md` left two questions open and asked the planner to decide them in writing rather
than default into them. Four more had to be settled to make the module writable. All six are
recorded here in the same shape `59-CONTEXT.md` records its own, so a reversal is recorded the
same way.

- **D-12: a `tools.json` value is a bare string.** `{"x64sc": "/opt/vice/bin/x64sc"}`, never
  `{"x64sc": {"path": "..."}}`. It is what a hand-written file most likely contains and what
  `DOCTOR-08`'s doctor-emitted template most naturally produces for a human to read. **Cost:**
  `DOCTOR-F2`'s deferred per-machine layering would have wanted a per-entry field, and adding one
  later means either a second file or a shape migration. The migration is not silent: the file
  validator refuses a non-string value **by name** from this phase onward, so the day an object
  shape is wanted, the refusal message is the migration point and no existing file quietly changes
  meaning. — **Reversibility: one-way** (user-facing file format; the same weight D-11 carries),
  which is why Task 1 is a decision checkpoint.

- **D-13: the compiled-artifact proof is two proofs, and neither is a new gate.** The *runtime*
  half — the compiled `resources/tool-location.mjs` actually resolving `prerequisites.json` from
  its own deeper location — lives in this seam's own colocated test, using the
  `build()`-then-dynamic-import idiom `prerequisites.test.ts:47-51` already established, because it
  must call the compiled module's exported resolver and that is the seam's behaviour, not the
  declaration's shape. The *packaging* half — the new artifact reaching a user who installed rather
  than cloned — extends `prerequisites.test.ts`'s existing `packedFileList()` case (plan 59-04),
  exactly as `59-CONTEXT.md` Specifics #2 instructs. No third npm-pack-driven test appears.

- **D-14: the module is `src/mcp/vice/tool-location.mts`.** A new `tool-location-*` domain prefix.
  Not `host-tool-*` — that domain is the MCP dispatch surface, not location (Discretion item 4).

- **D-15: this phase's probe layer is the `$PATH` walk and nothing else.** D-02 says the seam owns
  the walk as a named export and uses it for every id's third layer, and says the two existing
  private copies stay untouched so that exactly three coexist for one phase. Adding the fixed-prefix
  list or the vendored path here would make a fourth copy and make Phase 60's collapse harder. The
  `mechanism` union therefore *declares* all six values D-04 names, so Phase 60 adds no type change,
  while Phase 59's `resolveTool()` produces only `$PATH` from the probe layer, and only for
  `kind: "executable"` ids — a `$PATH` walk for a directory is meaningless and the result says
  `path: null` rather than recording a candidate nobody meant. **Cost to Phase 60:** it must supply
  the `sibling-of-x64sc`, `fixed-prefix-list` and `vendored-path` implementations when it collapses
  `findAcmeLib()`, `findDxaBinary()` and `findSiblingBinary()` into the seam — work its own
  criterion 4 already scopes ("the sibling probe is **widened, not replaced**").

- **D-16: an id declared `fileOverridable: false` is never resolved by this seam at all** — not
  through the environment, not through the file, not through `$PATH`. `resolveTool("dxa", …)` and
  `resolveTool("node", …)` return `path: null`, `layer: null`, `mechanism: null`, `tried: []` and
  the declared `reason`. A `$PATH` walk for `dxa` would hand back precisely the binary this project
  did not build and did not pin — the substitution `LOC-05` exists to refuse — and this seam has no
  business resolving the interpreter a bash launcher must find before any Node exists (`LOC-07`).
  Implemented in plan 59-02; stated here because it shapes the result type this plan writes.

- **D-17: the seam takes `toolsDir` and `projectRoot` as two separate required strings.** The
  caller resolves both; the seam derives neither from the other. Deriving the project root by
  taking the parent of the tools directory would embed a layout assumption that `repo-root.ts`
  already owns — the same "re-deriving a cross-cutting seam locally" anti-pattern
  `backend-detect.mts`'s own header warns about for `supervisorDir`.

## The result type, locked

This is the exact shape. Three later consumers walk it — plan 59-03's validator, Phase 60's
callsites, Phase 61's doctor row — so do not vary it.

`ToolLocationLayer` is the string union `"env" | "file" | "probe"`. `ToolLocationMechanism` is the
string union of all six values D-04 names: the four env-var names (`VICE_BIN`, `ACME_BIN`, `ACME`,
`GHIDRA_HOME`) are carried as the `mechanism` value when the env layer answers, plus
`"tools.json"`, `"$PATH"`, `"sibling-of-x64sc"`, `"fixed-prefix-list"` and `"vendored-path"`. Model
the env-var case as `string` rather than enumerating four literals, so a fifth declared env var
needs no type edit.

`ResolveToolResult` carries exactly six fields: `id` (the queried tool id), `path`
(`string | null`), `tried` (`string[]`, every candidate inspected in order), `layer`
(`ToolLocationLayer | null` — `null` when nothing answered), `mechanism`
(`ToolLocationMechanism | null`) and `refusal` (`string | null` — prose a caller shows a user,
never a code to map later, per this repo's `reason`-field convention).

`layer` and `mechanism` are two fields and not one, deliberately (D-04): `layer` names the thing a
user can go and fix, `mechanism` names the specific search. Merging them would force
`DOCTOR-03`'s row to either invent a fourth layer or overload one word to mean three searches.

## Where `~` and a relative path are resolved

Path handling belongs to the seam, not to each caller (ROADMAP cross-cutting constraint). Exactly
three normalisations happen, in this order, and only on a value that came out of `tools.json`:

1. A value beginning `~/` has the `~` replaced by the injected environment's `HOME`. A bare `~` with
   no separator is left alone — it is a legal relative path name and guessing is worse than not.
2. A value that is not absolute after step 1 is joined against `projectRoot`.
3. The result is passed to `node:path`'s own `resolve`, which is the only normalisation applied.
   No case folding. No Unicode normalisation. No comparison against a normalised form. A non-ASCII
   segment survives byte-identically.

The environment and probe layers keep today's `existsSync`-only behaviour and get none of this
(D-08); a `VICE_BIN` that is relative behaves exactly as it does today.

**Signal:** `pluralization` — the detector fired on "a second broker launch once raced the first", a

against the phase scope, the real delta is a `chosen` one and is recorded here rather than the

**The generalization.** A tool's location used to be *derived*: each callsite computed it from
whatever it happened to know — `process.env.ACME_BIN ?? "acme"` at one site, a fixed prefix list at
another, a sibling-of-`x64sc` probe at a third. There was no order, because there was nothing for an
order to be an order *of*. This phase makes location *chosen*: one module names three layers and
says which one answered.

**The noun that is now primary:** the **declared tool id** — a key under `tools` in
`src/mcp/vice/prerequisites.json`. The emulator binary, the assembler, the disassembler and the
interpreter stop being four different kinds of thing with four different lookup stories and become
eight instances of one noun, each with a `location` block saying how it is found.

**Decision: `add-alongside`, deliberately, for exactly one phase.**

The correct move is promote, and promote is scheduled — in Phase 60, not here. `59-CONTEXT.md` D-01
is explicit about why: any Phase 59 edit to `backend-detect.mts` regenerates a committed
`resources/*.mjs` artifact early and takes Phase 60's declared "**first** regeneration" deliverable
off it. So `resolvedBackend()` keeps its own `env.VICE_BIN ?? "x64sc"` read, `findAcmeLib()` keeps
its prefix list, `findSiblingBinary()` keeps its sibling probe, and the seam sits beside all three
resolving nothing that ships.

**Accepted debt, and what forces the promote.** For one phase the precedence order for `x64sc`
exists in two places, and three `$PATH`-walk copies coexist instead of one. Two already-scheduled
requirements force the promote rather than leaving it to intent: `LOC-02` in Phase 60 ("the
precedence order exists in exactly one place") and `LOC-01` ("every code path that resolves that
