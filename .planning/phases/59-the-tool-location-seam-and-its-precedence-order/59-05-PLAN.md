`parseCitationLedger()` and `extractCitations()`, and its `CitationAuditOptions` interface exists —

The placement document is therefore audited by **adding one test case to that file**, calling the
same exported function with the new document's path. No second implementation appears, and the file
is not renamed: renaming a test file is churn with no correctness benefit, and its header gains one

## The template's shape, locked

`toolsFileTemplate(resolved, deps): string` returns JSON text, two-space indented, with a trailing
newline. `resolved` is a read-only map from declared tool id to an absolute path the **caller**
resolved. `deps` carries the optional `here` override so the builder reads the same declaration the
rest of the seam reads.

The emitted object's keys, in this order:

1. `_readme` — prose naming what the file is for, the precedence order in words (environment
   variable, then this file, then a search), and the rule that any key beginning with an underscore
   is prose and is ignored.
2. `_viceBrokerNode` — prose quoting the `node` record's declared `reason` verbatim and naming the
   environment variable as the route that exists instead. This is criterion 4's "documented in the
   written template".
3. `_dxa` — prose quoting the `dxa` record's declared `reason` verbatim.
4. One key per entry in `resolved` whose id is a declared, file-overridable tool, in declaration
   order, with the caller's path as a bare string value (D-12).

Nothing else. An id in `resolved` that the declaration says may not be named by the file is omitted
and reported by no mechanism here — the builder emits a template, it does not judge its caller's
map; `validateToolsFile()` is what judges a file. An empty `resolved` yields the three prose keys
alone.
