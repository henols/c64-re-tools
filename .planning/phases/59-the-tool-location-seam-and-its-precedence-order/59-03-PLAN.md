## Read `LOC-06` with its amendment or you will build the wrong triad

`.planning/REQUIREMENTS.md`'s `LOC-06` row says a path that is "absent, not executable, **or a
directory**" is refused. Two of the eight declared tools — the assembler's library directory and the
Ghidra installation — are declared `kind: "directory"`, for which a directory is the *correct* state.
The literal clause is therefore inverted for a quarter of the declaration.

`59-CONTEXT.md` amends the criterion explicitly rather than leaving it to be reinterpreted. The
amended text, which every task here implements:

> A `tools.json` entry is refused by name when the path is absent, or is not what its record's
> `kind` declares, or — for a `directory` kind — does not contain its declared marker; and the
> refusal says the file supplied it.

The executable-bit clause survives, narrowed to `kind: "executable"`, and is tested with
`accessSync(path, X_OK)`. The one precedent in this tree is a test assertion at
`src/mcp/vice/host-scripts.test.ts:283`; this phase promotes the same primitive into production
validation for the first time, on the file layer alone (D-08).

## The problem shape, locked

`ToolsFileProblem` carries exactly three fields: `toolId` (`string | null` — the declared id the
problem is about, or `null` for a problem about the file as a whole), `key` (the raw key as written
in the file, or the empty string for a file-level problem) and `message` (prose a caller shows a
user; this repo's `reason`-style convention, never a code to map later).

`validateToolsFile(deps)` returns `ToolsFileProblem[]`. An empty array is a pass. This matches the
named-validator-returns-offender-list idiom `prerequisites.test.ts` already uses four times over, so
the clean case and the planted-violation case assert on the same shape.

`ValidateToolsFileDeps` is one destructured options object: `toolsDir: string` and
`projectRoot: string` required, plus optional `env`, `exists`, `statKind`, `access`, `readFile`,
`here` and `raw`. `raw` lets a test hand the validator file text directly without writing a file;
when it is absent the validator reads `join(toolsDir, "tools.json")`.

The accepted key set is derived from `Object.keys(doc.tools)` at call time, never written as a
literal array in this module, so a ninth declared tool needs no edit here.

| hand-edited `tools.json` → the validator | The one input to this module this project did not write. It is local configuration on the user's own machine rather than adversarial network input, but every key and every value is user-supplied and every value becomes a filesystem path. |

## Flagged Planner Assumptions

- **`validateToolsFile()` reads the file rather than receiving its text.** `59-RESEARCH.md` sketches
  `validateToolsFile(raw, deps)`. This plan uses the deps-object form for consistency with
  `resolveTool()`, with an optional `raw` override so a test can hand text in directly. D-10 specifies
  the export's job, not its parameter list, so this is a planner choice rather than a decision
  reversal — recorded here so it is not mistaken for either.
- **The file-layer refusal does not fall through to the probe layer.** `LOC-06` says a bad entry is
  refused; it does not say in as many words that resolution stops. This plan reads "refused" as
  terminal for that id, because continuing to `$PATH` would report success while resolving something
  other than what the file named. If the intent was "refuse loudly and continue", the behaviour here
  is one choice away from it and the doctor's row in Phase 61 is where that would surface.
