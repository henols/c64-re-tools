<objective>
Police the fields the refusals depend on, in the one place that already polices this document.

A refusal that quotes a declared reason is only as good as the guarantee that the reason exists. A
directory check that looks for a declared marker is only as good as the guarantee that every
directory record has one. Three new validators close both, in the same named-function,
planted-violation idiom the four existing ones already use.

Then prove the new compiled artifact reaches a user who installed rather than cloned — off the
packed tarball's own file list, which is the only evidence that crosses that boundary honestly.

Purpose: make the declaration's new fields as well-guarded as its old ones, without creating a
second gate that could disagree with the first.
Output: three new exported validators with their non-vacuity pairs, an extended record type, and one
more assertion inside the existing packaging section.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| committed declaration → the refusals that quote it | Whatever `location.reason` says is what a user is told when an exclusion fires. An absent or empty field produces a refusal with nothing in it. |
| repository → published npm tarball | A file present in a clone is not thereby present in the package. The tarball's own file list is the only evidence that crosses this boundary honestly. |
| validator → the document it validates | A validator with no planted-violation case cannot distinguish "always passes" from "correctly passes", and is therefore documentation wearing a test's clothes. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-59-14 | Spoofing | an exclusion refusal with an absent `reason` | high | mitigate | A record declaring itself not file-overridable with no reason produces a refusal that names a tool and explains nothing, leaving a user to conclude the tool is simply broken and to work around the exclusion. Mitigation: `assertLocationBlockShape` requires a non-empty `reason` on every non-overridable record, with a planted-violation case for both the missing and the empty-string form. |
| T-59-15 | Tampering | a `directory` record with no `marker` | medium | mitigate | Without a marker the directory check degenerates to "is a directory", and any directory a user names is accepted as a tool root and handed onward. Mitigation: `assertKindAndMarker` requires a non-empty marker on every directory record and forbids one on every executable record, both with planted violations. |
| T-59-16 | Tampering (by omission) | the compiled seam artifact in the published package | medium | mitigate | An artifact that does not survive packing is discovered by an end user, who gets a seam that cannot find the declaration with no signal anything is missing. Mitigation: the assertion reads the packed tarball's own file list via the single existing `npm pack --dry-run --json` helper; a repository-path check is explicitly forbidden and gated against. |
| T-59-17 | Spoofing | a declared tool id beginning with an underscore | low | mitigate | Plan 59-03's validator skips underscore-prefixed keys before its unknown-key check, so a real tool id beginning with one would be silently unreachable through the file. Mitigation: `assertNoReservedToolId`, with a planted violation. |
| T-59-SC | Tampering | npm/pip/cargo installs | low | accept | No package is added and no install task exists. `npm pack --dry-run` reads the local package and installs nothing; the Package Legitimacy Gate has nothing to check, as recorded in `59-RESEARCH.md` § Package Legitimacy Audit. |
</threat_model>
