<objective>
Close folded todo 2 — `acme-build`'s scaffold cannot be assembled on either documented
ACME provisioning route, and CI has the identical gap silently.

`template.a` sources `<cbm/c64/vic.a>`, `<cbm/c64/kernal.a>` and `<cbm/c64/cia1.a>`.
Neither a bare `~/.local/bin/acme` nor the Debian trixie `apt` candidate supplies that
library — both verified during Phase 8.1 (FINDING-A1), which is why that phase had to
hand-roll a library-free capture target. CI installs `acme`, checks the binary exists and
greps its banner, and never assembles anything, so the gap has never reddened a build.

This lands in Phase 10 because criterion 4 is already editing `acme-build/SKILL.md` and,
more importantly, because criterion 4's whole proof is "run a real assembler": the
`r2000 verify` route spawns ACME. An ACME installation that cannot assemble this
project's own scaffold is not a foundation that proof should rest on.

**Chosen fix: rewrite `template.a` to use local hardware constants**, not vendoring a
`cbm/c64/*.a` library beside the scaffold. Vendoring would add third-party assembly source
to both published packages, with the licence, `files[]` and notices consequences that
implies, to save a dozen lines; the scaffold needs exactly four registers and one KERNAL
entry point. `acme.mjs`'s `findAcmeLib()` probe stays — it still serves user sources that
use angle-bracket includes — but the scaffold stops depending on it.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| CI runner environment → the assembled scaffold | An untrusted-ish package-manager-provided toolchain produces a binary artifact checked by the build |
| documented setup instructions → a user's machine | Prose that determines what a user installs |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-10-13 | Repudiation | a green CI that proves nothing | mitigate | The install step's banner grep proved only that a binary named `acme` exists. The new step assembles the shipped scaffold and asserts the emitted load address, so the claim "the scaffold builds" is backed by an artifact check rather than a version string |
| T-10-02 | Tampering | subprocess invocation in the CI step and in `acme.mjs` | mitigate | `acme.mjs` already spawns `acme` with an argv array and no shell string; the CI step invokes `node acme.mjs …` with fixed literal arguments and a runner-temp path, never interpolating untrusted input |
| T-10-14 | Denial of Service | CI build time | accept | The added step assembles a five-line scaffold and costs well under a second, against an ACME install the job already performs. Deliberately NOT added: a regenerator2000 install, measured at 4m48s-5m39s, which D-11 keeps out of CI |
| T-10-SC | Tampering | third-party assembly source | mitigate | Vendoring a `cbm/c64` library was rejected precisely to avoid pulling third-party GPL-adjacent assembly source into two published packages; the scaffold defines five constants of its own instead, so no third-party material enters the tarballs and `THIRD-PARTY-NOTICES.md` needs no new entry for this change |
</threat_model>
