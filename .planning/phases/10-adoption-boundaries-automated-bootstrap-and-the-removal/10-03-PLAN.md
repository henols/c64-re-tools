<objective>
Give the bootstrap a `.d64` input that never guesses (criterion 3, `R2000-09`, **D-02**).

`parseDirectory()` in `c64-ram-capture`'s `d64-parse.mjs` already walks the directory
chain, but there is no exported file-extraction function anywhere in the repo — following
an entry's own chain to recover its bytes is new work. This plan writes that as a
container-side module beside the rest of the r2000 seam.

**Where it lives, and why — resolving RESEARCH.md Open Question #2 as a decision.** The
researcher recommended extending `d64-parse.mjs` in place. That is not reachable: the
seam is published as `@henols/vice-mcp`, whose `files[]` contains only
`.claude/mcp/vice/` contents, and `.claude/skills/**` ships in the *other* package
(`@henols/c64-re-tools`). An import from the seam into a skill script cannot resolve in
either npm-installer route, and `scripts/check-npm-packages.mjs`'s transitive-closure
walk would fail the pack for a reachable module that is not in `files[]`. So the
extractor lands container-side as `r2000-d64.ts`, `d64-parse.mjs` is left untouched, and
the new module's header cites `d64-parse.mjs` as the algorithm it was modelled on — one
extractor per package, not two in one.

Purpose: **D-02** exists because a silent auto-pick would analyse a cracktro or loader
stub instead of the game — precisely the failure `c64-provenance-diff` exists to prevent.

Output: `.claude/mcp/vice/r2000-d64.ts` and `.claude/mcp/vice/r2000-d64.test.ts`.
</objective>

Create `.claude/mcp/vice/r2000-d64.ts`, a pure, offline `.d64` reader with no filesystem
access inside the functions (callers pass a `Uint8Array`).

Header comment must state: (a) WHY it exists here rather than in
`c64-ram-capture/scripts/d64-parse.mjs` — the package boundary: `.claude/skills/**` is
not part of `@henols/vice-mcp`'s `files[]`, both npm-installer routes launch the server
via `npx` with no skill files on disk beside it, and `scripts/check-npm-packages.mjs`'s
transitive-closure walk would fail a pack that reached outside the package. (b) That
`d64-parse.mjs` is the algorithm's origin and remains the skill-side owner — this module
must not grow beyond what the r2000 bootstrap needs, and neither copy may silently drift
into a general disk-image library. (c) WHAT NOT TO DO: never auto-pick a directory entry
(D-02), and never walk a sector chain without a visited-set guard.

Exports:
  - `sectorsPerTrack(track: number): number` and `tsToOffset(track: number, sector: number): number`
    — the standard 1541 geometry, transcribed to match `d64-parse.mjs`'s own values.
  - `interface D64Entry { name: string; type: string; track: number; sector: number; sizeBlocks: number }`
  - `function listEntries(image: Uint8Array): D64Entry[]` — walks the directory chain
    from track 18 sector 1, decoding names as `d64-parse.mjs` does ($A0-padding stripped;
    no general PETSCII table, deliberately, and say so inline).
  - `function extractEntry(image: Uint8Array, entryName: string): Uint8Array` — resolves
    the entry by exact, case-insensitive name match against `listEntries()`; if zero
    entries match, throw an Error naming the requested entry AND listing the available
    names; if more than one matches, throw naming the ambiguity — never pick one. Then
    follow that entry's OWN chain from its `first_track`/`first_sector`, concatenating
    each sector's 254 payload bytes, and honour the DOS end-of-chain convention: when
    byte 0 of a sector is 0, byte 1 holds the count of used bytes in that final sector
    (so the last sector contributes `byte1 - 1` payload bytes, not 254). Apply the same
    visited-set cycle guard `d64-parse.mjs` uses, and the same `isInImage` bounds check;
    on either violation, throw an Error naming the offending track/sector, matching that
    module's defensive posture — never a bare `while (track !== 0)` loop.
  - `function assertPlainImage(image: Uint8Array): void` — throws unless the length is
    exactly 174848, with the actual length in the message. State inline that 40-track and
    error-info-byte variants are deliberately out of scope for this phase, inherited from
    `d64-parse.mjs`'s documented limits.

`extractEntry` returns the file's raw bytes INCLUDING the 2-byte PRG load address, so the
caller can hand them straight to `parsePrg()` in `r2000-project.ts` — say so in the
function's doc comment, since that is the whole point of the module.

The fail-loud "no name given → print the directory listing → exit non-zero" contract of
D-02 belongs to the CLI caller (plan 10-04), not here: this module never calls
`process.exit` and never prints. Say that in the header too.

Import nothing from `hostpath.ts` or `containerpath.ts` — plan 10-01's extension of
`hostpath-consumers.test.ts` already names `r2000-d64.ts` on the absence side.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| untrusted `.d64` image bytes → `listEntries`/`extractEntry` | A caller-supplied, possibly corrupt or adversarial disk image is parsed |
| caller-supplied entry name → `extractEntry` | An arbitrary string selects which bytes are analysed |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-10-03 | Tampering | `.d64` sector-chain traversal | mitigate | A self-referential or cyclic next-sector pointer is caught by a visited-set guard, and an out-of-image pointer by an `isInImage` bounds check — both throwing with the offending track/sector named, mirroring `d64-parse.mjs`'s existing defensive posture (ASVS V5). Tests 6 and 7 prove both paths |
| T-10-07 | Spoofing | entry selection | mitigate | The wrong file inside a disk image (a cracktro or loader stub presenting as the game) is the substantive risk D-02 names. Mitigated by refusing to auto-pick: zero matches and multiple matches both throw, and the caller must name the entry explicitly |
| T-10-02 | Tampering | entry name reaching a subprocess | mitigate | This module never spawns anything; the entry name never reaches a shell. The CLI caller (plan 10-04) passes file paths to `regenerator2000` only through `r2000-launch.ts`'s argv arrays |
| T-10-05 | Information Disclosure | host-path leakage | mitigate | `r2000-d64.ts` imports no host-path module; the absence is asserted by plan 10-01's extension of `hostpath-consumers.test.ts`, which names this file explicitly |
| T-10-SC | Tampering | npm/cargo installs | accept | No dependency is added — the module uses Node built-ins only |
</threat_model>
