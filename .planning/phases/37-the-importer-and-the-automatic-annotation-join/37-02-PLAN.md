<objective>
Build the two things `AUTO-04` and `AUTO-05` cannot be verified without, and that nothing in
the tree provides today: a synthetic fixture with a genuinely path-dependent `$01` site, and
an addressed recovered-constant export section.

Purpose: `bank.a` is MEASURED to be straight-line code with three separate `$D020` program
points, none of them reached from two bank contexts — so "the join declines on the fixture"
would pass for the wrong reason, and a flip control run against it would be vacuous. And
`## DECOMPILED_TEXT` today yields `DAT_0001 = 0x37;` with no per-statement address at all,
so a join cannot answer "what was the processor port at THIS address?" from the committed
export. `37-RESEARCH.md` names this the phase's single load-bearing gap and its own Open
Question 1.

Output: `fixtures/ghidra/bank-path-dependent.a` and its assembled `.prg`, an additive
`## CONST_WRITES` section in `GhidraStructExport.java`, a committed real capture of that
section over the new fixture, and the container-side parser for it.
</objective>

<decisions>

**D-37-06 — The new section is `## CONST_WRITES`, not `## BANK_WRITES`, and it serves two
requirements from one mechanism** (resolves `37-RESEARCH.md` Open Question 1, generalising
its recommendation). `AUTO-04` needs `(address, $01-literal)` pairs. `AUTO-06` needs the
constant values a program wrote to `$DD00`, `$D018` and `$D011` — the same class of fact,
recovered the same way, from the same p-code walk. Emitting one section over a declared
watched-address set costs the same Java work as emitting one over a single address and
removes a second export extension from plan 37-07's scope. The watched set is a named
constant in the Java source: `$0001` (the processor port), `$D011`, `$D018` and `$DD00`.
The line shape is `<store-address> <target-address> <constant-value>`, three whitespace-
separated hex tokens, so a consumer never has to know the watched set to parse a line.

**D-37-07 — The section is derived from p-code STORE operations, never from decompiled C
text.** `37-RESEARCH.md` § *Common Pitfalls* #1 names the failure precisely: decompiler
restructuring reorders statements relative to their real addresses, so treating source order
as address order is a silent correctness bug that reproduces exactly the confident-wrong-
comment failure this phase exists to prevent. The walk therefore takes each `PcodeOp` of
kind STORE (and the COPY-into-a-known-address form the 6502 store pattern produces), reads
the operation's own sequence-number address, and emits a line ONLY when the stored value's
varnode is a constant. A store whose value varnode is not constant emits NOTHING — that
absence is `AUTO-05`'s decline signal, and it is a fact rather than a gap.

**D-37-08 — The fixture's shared program point is a subroutine called twice.** The
structural requirement `bank.a` fails is a single instruction address reached under two
different `$01` values. The cheapest construction that satisfies it, and the one the
disassembler will present unambiguously, is a `jsr` to a fixed-address subroutine performing
one `sta $d020` and one `lda $d000,x`, called once after `lda #$34 / sta $01` and once after
`lda #$33 / sta $01`. The two `$01` values are chosen to match `bank.a`'s own vocabulary and
`AUTO-04`'s criterion text: `$34` (bits 1-0 clear, so the I/O area reads as RAM) and `$33`
(bit 2 clear with bits 1-0 set, so `$D000-$DFFF` is Character ROM). Both call sites and the
subroutine live at addresses the README records per route.

**D-37-09 — The captured export section is committed as a fixture; the live run that
produced it is not a CI gate.** This mirrors `ghidra-harness-gates.test.ts` exactly: real
captured `analyzeHeadless` output committed under `fixtures/ghidra/`, with the exact command,
date and exit status recorded in that directory's `README.md`, and hermetic tests that parse
it with no JVM. The live producing run lands as new cases inside the EXISTING
`ghidra-live.test.ts`, which is already `MANUAL_ONLY_TESTS` entry eleven and already gates on
`VICE_LIVE_GHIDRA=1` plus `GHIDRA_HOME` through a `SKIP_REASON` computed once. Adding cases
there rather than creating a new manual-only file avoids editing the frozen
`MANUAL_ONLY_TESTS` array and its drift guard. Because `test:automated` skips manual-only
files entirely, the committed capture plus its hermetic parser tests are the automated
counterpart, without which this work would ship with no CI gate at all.

</decisions>

**The watched-address constant.** Declare a `private static final` array named `CONST_WRITE_WATCHED_ADDRESSES` holding four addresses: `0x0001`, `0xD011`, `0xD018` and `0xDD00`. Document each in a comment by what it selects: the processor port's bank state for `AUTO-04`, the display-mode bit for `AUTO-06`, the screen and character-base nibbles for `AUTO-06`, and the VIC bank bits for `AUTO-06`. **The walk.** Build the section from the SAME `DecompInterface` results the structural-facts section already walks, in the same pass — do not construct a second interface and do not re-decompile. For each decompiled function, iterate its high-level p-code operations; for each operation that stores a value to a memory location, resolve the destination address; if the destination is one of the watched addresses AND the stored value's varnode is a constant, emit one line. The line is three whitespace-separated tokens: the operation's own sequence-number address, the destination address, and the constant value. Use the same address rendering the reference section already uses so a consumer parses one address form, not two.

**What must NOT be emitted.** A store whose value varnode is not a constant emits nothing. That silence is the fact `AUTO-05` reads as a decline, and the section's comment must say so explicitly, because a later reader tempted to "fill in" a computed store with a guessed value would be reintroducing exactly the confident-wrong-comment failure this phase exists to prevent. Under no circumstances derive a value from the decompiled C rendering or from any address-free token stream; D-37-07 records why.

**The trailers.** After the body, append `## CONST_WRITES_COUNT ` and the number of lines emitted, mirroring the reference section's trailer. When the count is zero, emit an explicit `## CONST_WRITES_NONE` line inside the section before the count line, mirroring the structural-facts section's per-kind explicit-not-found discipline. An absent section and a section that found nothing are different facts and must read differently.

**The mode branch.** The structural-facts and accounting sections behave differently under the two modes. Under the mode that does not construct a decompiler interface, the new section emits the explicit not-found line and a zero count rather than being omitted — the section's presence is part of the file's fixed shape.

**Placement.** Append the new section after all six existing sections at the single write site. Do not rename, reorder or reshape any existing section: the live gate tests from plan 36-04 assert against the current fixed order, and the file's own header states the additive-only convention.
