<objective>
Implement the three selection rules that decide what a machine address means, and the
provenance every derived row carries — narrowest-containing-range with its `sym` tie-break
(`AUTO-02`), the in-image skip (`AUTO-03`), and the `memmapSha256` token (`AUTO-08`).

Purpose: two of these three rules fail SILENTLY. Getting them wrong does not produce an
error; it produces a plausible, confident, wrong comment, and each was got wrong on the first
attempt during the pivot exploration. This plan lands the rules and their positive
assertions. Plans 37-04 and 37-05 land the four observed-red controls that make those
assertions worth anything — deliberately in separate tasks in separate plans, because
`.planning/research/PITFALLS.md` § *Pitfall 23* names batching them into "the controls are in
place" as the exact failure mode.

Output: `selectMemmapEntry()` with a complete, stated selection order; the in-image skip
placed before the lookup rather than after it; and a fixed-format provenance token on every
derived comment.
</objective>

<decisions>

**D-37-10 — The selection order is THREE rules deep, not two, and the third is stated
because the data forces it.** `AUTO-02` names two: narrowest containing range, then tie
toward the entry carrying a `sym`. MEASURED at plan time against the committed
`memmap.json`: `$D020` is covered by **8** entries, of which **two** are exactly 1 byte wide
and **neither carries a `sym`**. So the two stated rules do not resolve the phase's own
headline example. The third rule is therefore stated rather than left to scan order: among
contenders equal on width AND equal on `sym`-presence, the one appearing FIRST in
`memmap.json`'s `entries` array wins. MEASURED: that is the entry at index 506, sourced from
the `sta` table, labelled `Border color (only bits #0-#3)`; the loser is index 507, sourced
from the `io` table, labelled `Border Color`. The probe's `ordering` edge for this
requirement is exactly this question and this is its answer.

**D-37-11 — The `sym` tie-break's real fixture is address `$0000`, and it has THREE
contenders, not two.** MEASURED at plan time: three entries are exactly `start=0, end=0` —
index 0 (`Processor port data direction register`, no `sym`), index 1 (`6510 On-chip Data
Direction Register`, `sym: "D6510"`), and index 2 (a further no-`sym` entry). `37-RESEARCH.md`
§ C states two; it is three. The tie-break must therefore select index 1 out of three
equal-width contenders, and a test asserting "two contenders" would be asserting something
false about the committed data. Assert the `sym`-bearing winner and the contender count as
measured, and re-measure rather than trusting either number if `memmap.json` changes.

**D-37-12 — The in-image skip runs BEFORE the lookup, and its range comes from the image's
own bytes.** `AUTO-03` says an in-image address is "never looked up in `memmap.json`". That is
a statement about control flow, not about the result: computing a selection and then throwing
it away would satisfy a naive test and violate the requirement. The skip is therefore an
early return placed before the `selectMemmapEntry()` call site, and plan 37-05's control
observes the red by removing it. The range is `[origin, origin + body.length - 1]` inclusive,
taken from the existing `loadImage()` helper's own result — never a caller-supplied number
pair, which would let a wrong argument silently widen or narrow the program's own extent.

**D-37-13 — Provenance is a fixed-format trailing token in the comment text** (resolves
`37-RESEARCH.md` Open Question 3; the carrier decision is recorded in plan 37-01 as D-37-03).
The token is the `PROVENANCE_TOKEN_PREFIX` literal followed by the full 64-character sha256
hex of `memmap.json`'s bytes, appended to the comment text after a single separating space,
always last, always the full digest. Full rather than truncated because a truncated digest
answers "probably this version" and the requirement asks "which map version produced this
annotation". `MAX_COMMENT_BYTES` is 4096, so the cost is affordable. `setComment()` refuses an
embedded newline, so the token is appended inline. A comment with no map entry behind it
carries no token at all — a placeholder digest would be a lie about provenance, which is
worse than its absence.

</decisions>
