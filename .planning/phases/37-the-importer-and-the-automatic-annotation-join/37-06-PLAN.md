<decisions>

**D-37-21 — The decode is arithmetic over bits 2-0, and the three region rules are stated
explicitly.** `memmap.json` carries the bank condition ONLY as free text inside a description
field — MEASURED, 6 of 959 entries mention it at all and the schema has no structured field —
so the decode is a hand-written rule cross-checked against the map's own entries, never parsed
from them. `37-RESEARCH.md` § *Common Pitfalls* #2 names the alternative (a regex over
description text) as fragile and forbidden. The rules, from the map's own canonical
description of the I/O area:

- Take `b = value & 0x07`.
- `$D000-$DFFF`: when `b & 0x03` is zero, the region is RAM — regardless of bit 2. Otherwise,
  when bit 2 is clear, it is Character ROM; otherwise it is the I/O area.
- `$A000-$BFFF`: BASIC ROM when bits 1 and 0 are BOTH set; otherwise RAM.
- `$E000-$FFFF`: KERNAL ROM when bit 1 is set; otherwise RAM.

The two values the fixture uses decode as: the all-RAM value has bits 1 and 0 clear, so
`$D000-$DFFF` is RAM; the character-ROM value has bits 1 and 0 set and bit 2 clear, so
`$D000-$DFFF` is Character ROM. **`bank.a`'s own inline comment mislabels the first value's
bit 2 as clear — it is set — and reaches the right conclusion anyway, because the RAM case
does not depend on bit 2.** Plan 37-02's new fixture records the correction; this module's
source must state the rules as bit arithmetic so no reader re-derives them from a comment.

**D-37-22 — Bank state constrains the CANDIDATE SET, not the answer.** `AUTO-04` says bank
state is resolved "before the address". Implemented as a post-filter — select the entry, then
check whether the bank allows it — the rule would sometimes produce no answer where a correct
one exists, and would make the phrase "before" meaningless. So `resolveBankedRegion()` returns
a region, and the join passes that region to the selection as a candidate CONSTRAINT: for an
address inside one of the three bank-conditional ranges, only entries consistent with the
resolved region are contenders. Outside those three ranges the region is irrelevant and the
candidate set is unconstrained — which is why `BANK_CONDITIONAL_RANGES` exists as an explicit
list rather than the rule being applied everywhere.

**D-37-23 — Reaching-values are a SET per program point, and a set of size other than one is a
decline.** For each address the join is about to annotate, collect the recovered processor-port
values that reach it. Size one: resolve and annotate. Size zero: decline, with a reason naming
that no value was recovered — never default to the power-on value, because an assumed bank is
exactly the confident-wrong-comment failure. Size two or more where all values decode to the
SAME region for that address's range: annotate, because the program does determine the meaning
even though it does not determine the byte; state this equivalence rule in the source, because
a reader will otherwise assume any multi-value set declines. Size two or more decoding to
DIFFERENT regions: decline, with a reason naming both values and the address they disagree at.

**D-37-24 — The reaching-values computation is deliberately conservative and its limit is
stated.** This plan does NOT build a dataflow analysis. It uses what the export gives: the
recovered constant stores to the processor port, each with its own address, and the
cross-reference graph the importer already stored. The reaching-values set for an address is
the set of recovered processor-port values whose store address can reach it, computed over the
stored reference graph. Where that computation cannot decide — an unresolved computed jump, a
reference the importer dropped as an unmapped kind — the result is UNKNOWN, and UNKNOWN
declines. Being conservative here is correct: a decline is a stated absence, and the whole
requirement is that a stated absence beats a confident guess. State the limit in the module
header rather than leaving a later reader to discover it.

**D-37-25 — The reserved store column stays NULL.** Restated here because this is the plan
that would be tempted. Plan 37-01's D-37-02 records the two committed facts that settle it:
the requirements document excludes bank-qualified addressing as a modelled store feature, and
the store's own test asserts every row it writes has a null bank AND that no branch, comparison
or arithmetic on a bank value exists in the store module. The resolved state is recorded in the
annotation's provenance text in axis-qualified form, naming the processor-port axis, so a later
phase adding the second VIC banking axis is additive.

</decisions>

Land the decode, the region resolution, the candidate constraint and the decline.

**`src/mcp/vice/anno-bank.ts`.** Same module posture as its siblings: it never names the persistence dependency, never opens the store, never imports the host-path module, and takes plain data.

`BankedRegion` — a frozen vocabulary naming what a bank-conditional range currently contains: the I/O area, character ROM, RAM, BASIC ROM, KERNAL ROM, and an explicit member meaning the address is not in a bank-conditional range at all. That last member exists so a caller can tell "no constraint applies" from "the constraint resolved to RAM"; collapsing them would make an out-of-range address silently RAM-constrained.

`BankState` — the decoded triple: what each of the three bank-conditional ranges currently holds, plus the raw value it was decoded from.

`decodeBankState(value: number): BankState` — the arithmetic in D-37-21, written as bit tests with a comment per rule naming the signal by its conventional name. Mask to bits 2-0 first, so values differing only in higher bits decode identically; assert that property in a test rather than trusting the mask. Keep this function small and self-contained: Task 2 mutates it with one textual replacement.

`resolveBankedRegion(address: number, state: BankState): BankedRegion` — look the address up in `BANK_CONDITIONAL_RANGES`; return the not-applicable member when it is in none, otherwise the decoded region for the range it falls in.

**The reaching-values computation, in `anno-join.ts`.** For each address the join is about to annotate, compute the set of recovered processor-port values that reach it, over the recovered const-write facts and the stored cross-reference graph, per D-37-24's conservative rule. Represent the result as one of three shapes: exactly one value; several values; or unknown. Where the graph cannot decide, the answer is unknown. State the limit in the module header.

**The four outcomes, in the join.** One value: decode, resolve the region, pass it as the candidate constraint to the selection, annotate. Several values all resolving to the same region for that address: same, and record in the decision that the values differed but the region did not. Several values resolving to different regions: DECLINE — push a decision whose outcome names the decline and whose reason names both values, the two regions they resolve to, and the address they disagree at. Unknown or empty: DECLINE, with a reason naming which of the two it was. Never default to the power-on value; never carry one value forward past a disagreement. Keep the decline branch a single small region of source: Task 3 mutates exactly it.

**The candidate constraint.** Extend `selectMemmapEntry()` with an optional region constraint. When supplied and the address is in a bank-conditional range, only entries consistent with the resolved region are contenders — the constraint narrows the candidate set BEFORE the three-step order runs, which is what makes the resolution "before the address" rather than a post-filter. Consistency is decided by matching the region against the entry's own label and description using a small explicit table in `anno-bank.ts`, not a free-form text search: the table maps each region member to the entry labels that represent it in the committed map, and a map entry matching no region member is excluded from a constrained selection rather than silently admitted.

**The provenance addition.** For an annotated address in a bank-conditional range, append the resolved state to the comment in the axis-qualified form D-37-02 fixed — naming the processor-port axis and the value — before the map digest token, so the digest stays last. Do not write the reserved store column.
