<objective>
Derive the graphics areas — screen matrix, character set or bitmap, and sprite pointers —
from the VIC pointer registers rather than from cross-references.

Purpose: the video chip fetches its data by direct memory access, so a character set may be
referenced by **no instruction anywhere in the program**. That is the case cross-references
structurally cannot find, and it is `AUTO-06`'s entire reason to exist. `37-RESEARCH.md` § E
measured that no existing code in this repository decodes these registers for this purpose:
the two stock-backend modules that name them read live emulator state over the binary monitor,
which is a different question. This is genuinely new container-side arithmetic over the
recovered register values plan 37-02's export section already carries.

Output: `anno-graphics.ts`, a pure derivation over recovered register values, and its
hermetic tests driven from the committed captured export.
</objective>

<decisions>

**D-37-26 — The derivation takes recovered register VALUES and nothing else.** Its only input
is the const-write facts plan 37-02's export section produces. It does not receive a store
handle, does not read cross-reference rows, and does not import the join. This is not tidiness:
`AUTO-06`'s criterion is that a charset referenced by no instruction is still found, and a
module that could see the reference graph would let an implementation quietly lean on it. The
structural assertion in Task 2 is over this module's own import list.

**D-37-27 — One map per distinct register-value combination, never a merged map.** The ROADMAP
states it directly: a program that switches bank or charset per raster split has several valid
graphics maps, and a single derived map is wrong for all but one — the same path-dependence
limit `AUTO-05` names. So `deriveGraphicsRanges()` returns an ARRAY of maps, one per distinct
combination of the recovered values, each carrying the values that produced it. A caller that
wants one map picks one and knows it chose; a caller handed a merged map would not know there
was a choice.

**D-37-28 — A missing register is a stated absence, never a default.** Power-on defaults exist
and are well known, which is exactly why substituting one is tempting and wrong: a derived
range built on an assumed register value is indistinguishable in the output from one built on a
recovered value, and this phase exists to prevent exactly that class of confident wrong output.
Where a required value was not recovered, the map that depended on it is not produced, and the
result names which register was missing.

**D-37-29 — Sprite BITMAP locations are explicitly out of scope and this module must not
appear to promise them.** The requirements document records sprite bitmap locations as a
carried, unowned gap: the pointer VALUES are program data usually written at run time, so they
are not register values a static analysis recovers. This module derives the sprite POINTER
range — the eight bytes the chip reads pointers from — and stops there. Its header must say so
in one sentence, because a reader seeing sprite pointers derived will otherwise assume the
bitmaps followed.

**D-37-30 — The derived rows type as an existing data-type member.** The store's data-type
vocabulary is a frozen twelve with no graphics-specific member, and widening it would require
re-auditing every consumer of that frozen list, including the disassembler-feedback module's
own derivation of which types are data-bearing. This module therefore emits ranges carrying an
existing byte-shaped type, and records the choice and its cost in its header. Widening the
vocabulary is a schema decision no plan in this phase makes.

</decisions>

  <action>
Write the derivation as pure arithmetic over recovered register values, with every rule stated and every absence named.

**Module posture.** `anno-graphics.ts` never names the persistence dependency, never opens the store, never imports the host-path module, and — new to this module and load-bearing per D-37-26 — never imports the join or anything that reads the cross-reference graph. Its header states that, and states D-37-29's sprite-bitmap boundary in one sentence.

**Types.** `GraphicsRange` — `{ start: number; endInclusive: number; kind: string; dataType: DataType; derivedFrom: Record<string, number> }`, where `kind` names which of the four things it is (screen matrix, character set, bitmap, sprite pointers) and `derivedFrom` records the register values that produced it. Shape the range fields so a `KnownDataRow` can be produced from one without a translation layer — read the existing interface first and match it.

`GraphicsMap` — `{ ranges: GraphicsRange[]; registerValues: Record<string, number>; missingRegisters: string[] }`. A map with a non-empty `missingRegisters` carries only the ranges that did not depend on the missing value, so a partial recovery yields partial, honest output rather than nothing or a guess.

**The arithmetic, stated as rules with their reasons.**

The VIC bank: take the bank-select register's low two bits, invert them, and multiply by the 16-kilobyte bank size to get the bank base. The inversion is the part every implementation gets wrong once; state it in a comment as the chip's own convention, and cover both extreme values in tests so the inversion has a failing direction.

The screen matrix: the memory-control register's high nibble, multiplied by the screen-matrix granularity, added to the bank base. Its size is the fixed thousand-and-twenty-four-byte matrix.

The character set or bitmap: the memory-control register's low nibble's upper three bits, multiplied by the character-base granularity, added to the bank base. Which of the two it is comes from the control register's mode bit — clear means a character set of the character-set size, set means a bitmap of the bitmap size. Do not derive the kind from the size; derive the size from the kind, so a wrong mode bit produces a wrong kind rather than a plausible range of the wrong length.

The sprite pointers: eight inclusive bytes at the screen-matrix base plus the fixed sprite-pointer offset. Stop there — D-37-29.

Cross-check every one of these against `stock-vicii.ts`'s existing decode of the same registers, and record in the summary where the two agree and where they differ. A disagreement is a finding to report, not a number to quietly pick between.

**Multiple combinations.** Group the recovered facts by distinct combination of the three register values and produce one map per combination, in a stated deterministic order — ascending by the tuple of the three values — so two runs over the same facts produce the same array. State in the header that several maps is the correct answer for a program that switches per raster split, and that merging them would be wrong for all but one.

**Missing values.** A combination lacking a value required by a range does not produce that range, and names the register in `missingRegisters`. Never substitute a power-on default; state in the header that the defaults are well known and that using them is precisely the temptation this rule forbids.

**Tests first.** Write every `<behavior>` bullet against hand-built fact lists, where the arithmetic is the point, and cover both extremes of the bank inversion. Check the committed capture for VIC register writes; if it has none, say so plainly in the summary and note that plan 37-08's fixture supplies the real-capture case.
