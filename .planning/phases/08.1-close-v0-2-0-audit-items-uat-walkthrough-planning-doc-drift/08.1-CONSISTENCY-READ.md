## "Total plans completed" — why 76 and 80 are both correct

STATE.md frontmatter `completed_plans: 80` is a real-time, disk-derived count (every
`-SUMMARY.md` file across every phase directory in the milestone, including Phase
8.1's own 4 landed plans at read-time). STATE.md's body "Total plans completed: 76"
(Performance Metrics → Velocity) is a **phase-boundary** counter: it is only
incremented by the SDK's `phase.complete` handler, by exactly the completing phase's
own plan count, at the moment a phase is marked done. 76 = 4+10+18+7+13+18+6 (phases
1,2,3,4,5,7,8 — every phase that has actually gone through a `phase.complete` call).
Phase 8.1 has not yet gone through `phase.complete` (that is the orchestrator's next
step, after this plan), so its 4 (soon 5) plans are correctly **excluded** from the
phase-boundary counter, even though they are correctly **included** in the real-time
disk count. This matches this plan's own `<canonical_numbers>` table ("Plans
complete: 76 of 76" — a phase-boundary-scoped figure understood to exclude the
still-open Phase 8.1). Both numbers are individually correct for what they measure.
**This is not RESIDUAL material** — no edit is applied — but it is recorded here so a
future reader is not confused by two different "total plans" numbers in the same
file. See FINDING-2 below for what happens to the 76 figure once `phase.complete`
finally runs.

## Residuals fixed

### RESIDUAL-1: STATE.md Progress line (99% -> 78%)

**Root cause, traced to source (not guessed):** two different GSD SDK verbs recompute
this same body field with two different, disagreeing formulas, and both are wired
into this project's standard per-plan closing steps:

- `state.update-progress` (`sdk/src/query/state-mutation.ts:758`) computes
  `percent = round(totalSummaries / totalPlans * 100)` — a raw, real-time,
  **uncapped** plan-file ratio across every `*-PLAN.md`/`*-SUMMARY.md` in the
  milestone's phase directories, with no awareness of phase boundaries.
- `phase.complete`'s own frontmatter recompute, and the separate `state.sync`
  command, both route through `computeProgressPercent()`
  (`sdk/src/query/state-document.ts:71`), which takes
  `min(planFraction, phaseFraction)` — deliberately capping the reported percent at
  the phase-completion ratio so an in-flight phase's own landed plans cannot make
  the project look further along than the phase count supports.

Every prior plan in this phase (08.1-01 through 08.1-04) called the generic
`state.update-progress` step during its own closing `<state_updates>`. Each call
recomputes `totalSummaries/totalPlans` against the growing count of Phase 8.1's own
plans, so the body line drifted upward every time (this is the third occurrence:
first caught and fixed to 78% in plan 08.1-02, then re-broken to 99% by 08.1-03/04's
own closing steps). Verified live against this repo's actual disk state: as of Task 2
(before this plan's own `08.1-05-SUMMARY.md` exists), `totalSummaries=80`,
`totalPlans=81`, giving `round(80/81*100)=99%` — reproducing the observed drift
exactly. Once this plan's own summary lands, the same formula gives
`round(81/81*100)=100%`, which would have violated this very task's acceptance
criterion (`grep -c '100%' STATE.md` must return 0).

**Fix applied:** the body line is rewritten to `78%` (matching frontmatter and
ROADMAP.md's phase-based figure) with an inline label naming both quantities
explicitly, so a future reader is never confused about which ratio the line reports.
**Deviation from the standard closing workflow:** this plan's own `<state_updates>`
step deliberately does **not** invoke `gsd-sdk query state.update-progress` (the
uncapped verb) after Task 2, specifically because doing so would reintroduce this
exact regression a third time inside this same plan's execution. `state.record-metric`,
`state.add-decision` and `state.record-session` are still used normally — only the
`update-progress` sub-step is skipped, with this note as the record of why (Rule 1/3
deviation: avoiding a self-inflicted regression against this plan's own acceptance
criteria).

**Does `phase.complete "08.1"` (the orchestrator's next step) re-break this?**
Traced through `sdk/src/query/phase-lifecycle.ts`'s `phaseComplete` handler directly
against this repo's actual `ROADMAP.md`:

- It does **not** touch the STATE.md body `Progress:` field at all — no such
  regex/replacement exists anywhere in that handler (grepped the full function body
  for `'Progress'`; zero matches). **The 78% fix is safe from this specific call.**
- Its frontmatter `percent` recompute (line ~1731-1737) depends on
  `derivedCompletedPhases`/`derivedTotalPhases`, themselves parsed from ROADMAP.md's
  progress table via two regexes that require a `| Phase | Plans | Status |
  Completed |` header and single-token phase-name cells. **This project's actual
  table header reads `| Phase | Plans Complete | Status | Completed |`** (extra word)
  and its phase-name cells contain spaces (`| 1. Corrected Ground Truth | ... |`) —
  confirmed by executing both regexes against the live file with `node -e`: both
  return zero matches. So `derivedCompletedPhases`/`derivedTotalPhases` are `null`,
  the handler falls back to the **existing, unchanged** frontmatter values (7, 9),
  and recomputes the same `78%` from the same inputs — a no-op, not a break.
- Its `updatePerformanceMetricsSection` **will** increment STATE.md's body
  `Total plans completed: 76` line by Phase 8.1's own `summaryCount` (5, once this
  plan's own summary exists), producing `81` — this is **correct** (76 covers phases
  1-8; +5 for 8.1 = 81, the true final total) and is the intended, by-design
  transition documented above under "Total plans completed" — not a D-5 regression,
  since D-5's own assertion for this line already anticipates it will read `76`
  **only until `phase.complete` runs** (`08.1-d-checklist.sh`'s own header comment:
  "D-4 and D-5 ... belong to plan 08.1-02 ... expected to stay FAIL until that plan
  lands" establishes the same "this value is a snapshot, not a permanent literal"
  precedent this finding extends).

**Plain answer:** No, `phase.complete "08.1"` cannot re-break D-5's `] 78%`
sub-assertion — traced to the specific code path and confirmed by direct execution of
its parsing regexes against this repo's live ROADMAP.md, not merely inferred. It
*will* change `Total plans completed: 76` to `81`, which is the correct, intended
value, not a regression. The one durable risk that remains outside this plan's
control: `total_phases`/`completed_phases`/`percent` in STATE.md's frontmatter will
stay stuck at `9`/`7`/`78` even after Phase 8.1 truly completes across ROADMAP.md
(which will correctly show 8/9 `Complete` rows), because of the header/cell-format
mismatch above — a latent SDK-parsing limitation of this repository's ROADMAP table
layout, pre-existing and out of this docs-only plan's scope to fix (it would require
either patching the externally-installed SDK package or reformatting ROADMAP's
progress-table header, neither requested nor safe to do unreviewed here). Recorded
as a finding for a future quick task, not silently absorbed.
