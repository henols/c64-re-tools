## Summary

This phase closes two kinds of debt the `/gsd-audit-milestone` run recorded on 2026-08-19 in
`.planning/v0.2.0-MILESTONE-AUDIT.md`: one unwitnessed claim (the install-to-RAM-capture
walkthrough) and seven stale planning documents. Critically, **one of the audit's own two
headline findings has already been resolved** between the audit landing and this research
session: commit `4306338` ("update validation strategy after Nyquist audit") already flipped
`08-VALIDATION.md` to `status: audited` / `nyquist_compliant: true`. Success criterion 2 is
**already satisfied** — the planner should verify this rather than re-plan work for it.

Criterion 3 (the seven D-1..D-7 documentation-drift items) is entirely mechanical: every one
was independently re-derived and confirmed against the live repo state during this research
session (exact line numbers below), and two of the seven-item's target files (`ROADMAP.md`,
`STATE.md`) already carry an **uncommitted, partial fix** from whatever process inserted Phase
8.1 into the roadmap. That partial fix correctly added the Phase 8.1 section and milestone
heading, but left D-4 (Phase 7's stale `[ ]`/"NOT complete" text) completely untouched, and its
D-5 fix for STATE.md's progress numbers, while *not wrong*, is not what the audit's original
prose literally asked for — because the audit's suggested fix ("sync to 7/7, 100%") was written
**before** Phase 8.1 existed. Forcing 100% now would introduce a *new* false claim (that the
milestone is done). The correct target is "7 of 9 phases complete, Phase 8.1 in flight" — which
is what the uncommitted `percent: 78` is already close to, except the STATE.md body text (an
ASCII progress bar reading 71%) still contradicts its own frontmatter (`percent: 78`).

Criterion 1 (the human walkthrough) is a genuinely different kind of problem, and the research
here surfaces a finding **not named anywhere in the audit or the ROADMAP notes**: neither of
the two documented install routes currently gives a fresh installer the feature under test.
`origin/main` on GitHub is 16 commits behind this checkout's `HEAD` (missing Phases 7, 8, and
the entire audit-response work) and the last npm publish (`@henols/vice-mcp@0.1.12`,
2026-08-17T15:16Z) predates Phase 7 and Phase 8 entirely. A person following either README
route *today* would install a build with no stock backend at all — they could not set
`VICE_BACKEND=stock` because the switch does not exist yet at that install point. This must be
surfaced to the user before criterion 1 can be executed honestly; see Open Questions.

**Primary recommendation:** Treat this phase as two independent, parallel tracks exactly as the
ROADMAP notes already say. Track A (documentation drift, criterion 3, mechanical, plus verifying
criterion 2 is already closed) can be planned and executed immediately with no external
dependency. Track B (criterion 1, the walkthrough) has a hard prerequisite — getting the tested
code reachable via one of the two documented install routes — that is a **push/publish
decision**, not an engineering task, and should be raised to the user as an explicit
checkpoint before the walkthrough itself is attempted.

### Anti-Patterns to Avoid

- **Blindly replacing every "two" with "three" in ROADMAP.md.** Several "two" occurrences are
  unrelated (Phase 2's "two known defects" in the vendored protocol client, Phase 7's "the last
  two" skill-called tools which are `vice_cycles_stopwatch`/`vice_run_until`, not the impossible
  tools). Only fix occurrences that are actually about the SID/keyboard-matrix/keyboard-restore
  impossible-tool count.
- **Fixing the "two"→"three" wording without fixing the arithmetic it feeds.** `ROADMAP.md:37-38`
  and `:350`, and `REQUIREMENTS.md:269-280`, all derive a total tools-called-by-skills figure
  (**28**) as `16 (native) + 10 (buildable) + 2 (impossible)`. With the corrected count of three
  impossible tools, the total is **29**, not 28 — `STATE.md` already uses the corrected "29
  tools... 3 impossible" framing (see STATE.md's own current text) and should be the template
  the other two files are brought into line with. Fixing only the "two"→"three" word while
  leaving "28" unchanged creates a **new**, self-inconsistent document.
- **Forcing STATE.md to "7/7, 100%" per the audit's literal fix text.** That text was written
  before Phase 8.1 existed. Since 8.1 is now a real, not-yet-started phase, "100%" would be a
  fresh false claim. Use the actual current phase count (7 of 9 total phase slots complete,
  counting the cut Phase 6 and the not-yet-started 8.1) instead — or whatever convention this
  project's own `gsd-tools.cjs` state machinery computes; do not hand-pick a number that
  contradicts it.
- **Treating "capabilities" and "tools" as interchangeable when fixing D-6.** The project loses
  two *hardware capabilities* (SID register read-back, raw keyboard-matrix/RESTORE control) but
  three *tools* map onto them (`vice_sid_get_state`; `vice_keyboard_matrix` and
  `vice_keyboard_restore`, both under the keyboard-hardware capability). `ROADMAP.md:22`'s "the
  fork's two exclusive capabilities" may still be defensible as a *capability* count — do not
  reflexively bump it to three without checking which noun ("capabilities" vs "tools") the
  sentence actually uses.
- **Rewriting the historical Phase 5/Phase 8 success-criteria text to retroactively say
  "three."** Those criteria are dated records of what was believed true when the phase was
  planned; the project's own convention (see Pattern 2) is to append a correction, not overwrite
  history.

## Common Pitfalls

### Pitfall 1: Assuming the audit's tech_debt list is still 100% current

**What goes wrong:** Planning fixes for "08-VALIDATION.md is draft/nyquist_compliant:false"
(criterion 2) when it has already been fixed.
**Why it happens:** The audit report (`.planning/v0.2.0-MILESTONE-AUDIT.md`, committed
`976839f`, 2026-08-19T00:12Z) was itself superseded four hours later by commit `4306338`
(2026-08-19T09:34:55Z), which updated `08-VALIDATION.md` to `status: audited`,
`nyquist_compliant: true`, `manual_only_open: 1`. The audit report's own frontmatter
(`nyquist.partial_phases: [8]`) is now stale relative to the file it describes.
**How to avoid:** Read `08-VALIDATION.md` directly (not just the audit report) before planning
any task against criterion 2. This research confirms it is already satisfied; the plan should
include a verification-only task (re-read the frontmatter, confirm no regression), not a
content-authoring task.
**Warning signs:** A plan that includes a task titled something like "flip 08-VALIDATION.md to
audited" is planning against stale information.

### Pitfall 2: Fixing D-6's wording without fixing its arithmetic

See "Anti-Patterns to Avoid" above — this is the single easiest way to introduce brand-new
drift while closing old drift. `STATE.md` already has the corrected phrasing and is the
reference template.

### Pitfall 3: Treating the walkthrough as blocked-and-therefore-skippable

**What goes wrong:** Concluding that because a full human/live-agent session "was not available"
in the Phase 8 executor run, it remains unavailable now, and marking Test 1 `skipped` or leaving
it `pending` again.
**Why it happens:** The blocker recorded in `08-HUMAN-UAT.md` ("no human tester and no second
live agent session were available to this executor run") describes a **prior execution
context**, not a structural impossibility. This research confirms: `claude -p` (headless,
non-interactive mode) exists in this environment, `npm` has live registry access, ACME is
installed and working, and `/usr/bin/x64sc` is a genuine unpatched stock VICE 3.9 binary
(confirmed: `x64sc (VICE 3.9)`, shadowed on `PATH` by the fork build at `/usr/local/bin/x64sc` —
consistent with the standing memory note).
**How to avoid:** The plan should attempt a concrete procedure (see Open Questions) rather than
re-recording `pending`. Criterion 1's own wording — "recorded as observed — pass or fail — not
as pending" — forbids simply carrying the old `pending` status forward without a genuine attempt
or an explicit, reasoned decision recorded in its place.
**Warning signs:** A plan whose only action for criterion 1 is "re-confirm still pending, get
user approval to close on that basis (again)" — this repeats Phase 8's own resolution and does
not satisfy the ROADMAP's explicit "not as pending" requirement.

### Pitfall 4: Testing against a stale install artifact and calling it proof

**What goes wrong:** Running `npx @henols/c64-re-tools` today and having it silently succeed
(the installer itself works fine) while never actually reaching the `VICE_BACKEND=stock` code
path, then recording the walkthrough as a pass.
**Why it happens:** `npx @henols/c64-re-tools` installs the CURRENTLY PUBLISHED
`@henols/vice-mcp@0.1.12` (published 2026-08-17T15:16:19Z), which predates Phase 7 (completed
2026-08-18) and Phase 8 (completed 2026-08-18). The installer would run without error; the user
would simply never be able to select or exercise the stock backend at all, and a naive "it
installed and the tools worked" observation would be **testing v0.1.x, not v0.2.0**.
**How to avoid:** Before running the walkthrough, confirm which artifact will actually be
exercised. Either wait for the milestone to be pushed/published, or use a route that reaches
this checkout's current `HEAD` (see Open Questions for options), and record explicitly in
`08-HUMAN-UAT.md` which artifact (commit sha or npm version) was actually tested.
**Warning signs:** A recorded "pass" for Test 1 that does not name a specific commit sha or npm
version as the tested artifact.
