## 2. Capture target

**Blocked — FINDING-A1.** The unmodified scaffold does not assemble in this environment.

`cp .claude/skills/acme-build/template.a /tmp/gsd-08.1-walkthrough/artifact/walkthrough.a`
succeeded (byte-identical copy, unmodified). Then:

```
$ node .claude/skills/acme-build/scripts/acme.mjs build /tmp/gsd-08.1-walkthrough/artifact/walkthrough.a
/tmp/gsd-08.1-walkthrough/artifact/walkthrough.a:7: error: "ACME" environment variable not found.
/tmp/gsd-08.1-walkthrough/artifact/walkthrough.a:8: error: "ACME" environment variable not found.
/tmp/gsd-08.1-walkthrough/artifact/walkthrough.a:9: error: "ACME" environment variable not found.
  for <...> includes, set $ACME to the directory holding cbm/c64/vic.a (looked in: /usr/local/share/acme, /usr/share/acme, /usr/lib/acme, /home/henrik/.acme)
build FAILED (3 error(s))
```

**Root cause, confirmed by direct filesystem search:** `acme` on this machine is a bare
binary at `/home/henrik/.local/bin/acme` (ELF, stripped, mtime 2026-08-17) with **no**
accompanying `cbm/c64/*.a` library anywhere on the filesystem. `find / -iname vic.a` and
`find / -type d -iname cbm` both returned nothing. None of `acme-build/scripts/acme.mjs`'s
four probed locations (`$ACME`, `/usr/local/share/acme`, `/usr/share/acme`,
`/usr/lib/acme`, `~/.acme`) exist. `dpkg -l acme` confirms the package was never installed
via `apt` — only the bare binary was placed on `$PATH`. `apt-cache policy acme` shows a
candidate (`1:0.97~svn20211115+ds-2`) is available from the configured repositories — the
same package name `.github/workflows/ci.yml`'s "Install ACME cross-assembler" step already
installs via `sudo apt-get install -y acme` — but `sudo -n true` confirms this session has
**no passwordless sudo**, so installing it is not something this executor can do silently.

This is a genuine environment gap in `acme-build/SKILL.md`'s own claim ("Verified live in
this container on 2026-08-04: the library resolves to `/usr/local/share/acme`") — that
claim no longer holds on this machine as of this session. It is not a defect in the
scaffold, the driver script, or this plan's procedure; it is a missing system dependency.

**Per this task's own explicit instruction, no hand-edit of the template was attempted**,
and per the executor's standing deviation rules, installing a package via a package
manager (`apt-get install acme`) is excluded from autonomous auto-fix — it requires an
explicit human decision (Rule 3's package-install exclusion), which this document defers
to plan 08.1-04 / the user rather than silently working around.

**Consequence for this plan:** `walkthrough.prg` and `walkthrough.d64` were not produced.
Task 3 (the scratch project) proceeds independently below, since it does not itself
require the capture target to exist — but its release registry entry necessarily records
this as an open dependency rather than a working `disk_image`, and the walkthrough
(plan 08.1-04) cannot exercise `c64-ram-capture`'s disk-first procedure against a real
image until either (a) `sudo apt-get install -y acme` is run once on this machine, or
(b) an equivalent ACME library is supplied by hand at `$ACME`.

**FINDING-A1** — `acme-build`'s SKILL.md documents a verified-working library probe
location that no longer holds on this machine; the skill has no self-check that surfaces
"binary present, library absent" as a distinct, actionable error from "ACME not installed
at all" (both currently print the same four-location miss message). A one-line addition
distinguishing "binary found, no library" from "no binary" would have caught this without
a full build attempt.

### FINDING-A1, corrected and widened (human decision, recorded before this correction)

A human reviewed the blocker above and made an authoritative correction to its scope,
which supersedes the "Consequence for this plan" and "(a) `sudo apt-get install -y acme`"
remedy suggested above — **that remedy is wrong and would not have worked**. The original
finding is not deleted; it stands as the accurate record of what this session observed.
What follows widens it with evidence the human directed this executor to gather and
record:

**`sudo apt-get install -y acme` would NOT have fixed this.** Verified directly: the
Debian trixie candidate package (`apt-cache policy acme` → `1:0.97~svn20211115+ds-2`) was
fetched with `apt-get download acme` and extracted with `dpkg-deb -x` (no `sudo`, no
system install performed — a read-only inspection). Its complete file list is:

```
usr/bin/acme
usr/bin/toacme
usr/share/doc/acme/{65816.txt,AddrModes.txt.gz,AllPOs.txt.gz,changelog*.gz,copyright,
  Errors.txt.gz,examples/**,Example.txt,Floats.txt,Help.txt.gz,Illegals.txt.gz,Lib.txt,
  QuickRef.txt.gz,Source.txt,Upgrade.txt.gz}
usr/share/lintian/overrides/acme
usr/share/man/man1/acme.1.gz
```

**No `cbm/c64/*.a` standard library anywhere in the package.** `usr/share/doc/acme/examples/`
contains sample sources (`c64misc.a`, `c64doubledabble.a`, `ddrv.a`, etc.) but not the
`cbm/c64/vic.a`, `cbm/c64/kernal.a`, or `cbm/c64/cia1.a` files `acme-build/template.a`
`!source`s. Installing this package would place a *second* bare `acme` binary on `$PATH`
(shadowing or shadowed by `/home/henrik/.local/bin/acme`, itself already a working,
unstripped-of-function ACME 0.97 "Zem" build) and would change nothing about the missing
library.

**Therefore CI has the identical gap, silently.** `.github/workflows/ci.yml:58` runs this
exact command (`sudo apt-get install -y acme`) and lines 59-61 only check that the binary
exists and prints a version banner — it never assembles anything against
`.claude/skills/acme-build/template.a` or any file that `!source`s the `cbm/c64/*`
library. `disasm-roundtrip.test.ts` (the test that does exercise ACME in CI) does not use
the scaffold either. CI stays green today for the same reason this session's `acme
--version` succeeds while `template.a` fails to build: presence of the binary was
verified, presence of the library never was.

**Bare ACME itself is not broken.** Verified live: `~/.local/bin/acme -o
/tmp/acme-probe.prg /tmp/acme-probe.a` (a one-line, library-free `.a`) assembles
successfully. The defect is scoped precisely to "any source that `!source`s the
`cbm/c64/*` library, on a machine provisioned by the currently-documented routes (bare
binary on `$PATH`, or the `apt` package above)" — not to ACME as a tool, and not to this
plan's procedure.

**Corrected scope of FINDING-A1:** `acme-build`'s scaffold route (`template.a` plus its
library `!source`s) is broken on *any* machine provisioned the documented way, including
GitHub Actions' own CI runner — not merely this one development machine. The original
finding undersold the problem as a local environment gap; it is a systemic gap between
what `acme-build/SKILL.md` promises ("Verified live in this container on 2026-08-04") and
what either provisioning route actually delivers.

**Human decision (authoritative):** installing a third-party ACME standard library was
explicitly rejected as needlessly invasive for this walkthrough's purpose. Criterion 1
tests the `c64-ram-capture` skill, not `acme-build` — the capture target is incidental
scaffolding to that end. The decision: produce the capture target from a small,
self-contained, library-free `.a` instead of `template.a`, hand-rolling the few hardware
addresses needed (`$d020`, `$d021`, `$ffd2`) as local constants. This is recorded as an
explicit, named deviation below, not as a silent workaround.

### Deviation: capture target built from a library-free source, not `template.a`

- **Documented route:** copy `.claude/skills/acme-build/template.a` unmodified and build
  it with `acme.mjs`. This is what Task 2 originally attempted (see the blocked attempt
  above) and is the scaffold `acme-build/SKILL.md` itself documents.
- **Why it could not be used:** FINDING-A1 (corrected/widened above) — the scaffold
  `!source`s a `cbm/c64/*.a` library that does not exist on this machine, is not supplied
  by the `apt` package that would provision it, and is not supplied by CI's provisioning
  either.
- **What was done instead:** a new file,
  `/tmp/gsd-08.1-walkthrough/artifact/walkthrough.a`, was authored from scratch with the
  same structural shape as `template.a` (6510 CPU, `* = $0801`, a computed-digit BASIC
  `SYS` stub, a border/background colour change, a KERNAL `CHROUT` print loop) but with
  the three `!source` lines removed and `vic_cborder`/`vic_cbg`/`k_chrout` declared as
  plain local constants (`$d020`/`$d021`/`$ffd2`) instead of library symbols. It was built
  with the skill's own driver, unmodified: `node .claude/skills/acme-build/scripts/acme.mjs
  build /tmp/gsd-08.1-walkthrough/artifact/walkthrough.a`.
- **Why this does not weaken criterion 1's evidence:** the skill under test in
  `08-HUMAN-UAT.md` Test 1 is `c64-ram-capture`, not `acme-build`. `c64-ram-capture`'s
  documented procedure (`d64-parse directory` → `vice_disk_attach` → `vice_autostart` →
  RAM capture) operates on the resulting `.prg`/`.d64` identically regardless of whether
  the source that produced them used the `acme-build` scaffold's library or hand-rolled
  constants — the capture skill never inspects the assembly source, only the built disk
  image and the running machine's RAM. `acme-build`'s own defect is real and is tracked
  above as FINDING-A1 (corrected/widened); it is a finding about a *different* skill than
  the one plan 08.1-04 exercises, and is not fixed, hidden, or worked around by this
  substitution.
