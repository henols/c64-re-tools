**FINDING-C3 — `resolvedBinaryPath` is not trustworthy in this broker/pool architecture, and
was avoided as the source of truth for binary identity here.** The field above reads
`/usr/local/bin/x64sc` — the FORK build's install path — even though `backend` correctly says

source of truth used by this plan instead is the broker's own launch record and the live process

## 4. Failure

**Failing command(s):**
`mcp__vice__vice_autostart {path:"/tmp/gsd-08.1-walkthrough/artifact/walkthrough.d64", run:true, index:0}`,
and, per the SKILL's own documented fallback which was also tried and hit the identical block:
`mcp__vice__vice_keyboard_type "LOAD\"*\",8,1\n"` + `mcp__vice__vice_execution_run` +
`mcp__vice__vice_keyboard_type "RUN\n"` + `mcp__vice__vice_execution_run`.

**Runtime symptom (verbatim, from the driving session's report):** screen memory at `$0400`
after autostart shows the auto-typed `LOAD"*",8,1` followed by `SEARCHING FOR *` and
`?DEVICE NOT PRESENT ERROR`; `vice_memory_read $0801 size=32` returned the reset-pattern
`0000ffffff00000000ffffffff00000000ffffffff00000000ffffffff000000` (no program loaded).

**Root cause — corrected and confirmed by this executor's own follow-up investigation
(the driving session's own diagnosis, quoted first, was wrong; corrected below per this
phase's own "correct in the open, do not silently erase" convention — see 08.1-03-SUMMARY.md's
FINDING-A1 for the precedent):**

> Driving session's own words (verbatim, now superseded): "Found the root cause: VICE was
> launched without 1541 drive ROMs. That's why LOAD hits `?DEVICE NOT PRESENT ERROR`."

That diagnosis does not hold up. The actual launch log for the leased instance
(`.vice-supervisor/6604/logs/x64sc-1787135071821-e3.log`) shows the 1541 ROM loaded
successfully:

```
DriveROM: Error - 1540 ROM image not found. Hardware-level 1540 emulation is not available.
Loading system file `/home/henrik/.local/share/vice/DRIVES/dos1541-325302-01+901229-05.bin'.
DriveROM: Error - 1541-II ROM image not found. Hardware-level 1541-II emulation is not available.
DriveROM: Error - 1570 ROM image not found. Hardware-level 1570 emulation is not available.
... (1581, 2000, 4000, CMDHD, 2031, 2040, 3040, 4040, 1001/8050/8250, D9090/9060 — none needed)
Drive: Finished loading ROM images.
```

There is no `1541 ROM image not found` line — only the unrelated drive models this walkthrough
never asked for. The `dos1541-...bin` file the actual 1541 needs loaded with no error, from
`/home/henrik/.local/share/vice/DRIVES/`. **Drive ROMs were present and loaded correctly.**

**The real root cause, confirmed live by this executor (read-only diagnosis, no source file
touched):** with no active binary-monitor client connected (the headless session's own MCP
server process had already exited), this executor connected briefly, read-only, to the
already-running broker-managed instance's **text monitor** (`-remotemonitor`, a *separate*
port from the binary monitor the walkthrough used, so this did not contend with or disturb
the single-client binary-monitor constraint) and queried the live resource state directly:

```
$ (raw TCP to remotemonitor port)
resourceget "Drive8Type"          -> Drive8Type=0
resourceget "Drive8TrueEmulation" -> Drive8TrueEmulation=1
resourceget "FileSystemDevice8"   -> FileSystemDevice8=1
```

**`Drive8Type=0` means NONE — no drive model is configured on unit 8 at all**, regardless of
ROM presence or true-drive-emulation being on. From the emulated machine's own point of view,
there genuinely is no drive answering the IEC bus at unit 8, so `?DEVICE NOT PRESENT ERROR` is
the textbook-correct KERNAL response — not a wedge, not a missing ROM, not a bad disk image.
This matches this plan's own standing constraint almost exactly (`CLAUDE.md`: "the real gate is
`Drive8TrueEmulation` plus a non-zero `Drive8Type`"), one level further: with `Drive8Type=0`,
true-emulation being on is moot.

**Confirmed as the actual, sufficient fix, live, standalone (no broker involved, a disposable
probe instance on scratch ports, killed immediately after):**

```
$ /usr/bin/x64sc -default -binarymonitor -binarymonitoraddress ip4://127.0.0.1:17602 \
    -remotemonitor -remotemonitoraddress ip4://127.0.0.1:17603 \
    -drive8type 1541 -8 /tmp/gsd-08.1-walkthrough/artifact/walkthrough.d64
(remotemonitor) resourceget "Drive8Type"   -> Drive8Type=1541
(remotemonitor) load "walkthru" 8          -> Loading 'walkthru' from 0801 to 084B (004B bytes)
```

75 code bytes (`0801`-`084B` inclusive), exactly matching plan 08.1-03's own build record
("75 bytes of code"). With `-drive8type 1541` set at launch, unit 8 answers and the load
succeeds immediately. **This is airtight confirmation of the root cause.**

**Why neither `vice_disk_attach` nor `vice_autostart` can fix this from the MCP tool surface
alone:** read directly from source (`stock-machine.ts`), both handlers construct their AUTOSTART
(`0xdd`) wire request and send it — **neither ever issues a resource-set for `Drive8Type`, and
the stock backend's tool manifest exposes no `RESOURCE_SET`-equivalent tool at all** (the full
37-tool stock surface this session's own smoke test enumerated has no `vice_resource_set`).
An agent following `c64-ram-capture/SKILL.md`'s documented procedure, using only the tools it
names, has **no way to correct this from within the tool surface** — it is not a step the skill
omitted; it is a gap the tool surface itself does not cover, upstream of the skill entirely.

**Which document/code would have had to say something different:** this is a **code** gap, not
primarily a documentation gap — `.claude/mcp/vice/broker-launch.mts`'s `buildViceArgs()` (stock
branch, around line 173) constructs `["-binarymonitor", "-binarymonitoraddress", ...]` and
optionally `-remotemonitor`/`-remotemonitoraddress`, but never `-drive8type`/`-drive8truedrive`
or any other drive-configuring flag, so every stock instance this broker ever launches boots
with `Drive8Type=0` by construction. Until that is fixed (a follow-up finding, not this plan's
job to fix — Rule 4 territory, an architectural launch-argument change, explicitly out of this
plan's scope which forbids editing source to force a pass), `README.md`'s "Installing VICE, and
choosing a backend" section and `c64-ram-capture/SKILL.md`'s "Boot a disk" section would each
need a stated manual workaround (e.g., "before attaching, set `Drive8Type` to `1541` over the
text monitor — no MCP tool does this for you on stock") for a human to succeed where this
agent session did not.

## 5. Findings

**FINDING-C1 (primary, load-bearing).** Stock VICE launched by this project's own broker boots
with `Drive8Type=0` (NONE) because `broker-launch.mts`'s `buildViceArgs()` never sets any drive
configuration flag for the stock backend, and neither `vice_disk_attach` nor `vice_autostart`
(`stock-machine.ts`) resource-sets `Drive8Type` before sending `AUTOSTART`. There is no
`vice_resource_set`-equivalent tool on the stock MCP surface to work around this from a client.
**This blocks every disk-based `c64-ram-capture` walkthrough against genuine stock VICE
launched through this broker, not just this one.** Confirmed root cause (§4) and confirmed fix
(`-drive8type 1541` at launch, verified live).

**FINDING-C2.** The driving session's own self-reported root cause ("launched without 1541
drive ROMs") was incorrect — the actual launch log shows the 1541 ROM loaded with no error.
Recorded and corrected here, not silently replaced, per this phase's established convention of
correcting findings in the open (see 08.1-03-SUMMARY.md's FINDING-A1 correction for precedent).

**FINDING-C3.** `vice_ping`'s `resolvedBinaryPath` field is unreliable in this broker/on-demand
-pool architecture — it reflects a one-time, static, bare-`x64sc` PATH probe done at MCP-server
process startup (`vice-proxy.ts:192`), independent of whichever binary the broker actually
launches for the leased instance. On this machine it always reads `/usr/local/bin/x64sc` (the
fork) on the stock backend, which is misleading for exactly the kind of binary-identity audit
T-08.1-08 exists to prevent. The broker's own `epoch.json` and live process argv are the
authoritative source and were used instead (§2).

**FINDING-C4.** Neither `README.md`'s backend section nor `c64-ram-capture/SKILL.md`'s
documented "Boot a disk" procedure names any drive-type/true-drive-emulation prerequisite —
both assume attach-then-autostart is sufficient, which this walkthrough disproves for a freshly
launched, unconfigured stock instance.
