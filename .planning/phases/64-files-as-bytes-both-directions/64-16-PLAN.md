The defect, as measured by the planner at HEAD df1272d4:
- `vice-broker.mts`'s `run()` calls `sweepOrphanedStaging({ root: brokerStagingDir() })` at
  :2226, before the control-port bind at :2314.
- `sweepOrphanedStaging()` (`broker-kill.mts` :863-882) removes every directory under the root,
  recursively, with no check of any kind.
- Consider a second broker started while a live broker holds the control port, for example an
  operator starting one by hand beside the systemd unit. That second broker removes every
  staging session directory the live broker's sessions own, before EADDRINUSE tells it that it
  lost. That can include a disk image attached to unit 8 and a file in the middle of a transfer.
- D-07's own argument is that the residue is unambiguous at the moment the next broker starts.
  That holds only for the next broker that actually becomes the broker.

**Mechanism chosen: route (a).** The staging sweep runs only in the process that has won the
control-port bind, and it runs before that process publishes its token. Route (b) is not built.
Route (b) would give each session directory an owner record and check pid liveness before
removing it. Three reasons for route (a):
1. It keeps D-07's startup-only shape and needs no new on-disk record.
2. It makes D-07's premise true by construction. The kernel's refusal to bind one address and
   port twice decides who is "the next broker".
3. The broker's own startup header, at the top of `run()`, already records why this code
   retired a pid-liveness heuristic in favour of the kernel-enforced bind: pids get reused.
   Route (b) would reintroduce that heuristic for staging directories.

**The broker's own sessions are never swept, and the plan proves it.** It does not rely on the
window being short. The executor re-verifies each link against the tree by function name,
because line numbers move.
- Only two code sites create a directory under the staging root:
  - `stageFileSlot()` in broker-transfer.mts (:645-646, `ensureBrokerDir(join(brokerStagingDir(), grantId))`).
  - `receivePayloadToFile()` in broker-transfer.mts (:451, `mkdirSync(dirname(destPath))`),
    where `destPath` is a staged entry's own path.
- `stageFileSlot()` is reached only through `handleStageFile()`. That in turn is reached only
  from broker-control.mts's `stage_file` arm (:1730). The arm sits after the token gate (:1492)
  and requires `ownsTarget()`, meaning a grant this connection won through `acquire`. `acquire`
  is behind the same gate.
- `receivePayloadToFile()` is reached only for a handle present in this process's in-memory
  handle index, and only `stageFileSlot()` fills that index. The `transfer` arm sits ahead of
  the token gate, but it cannot create an entry.
- The token is minted in this process: `newControlToken()` returns 32 random bytes. Its only
  distribution channel is broker.json, which `writeBrokerRecordFile(args.stateDir, record)`
  writes after the bind block. A previous broker's record carries a different token.
- `startControlListenerOnHosts()` attaches the protocol to each host as soon as that host
  binds, so a connection can arrive before `run()` resumes. Nothing that connection can do
  without the token creates a staging directory.
- So no directory under the root can belong to this process's own sessions if the sweep runs
  after the loopback bind is confirmed and before `writeBrokerRecordFile()`. The sweep is
  synchronous (`readdirSync` and `rmSync`), so nothing interleaves while it runs.

**Residual, named and not built.** The singleton is the kernel refusing a second bind of the
same loopback address and port. It does not cover two brokers that share one VICE_BROKER_HOME
while bound to different addresses and ports:
- a broker deliberately configured onto a different control port, or onto an explicit control
  host the first broker did not bind;
- a broker the test suite starts on an ephemeral port (`VICE_BROKER_CONTROL_PORT=0`).

Either one wins its own bind and sweeps the shared staging root. `vice-broker.mts:2311` already
states this scope limit for the singleton itself. The code comment at the new call site states

The configuration that is actually reachable on this host is the suite's. `broker-control.test.ts`

The detector fires on "wire" and "endpoint". Both words refer to this project's own broker
protocol. This plan integrates no external API, SDK or service: it moves one call in the
broker's startup and adds tests that spawn the broker itself. The seal-time gate reads only the
phase's `COVERAGE.md`, and that file does not exist. The orchestrator scoped this planning

<assumption_delta_decision>
The detector fired with signal "second" (pluralization). This gap really is about a second
broker process, so the question was answered on the merits.
- Primary noun: the owner of a staging session directory. Today that is implicitly "the one
  broker that holds this machine's control port". The gap shows that a second broker process
  can exist at the same moment.
- Decision: no-change to the identity model. The singleton broker stays the owner. The one
  destructive consumer of that assumption, the startup sweep, moves inside the region where
  the kernel enforces the singleton.
- Why not promote (route b, per-directory owner records): it would bring back the pid-reuse
  heuristic that `run()`'s startup header records retiring. It would also protect staging in
  only one configuration, two brokers deliberately sharing a home on different ports or hosts.
  In that configuration the second broker's unconditional pre-bind reap already voids the first
  broker's instances.
- Accepted debt: that shared-home, different-bind configuration. A promote would be forced if a
  later phase makes more than one broker per VICE_BROKER_HOME a supported topology.
- Invariant test: truth 1's test is the invariant. It fails the moment the sweep moves back
  ahead of the bind.

The detector's other signal, "optional", comes from the phase's own roadmap note "Backpressure
is not optional" and is not a transition this plan introduces.
</assumption_delta_decision>
