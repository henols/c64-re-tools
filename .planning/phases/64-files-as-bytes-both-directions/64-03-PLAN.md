<objective>
Give the broker a staging model: it mints the handle, it chooses the path, it
supersedes a slot on reuse, and it deletes the whole directory when the session's
connection closes.

Purpose: `XFER-04` says the broker chooses its own staging paths and a client never
supplies one; `XFER-07`'s first half says staged files are removed when their
session closes. D-06 makes "gone when the session closes" one recursive delete of
one directory rather than per-file bookkeeping — far harder to get wrong — and D-05
keys a slot so staged bytes are bounded by (slots x cap) rather than
(uploads x cap).

Output: the staging directory layout and handle minting in `broker-transfer.mts`,
the staging state map and the two callbacks wired in `vice-broker.mts`, and the
session-close cleanup on the paths that already reclaim a session.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client-supplied slot string → broker filesystem | A caller-chosen slot name used to key staging; it must never reach a path |
| presented handle → staged file | An opaque token from an unauthenticated connection resolving to a real file on the broker's disk |
| uploaded bytes → broker's own disk | Untrusted bytes written under the broker's machine-level root |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-64-12 | Tampering / Elevation of Privilege | `stageFileSlot()` — a slot string carrying a separator, a traversal segment or a NUL byte escaping the staging root | high | mitigate | The slot is sanitised with an allow-list and REFUSED on failure, never rewritten; and the staged file's own name is derived from the minted handle, so no client-supplied text reaches the filename at all. |
