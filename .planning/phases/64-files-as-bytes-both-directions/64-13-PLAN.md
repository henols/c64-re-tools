<objective>
Close G-64-3: vice_disk_attach, vice_snapshot_load and vice_autostart intermittently return
binary monitor error 0x8f because each sends AUTOSTART or UNDUMP naming a staged file the
broker has not yet published. defaultTransferFile() resolves an upload when the CLIENT's own
pipeline into the transfer socket finishes; the broker still has to drain the socket, close
the temp file, verify the digest and rename the file into place, and it never says when it
has. On a same-host broker the relayed command wins that race 37-67% of the time (measured
20 failures in 30 calls on the unmodified code; 0 in 30 once the send waited for the file).

The fix is the reply the transfer protocol already named and never sent: the broker writes
`{ kind: "transfer_complete", byteLength, sha256 }` after the rename (64-02's wire vocabulary),
and the client resolves an upload only on it. It rides the same short-lived transfer
connection, authorised by the same handle (D-01), and it is one JSON reply line — no new
envelope (D-02). Streaming through the hashing Transform is unchanged (D-04); the echoed
digest is the client's end-to-end confirmation that the broker published exactly what it was
sent (D-11, XFER-06).

Same fault class as G-64-4 (plan 64-12), different seam, no shared code: a separate plan,
after 64-12 because the two share `vice-broker.mts`, `broker-endpoint.ts`, `stock-handler.ts`
and the compiled `resources/vice-broker.mjs`.

Purpose: the four migrated tools succeed on every call, which is XFER-08's own claim.

Output: the upload acknowledgement on both sides; regression tests whose broker publishes
late and whose stub emulator opens the file at once; truthful 0x8f text.
</objective>
