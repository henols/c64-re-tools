# Phase 64: Files as Bytes, Both Directions Verification Report

**Phase Goal:** The four file-carrying tools work with no shared filesystem
between client and broker at all. Bytes cross the socket; the client writes
only under its own `.c64-re-tools/`; the broker chooses and owns every path
on its own side; neither ever names a path the other must be able to open.

**Verified:** 2026-09-24
**Status:** gaps_found
**Re-verification:** Yes — round 3, after gap-closure plan 64-15 (G-64-5,
CR-01 from the round-2 review).

## What changed since the previous verification round

The previous round (2026-09-24, round 2) scored 7/8 truths verified and left
one gap open: **G-64-5** (CR-01 in the round-2 review) — three of
`receivePayloadToFile()`'s caught-fault branches in `broker-transfer.mts`
built the client-facing `wireReason` from a real filesystem error's raw
`.message`, which Node embeds the broker's absolute staging paths into
verbatim. Plan **64-15** closed this: `formatPathFreeFault()` is now the one
builder of wire text for a caught transfer fault (a fixed phrase plus at
most a validated errno token), a stricter `ReceivePayloadToFileResult` type
makes path-free wire text mandatory on every failure branch, and five new
tests (plus one converted from a synthetic to a real fault) prove the fix
against genuine `renameSync`/`createWriteStream`/hook filesystem failures —
not the synthetic, already-path-free rejection the round-2 gap named as the
detection hole.

This verifier independently re-confirmed the closure against source (not
from `64-15-SUMMARY.md`'s own claims): read every changed line of
`broker-transfer.mts` and `vice-broker.mts`, confirmed zero remaining
`${message}` interpolations into `wireReason` and zero remaining
`wireReason ??` fallbacks, and independently re-ran the cited test files —
129/129 pass across the six directly-relevant files, and 4274/4265/0/9 on
the full automated gate (matching the orchestrator's own measurement
exactly). `npm run typecheck` exits 0.

**However**, this round's own code review (`64-REVIEW.md`, which reviewed
the seven 64-15-changed files at *full-file*, not diff-only, depth) found a
second, unrelated critical finding in the same staging/transfer subsystem
this phase owns: `sweepOrphanedStaging()`, called unconditionally by
`vice-broker.mts`'s `run()` before the singleton control-port bind is even
decided, has no liveness check at all and can delete a live broker's active
staging directories — including a disk image a running emulator has
attached — if a second broker process races the first and loses. This
defect predates plan 64-15 (proven by diff: the call site and the swept
function are both untouched by 64-15's own change) and was not caught by
round 1 or round 2 verification. It is not a regression 64-15 introduced,
but it is a genuine, independently-confirmed, previously-undisclosed
violation of this phase's own Success Criterion 5 / XFER-07 ("a sweep
removes those left behind by a crash" — not a live session). This is what
keeps the phase at `gaps_found` rather than `passed`.

A second review finding, CR-02 (an unguarded `mkdirSync()` inside
`receivePayloadToFile()` whose only caller has no `.catch()`, so a real
fault there is an unhandled rejection that this codebase documents as
killing the whole VICE pool), is **not** treated as a new blocking gap in
this verification: it was already disclosed — named in 64-15-PLAN.md's own
"Known residuals" section, explicitly scoped out of 64-15's own work with
stated reasoning, and recorded in `.planning/WINDOWS.md` entry 77 (status
`open`) before this review even ran. See "Anti-Patterns Found" below for
the independent confirmation and severity discussion.
