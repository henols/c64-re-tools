<objective>
Put the two new control-plane operations on the wire and give the client the one
authoritative way to dial a transfer connection: a `stage_file` op on the
grant-holding connection that mints an opaque handle and chooses a broker-side
staging path, and a `transfer` op on a fresh short-lived connection that presents
that handle and nothing else.

Purpose: D-01 resolves a real contradiction between `REQUIREMENTS.md` decision 6
(short-lived stateless connections carry files) and the ROADMAP's Phase 64
cross-cutting constraint (a file-transfer op runs through the same
connection-holds-grant check the recycle path uses). This plan is where that split
becomes wire vocabulary — ownership checked where the command is issued, payload
authorised by the handle.

Output: two new `ControlRequestKind` members with their dispatch arms and
callbacks, `dialFileTransfer()` beside `dialMonitorRelay()`, `stageFile()` on the
control session, and the two client-side seams `stock-machine.ts` will use.
</objective>

<wire_vocabulary>
The literal strings this plan puts on the wire. `64-RESEARCH.md`'s Assumption A3
records that no decision picks these; they are chosen here so the three modules
that must agree cannot drift, and every later plan cites this block rather than
re-deciding.

- New `ControlRequestKind` member, TWELFTH: `"stage_file"`.
  Request: `{ op: "stage_file", id, target_id, slot, token }`.
  Reply on success: `{ kind: "file_staged", handle, emulator_filename }`.
  Reply on refusal: `{ kind: "error", code, message }`.
  `slot` is an open-ended string, not a closed union — `"autostart"`, `"disk8"`
  and `"snapshot"` are what this phase sends. It is sanitised broker-side with the
  same allow-list posture `sanitiseSessionLabel()` already applies to a session
  label.

- New `ControlRequestKind` member, THIRTEENTH: `"transfer"`.
  Request: `{ op: "transfer", direction, handle, byteLength, sha256, token }`,
  where `direction` is `"upload"` or `"download"`. `byteLength` and `sha256` are
  present on an upload and absent on a download.
  Reply, upload: `{ kind: "transfer_ready" }`, after which the CLIENT writes
  exactly `byteLength` raw bytes, and the broker then answers
  `{ kind: "transfer_complete", byteLength, sha256 }`.
  Reply, download: `{ kind: "transfer_payload", byteLength, sha256 }` followed
  immediately by exactly `byteLength` raw bytes written by the BROKER.
  Reply on refusal, either direction: `{ kind: "error", code, message }`.

- New hello tag: `TRANSFER_TAG = "file-transfer"`, joining `RELAY_TAG_BINARY` and
  `RELAY_TAG_TEXT` as an open-ended value (62-CONTEXT's specifics note: the tag
  vocabulary stays open-ended so the `anno` stateless call can join later without
  a rewrite).

**`emulator_filename` — read this before assuming it violates D-17.** It is the
absolute broker-side path the EMULATOR must open, and the client's only use for it
is to place it in the `AUTOSTART`/`DUMP`/`UNDUMP` request body, which travels
byte-transparently over the Phase 63 relay to a process running on the broker's own
host. The client never opens it, never stats it and never puts it in a tool result.
This is unavoidable: those three binary-monitor commands each carry a filename
field, the emulator runs on the broker's side, and the relay is byte-transparent by
design, so something must carry the broker's chosen path across. What D-17's
disjoint-roots proof asserts is that no broker-side path appears in any TOOL RESULT
and that the client never successfully opens one — which disjoint roots make
structurally true. **Planner finding, surfaced rather than implemented silently:**
the option wording "no B-side path appears in any tool result or any wire field"
cannot hold literally for the binmon filename field; it is honoured here as "no
B-side path in any tool result, and no client-CHOSEN broker path anywhere". Plan
64-07 asserts exactly that, and records this narrowing in the phase evidence.
</wire_vocabulary>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| transfer connection → broker dispatch | A brand-new, unauthenticated-by-grant connection presenting only a handle |
| control connection → `stage_file` arm | A grant-holding connection asking the broker to allocate storage on its own disk |
| broker reply → client dial | Every field of a reply line is untrusted input from an unknown TCP listener |
