<objective>
Close G-64-5, which is CR-01 in `64-REVIEW.md` and truth #8 in `64-VERIFICATION.md`. This is
NOT the `CR-01` that `STATE.md` carries at `text-protocol.ts:850`. That is a different item,
carried by decision, and this plan does not touch `text-protocol.ts`.

The defect: when an upload's publish failed on a real filesystem error, the broker sent its
own absolute staging paths to the client. `receivePayloadToFile()` in
`src/mcp/vice/broker-transfer.mts` has three caught-fault branches: the receive pipeline
(:353-364), the pre-publish hook (:377-390) and the publish rename (:392-403). Each builds
`wireReason`, the field documented as path-free, from a fixed prefix plus the caught error's
raw message. Node fs errors put both absolute paths in that message. This was MEASURED by the
planner on Node v24.20.0 against the current compiled `resources/broker-transfer.mjs`:
- A temp file that cannot be opened yields `ENAMETOOLONG: name too long, open '<tmp>'`.
- A hook failing on a real fs error yields `ENOENT: ... '<path>'`.
- A rename whose directory vanished yields `ENOENT: ... rename '<tmp>' -> '<dest>'`.
All three landed in `wireReason` with the fixture directory in them.

Plan 64-13 then made the leak reachable:
1. `vice-broker.mts`'s `writeUploadCompletionReply()` (:1179-1192) writes that text as the
   `error` line on the transfer connection. That listener binds the bridge gateways too, so
   the text crosses the container/host boundary.
2. `broker-endpoint.ts`'s `awaitTransferComplete()` (:1248-1255) forwards the text verbatim.
3. `stock-connect.ts`'s `defaultTransferFile()` (:549-550) forwards it again.
4. The handlers put it in the tool's isError text (`stock-machine.ts` :223, :385, :629).

The only test on this path is `stock-machine.test.ts:1338`. It rejects with a synthetic,
path-free message, so it cannot see the leak by construction.

The fix goes at the source, and it is structural rather than three one-line edits:
- One helper, `formatPathFreeFault()`, is the only builder of wire text for a caught transfer
  fault. It is a fixed phrase plus at most a validated errno token.
- A stricter result type makes that text mandatory on every failure.
- The reply writer loses the fallback that would put the full reason on the wire.

The full reason, paths included, stays in the broker's own stderr line (D-15, D-17).

This plan follows the gap's first `missing:` line, "at most an errno code". Two reasons make
carrying a code safe here, although `broker-relay.mts`'s `buildEmulatorUnreachableMessage()`
deliberately carries none:
- That message avoids a code because `stock-handler.ts:113`'s `convertHandshakeError()`
  matches ECONNREFUSED, EHOSTUNREACH and ENETUNREACH and then gives container-bind advice.
- Upload-failure text never passes through that converter, because the handlers return
  isErrorText directly. No filesystem code matches that regex either.

Live check: none, decided on evidence rather than by default.
- Every upload handler returns before it sends AUTOSTART or UNDUMP when the upload is refused
  (`stock-machine.ts` :221-224, :383-386, :627-630, read directly). The emulator never sees
  the failing path.
- The fault is on the broker's own filesystem.
- The production `run()` wiring supplies no pre-publish hook. A deterministic fault against a
  live broker would mean destroying files under the machine-level `~/.c64-re-tools/staging/`
  during an upload.
- The real-listener tests below run the compiled `handleFileTransfer()`, the real
  `awaitTransferComplete()` and the real handler. A live run would add no code path.

Purpose: the phase goal says the two sides never name "a path the other must be able to
open". An upload failure currently names two of them.

Output:
- Path-free wire text on every upload failure.
- A type that keeps it path-free.
- Regression tests that fail against today's tree under real rename, open and hook faults.
- A recorded sweep of the transfer protocol's other failure texts in both directions.
</objective>
