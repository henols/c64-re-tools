<assumption_delta_decision>
**Noun that is now primary:** *how a file crosses the client/broker boundary*.
Before this phase it crossed as a **shared-filesystem path** translated by
`withEmulatorSidePath()`/`hostpath.ts`/`containerpath.ts`. This phase introduces a
second route: **bytes over the socket**.

**Decision: `promote`.** For the four file-carrying tools the socket route
REPLACES the shared-filesystem route outright — it is not added alongside it.
`stock-machine.ts` ends this phase with zero `withEmulatorSidePath()` call sites
and no import of `stock-paths.ts` at all (plan 64-06 task 3). No fallback to the
old route is retained on any failure path.

**Rationale (one line):** the milestone's own exit hypothesis is falsifiable —
"the old boundary seam must be *gone from production code rather than merely
bypassed*, and a retained fallback route falsifies it" (`STATE.md`) — so keeping
both routes live for the migrated tools would defeat the thing this milestone
exists to prove.

**What this decision does NOT promote, and why that is not an add-alongside:**
`stock-paths.ts` the *module* survives this phase, because three other production
modules still reach `hostpath.ts`/`containerpath.ts` for reasons outside this
phase's scope, and `RM-01` (Phase 66) is where the file is deleted. Its survival
is a *deletion-scheduling* fact, not a retained alternative route for these four
tools. The two things this plan moves out of it — the snapshot name rule and the
snapshot path builders — are pure client-side naming that never touched the
host/container seam at all, and they move so `stock-machine.ts` can drop the
import cleanly (D-18's stated mechanism for the convergence metric).

**The two detector signals, checked and refuted:** "second upload" is about D-05's
staging retention policy (supersede on reuse), not a required→optional transition;
"backpressure is not optional" is a negation in the ROADMAP's own cross-cutting
constraint, not an optionality change. Neither is a structural generalization
signal. The real candidate was the one answered above.
</assumption_delta_decision>

- `writeTransferHeader(socket, header)` — serialises the header object to JSON,
  appends a single `0x0a`, writes it. Header fields for this tracer:
  `kind` (a short string naming the frame), `byteLength` (a non-negative safe

- `readTransferHeader(chunk, carry)` — the byte-level terminator search copied
  from `readAttachLine()`: concat carry and chunk, `indexOf(0x0a)`, decode ONLY
  the bytes strictly before the terminator, return `{ header, remainder, overflow }`
  where `remainder` is a raw Buffer that may already hold payload bytes from the
  same TCP segment. Parse the JSON inside try/catch and type-check every field
  before use; a malformed header is a refusal, never a throw.
- `sendPayloadFromFile({ socket, sourcePath, capBytes })` — stats the file, refuses
  before writing anything when the size exceeds the cap (D-11 sender half), writes
  the header, then `await pipeline(createReadStream(sourcePath), transform, socket)`.
  Resolves `{ ok: true, byteLength, sha256 }` or `{ ok: false, reason }`.
- `receivePayloadToFile({ socket, destPath, header, pending, capBytes })` — writes

  own TCP segment); `await pipeline(source, transform, createWriteStream(tmpPath))`;
  compares observed against the header's declared values with `verifyObserved()`;

  returns `{ ok: false, reason }`. The rename is the only way a byte becomes

Extend `transfer-hash.mts` and `broker-transfer.mts` so the cap is enforced
independently at BOTH ends (D-11) and the mid-stream failure paths unwind cleanly
(D-04's named, accepted cost).

Sender half: `sendPayloadFromFile()` stats the source and refuses before a single
payload byte moves when the size exceeds `TRANSFER_MAX_BYTES` — fail fast, nothing
wasted, one round trip. The refusal reason states the observed file size and the
limit as decimal byte counts.

Receiver half: `receivePayloadToFile()` never trusts the header's declared
`byteLength`. Validate it first — a value that is not a non-negative integer, is
not `Number.isSafeInteger`, or exceeds the cap is refused before the pipeline is
constructed, with a reason naming the field and the offending value. Then, as
bytes actually arrive, the same `createHashAndCountTransform()` enforces the cap
from the observed count; when it fires, the error propagates out of `pipeline()`,
the write stream is destroyed, the temp file is removed, and the socket is
destroyed. A sender that lies about its length, or is simply buggy, cannot make
the receiver allocate past the cap.

Add a short-read guard: when the pipeline completes with fewer observed bytes than
the header declared, that is a refusal naming both counts, never a success — an
interrupted transfer must never report completion.

Prove backpressure with a receiver that deliberately stops reading, as the
ROADMAP's own cross-cutting constraint requires: the test server accepts the
connection, reads the header, then pauses its socket and does not resume for a
bounded interval. Assert that the sender's promise has NOT settled while the
receiver is paused (sample it after the interval), that the number of bytes the
receiver has actually observed is far below the payload size, and that the transfer
completes correctly once the receiver resumes. A test that passes because the
sender already buffered everything is the exact false green Pitfall 3 names; the
byte-count sample is what distinguishes the two.

Every new test case uses a fresh `mkdtempSync` fixture directory removed in a

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| transfer socket → receiver | Every byte and every header field arriving on a transfer connection is untrusted input from an unauthenticated peer |
| broker-supplied name → client filesystem | A destination name the other side chose, used to build a path under the client's own per-kind directory |
