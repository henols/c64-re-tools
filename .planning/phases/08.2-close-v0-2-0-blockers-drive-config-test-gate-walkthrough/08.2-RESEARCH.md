### Pattern 1: The single-owner launch-argv function stays synchronous and pure

**What:** `buildViceArgs(port, opts)` is a pure function (no I/O except the one-time
stderr warning) that returns `string[]`. It must remain synchronous and free of
side effects beyond the existing one-time bind-widening warnings.
**When to use:** Any addition to stock's argv (this phase's `-default
-drive8type 1541`) belongs inside this function's existing `if (backend ===
"stock")` branch, appended to the `args` array already being built — not as a
second call site, not duplicated in `spawnAndRecordInstance()`.
**Example:**
```typescript
// Source: .claude/mcp/vice/broker-launch.mts:162-187 (current, before fix)
if (backend === "stock") {
  const host = binmonHost ?? process.env.VICE_BROKER_BINMON_HOST ?? "127.0.0.1";
  // ... one-time warning ...
  const args = ["-binarymonitor", "-binarymonitoraddress", `ip4://${host}:${port}`];
  if (typeof remoteMonitorPort === "number") {
    // ... appends -remotemonitor ...
  }
  return args;
}
```
The fix prepends `-default` and the drive flags **before** the existing
`-binarymonitor` push, matching the documented ordering constraint (`-default`
must precede `-binarymonitor` or the monitor never binds — CLAUDE.md, confirmed
by earlier phases' live testing). `-drive8type` has no evidence of an ordering
sensitivity relative to `-binarymonitor` itself, but it **does** need to come
**after** `-default` in the same argv (see Pitfall 1 below) if `-default` is
added in the same pass, which the I-1 rider requires.

### Pattern 2: `spawnFn` gains an options parameter without breaking existing callers

**What:** `TryLaunchDeps.spawn` and `AcquirePortAndLaunchDeps.spawn` are currently
typed `(command: string, args: string[]) => ChildProcess`. Widen to `(command:
string, args: string[], options?: SpawnOptionsWithoutStdio) => ChildProcess`, and
have `spawnAndRecordInstance()` pass a third argument only when `backend ===
"stock"` (an env object carrying a fresh scratch `XDG_CONFIG_HOME`, mirroring the
pattern already used in `stock-live.test.ts`/`stock-live-broker-monitor.test.ts`).
**When to use:** This is the exact seam ROADMAP names: "`buildViceArgs()` /
`spawnFn` are already open for item 1, so give `spawnFn` an options parameter...
while there."
**Example (test precedent already in this tree):**
```typescript
// Source: .claude/mcp/vice/stock-live.test.ts:220 (existing test-only pattern)
const child = spawn(
  resolvedBinPath,
  ["-binarymonitor", "-binarymonitoraddress", `ip4://127.0.0.1:${port}`],
  { stdio: "ignore", env: { ...process.env, XDG_CONFIG_HOME: scratchDir } },
);
```
The production fix generalises this into `spawnAndRecordInstance()`'s own default
spawn wrapper (`deps.spawn ?? ((cmd, args, opts) => nodeSpawn(cmd, args, opts))`),
computing a fresh `mkdtempSync()` scratch dir per launch when `backend ===
"stock"` and passing it as `env.XDG_CONFIG_HOME` — never the shared
`$HOME/.config/vice/vicerc` a production host may already have (which round 1
live-tested and found merely a warning, not a blocker, but which this rider
closes properly per audit §4.4).

### Pattern 3: Live coverage goes through the real broker launch primitive, not a hand-spawned instance

**What:** Every existing live test (`stock-live.test.ts`,
`stock-live-triage.test.ts`) spawns `x64sc` **directly** with `node:child_process`
and builds its own `StockConnectSession`/`StockDispatchDeps` — it never calls
`buildViceArgs()`, `tryLaunchOne()`, or `acquirePortAndLaunch()`. This is precisely
why the Drive8Type defect hid: no test, live or unit, ever exercised the actual
argv the broker constructs and passes to `spawn`.
**When to use:** Item 1's mandated new coverage MUST call
`acquirePortAndLaunch("live-test", { ..., backend: "stock", viceBin:
"/usr/bin/x64sc", spawn: nodeSpawn })` (or `tryLaunchOne` with a fixed port) —
the real function under test — then dial the granted port with a real
`ViceMonitorClient`/`stockConnect()` and dispatch `vice_disk_attach`/
`vice_autostart` through `dispatchStock()`, exactly like `stock-live.test.ts`
does for its session, but with the launch itself also going through the real
broker primitive.
**Example (skeleton, following `broker-e2e.test.ts`'s stub-VICE_BIN convention but
with a real binary):**
```typescript
// New file: stock-broker-live.test.ts (opt-in, manual-only -- add to

const result = await acquirePortAndLaunch("live-broker-disk-test", {
```

## Common Pitfalls

### Pitfall 1: Flag-order clobbering between `-default` and `-drive8type`

**What goes wrong:** If `-default` (which resets VICE resources, including drive
configuration, to their compiled-in defaults) is emitted **after**
`-drive8type 1541` in the argv array, the drive type gets reset back to whatever
the default build ships (which per this investigation's own evidence is `0`/NONE
for a stock launch with no disk pre-attached) — silently reintroducing the exact
defect this phase exists to fix, while the fix appears to be present in the code.
**Why it happens:** VICE processes command-line flags left-to-right, applying each
in order; `-default` is a "reset to defaults" instruction, not a "these are the
defaults, apply overrides after" no-op. CLAUDE.md already documents `-default`
must precede `-binarymonitor` for exactly this reason.
**How to avoid:** Order the stock branch's returned args as `["-default",
"-drive8type", "1541", "-binarymonitor", "-binarymonitoraddress", ...]` — `-default`
strictly first, before every other flag this branch emits.
**Warning signs:** A live test (or the walkthrough) that still shows
`Drive8Type=0` via a `resourceget` even after the code change lands, with the
argv array containing both flags in the wrong order — check `spawnAndRecordInstance()`'s
logged `vice-broker: launching ...` line first; it prints the exact resolved
argv before every spawn.

### Pitfall 2: Reproducing the "confirmed fix" claim without going through the broker

**What goes wrong:** The Phase 8.1 evidence's "confirmed as sufficient" test (§4 of
`08.1-WALKTHROUGH-EVIDENCE.md`) launched `x64sc` **directly** on scratch ports with
a hand-built argv string, not through `buildViceArgs()`/`tryLaunchOne()`. It is
airtight evidence the *flag* works, but it is not evidence the *code path* is
fixed — a plan that treats that standalone reproduction as satisfying item 1's
"add live coverage through the broker" clause would be reusing evidence for a
claim it does not support.
**Why it happens:** The standalone probe was deliberately out-of-scope of Phase
8.1 (that plan explicitly declined to edit source to force a pass) — it proved
the *emulator's* behaviour, not this *codebase's* behaviour.
**How to avoid:** Item 1's new test must call the real `buildViceArgs()` /
`acquirePortAndLaunch()` functions (Pattern 3 above), not a parallel hand-built
argv string.
**Warning signs:** A plan task whose verification step only re-runs the manual
probe command from §4 of the evidence file, rather than adding or running a new
automated test file that imports `broker-launch.ts`/`.mts` directly.

### Pitfall 3: The `.prg`-only blast radius is inference, not fact — do not plan around an assumed answer

**What goes wrong:** Assuming either "PRG autostart is unaffected" (because it
never mentions a specific unit) or "PRG autostart is affected identically to
`.d64`" (because `AutostartHandleTrueDriveEmulation` sounds like it always routes
through a temp disk) without actually running the test. The audit explicitly
labels this "reasoned inference, not a confirmed fact" (§4.2, cross-cutting tech
debt list) — nobody has tested a `.prg`-only autostart against a stock instance
with `Drive8Type=0`, ever, in this project's history.
**Why it happens:** VICE's `AutostartHandleTrueDriveEmulation` resource
(default-on behaviour per general VICE knowledge, `[ASSUMED]` in this repo — not
independently confirmed here) governs whether PRG autostart uses a virtual/temp
disk under true-drive-emulation; whether that path is sensitive to `Drive8Type`
the same way a real `.d64` load is has never been probed in this codebase.
**How to avoid:** Resolve this empirically as part of item 1's own work (the
ROADMAP explicitly assigns it there), using the same new broker-launched live
test harness — add a second case that autostarts a bare `.prg` with no disk image
attached, both before and after the `-drive8type` fix, and record the observed
behaviour rather than assuming it.
**Warning signs:** A plan or its verification report that states the blast radius
("disk loads only" vs "all program loads") as settled fact without a
corresponding live-test result cited.

### Pitfall 4: Untracking the checklist script without checking who else depends on its presence in git

**What goes wrong:** `08.1-CONSISTENCY-READ.md` and `08.1-VERIFICATION.md`
reference `08.1-d-checklist.sh` and its recorded baseline as evidence of Phase
8.1's own closure. Untracking (removing from git) the script itself does not
retract that evidence — the SUMMARY/VERIFICATION files already captured its
output as text — but a plan that also deletes the file from disk (rather than
just `git rm --cached`, leaving it on disk as an ignored local file, or deleting
it outright since its job is done) should confirm no *later* phase or todo
expects to re-run it.
**Why it happens:** "Untrack" and "delete" are easy to conflate; `git rm
--cached` untracks while preserving the working-tree file (which would then need
a `.gitignore` entry or it reappears as untracked-but-present, which the
`host-scripts.test.ts` test does not check for, but a stray untracked file in
`.planning/phases/08.1-.../` is otherwise harmless clutter).
**How to avoid:** Prefer outright deletion (`git rm` — not `--cached`) given the
script is explicitly a throwaway with its evidence already captured in committed
Markdown; this is also the cleaner choice per the test's own error message
("untrack the throwaway script"). If keeping it on disk is desired for a
future audit round to re-run, extend the allowlist instead (the other
ROADMAP-licensed route) rather than a half-untrack.
**Warning signs:** `git status` showing the file as untracked after the "fix"
commit, when the intent was full removal.

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Widened `spawn` options accidentally exposing a shell (`{ shell: true }`) | Elevation of Privilege | Never set `shell: true` on the options object threaded through — the existing array-form `spawn(cmd, args)` call already avoids shell interpretation entirely; the new options object should carry only `env` (and possibly `stdio`), never `shell` |
