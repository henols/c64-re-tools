## Warnings

### WR-01: Stale "still-dropped-at-four-hops" comment left uncorrected after the very fix it describes landed in this phase

**File:** `.claude/mcp/vice/broker-launch.mts:300-309` (and duplicated verbatim in `.claude/mcp/vice/broker-launch.test.ts:1814-1828`)

**Issue:** The large "Scope boundary (do not remove this note)" comment inside
`spawnAndRecordInstance()`, written by plan `08.2-02`, states in the present
tense:

> "...this options argument is dropped again at four further hops --
> makeLoggingSpawn() and maintainWarmFloorForRealBroker's inner stashingSpawn
> in vice-broker.mts, and withCrashSupervision()'s wrapper body and
> launchSupervised()'s defaultRealSpawn in this file. Plan 08.2-06 (wave 2)
> owns threading it through those four hops and owns the non-bypassable
> proof..."

This phase's own plan `08.2-06` (same phase, later in the same diff range)
already fixed all four of these named hops — confirmed directly:
`withCrashSupervision()`'s wrapper body now forwards `options`
(`broker-launch.mts:1328-1329`), `launchSupervised()`'s `defaultRealSpawn`
merges it (`broker-launch.mts:1395-1397`), `makeLoggingSpawn()` merges it
(`vice-broker.mts:270`), and `maintainWarmFloorForRealBroker`'s
`stashingSpawn` forwards it (`vice-broker.mts:845-847`). The comment was never
updated after plan `08.2-06` landed, so it now asserts a defect that no longer
exists and attributes its fix to a plan phrased as still-pending ("Plan
08.2-06 ... owns threading it through those four hops") when that plan has
already completed within this same phase.

**Why it matters:** This is exactly the kind of "documentation-as-code" drift
CLAUDE.md's own conventions warn against (source comments are the project's
authoritative record of WHY/WHAT-NOT-TO-DO). A future maintainer — human or
an LLM agent working from this file alone — reading this comment today would
wrongly conclude I-1 is still only half-closed and either (a) distrust the
now-correct composition, or (b) attempt to re-thread options through hops
that are already fixed, wasting effort or introducing a redundant/conflicting
change. The duplicate copy in `broker-launch.test.ts` compounds this: a
reader checking the test file for corroboration finds the same false claim.

**Fix:** Update both comments to past tense, reflecting that plan `08.2-06`
already closed this rider in the same phase, e.g.:

```
// Scope boundary (historical -- kept for the reasoning, not as a live
// warning): at the time this seam was added (plan 08.2-02), the production
// broker daemon always supplied its own deps.spawn/deps.spawnFactory, so
// this default wrapper was dead code on the real launch paths, and the
// options argument was dropped again at four further hops --
// makeLoggingSpawn() and maintainWarmFloorForRealBroker's inner
// stashingSpawn in vice-broker.mts, and withCrashSupervision()'s wrapper
// body and launchSupervised()'s defaultRealSpawn in this file. Plan 08.2-06
// (same phase) threaded options through all four hops and proved it with a
// non-bypassable composition test (vice-broker-acquire.test.ts) -- see that
// plan's SUMMARY. This wrapper remains dead code on real launch paths, but
// the value it computes is no longer dropped anywhere downstream.
```

Apply the equivalent tense correction in `broker-launch.test.ts`'s copy of
the same comment.

### WR-02: `withCrashSupervision()`'s doc comment describes `baseSpawn`'s shape incompletely, omitting the (now load-bearing) third parameter

**File:** `.claude/mcp/vice/broker-launch.mts:1299-1302`

**Issue:** The exported function's doc comment reads:

> "Wraps `baseSpawn` (a plain spawn function of the same shape
> `(command, args) => ChildProcess` every launch path already threads
> through) ..."

The actual type of `baseSpawn` (and of the function's own parameter and return
type, both updated by this phase) is
`(command: string, args: string[], options?: SpawnOptionsWithoutStdio) => ChildProcess`.
The doc comment was not updated when the signature was widened, so it now
describes a narrower shape than the code actually has — specifically it omits
the exact argument (`options`) whose correct forwarding is this phase's whole
point, in the doc comment of the very function that forwards it.

**Why it matters:** Lower stakes than WR-01 (this doesn't assert something
actively false about *whether* the fix works), but it's a comment error in
the one function CLAUDE.md's architecture doc calls "the single exit-listener
installation point in the whole module tree" — exactly the kind of seam whose
doc comment other code should be able to trust as the accurate contract.

```
 * threads through -- see the I-1 rider comment below for why the optional
 * third argument matters) so the returned spawn function ...
```
