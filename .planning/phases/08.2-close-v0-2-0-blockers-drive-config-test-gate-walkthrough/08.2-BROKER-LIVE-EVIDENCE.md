# Phase 08.2 Plan 03 — Broker-Launched Live Coverage Evidence

This document is the literal transcript and settled verdict for the two things plan
08.2-03 exists to produce: the first live test in this tree that launches genuine stock
VICE through the real `buildViceArgs()`/`tryLaunchOne()`/spawned broker daemon path (audit
item I-2's mandated coverage clause), and the empirical answer to the one open question the
ROADMAP assigns to item 1 — does a bare `.prg` autostart hit the same `Drive8Type=0` wall a
`.d64` load does?

**What was tested:** this repository's local working checkout at commit
`066bfee1713e96a51ded416caadb57e5868b4125` — the commit that lands
`.claude/mcp/vice/stock-broker-live.test.ts` in full (both this plan's Task 1 and Task 2
commits). `/usr/bin/x64sc` reports itself as `x64sc (VICE 3.9)`; `/usr/local/bin/x64sc` (the
fork build, confirmed NOT under test anywhere in this document) reports `x64sc (VICE 3.10)`.
Node `v22.22.0`. `/usr/bin/c1541` is present and was used, by absolute path, to wrap the
synthetic `.prg` fixture into a `.d64`.

## 1. What was under test and what was not

This is the first test in the tree that launches through `buildViceArgs()`/`tryLaunchOne()`
with a real binary, via the real spawned `resources/vice-broker.mjs` artifact — not an
in-process library call and not a hand-built argv string. Every existing live test
(`stock-live.test.ts`, `stock-live-triage.test.ts`) spawns `x64sc` directly with
`node:child_process` and never calls `buildViceArgs()`, `tryLaunchOne()`, or
`acquirePortAndLaunch()` — that gap is exactly where FINDING-C1 (`Drive8Type=0`) hid: no
test, unit or live, ever exercised the argv the broker actually constructs and passes to
`spawn`. Phase 8.1's own "`-drive8type 1541` is sufficient" proof
(`08.1-WALKTHROUGH-EVIDENCE.md` §4) was a standalone probe that hand-spawned `x64sc` on a
scratch port with a hand-built argv string — airtight evidence the *flag* works, not evidence
the *code path* is fixed (`08.2-RESEARCH.md` Pitfall 2). This document's `.d64` and post-fix
`.prg` cases close that gap: both launch through the real spawned broker daemon, so
`buildViceArgs()` **and** the production `makeLoggingSpawn()` + `withCrashSupervision()`
composition are both in the call path. Only the pre-fix `.prg` baseline (§3, second case)
uses the in-process `tryLaunchOne()` route, and only because a static `VICE_ARGS` cannot
interpolate a daemon-allocated port — that case is an emulator-behaviour probe, not a
code-path proof (the code path is already proven by the other two cases).

### Pre-fix baseline (in-process `tryLaunchOne()`, `VICE_ARGS` static override)

exact pre-08.2-02 stock-branch shape without reverting the real fix anywhere in source — no

## 4. Blast-radius verdict

The audit's `.prg`-row text (`v0.2.0-MILESTONE-AUDIT.md` §4.2, Blast radius table), quoted
verbatim:

> `.prg`-only autostart on stock | **Unknown.** VICE's `AutostartHandleTrueDriveEmulation`
> (default on; this machine's `Drive8TrueEmulation=1`) routes PRG autostart through a temp
> disk when true-drive-emulation is active, which would put it on the same IEC path. Reasoned
> inference, untested either way. **Resolving this decides whether the blast radius is "disk
> loads" or "all program loads."**

**Corrected, measured verdict: `all-program-loads`.** A bare `.prg` autostart hits the
*identical* `Drive8Type=0` wall a `.d64` load does — the AUTOSTART wire command is refused
outright (§3, pre-fix case), the same command succeeds cleanly once `Drive8Type=1541` is set
(§3, post-fix case; §2, `.d64` case), and the pre-fix payload region never matches across a
6-second bounded poll. This is not inference from `AutostartHandleTrueDriveEmulation`'s
documented behaviour — it is the measured, reproduced result of actually running both the
pre-fix and post-fix launches against genuine `/usr/bin/x64sc` and comparing.

Consequence for `c64-ram-capture`: the skill's own documented boot path
(`SKILL.md:76-81`, `vice_disk_attach` → `vice_autostart` → `vice_execution_run`) was not
merely inconvenient relative to a raw-`.prg` alternative — no raw-`.prg` workaround existed
either, since PRG autostart shares the exact same failure mode as disk-based loads on a
`Drive8Type=0` instance. Both routes were equally blocked pre-fix, and both are equally
unblocked post-fix.

## 5. Assumptions revisited

`08.2-RESEARCH.md`'s Assumptions Log:

- **A1** (`AutostartHandleTrueDriveEmulation` routes PRG autostart through a temp/virtual disk
  under true-drive-emulation — not independently confirmed against this repo's own stock 3.9
  binary in the research session): **this run is CONSISTENT WITH A1, but does not confirm the
  mechanism.** The observed behaviour (a bare `.prg` autostart fails identically to a `.d64`
  load, pre-fix, and succeeds identically, post-fix) is exactly what A1 predicts, but this
  test observed outcomes at the AUTOSTART wire-command and memory-content level, not VICE's
  internal drive-emulation code path — it cannot distinguish "PRG autostart genuinely routes
  through a temp disk" from any other internal mechanism that happens to produce the same
  Drive8Type=0-dependent failure/success pattern. Do not upgrade this from "consistent with"
  to "confirmed" on the strength of this run alone.
- **A3** (`Drive8TrueEmulation` defaulting to 1 on this specific stock 3.9 build generalises to
  other stock installs): **this run says nothing about it.** Every case in this document ran
  against the same single binary (`/usr/bin/x64sc`, VICE 3.9) already characterised by Phase
  8.1's own probe. This plan did not test any other stock build, so it neither confirms nor
  refutes whether `Drive8TrueEmulation` defaults to 1 elsewhere.

## 6. Findings

**FINDING-D1 (fixture design, not a source defect).** A raw machine-code `.prg` loaded to
`$0801` does not survive a LOAD+RUN autostart byte-for-byte at its first two bytes. VICE's own
BASIC-relink pass (run as part of AUTOSTART's simulated "RUN" keystroke) scans forward from
`$0801` looking for a zero byte to compute a fresh "next line" link-pointer value, and
overwrites the first two loaded bytes with that computed value — confirmed empirically twice
during this file's development, with two different fixture contents (`0xEA`-filled and
`0x41`-filled) both landing on the identical computed override (`$0812`, one byte past this
fixture's own 16-byte block, where the scan first reaches a zero byte in fresh RAM). This is
genuine, well-known C64 KERNAL/BASIC behaviour — it is why every real SYS-based loader begins
with a proper `10 SYS n` BASIC stub rather than dropping raw code at `$0801` — and is **not**
a defect in `stock-machine.ts`'s `handleAutostart`/`handleDiskAttach` (both send the AUTOSTART
wire command exactly as they should; the relink happens entirely inside the emulated machine,
after the wire command already succeeded). To close: none required — the test fixture already
accommodates this by reserving the first two loaded bytes as an explicit, never-asserted
sacrificial field and verifying the recognisable payload from `$0803` onward instead.

**FINDING-D2 (test-timing discipline, not a source defect).** The binary monitor halts the
emulated CPU on any inbound byte (documented already, `CLAUDE.md`/`stock-connect.ts`'s CR-02
comment) and only `vice_execution_run`'s EXIT resumes it. AUTOSTART's own wire handler resumes
the machine itself as part of completing the load (confirmed live: the answer's own
`runState` reads `"running"` immediately after both `vice_disk_attach` and `vice_autostart`) —
but any test's own subsequent `vice_memory_read` polls are themselves inbound bytes and each
one re-halts the machine the instant it arrives. Reading memory immediately after resuming
(no sleep in between) starves the CPU of real run time almost entirely — confirmed
empirically while writing this file's poll loop: back-to-back resume-then-read calls with no
delay never observed the load complete even after 40 attempts, while resume-then-sleep(500ms)
-then-read reliably observed it complete within 1-2 attempts. This is not a defect either; it
is simply the live-timing discipline any future live test against this monitor must follow.
No further action required — the shipped poll loop (`pollUntilBytesMatch()`) already
implements the correct order.

No other new findings.
