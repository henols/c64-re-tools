## 3. Driving mechanism: two failed nested-session attempts, then a direct MCP client script

**Rung 1 (`headless-claude-p` with `--permission-mode bypassPermissions`) was refused outright**

No workaround to the classifier's own refusal was attempted; a narrower-privilege alternative
(`--allowedTools "mcp__vice__*"`, scoping the headless session to only the `vice` MCP tools

**Two full headless sessions with `--allowedTools "mcp__vice__* Bash Write Read Glob Grep"`
were run to completion or killed:**

- The **first** session ran the SKILL's literal phase order (boot fully, confirm PC moved,
  *then* add the checkpoint, *then* run again) and reported, honestly, `OUTCOME: fail` — the
  checkpoint at `$080D` never registered a hit across ~7 ping polls and 3 checkpoint-list checks,
  even though screen memory showed the program's own message
  (`"HELLO FROM WALKTHROUGH (LIBRARY-FREE)"`) had printed. Root cause, reasoned from this
  fixture's own design: `walkthrough.prg` is a single-shot fixture (`SYS 2061` → print → `RTS`
  back to BASIC) with no loop, so the SKILL's literal ordering — armed only *after* the initial
  boot already ran the entry point once and returned to READY — races against a fixture that
  will not pass through `$080D` again unless BASIC's program is genuinely re-run. This is a
  **fixture-design limitation** (the same class as plan 03's FINDING-D1, not a fresh code
  defect), not a defect in `buildViceArgs()`, the broker, or the stock dispatch layer. No
  workaround was applied inside that session; its own honest `fail` is preserved as this run's
  own first-recorded finding (**FINDING-E1** below), not discarded.
- The **second** session was given an explicit correction (documented, not silent): arm the
  checkpoint **before** triggering `vice_autostart`, plus the resume→real-sleep→read poll
  discipline plan 03's FINDING-D2 already established as mandatory. This session's own process
  was killed by the execution environment partway through printing its final structured summary
  (empty final transcript, non-zero exit) — but it had, by that point, **already completed the
  entire capture successfully** using a Node script it wrote itself
  (`.gsd-walkthrough-run.mjs`, a genuine `@modelcontextprotocol/sdk` MCP client — see §2(b)).
  The completed artifacts (`chunks.json`, `raw.json`, the full `write-set` output) were found
  intact on disk after the session died; §5 below is built entirely from this genuinely-real,
  self-consistent data, not reconstructed or estimated by this executor.

## 6. Findings

**FINDING-E1 (fixture-design limitation, not a code defect — same class as plan 03's
FINDING-D1).** `walkthrough.prg`'s single-shot, no-loop structure means the SKILL's literal
"boot fully, then arm the checkpoint" ordering only reaches the entry point if the checkpoint is
armed before the very first (and, for this fixture, only naturally-occurring) pass through
`$080D`. Confirmed twice: the first driving session followed the literal order and never got a
hit despite the program demonstrably having run; the second session armed the checkpoint first
and got an immediate hit. No `buildViceArgs()`, broker, or dispatch-layer file was touched to
produce this outcome — it is a property of this specific synthetic fixture, not of the fixed
code path under test.

**FINDING-E2 (open, secondary — the keyboard-fallback route on this stock configuration).**
`vice_keyboard_type "LOAD\"*\",8,1\n"` followed by `vice_execution_run` and a bounded 20-second
poll did not progress the machine past the BASIC/KERNAL READY vicinity, even with the checkpoint
armed ahead of time. A plausible cause consistent with FINDING-D2 (every inbound monitor byte
re-halts the CPU): the keyboard-typed `LOAD` command requires many real seconds of uninterrupted
CPU time to complete the IEC-emulated disk load before `RUN` can find a loaded program to run,
and the specific resume/sleep intervals this run used may not have given the load enough
real wall-clock time before the machine was next queried. This was not investigated further
within this run's own time budget; it is recorded here as an open question for whichever plan
next touches the keyboard-fallback path, not fixed or forced. It does not block this task's
`pass` verdict, which rests on the `vice_autostart` route's own complete, independent success.

**FINDING-E3 (environment-specific, not a product defect).** This execution environment's own
auto-mode classifier refuses a nested `claude -p ... --permission-mode bypassPermissions`
invocation outright, where Phase 8.1's environment allowed it. A narrower `--allowedTools
"mcp__vice__*"` invocation was not refused. Recorded because it changed this run's own driving
mechanism (§3), not because it says anything about the code under test.
