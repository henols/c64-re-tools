<objective>
Add the live coverage whose absence hid the `Drive8Type=0` defect, and settle the one
open question the ROADMAP explicitly assigns to item 1.

The audit's §4.2 finding is not only "the argv was wrong" — it is "**no test, unit or
live, ever exercised the argv the broker actually constructs.**" Every existing live
test (`stock-live.test.ts`, `stock-live-triage.test.ts`) hand-spawns `x64sc` with its
own argv and never calls `buildViceArgs()`, `tryLaunchOne()` or
`acquirePortAndLaunch()`. `stock-live.test.ts` contains zero occurrences of
`autostart`, `disk_attach`, `Autostart` or `DiskAttach`. That is exactly where the
defect hid, and plan 02's unit tests do not close it: a unit assertion on an argv
array cannot prove a real emulator answers unit 8.

This plan creates `stock-broker-live.test.ts` — the first test in the tree that
launches through the real broker primitive with a real genuine-stock binary and then
dispatches `vice_disk_attach` / `vice_autostart` against it — and uses that same
harness to answer the `.prg`-only question: does a bare `.prg` autostart hit the same
`Drive8Type=0` wall as a `.d64` load, or bypass the drive entirely? The audit labels
the current answer "reasoned inference, untested either way," and says resolving it
"decides whether the blast radius was 'disk loads' or 'all program loads'." Nobody has
ever probed it in this project's history.

Purpose: item 1's mandated coverage clause, plus the open question item 1 owns. It also
serves as the ordering gate the VALIDATION contract names — this file must pass before
plan 04's walkthrough re-run.
Output: one new opt-in live test file, registered as the seventh `MANUAL_ONLY_TESTS`
entry, plus a recorded evidence document stating the blast-radius verdict as a measured
result.
</objective>
