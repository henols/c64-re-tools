## The five line shapes, MEASURED

Reproduced here so the executor implements against a list rather than rediscovering one.
Shapes 1, 2 and 4 were observed directly this session against the pinned binary on
`fixtures/dxa/tracer.prg`; shape 3 and shape 5 come from Phase 23's committed
`fixture-baseline.txt` transcript.

| # | Shape | Example | Matches the regex? | Classification |
|---|---|---|---|---|
| 1 | byte-emitting instruction line, TAB before the mnemonic | `0812 8d 20 d0 \tsta $d020` | yes | code |
| 2 | byte-emitting `.byt` data line, TAB | `08bf 00 \t.byt $00` | yes | data |
| 3 | byte-emitting `.word` data line, SPACES not tab | `08b7 92 08      .word l892` | yes | data |
| 4 | label-only line, blank byte column | `0810          l810:` | **no** — correctly skipped | emits no bytes |
| 5 | mid-instruction label line, blank byte column, `= * + n` suffix | `08a6          l8a6 = * + 1` | **no** — correctly skipped | emits no bytes |

Two further non-byte-emitting preamble lines exist and are also correctly skipped:
`\t.word $0801` and `\t* = $0801`. Neither carries an address column, so neither can match.
Their correct skipping is a case worth asserting, not an omission.

  <behavior>
    - Two byte-emitting lines claiming the same address, one classifying it code and one data: that address appears in NEITHER the code set nor the data set, and appears in the unclassified set exactly once.
    - Its unclassified entry carries a reason naming both source lines verbatim and both claimed classes.
    - Two byte-emitting lines claiming the same address with the SAME class: still unclassified — a byte claimed twice is ambiguous regardless of whether the two claims agree, and a rule that resolved agreement would be a tie-break by another name.
    - An overlapping listing whose distinct in-window coverage equals the declared image size does NOT throw: the byte total is distinct coverage, and unclassified addresses count toward it exactly once.
    - An overlapping listing whose distinct coverage falls short of the image size still throws, and its message reports the unclassified count alongside the accounted total so the two causes are distinguishable.
    - The unclassified set participates in the rendered range list as its own class, sorted with the others and never merged into an adjacent code or data run.
    - A `jsr` landing one byte into a three-byte instruction, expressed as two real `-a dump` lines: the two overlapping bytes are unclassified and the non-overlapping bytes of each line keep their own classification.
  </behavior>
  <action>
Add the overlapping-decode disposition to `dxa-listing.ts` and its cases to
`dxa-listing.test.ts`. Tests first.

**The disposition, stated.** When two byte-emitting lines claim the same address, that
address is removed from whichever class set already holds it, added to an `unclassified`
map, and never entered into a class set again — including by a third line claiming it. The
map's value is a structured reason carrying both claiming lines verbatim and both claimed
class names. There is no tie-break, no first-wins, no last-wins, no longest-span-wins and
no code-beats-data. A byte-per-address map structurally cannot represent two decodes of the
same byte, so the honest answer is that this project declines to decide, and says why.

**Agreement is not resolution.** Two lines that both classify an address as data still
produce `unclassified`. Resolving the agreeing case would be a tie-break rule that happens
to be unobservable on the agreeing input and wrong on the disagreeing one; keeping the rule
uniform is what makes it a mechanism rather than three point behaviours.

**The byte total.** Distinct in-window coverage is the union of the code, data and
unclassified address sets. An overlapping listing therefore does not spuriously refuse. The
refusal message reports the unclassified count separately from the accounted total, so a
reader can tell a short listing from an ambiguous one.

**Rendering.** The unclassified class flows through the same range renderer as code and
data, sorted with them and never coalesced across a class boundary.

**The `jsr` case.** Build the fixture as two real `-a dump` lines with genuinely overlapping
spans, not as an abstract pair of address ranges, so the test exercises the same regex and
the same hex-column length reading the production path uses. Assert both that the shared
bytes are unclassified AND that each line's non-shared bytes keep their own class — a
disposition that swallowed the whole line would pass a weaker assertion.
