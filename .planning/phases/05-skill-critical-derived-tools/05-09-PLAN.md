<plan_decision_D-05-14>
**A bank NAME is resolved through one exported seam in `stock-memory.ts`; no consumer
re-derives the lookup, and no wire bank id is ever written as a literal.**

`stock-memory.ts` already owns the per-session bank catalog (`bankCatalogFor()`, a
`WeakMap` keyed on the session object) and a *private* `resolveBank()` whose contract is
"an omitted bank means wire id `0x0000`". That default is correct for `vice_memory_read`
(the caller asked for the CPU view) and catastrophic for a chip-state read (the caller
asked for registers). So this plan adds a **second, differently-contracted** exported
function rather than widening the existing one:

`resolveRequiredBank(toolName, bankName, session)` — the bank name is **mandatory**, and an
absent catalog entry is a **refusal**, never a fallback. The private `resolveBank()` is
refactored to delegate its name-lookup branch to it, so there is exactly one place that
maps a name to an id and exactly one refusal wording.

**Rejected: each derived module calling `bankCatalogFor()` and doing its own
`byName.get("io")`.** That is CLAUDE.md's named "re-deriving a cross-cutting seam locally"
anti-pattern, and it would produce three subtly different refusal messages for the same
condition.

**Rejected: hardcoding `io = 3` / `ram = 1`** (the ids observed live on VICE 3.9). Bank ids
are build- and machine-specific; `stock-memory.ts`'s own header already forbids a hardcoded
table for exactly this reason. A grep gate in this plan's acceptance criteria enforces it.
</plan_decision_D-05-14>

<plan_decision_D-05-15>
**The answer states the bank it read, and the manifest pins the name with `enum: ["io"]`.**

Two independent enforcement mechanisms, following D-05-07's precedent that one structural
check is not enough:

1. **A schema pin.** `bank` is declared on both tools' `outputSchema` as
   `{ type:"object", properties:{ id:{type:"integer"}, name:{type:"string", enum:["io"]} },
   required:["id","name"] }` and added to each schema's own top-level `required` list.
   Because the conformance harness validates the *real* answer against the declared schema,
   a regression that read `cpu`/`default`/`ram` and honestly reported it fails the harness.
2. **A live behavioural test** (task 3) at the `$01 = $34` condition, which is the only
   check that can distinguish a real fix from an unused import.

The shape mirrors `vice_memory_read`'s existing `bank: { id, name }` form, so the two
families report the same thing the same way.
</plan_decision_D-05-15>
