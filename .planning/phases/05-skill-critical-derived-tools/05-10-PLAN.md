<plan_decision_D-05-16>
**Two banks, named for what each read is for: `io` for registers, `ram` for what the VIC-II
fetches.**

The three reads in `readSpriteContext()` are not one kind of read. The VIC-II register block
(`$D000-$D02E`) and `$DD00` are **I/O registers** — they need the `io` bank, exactly as
05-09's chip tools do. The sprite pointer table (`screenBase + $3F8`) and the 63-byte sprite
data block are **what the VIC-II chip itself fetches**, and the chip never sees I/O or
cartridge ROM — they need the `ram` bank. Reading the second pair through `io` would be as
wrong as reading the first pair through `cpu`.

The answer therefore reports **two** fields, not one: `registerBank` and `dataBank`. A single
`bank` field would have to lie about one of the two.

**The char-ROM note stays.** `ram` still cannot show the character ROM the chip fetches at
`$1000-$1FFF` in VIC banks 0 and 2, so `spriteRomWindowNote()`'s condition is unchanged. The
new note is a **second, independent** condition: VIC bank 3 plus a resolved address in
`$D000-$DFFF`, where reading through `ram` is now correct and reading through the CPU view
would have returned registers. Both notes are emitted from one function so a caller sees one
`notes[]` array with one shape.
</plan_decision_D-05-16>

<plan_decision_D-05-17>
**Two legend constants, both exported; the single-constant `SPRITE_ASCII_LEGEND` is
removed rather than aliased.**

`renderSpriteAscii(bytes, multicolour)` already has two genuinely different alphabets:
hi-res emits one character per **bit** (`'.'`/`'#'`), multicolour one per **bit pair**
(`'.'`/`'@'`/`'#'`/`'%'` through `MULTICOLOUR_LEGEND`). The legend is a property of the
render, so it is selected by the same flag that selects the renderer.

`SPRITE_ASCII_LEGEND` is deleted, not kept as a deprecated alias: its only consumers are
`stock-sprites.ts` itself and `stock-sprites.test.ts:318` (confirmed by repo-wide grep — no
skill, script, doc or manifest string references the identifier), and leaving an alias in
place invites the next caller to attach the wrong one again.
</plan_decision_D-05-17>
