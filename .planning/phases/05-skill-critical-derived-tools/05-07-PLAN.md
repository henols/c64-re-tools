<plan_decision_D-05-07-schema>
**Criterion 3's second enforcement mechanism is a schema pin, not a second unit test.**

05-03 and 05-04 each assert in their own test files that every unavailable field is
`{ available: false, reason }`. That is mechanism 1, and it is a test written by the same
pass that wrote the decoder — which Phase 2's post-mortem and Phase 3's `sizeBits` blocker
both showed proves less than it looks like it does.

**Mechanism 2, added here:** each unavailable field is declared in `outputSchema` as an
object with `available` carrying `enum: [false]`, `reason` typed `string`, and
`required: ["available", "reason"]`. `checkAgainstSchema()` supports `type`, `enum`,
`properties` and `required`, so this validates with **no change to
`stock-schema-check.ts`**. Because the conformance harness runs the *real* answer through
the *declared* schema, a regression that turned a field into `0`, into
`{ available: true, value: 0 }`, or into an absent key fails a gate derived from the
manifest rather than from the decoder.

The two mechanisms are independent by construction: one reads the decoder's output against
hand-written expectations, the other reads it against the published contract.
</plan_decision_D-05-07-schema>
