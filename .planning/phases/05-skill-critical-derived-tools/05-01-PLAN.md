<plan_decision_D-05-01>
**`vice_memory_compare`'s `mode: 'snapshot'` is refused by name, not implemented.**

The fork's schema names a `snapshot_name`, but grepping both manifests finds **no
memory-only snapshot producer tool** — only `vice_snapshot_save`, a whole-machine
`.vsf` dump — and no skill anywhere calls `mode:'snapshot'`. The only two ways to
serve it are (a) destructively restoring the snapshot to read memory out of it,
corrupting whatever session state the agent had, or (b) guessing at the VICE `.vsf`
binary module layout, which is unverified in this repo and has no existing parser.

**Decision: refuse `mode:'snapshot'` explicitly, naming the reason and the two
working alternatives.** This follows the precedent Phase 3's D-15
(`vice_checkpoint_set_ignore_count`, trimmed) and D-16 (`vice_snapshot_list`,
deleted) already set for "no consumer, no obligation to build it". The refusal fires
**before any `MEM_GET` is sent** — asserted by a zero-sends test.

**The `snapshot_name`, `start` and `end` properties stay DECLARED in the stock
`inputSchema`** (05-06's job). They are not dropped: `stock-dispatch.test.ts`'s D-03
input-compatibility test asserts every fork-declared property is also declared on
stock with a matching `type`, so removing them would fail that gate. The trim is a
runtime refusal named in the tool's `description`, never a silently missing argument.

**Rejected:** a destructive restore-then-read (breaks D-05's no-unrequested-state-change
posture far more severely than a resume would). **Rejected:** a `.vsf` parser
(unverified binary layout, for a feature with zero callers).
</plan_decision_D-05-01>

   can never match, so it is a validation failure, not a zero-result answer.

   `mask.length !== pattern.length` naming both lengths and stating the mask is never
   padded or truncated to fit.
6. `max_results` — optional; `parseByteCount(args.max_results, { max: MAX_MAX_RESULTS, what: "max_results" })`
   in a try/catch, defaulting to `DEFAULT_MAX_RESULTS` when absent. (`parseByteCount`
   already refuses `0`, negatives and non-integers.)
7. Build `memGetBody({ sidefx: false, start, end, memspace: 0x00, bank: 0x0000 })` and
   send `CommandType.MemoryGet` inside a try/catch →
   `convertWireError("vice_memory_search", err)`.
8. Guard `response.type !== "memory_get"` with the "expected \"memory_get\"" wording
   `handleMemoryRead` uses, and guard a short read
   (`response.bytes.length !== end - start + 1`) with the same "a short read is a wrong
   answer, not a partial success" framing.
9. **Scan**, a plain forward loop over `offset` from `0` to
   `bytes.length - pattern.length` inclusive. A match at `offset` requires, for every
   `index` in the pattern: with a mask,
   `(bytes[offset + index] & mask[index]) === (pattern[index] & mask[index])`; without
   one, `bytes[offset + index] === pattern[index]`. Matches may overlap — advance
   `offset` by 1, never by `pattern.length`. Collect `start + offset` into `matches`.
   Stop the scan the moment `matches.length === maxResults` and set `truncated = true`;
   otherwise `truncated = false`.
10. Answer through `stockAnswer(session.client, payload)` with exactly these keys:
    `start`, `end`, `searched` (= `end - start + 1`), `pattern` (the validated array),
    `mask` (present ONLY when supplied), `maxResults`, `matches` (number[] of
    addresses), `count` (= `matches.length`), `truncated`. Never a hand-built
    `{ content, isError: false }` literal.

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-01-01 | Tampering | `start`/`end`/`range1_*`/`range2_start` argument validation (ASVS V5) | mitigate | Every address routes through `stock-address.ts`'s `parseAddress()` — the one parser, already enforcing `0..0xffff`. `range2_end` is *derived*, then refused above `$ffff` before any request is built (task 2 step 5), so a crafted `range2_start` cannot request past the 16-bit space. |
| T-05-01-02 | Denial of Service | unbounded `pattern`/`mask` arrays | mitigate | `pattern` is refused when longer than `MAX_PATTERN_BYTES` (0x1000) **and** when longer than the range searched — a pattern that cannot possibly match fails validation rather than driving a pointless full scan. `mask` must equal `pattern.length` exactly; it is never padded. Both arrays are per-element validated as integers 0..255 through the same loop shape `vice_memory_write` uses. |
| T-05-01-03 | Denial of Service | unbounded answer payload via `max_results` / `max_differences` | mitigate | Both default to `100` and are refused above `10000` — the fork's own documented ceiling — through `parseByteCount`, which also refuses `0`, negatives and non-integers. The scan *stops* at the cap rather than collecting everything and slicing, and `truncated: true` tells the caller the answer is partial. |
| T-05-01-04 | Tampering | side effects from reading I/O registers | mitigate | `sidefx: false` is hardcoded at all three `memGetBody` call sites with no argument to override it, so searching or comparing across `$D000-$DFFF` can never clear `$D01E`/`$D01F`/`$DC0D`/`$DD0D`. Asserted as a source gate (tasks 1-2) and as a wire-body assertion on `calls[n][1][0] === 0x00` (task 3). |
| T-05-01-05 | Denial of Service | an unrequested resume of the user's program | mitigate | These handlers send `MEM_GET` and nothing else; no `EXIT` is ever issued (Phase 3 D-05). Grep-asserted to zero `CommandType.ExitLoop`/`Exit`/`Continue` occurrences. `runState` on the answer (via `stockAnswer`) reports the halt honestly. |
| T-05-01-06 | Tampering | `mode:'snapshot'` implemented as a destructive snapshot restore | mitigate | Refused by name **before any wire send**, with the reason and two working alternatives stated (D-05-01). The alternative implementations — restoring the machine to read memory out of it, or guessing at the `.vsf` binary layout — would either destroy live session state or return confidently wrong bytes. Asserted by a zero-sends test. |
| T-05-01-07 | Repudiation | an answer that looks complete but silently dropped matches | mitigate | `truncated` and `maxResults`/`maxDifferences` are explicit answer fields, and `identical` on compare is computed as `count === 0 && !truncated` so a truncated compare can never claim the ranges are identical. |
