<plan_decision_D-05-07>
**Only the enumerated internal-only fields carry the `{ available: false, reason }`
wrapper; readable registers are plain decoded values.**

The research's Pattern 4 proposes a per-field availability wrapper. Applied to *every*
field it would double the access cost of ~40 readable values for zero information —
every one of them is unconditionally readable from the register block. Applied to the
**enumerated unavailable set only**, it says exactly the thing criterion 3 asks for and
nothing else.

**Two independent enforcement mechanisms** (following 04-CONTEXT's D-02 precedent that
one structural check is not enough):
1. **A schema pin.** In `tools-manifest.stock.json` (05-07's task) each unavailable
   field is declared as an object whose `available` property carries
   `enum: [false]` and whose `required` is `["available", "reason"]`. Because the
   conformance harness validates the *real* answer against the declared `outputSchema`,
   a regression that turned one of these fields into `0`, or into
   `{ available: true, value: 0 }`, fails the harness — not merely a hand-written test.
2. **A dedicated unit test** asserting, for every member of
   `VICII_UNAVAILABLE_FIELDS`, that the answer's field is a plain object with
   `available === false` and a non-empty `reason` string, and that it is neither the
   number `0` nor an absent key.

**The unavailable fields are grouped under one `unavailable` object** rather than mixed
in at top level, so the shape is self-describing and the schema pin is one nested
declaration instead of six scattered ones.
</plan_decision_D-05-07>

<plan_decision_D-05-10>
**`vice_vicii_get_state` decodes only the `$D000-$D02E` block — one read, no `$DD00`.**

`$D018`'s screen/charset/bitmap pointers are *bank-relative*; turning them into
absolute addresses needs the VIC bank from CIA2 port A (`$DD00`), which is outside this
chip's register block.

**Decision: report them as bank-relative offsets** (`screenOffset`, `charsetOffset`,
`bitmapOffset`) and name, in the tool's own description, where the missing half comes
from: `vice_cia_get_state` with `cia: 2` reports `vicBank`, and `vice_sprite_get`
resolves the whole pointer chain to absolute addresses. This matches the fork's own tool
split (`vice_vicii_get_state` = "Get VIC-II internal state"; `vice_sprite_get` =
"Get sprite state") and keeps the bank/screen-base arithmetic in **exactly one module**
(`stock-sprites.ts`, 05-05), rather than duplicating it here.

**Rejected:** a second `MEM_GET` of `$DD00` inside this handler. It would make two
modules own the same pointer-chain arithmetic — the "re-deriving a cross-cutting seam
locally" anti-pattern — for a field the caller can already get from two other tools.
</plan_decision_D-05-10>

Also state the `$D019`/`$D01A` clarification explicitly, because conflating them with
the collision registers is the documented trap: **`$D019` is an interrupt STATUS
register that does NOT clear on read** (it is cleared only by *writing* a 1 to a bit)
and **`$D01A` is a plain enable mask with no read side effects at all**. The correct
discipline is ONE unconditional `sidefx: false` read covering the whole block — never a
per-register side-effect decision.

**Module constants:**
- `VICII_BASE = 0xd000`, `VICII_END = 0xd02e`, `VICII_LENGTH = 0x2f` (47).
- `VICII_UNAVAILABLE_FIELDS` — a frozen array of `readonly` `[fieldName, reason]` pairs,
  exported, with exactly these six members and reasons that each name **why** it is
  unreadable and **what is readable instead** where applicable:
  - `rasterIrqLine` — the raster-compare latch written to `$D012` plus `$D011` bit 7;
    reading those addresses returns the CURRENT raster line, not the compare value, and
    the binary monitor has no VIC-II command that exposes the latch. The current raster
    line IS available as this answer's own `rasterLine`.
  - `videoCounter` — the VIC-II's internal VC/VCBASE counter; not in the memory-mapped
    register map.
  - `rowCounter` — the internal RC counter; not in the memory-mapped register map.
  - `badLineCondition` — the internal bad-line flip-flop; not in the register map.

    the register map.
  - `spriteDmaState` — the internal per-sprite DMA / MC / MCBASE sequencer state; not in
    the register map.

**`export function decodeVicii(bytes: Uint8Array): Record<string, unknown>`** — a
**pure** function taking exactly 47 bytes (throw a plain `Error` on any other length;
the handler guards the length before calling, so this is a programmer-error path) and
returning the decoded payload. Index `bytes[n]` by `n = address - 0xd000`. Decode:

- `registersHex` — the whole 47-byte block as lowercase hex (94 characters), so a caller
  can re-derive anything this decoder does not name.
- `spriteX` — `number[8]`: `bytes[0x00 + i * 2] | (((bytes[0x10] >> i) & 1) << 8)` — the
  9-bit X coordinate, low 8 bits per sprite plus bit 8 from `$D010`.
- `spriteY` — `number[8]`: `bytes[0x01 + i * 2]`.
- `spriteEnabled` — `boolean[8]` from `$D015` (`bytes[0x15]`), bit `i`.
- `spriteExpandY` — `boolean[8]` from `$D017`, bit `i`.
- `spritePriorityBehindBackground` — `boolean[8]` from `$D01B`, bit `i` (a set bit means
  the sprite is drawn *behind* background; name the field so the polarity is
  unambiguous).
- `spriteMulticolour` — `boolean[8]` from `$D01C`, bit `i`.
- `spriteExpandX` — `boolean[8]` from `$D01D`, bit `i`.
- `spriteColour` — `number[8]`: `bytes[0x27 + i] & 0x0f`.
- `control1` — an object from `$D011` (`bytes[0x11]`): `raw`, `yScroll` (bits 0-2),
  `rows25` (bit 3), `screenOn` (bit 4), `bitmapMode` (bit 5), `extendedBackgroundMode`
  (bit 6), `rasterMsb` (bit 7, boolean).
- `control2` — an object from `$D016` (`bytes[0x16]`): `raw`, `xScroll` (bits 0-2),
  `columns40` (bit 3), `multicolourMode` (bit 4).
- `rasterLine` — `bytes[0x12] | (((bytes[0x11] >> 7) & 1) << 8)`.
- `lightPenX` — `bytes[0x13]`; `lightPenY` — `bytes[0x14]`.
- `memorySetup` — an object from `$D018` (`bytes[0x18]`): `raw`,
  `screenOffset` = `((raw >> 4) & 0x0f) * 1024`, `charsetOffset` = `((raw >> 1) & 0x07) * 2048`,
  `bitmapOffset` = `((raw >> 3) & 0x01) * 8192`, and `relativeTo` = the fixed string
  `"vic bank"` so the answer states its own frame of reference (D-05-10).
- `interruptStatus` — an object from `$D019` (`bytes[0x19]`): `raw`, `rasterIrq` (bit 0),
  `spriteBackgroundCollisionIrq` (bit 1), `spriteSpriteCollisionIrq` (bit 2),
  `lightPenIrq` (bit 3), `anyIrqPending` (bit 7).
- `interruptEnable` — an object from `$D01A` (`bytes[0x1a]`): `raw`,
  `rasterIrqEnabled` (bit 0), `spriteBackgroundCollisionIrqEnabled` (bit 1),
  `spriteSpriteCollisionIrqEnabled` (bit 2), `lightPenIrqEnabled` (bit 3).
- `spriteSpriteCollision` — an object from `$D01E` (`bytes[0x1e]`): `raw` and
  `sprites` (`boolean[8]`).
- `spriteBackgroundCollision` — the same shape from `$D01F` (`bytes[0x1f]`).
- `borderColour` = `bytes[0x20] & 0x0f`; `backgroundColour` = `bytes[0x21] & 0x0f`;
  `extraBackgroundColour1/2/3` = `bytes[0x22/0x23/0x24] & 0x0f`;
  `spriteMulticolour1` = `bytes[0x25] & 0x0f`; `spriteMulticolour2` = `bytes[0x26] & 0x0f`.
- `unavailable` — an object built by mapping `VICII_UNAVAILABLE_FIELDS` to
  `{ available: false, reason }` per member. Build it from the registry, never as six
  hand-written literals, so the registry and the answer cannot drift.

Use a small private helper `function bits8(raw: number): boolean[]` returning the eight
