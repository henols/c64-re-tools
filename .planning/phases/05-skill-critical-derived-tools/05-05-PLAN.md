<plan_decision_D-05-03>
**`vice_sprite_inspect`'s `format: 'png_base64'` is omitted from the served set and
refused by name.**

No skill calls `vice_sprite_inspect` with an explicit `format` at all, so every real call
takes the `'ascii'` default. Building a PNG encoder for a value nothing requests is the
identical situation that got `SHOT-01`..`SHOT-05` (client-side screenshots and the
indexed-PNG writer) cut from this very milestone on 2026-08-17.

**Decision: serve `'ascii'` (default) and `'binary'`; refuse `'png_base64'` by name**,
with the refusal text naming `ascii` and `binary` as the served values and stating that
the PNG path was cut with `SHOT-01`..`SHOT-05`. The `format` **property stays declared**
in the stock `inputSchema` with `type: "string"` (05-07's task) — the D-03
input-compatibility gate in `stock-dispatch.test.ts` requires every fork-declared
property to be present with a matching type — but the stock schema's own enum and
description name only the two served values.
</plan_decision_D-05-03>

<plan_decision_D-05-04>
**The ASCII grid renders at native resolution per mode: 24 columns for hi-res, 12 for
multicolour, always 21 rows. No normalisation, no expansion scaling.**

The fork's own legend describes a fixed bit-pair mapping, which implies native width. A
normalised width would invent a design decision nothing in DERIV-06 asks for, and it
would make a multicolour sprite's ASCII stop corresponding 1:1 to its bit pairs — the
whole reason an agent reads the grid.

`$D017`/`$D01D` (Y/X expansion) are **reported as fields but do not scale the grid**: the
rendering is of the sprite's 63-byte *data block*, which is 24x21 regardless of how the
VIC-II stretches it on screen. The answer states this in a `notes` entry whenever either
expansion bit is set for the inspected sprite, so a caller comparing the grid against a
screenshot is not surprised.
</plan_decision_D-05-04>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| MCP client -> `vice_sprite_get` / `vice_sprite_inspect` | `sprite`, `sprite_number` and `format` are untrusted input |
| handler -> binary monitor socket | Three or four `MEM_GET` requests on the single-client stock monitor session |

| emulator I/O registers -> reader | The VIC-II block read includes `$D01E`/`$D01F`, which clear on read in hardware |
