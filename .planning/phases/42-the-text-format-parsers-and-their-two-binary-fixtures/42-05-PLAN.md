<objective>
PARSE-04: when the connected VICE was built without the tracing or profiling support a
command needs, tell the user which capability is missing and on which binary — never hand
back a silent empty result or a parse error that reads like a bug in this project.

Two findings shape this. VICE compiles `memmapshow` and `chis` behind the SAME build macro
and both print the identical disabled string, while `bt` and `prof flat` carry no build-time
guard at all and `io` degrades with its own text signal instead of refusing — so the design
is neither one guard per command nor one guard for all five, and probing each command on its
own is what stays correct under all three shapes. And a capability is a property of a binary
file, which is why D-42-2 keeps the cache in-process: a persisted answer would outlive the
VICE upgrade that invalidated it.

Purpose: the probe layer, dependency-injected and testable with no emulator.
Output: `text-capability-probe.ts` and its test file. No tool wiring (plan 42-07), no
`package.json` edit (see the note below).
</objective>

<plan_decisions>
**D-42-2 (locked, orchestrator), and the one thing this plan has to get right about it.**
The three locked properties are honored exactly: the cache is in-process, it is keyed by the
backend kind plus the resolved absolute binary path, and the key is never operator-supplied.

The locked decision also says to build the key from the already-memoised backend resolution
rather than re-deriving backend identity, and this plan does — but through the seam that
carries that value INTO the container rather than by importing the host-bound resolver.
`StockDispatchDeps` already exposes `resolvedBinaryPath` and `resolvedBinaryPathIsResolved`,
and its own doc comment states they are threaded down from the SAME single backend
resolution, never recomputed. That is the value D-42-2 names, delivered to exactly where
this module runs. Importing the host-bound resolver here instead would resolve a binary
against the CONTAINER's filesystem, which `vice-proxy.ts`'s own comment records as a
different question from which binary the broker actually launched.

**Because those two can disagree, identity is cross-checked rather than assumed.** The
broker's control session reports its own `vice_bin` and its own backend verdict, and
`vice-proxy.ts` already treats the broker's verdict as the authoritative one because it is
what decided the emulator's launch argv. So: key on the resolved identity from `deps`,
cross-check against the broker's record when the broker reports one, and on a DEFINITE
disagreement return the verdict uncached rather than filing it under a binary that may not
have answered. Absent evidence is not disagreement — a broker that reports nothing leaves
the cross-check unperformed, which is the same distinction this repo already draws at its
backend-mismatch seam. Attributing a capability answer to the wrong binary is precisely the
mislabelling failure the fixture batch's own README records having paid for once.

**A different, already-persisted fact this module must not touch.** The supervisor's backend
record already carries a `cpuHistoryAvailable` field. That is the BINARY MONITOR's opcode
availability — a protocol-version question — and it is not this one, which is a build-flag
question about the text monitor. This module neither reads, writes, nor overwrites it, and
its header comment says so, because the two answers can legitimately differ on the same
binary and collapsing them would produce a confidently wrong verdict.

**D-42-3 is inherited:** refuse by returning, never by throwing.

**No `package.json` edit in this plan.** This module joins `files[]` in plan 42-07, the plan
that makes shipped code import it.
</plan_decisions>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| VICE reply → classifier | Untrusted-in-shape input; a legitimate large reply must never be misread as a refusal |
| identity sources → cache key | Two sources can disagree about which binary answered; a wrong key files an answer against the wrong binary |
| cache → later answers | A cached verdict is asserted as fact to every later caller in this process |
