<plan_decisions>
**D-42-4 (decided here): the backtrace tool reuses the fork's existing tool name.** The fork
manifest already advertises a backtrace tool with one optional numeric depth argument and no
declared output schema; stock advertises no such tool, and its capability-registry entry
records the reason as nothing calling it rather than anything making it impossible. Landing
the text-monitor implementation under that same name satisfies this repo's compatibility rule
literally — same name, and an argument shape that removes nothing, retypes nothing and newly
requires nothing — and closes a parity gap instead of creating a second vocabulary for one
capability.

Two consequences are paid in this plan rather than deferred. The name leaves the
manifest-derived divergence set, so the mechanical completeness test requires its registry
entry be REMOVED (and the descoped block's provenance count updated). And the two backends
now answer that name with different response shapes — ours structured and declared, the
fork's undeclared — so the stock tool's description states that difference in one sentence.
No shipped skill calls the name today, which is why this is a safe moment to do it and why
the skill-text question stays out of scope (plan 42-06 records that finding).

Reversibility: `costly`, not one-way. Renaming later would be a manifest and registry edit
plus a support-table regeneration, with no stored data to migrate; the reason it is not
merely `reversible` is that the name is published to a registry on merge, so a rename after
that point is visible to anyone who already wrote it down.

**D-42-3 and D-42-1 are inherited**, from plans 42-01 and 42-04 respectively: parsers refuse
by returning, and only the transport builds a parameterized command string.

**Classify before parse.** Every handler runs the capability classifier over the RAW reply
before handing it to a parser. The ordering is the requirement, not a preference: a reply
that is VICE's disabled stub would otherwise reach the parser and come back as a
missing-header refusal — a parse error that reads like a bug in this project, which is
exactly the outcome PARSE-04 forbids. The tracer's own handler is retrofitted with the same
ordering in Task 3, since the probe did not exist when it was written.
</plan_decisions>
