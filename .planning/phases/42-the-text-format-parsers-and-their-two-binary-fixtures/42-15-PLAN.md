<plan_decisions>
**The remedy chosen, and what the other one would have cost.** `42-VERIFICATION.md`'s
`gaps[0].missing[0]` names two acceptable remedies and this plan takes the second as its
semantic fix and the first as its structural guard, deliberately, because each alone leaves a
real hole:

- *Remedy 1 alone* ("never cache `io` in the `cacheable` check") stops the staleness but leaves
  `handleIoRegisters` still asking a **capability** API a **content** question. The wrong
  abstraction survives in the code, so a later reader can re-enable caching by "simplifying" the
  predicate, and the in-flight dial memo — which is a second, independent way one caller's
  response reaches another caller — is untouched by it.
- *Remedy 2 alone* ("bypass the cache for `io`'s degradation check") fixes the handler but leaves
  `runProbe`'s `cacheable` predicate still willing to file an `io` verdict for any other caller
  that probes it. The trap stays loaded, just unsprung.

So both land: the handler classifies the fresh response through a **pure builder** with no cache
and no dial, and `io` is removed from the cache's domain by a named, exported set. Doing both is
inside the declared solution space (the verification says "either ... or"), and neither half is
load-bearing for the other's correctness.

**Why a pure builder rather than exporting the degradation matcher.** The handler's downstream
behaviour must not change on a COLD cache — today's cold-cache behaviour is the correct
behaviour, and the gap is only that it stops happening once the cache warms. A pure builder that
constructs exactly the verdict `runProbe` would have constructed, minus the dial and minus the
cache, preserves every one of the three rendered shapes byte-identically: the chip-degradation
line for the two fixed strings, the indeterminate line for an empty reply, and the empty string
for a real dump. Exporting only the degradation matcher would have silently dropped the
indeterminate branch for `io` and sent an empty reply to `parseIoRegisters`, which refuses
`empty-response` and — through the generic wrapper — reads as a defect in this project. That
would have traded one Criterion 5 violation for another.

**`runProbe` is refactored onto the same builder, not left as a second construction site.** This
module's own `identityDisagreementText()` doc comment states the discipline: "a thin wrapper ...
so there is exactly one wording in exactly one place". Two verdict constructors would drift.

**No new refusal code and no new rendered wording is minted.** The two degradation strings, the
indeterminate line and the missing-group line all keep their exact existing text, produced by
the same `textCapabilityRefusalMessage()`. This gap is about WHICH response gets classified, not
about how a classification reads.

**Canon-referral drop (prohibition probe, stage 2):** injection / path-traversal / OWASP-class
constraints on the text-monitor command path are already owned by `TEXT_COMMAND_ALLOWLIST` and
`buildTextCommand()`'s bounded builder, plus the project's security canon. Not minted here.
</plan_decisions>

<assumption_delta_decision>
The detector fired `pluralization` on this phase's scope. Read against the actual change, the
identity-model question it raises is real and worth answering explicitly rather than dismissing
as a prose match:

- **The noun that is primary:** *a build capability of a binary file*. That is what
  `probeTextCapability`'s cache key `(backend:binPath, command)` names, and it stays primary and
  unchanged.
- **Decision: `no-change`, with the second fact evicted rather than accommodated.** CR-02 is a
  second, different kind of fact (per-address, per-call chip content) that was filed under the
  primary noun's key. The tempting generalization — widen the key to
  `(backend:binPath, command, address)` — is exactly the "add-alongside" move, and it would still
  be wrong: the same address can answer differently after a bank switch, so no key shape makes a
  per-call fact safely memoisable for a process lifetime. The correct move is therefore to
  **narrow the cache's domain** so it holds only the primary noun, and to compute the second fact
  fresh every time.
- **What would force a later promote:** a future text-monitor command whose outcome is
  genuinely per-address AND genuinely expensive to re-dial. At that point the right answer is a
  separate, explicitly short-lived, address-keyed memo — a different abstraction with a different
  name — never a widened key on this one.
- **Invariant test encoding this intent (accepted, built in Task 2):** every command in
  `TEXT_CAPABILITY_COMMANDS` is either in `CPUHISTORY_GATED_COMMANDS`-style binary-wide territory
  and cacheable, or declared in `NEVER_CACHED_COMMANDS` and provably absent from the cache after
  a probe. A future command added to neither list fails the case by name.
</assumption_delta_decision>
