<plan_decisions>
**The choice between 42-REVIEW.md's two alternatives is made here, and it is (b): make the
sprite requirement chip-conditional. (a) — tightening `vice_io_registers`'s advertised address
range and refusing a non-VIC-II address before dialing — is rejected.**

Three reasons, recorded so a later reader does not re-open it as an oversight:

1. **(a) narrows a published contract; (b) does not.** CLAUDE.md's compatibility constraint
   says stock may add an optional parameter but never removes, retypes or newly-requires one.
   Narrowing `address`'s advertised 0-65535 range is the same class of change seen from a
   caller: an argument that validated yesterday stops validating today. That is a one-way door
   for anyone already calling the tool. Keeping the range and refusing by name inside the
   parser is a strictly additive change to the refusal set.
2. **(b) is what the module's own header already promises.** `IoRegisters.sections` is an array
   precisely because "the command itself accepts a bare invocation that dumps every chip, and a
   parser that hard-assumed one section would refuse a legitimate reply." A hard-assumed
   VIC-II is the same mistake one level down.
3. **(b) leaves the door open.** A later phase can decode CIA or SID registers by replacing the
   refusal with a real branch. (a) would have to un-narrow the published schema first.

**Refuse rather than return a partial section, and why.** The alternative shape — return the
section with a null `decoded` and null `sprites` — would give the caller the 64-byte dump, but
it changes `IoChipSection`'s published output shape for every consumer and makes two required
output fields nullable. That is a bigger blast radius than the gap warrants, and it re-opens
the "a caller cannot tell nothing-to-show from nothing-found" hazard this module's header
already forbids. A named refusal that states the dump read cleanly carries the same
information at zero contract cost.

**Placement matters and is specified, not left to the executor's judgement.** The gate goes
AFTER the dump-row loop and its `byteRows.length === 0` validation, and BEFORE the
blank-separator check. After the dump loop, so a drive-contaminated memspace still refuses
`unrecognised-memspace` first (CLAUDE.md's documented `default_memspace` hazard outranks a
chip-shape complaint) and so the message can cite the real base address and byte count. Before
the blank-separator and prose checks, so a chip this parser does not model is never reported as
a layout defect — and so 42-10's `incomplete-decoded-state`, which would otherwise fire on a
CIA section with all nineteen names, never sees a section it was not written for.

**IN-01 is folded in; IN-02 is not.** This plan's Task 2 edits the body of `handleIoRegisters`,
which is where IN-01's discarded classification sits, so removing it costs nothing extra.
IN-02 lives in `textmon-profile.ts` and is addressed, in the documentation half only, by plan
42-12 — recorded there rather than left unmentioned.

**Canon-referral drop (prohibition probe, stage 2):** injection / path-traversal / OWASP-class
constraints on the command path are owned by `TEXT_COMMAND_ALLOWLIST` and `buildTextCommand()`.
Not minted here.
</plan_decisions>
