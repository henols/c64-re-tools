<objective>
Fix the Wave-0 blocking defect: `probeCpuHistory()` sends `CPUHISTORY_GET` (0x86) with
`count=0`, which real VICE rejects with `InvalidParameter` (0x81) — an error code the
function does not classify, so it propagates out of `resolveCapabilities()` and fails
the **entire** stock connect handshake on any genuine VICE >= 3.10 build.

Purpose: nothing else in Phase 7 is reachable until this lands. `vice_cycles_stopwatch`'s
Route A gates on `session.capabilities.cpuHistory === "available"`, and that field can
never be reached on a real >= 3.10 build while the handshake itself throws at Step 5.
Output: a corrected probe plus the committed regression fixture matching the live
capture in `07-RESEARCH.md`.
</objective>

Change `probeCpuHistory()`'s request from `clampCpuHistoryCount(0)` to a count of `1`.
A count of `1` is the minimum VICE accepts (`monitor_binary.c:1491-1497` rejects
`requested_count < 1` with `INVALID_PARAMETER`), and it is the value
`docs/phase1-probe-results.md`'s own already-live-verified probe has always used. Keep
the request routed through `clampCpuHistoryCount()` so the single clamping seam still
owns the uint16-wrap guard described in `CPU_HISTORY_MAX_COUNT`'s comment; do not build
a second clamp.

Add `ErrorCode.InvalidParameter` (0x81) to the classified outcome set, mapping to
`"absent"`. Write the reason into the code comment beside it, concretely: with a
well-formed `count=1` request, a 0x81 can no longer originate from this client's own
malformed count, so it means the connected build's `CPUHISTORY_GET` rejected a minimal
well-formed request and the route is unusable on this build. `"absent"` is the correct
three-value collapse because `resolveCapabilities()`'s existing cache comment already
documents `"absent"` and `"not_compiled_in"` as both meaning "never attempt
CPUHISTORY_GET again", differing only in why. Do **not** widen `CpuHistoryCapability`
to a fourth member — that type is pinned by `vice_ping`'s own `capabilities` answer and
by `backend-detect.mts`'s boolean cache schema, and this phase does not touch either.

Update `clampCpuHistoryCount()`'s doc comment where it says "This handshake only ever
probes with count 0" — that sentence becomes false with this change and must state the
new value and why (0 is a malformed request on real VICE, not a valid "give me the
newest entry" request). Leave the function's own behaviour (floor of 0 for callers that
genuinely pass 0) unchanged; only the handshake's own call site and the comment change.
  </action>
