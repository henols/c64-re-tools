<objective>
Close **Gap 2** (07-VERIFICATION.md gap 2, findings **WR-01** and **WR-02**): make
`vice_run_until` honest about what happened and about the state it leaves the machine in.

The cleanup *mechanism* is correct and is not being touched — `temporary: true` on
`CHECKPOINT_SET`, exactly one `CHECKPOINT_DELETE`, `ObjectMissing` tolerated as benign, the delete
skipped entirely on `MachineRestartedError`, 15/15 unit tests green, live-checked against both real
binaries. Two reporting defects are:

- **WR-01** (`stock-run-until.ts:252-279`): when the cleanup delete comes back `ObjectMissing`, the
  code correctly recognises that VICE auto-deletes a temporary checkpoint the instant it fires
  (`mon_breakpoint.c:605-607`) — meaning the address almost certainly *was* reached — and then
  files that away as `cleanup: "already_gone"` while the top-level answer still asserts
  `reached: false, timedOut: true`. The strongest available signal is discarded and a falsehood is
  asserted in its place.
- **WR-02** (same region, live-reproduced in 07-REVIEW.md): the timeout path's own cleanup
  `CHECKPOINT_DELETE` halts the emulated machine — on stock, any inbound byte does
  (`monitor_binary.c:281`) and only `EXIT` resumes — and nothing resumes it. No field in the answer
  says so, while the `explanation` actively steers the caller away from suspecting a stopped
  machine. This is the one tool whose entire purpose is to not look like a wedge.

Purpose: a bounded answer that a triage agent can act on without being misled.
Output: a race-resolving timeout path, an explicit halted report on every answer, and tests that
fail if either regresses.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| tool arguments (`address`, `cycles`, `timeout_ms`) -> `handleRunUntil()` | Agent-supplied, unvalidated input; D-02's existing validation is the guard and stays intact |
| binary monitor socket -> `readProgramCounter()` / `CHECKPOINT_DELETE` reply | Untrusted wire input; a malformed `REGISTERS_GET` reply must not fabricate a PC |
| the answer payload -> a triage agent's next destructive decision | A wrong `reached`/`machineHalted` value can send an agent to `vice_recycle`, which kills the instance |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-14-01 | Spoofing | the `reached` field | mitigate | Task 1 forbids asserting `reached: false` on an unresolvable race; a fabricated PC value is forbidden, and the unresolved case omits the field rather than guessing. |
| T-07-14-02 | Repudiation | machine state after a timeout | mitigate | Task 2 makes `machineHalted` unconditional, so a halted machine can never be silently attributed to a wedge and escalated to a destructive recycle. |
| T-07-14-03 | Denial of Service | the added PC read | mitigate | The PC read happens only on the `already_gone` branch, is wrapped in its own try/catch, and is skipped entirely on `MachineRestartedError` (asserted in Task 3) so a dead instance is never probed. |
| T-07-14-04 | Tampering | `readProgramCounter()`'s wire reply | mitigate | The helper resolves the PC register id from the live `REGISTERS_AVAILABLE` catalog and throws when the reply omits it, rather than reading a hardcoded id or index. |
| T-07-14-05 | Elevation of Privilege | resource-set surface | mitigate | This plan adds no `RESOURCE_SET` path, so CLAUDE.md's three power-cycling resources stay unreachable from this tool. |
| T-07-14-SC | Tampering | npm/pip/cargo installs | mitigate | No package installs; no new dependency permitted. |
</threat_model>
