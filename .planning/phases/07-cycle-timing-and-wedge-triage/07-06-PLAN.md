**`resolveStockLiveIrqHandler(session)`** — the same three-read algorithm:
1. Read `$01` (1 byte) via `session.client.send(CommandType.MemoryGet, memGetBody({

   vector target.

   out — read `$FFFE`-`$FFFF` and use the hardware vector pair instead.

carrying the same substance as the fork's (which pair was used, why, and what it
resolves to). Memoise nothing — a disk swap, reset or different game retargets the
handler, so a cached address silently resolves the wrong pair.

banking discipline applies to **I/O-space registers** (`$D000`-`$DFFF`); `$01`, `$0314`
and `$FFFE` are the processor port, RAM and ROM in the CPU's own view, which is exactly
what the IRQ dispatch itself reads. Say so in a comment so a future reader does not
"fix" this into an `io`-bank read.

**Registration shape (the decision the pattern map flagged).** `handleDiagnoseStock` is
registered with `withDerivedTool("vice_diagnose", { needsSession: false }, ...)` and
acquires its own session by calling `ensureStockSession(deps)` inside its own
try/catch. Rationale, to be written into the file's header comment: the fork's
`handleDiagnose()` never throws past its own boundary and always answers
`isError: false` with a verdict, and `withDerivedTool({ needsSession: true })`'s
preamble would convert a `MonitorOwnershipError` into refusal *text* before this
handler's own return value existed — turning the fifth verdict into exactly the generic
error string it exists to replace. Also record the deliberate exception being taken:
`DerivedPureHandler`'s doc comment says a `needsSession: false` handler "structurally
cannot reach the wire"; this tool is the one declared exception, because it must own its
own session-acquisition error handling. Amend that doc comment in `stock-derived.ts` in
plan 07-09 (the registration plan), not here.

**Bounded acquisition (finding 4).** Wrap the `ensureStockSession(deps)` call in a race
against a deadline, `DIAGNOSE_SESSION_TIMEOUT_MS`, defaulting to `10000` and overridable
via the environment variable `VICE_STOCK_DIAGNOSE_SESSION_TIMEOUT_MS` (the same
env-override convention `CAPTURE_STEP_TIMEOUT_MS` uses in `vice-proxy.ts`). The failure
being diagnosed *is* an indefinite hang with no reply and no EOF; a diagnostician that
blocks while diagnosing a block is the defect. On deadline expiry return an
`isError: true` result naming the elapsed bound and stating that this state is
behaviourally indistinguishable from a second client holding the monitor socket, and
pointing at `monitor_held_elsewhere`'s remedy — do **not** invent a sixth verdict and do
**not** report one of the five it did not establish.

**Check order** (cheap to expensive, mirroring the fork's D-14 ordering):
1. Session acquisition, bounded as above. `MonitorOwnershipError` →
   verdict `monitor_held_elsewhere`, carrying `holderGrantId`, `holderClaimedAt` and
   `port` as evidence, at zero emulator calls. `MachineRestartedError` → verdict
   `restarted`, carrying `baselineEpoch` and `currentEpoch`.
2. Epoch comparison — zero emulator calls. Compare the epoch currently on disk at
   `session.deps.epochPath` against `session.baselineEpoch`; a difference is verdict
   `restarted`.
3. `gatherStockCheckpointTrapEvidence()` — several reads, **no resume**. `isTrap` →
   verdict `checkpoint_trap`, carrying the matched checkpoint, the trap reason, the PC
   and the IRQ-handler explanation.
4. The liveness bracket — the only step that resumes.

**`runStockLivenessBracket(session)`** (Pattern 5, exported for plan 07-07). Exactly:
one `readCycleBaseline()` (a halting read), one `CommandType.Exit` (resume), one
`await` on a real `setTimeout` of `DIAGNOSE_BRACKET_WINDOW_MS` — default `250`,
overridable via `VICE_STOCK_DIAGNOSE_BRACKET_MS` so tests run in milliseconds — with
**zero** socket traffic inside the wait, then one `readCycleBaseline()` (a halting read
which both re-pauses and samples). Return `{ route, before, after, advanced, elapsedMs }`.
`advanced` is: on the `cpu_history` route, `after.cycle > before.cycle`; on the
`frame_position` route, `after.position !== before.position || after.pc !== before.pc`
(both must be identical to call it stalled, because a frame position can alias across
exactly N frames — record that residual in the answer's evidence); on the `unavailable`
route, `null`, and the verdict path must then report the bracket as inconclusive rather
than as wedged. Write a header comment stating why this function deliberately uses
wall-clock time, unlike `vice-sync.ts`'s standing rule: that rule's rationale depended on
a non-pausing `vice_ping`, and stock has no non-pausing observation of any kind
(`monitor_binary.c:281` halts on any inbound byte).

Run a second bracket only when the first shows no advance — mirroring the fork's
short-circuit — and only then return verdict `wedged`. Any advance returns `live`.

**The verdict set is exactly five** (D-03): `["restarted", "checkpoint_trap", "wedged",
"monitor_held_elsewhere", "live"]`. Declare it as an exported frozen array
`STOCK_DIAGNOSE_VERDICTS` so the manifest `enum` in plan 07-09 and the tests both drive
one list. `stale_read_path` is deliberately absent: it exists on the fork only because
the fork mixes a non-pausing `vice_ping` with pausing reads, and on stock every read
pauses uniformly, so the state is unreachable by construction. Put that sentence in the
source as a comment — a missing verdict with no recorded reason reads as an oversight.

Every answer goes through `stockAnswer(session.client, payload)` and carries: `verdict`,
`evidence` (the per-check facts gathered), a human-readable `report` string, and
`machinePaused: true` on any path that ran a bracket (the final halting read leaves the
machine paused; the skill documents this and callers must not read it as a symptom).
The handler never throws: wrap the whole body so any unexpected error becomes a
well-formed `isError: true` result naming the stage it failed at.
