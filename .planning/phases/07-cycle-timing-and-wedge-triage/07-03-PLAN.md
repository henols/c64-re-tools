<objective>
Build `vice_run_until` for the stock backend: arm a temporary stopping exec checkpoint
at the requested address, resume once, wait event-driven for that specific checkpoint's
`CHECKPOINT_INFO`, and guarantee cleanup on each of the three named failure paths.

the existing `VICE_MCP_TIMEOUT_MS` default so one number governs both layers).

missing on stock, and the wedge-triage skill currently documents `vice_run_until` as
having *no working timeout* — a call against an unreachable address is indistinguishable
from a wedge.

table and manifest is plan 07-08's job, not this one.

  <action>
Create `.claude/mcp/vice/stock-run-until.ts` exporting `handleRunUntil:
StockSessionHandler` and a module-local `waitForCheckpointHit()`.

**Argument handling.**
`address` goes through `parseAddress(args.address, { what: "vice_run_until address" })`
— no second parser. When `address` is absent and `cycles` is a positive number, refuse
with the fork's own wording: `cycles-only mode not yet implemented; provide an address`
(`mcp_tools_debug.c:772`). Matching that refusal, rather than inventing a
cycles-bounded execution the fork never shipped, is what TIME-03 requires. When both
`address` and `cycles` are absent, refuse naming `address` as required.

`timeout_ms` is the new stock-only optional argument (D-02). Default `30000` when
absent, exported as a named constant `RUN_UNTIL_DEFAULT_TIMEOUT_MS = 30000` with a
comment citing D-02 and the `VICE_MCP_TIMEOUT_MS` default it matches. Validation:
a present `timeout_ms` that is not a finite number, or is `<= 0`, is **refused** with a
message naming the offending value and the valid range — never silently coerced to `0`
(an instant spurious timeout) and never to the default. A value above
`RUN_UNTIL_MAX_TIMEOUT_MS = 600000` is clamped to that ceiling and the answer carries
`timeoutClamped: true` so the caller is told rather than quietly given a different
deadline. Truncate fractional values with `Math.trunc` after the finiteness check,
matching `clampCpuHistoryCount()`'s discipline.

**Arming.** Send `CommandType.CheckpointSet` with
`checkpointSetBody({ start: address, end: address, stop: true, enabled: true,
operation: CheckpointOperation.Exec, temporary: true, memspace: 0x00 })`. Narrow the
reply on `response.type !== "checkpoint_info"` before reading `response.checkpoint.id`.
Write a comment at this call site stating it is this codebase's first `temporary: true`
caller and why (VICE auto-deletes the checkpoint on hit,
`mon_breakpoint.c:605-607`), so a reviewer reading `handleCheckpointAdd`'s
`temporary: false` comment knows this divergence is deliberate.

Do **not** call `registerTraceCheckpoint()` — that guard exists for `stop:false` trace
checkpoints, and this checkpoint always stops.

**Wait.** `waitForCheckpointHit(client, checkpointId, timeoutMs)` installs one
`client.on("event", ...)` listener, narrows with the same predicate shape
`isCheckpointInfoEvent()` uses (check the parsed item's own `.type === "checkpoint_info"`
discriminant, then `item.checkpoint.id === checkpointId`), and resolves with that event.
It races that against a single `setTimeout` deadline. It must remove its listener in a
`finally` on every path — resolve, timeout, and rejection — so a long session never
accumulates listeners. It must also settle if the client emits its disconnect/close
signal, so a socket that dies mid-wait produces a decision rather than sitting until the
deadline.

Order matters: install the listener **before** sending `CommandType.Exit`, so a
checkpoint that fires immediately after the resume cannot be missed in the gap. Send
`Exit` exactly once — the one-resume-per-wait invariant, preserved in its stock-native
form.

**Three cleanup paths.**
- *Hit*: return `stockAnswer(session.client, { requested: "run_until", reached: true,
  address, checkpointId, hitCount, timeoutMs })`. Call **no** `CHECKPOINT_DELETE` —
  VICE already deleted it. Put that reason in a comment citing
  `mon_breakpoint.c:605-607`.
- *Timeout*: send `CommandType.CheckpointDelete` with `cpNumBody(checkpointId)` exactly
  once. Catch `StockProtocolError` with `errorCode === ErrorCode.ObjectMissing` and
  treat it as benign "already gone" (the hit landed between the deadline firing and the
  delete), recording `cleanup: "already_gone"` in the answer; any other wire error is
  recorded as `cleanup: "delete_failed"` with the converted text, and the answer still
  returns. Return an answer with `reached: false`, `timedOut: true`, the address, the
  effective `timeoutMs`, and an explanation naming that an address which never executes
  looks exactly like a wedge — the trap `vice-wedge-triage/SKILL.md` documents.
- *Machine restarted mid-wait*: when a `MachineRestartedError` surfaces from any step
  after arming, attempt **no** delete at all — the instance and every checkpoint on it
  are already gone — and let the error propagate to `withDerivedTool()`'s own
  `convertWireError`/`convertHandshakeError` seam so the standard restarted wording is
  produced by the one existing converter rather than a second one written here.

Never wrap all three paths in a single undifferentiated `finally { delete }` — that is
the exact first-draft mistake Pitfall 4 names.

| Threat ID | Category | Component | Disposition | Mitigation Plan |

| T-07-02 | Denial of Service | `handleRunUntil()` timeout and cleanup paths | mitigate | `timeout_ms` is refused when non-finite, `NaN` or `<= 0` (a `0` would produce an instant spurious timeout) and clamped at `600000`; the timeout path sends exactly one `CHECKPOINT_DELETE`, asserted by call count, so an unreachable address cannot leave an armed checkpoint behind for the session's life |
| T-07-09 | Denial of Service (resource leak, client side) | `waitForCheckpointHit()` | mitigate | The `event` listener is removed in a `finally` on every path; test 9 asserts the listener count returns to baseline after 20 timed-out calls |
