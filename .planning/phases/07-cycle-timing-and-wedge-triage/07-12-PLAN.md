The phase's own `deferred-items.md` records the failure: a real `count:1` reply is **52 bytes**

minimum, `stock-protocol.ts:1436`). Every existing unit test for this case builds a synthetic body
from the same wrong assumption as the code, so the suite cannot catch it — the exact
shared-assumption failure mode Phase 2's and Phase 5's post-mortems warned about. This plan
therefore captures the real bytes **first**, commits them as fixtures, and only then changes the
parser.

Rewrite the `case ResponseType.CpuHistoryGet:` block (currently line 1417) so its offsets come from
the wire's own self-describing fields, matching what `monitor_binary_process_cpuhistory()` actually
writes. The layout the source establishes (confirm it yourself against the file, then confirm it
decodes the Task 1 fixtures):

  - Body starts with `count` as `uint32LE` at offset 0.
  - `response_size = 4 + count * (item_size + 1)`, so the **entry stride is `1 + item_size`** and
    `item_size` is the byte count of everything AFTER its own size byte — NOT the register-block
    length the current code assumes. That single misreading is the whole defect.
  - Inside one entry, after the `item_size` byte: a register block written by `write_registers()`
    — `regCount` as `uint16LE`, then `regCount` items of `size(1) + id(1) + value(uint16LE)` where
    the per-item stride is that item's own declared `size + 1` (identical discipline to the
    `RegisterInfo` case at line 1242).
  - Then `cycle` as `uint64LE` (`write_uint64(current->cycle, ...)`).
  - Then a one-byte `instruction_length` field, then exactly `instruction_length` bytes of
    instruction data: opcode, p1, p2, and a trailing `0xff` placeholder for a third parameter that
    exists on some machines.

Two semantic corrections the source forces, both of which must be stated in the comment:
  - `instruction_length` is a **hardcoded constant 4** in VICE (`uint8_t instruction_length = 4;`),
    not the real length of the decoded 6502 instruction. Nothing may treat
    `ParsedCpuHistoryEntry.instructionLength` as an instruction size.
  - The per-entry `LIN`/`CYC` registers are hard-filled with the sentinel `0xffff`, so the register
    block still must not be interpreted as raster position. Keep that existing rule.

Implementation requirements:
  - Every read is preceded by a `need()` call for the absolute body offsets it touches — no
    entry-relative arithmetic that can wrap past the body end. Compute `entryEnd = offset + 1 + itemSize`,
    `need(body, entryEnd, ...)` once up front, and then assert each inner field fits **within
    `entryEnd`** as well as within the body; an entry whose declared `item_size` does not leave room
    for `regCount`, the register items, `cycle`, `instruction_length` and its `instruction_length`
    data bytes is a `StockFramingError` naming the observed `item_size` and what did not fit.
  - Reject `count > 65535` up front with a `StockFramingError` naming the observed count and the
    ceiling: VICE's own `count` is a `uint16_t` (`monitor_binary.c:1492`), so a larger declared
    count is a desynced or hostile frame, and iterating it is a denial-of-service loop.
  - Require at least 3 instruction data bytes before reading `opcode`/`p1`/`p2`; a shorter declared
    `instruction_length` is a `StockFramingError`, so `ParsedCpuHistoryEntry`'s fields stay
    non-nullable numbers.
  - Advance `offset += 1 + itemSize` per entry — the stride from the source, never a recomputed sum
    of the fields just read.
  - Keep `cycle` a `bigint` via `readBigUInt64LE`. Do not narrow it here.

Provenance comments (WR-13). Replace the `confirmed against monitor_binary.c:1563-1617` claim on
this case, and the two `[CITED monitor_binary.c:1563-1617]` tags on `ParsedCpuHistoryEntry` /
