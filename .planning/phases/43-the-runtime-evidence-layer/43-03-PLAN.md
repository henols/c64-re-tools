<objective>
Give the measurement bracket a reset the session can actually reach: one
stock-only MCP tool that clears VICE's accumulated memory-access map and then
proves it cleared.

Purpose: EVID-05 requires a bracket that can be reset and re-measured without
a previous run's observations leaking into it. A bracket has two halves -- the
emulator's own accumulating access map, and the store's rows for a run
identity. This plan ships the first half. Plan 43-06 ships the second.

Output: `vice_memmap_zap`, registered through the six surfaces every derived
stock text tool already registers through, verified live against genuine stock
VICE.

## Why the tool dials TWO commands and not one

`memmapzap` is a clear, not a query: on its own it returns an
acknowledgement, and an acknowledgement is not evidence that anything was
cleared. So the handler dials `memmapzap` and then dials `memmapshow`, parses
the second reply through the shipped `parseAccessMap()`, and returns the
post-zap `addressesWithRecordedAccess` and `addressesQueried` figures. Two
things follow from that choice and both are deliberate:

  1. **The build-capability verdict is borrowed, not invented.**
     `classifyTextCapabilityResponse` is documented to render a
     build-capability claim only for the two members of
     `CPUHISTORY_GATED_COMMANDS`, whose disabled stub string is
     source-traced. Whether `memmapzap` prints that same stub on a build
     without `FEATURE_CPUMEMHISTORY` is NOT known from any source read in
     this phase, so `memmapzap` is deliberately NOT added to that set.
     Classifying the `memmapshow` reply instead reuses the proven guard and
     asserts nothing new. This is the honest route, and it is recorded here
     rather than left as an apparent oversight.
  2. **The answer carries an observable post-condition**, which is what makes
     the tool's own live test able to assert a relation rather than trust a
     status string.
