<objective>
Make the layer askable. Three verbs: where do the two classifiers disagree,
what evidence does this store hold, and reset this bracket.

Purpose: EVID-03 wants a user to ask where the byte-derived block
classification and the observed-execution evidence disagree and get the
disagreements first, with the block table left byte-derived and never
overwritten. EVID-04 wants every summary to carry its denominator and no
rendering to state `data` from absence. EVID-05 wants a bracket that can be
reset and re-measured without a previous run's observations leaking into it --
this plan ships the store-side half, beside plan 43-03's emulator-side half.

Output: `anno_evid_disagreements`, `anno_evid_runs` and `anno_evid_reset`,
plus a CLI route for the disagreement query.

## Three states, three renderings

`43-RESEARCH.md` Open Question 3 asked whether the disagreement query needs a
CLI route in addition to an MCP tool. It gets both, and the reason is not
convenience: EVID-03's own criterion is that "a planted test proves the
disagreement state is reachable and rendered distinctly from both agreement
and silence". A rendering is what makes "rendered distinctly" testable, and
the MCP tool returns JSON that a test can only inspect structurally. The CLI
route is where the three states become three different pieces of text, so the
planted test has something to distinguish.

The three states, and what each renders as:

  1. **disagreement** -- the block table says `data` and the emulator was
     observed executing. Rendered first, as rows, with a heading naming it
     the highest-value output.
  2. **agreement** -- rendered as a single count line, never as rows.
  3. **silence** -- no observation exists for an address the block table
     covers. Rendered as its own count line, with wording that states
     absence proves nothing rather than implying the address is data.

A fourth line reports observations outside any block and observations at an
explicitly-undefined block, so a reader summing the lines gets what the block
table covers and never what the program is.

## The RangeRow to BlockEntry mapping is reused, never duplicated

`blocksFromStore()` in `anno-cli.ts` is the one place a `RangeRow` becomes a
`BlockEntry`, and its own comment records why the `dataType` column is copied
verbatim and never compared there. The dispatch arm reuses it through a lazy
`await import("./anno-cli.ts")` inside the arm -- the same lazy pattern
`vice-proxy.ts` already uses to reach `runAnnoCli` -- rather than a static
import, because a static import would pull the whole CLI and its coverage,
memmap-render and export-asm dependencies into the MCP server's startup path.
Do NOT re-implement the three-field mapping: a second mapping site is a
second answer to "what class is this address", which is the boundary
`block-class.ts` exists to keep at one.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| MCP caller to the query and reset verbs | Run-identity filters and the reset's identity arrive from an agent and reach SQL parameters; the reset is destructive to evidence. |
| Caller-supplied store path to filesystem | An unconfined path is a store file created wherever the argument pointed. |
| The evidence layer's answer to an agent | Field names and rendered lines cross out to a reader who will act on them; a mis-named count is read as a claim about the unobserved remainder. |
| The query path to the block table | A query that could write would collapse the independence the disagreement signal rests on. |
