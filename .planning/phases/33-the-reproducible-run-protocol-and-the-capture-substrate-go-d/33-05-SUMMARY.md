# Phase 33 Plan 05: The Deterministic Stock Argv and the Re-grounded Warp Claim — Summary

**`buildViceArgs()`'s stock branch is now deterministic by construction — five nondeterminism sources pinned at launch, `-raminitrandomchance 0` the load-bearing one against a factory value of 10 — with `-console` at argv index 1 and `-warp` as additive, assertion-pinned launch knobs, the fork argv untouched, and the one sentence in the tree that stated a falsehood about VICE replaced by one that states both true things.**

## Accomplishments

- **The determinism block ships, unconditional on stock.** `-seed 4242`, `-raminitstartrandom 0`, `-raminitrepeatrandom 0`, `-raminitrandomchance 0`, `+autostart-delay-random`, in one fixed order between `-drive8type 1541` and `-binarymonitor`. `-raminitrandomchance` is the load-bearing one: the factory value on this build reads **10**, i.e. 0.1% of all RAM bits randomly flipped at power-up, which is the dominant term in the divergence this milestone removes (59 of 4080 addresses in the untouched `$C000-$CFEF` window → 0, 33-RESEARCH.md M3). `+autostart-delay-random` is a **fifth** flag beyond `REPRO-01`'s text and is recorded in the code comment as a deliberate addition, with the effect that is easy to miss named: it also selects *which* keyboard-buffer feed injects `RUN` (`kbdbuf_feed_runcmd` vs `kbdbuf_feed`), so disabling it is a behavioural change and not only a timing one.
- **`-console` at index 1 is now pinned by an assertion rather than by a comment.** The measured failure it protects against is a process that *dies* — `[-default -drive8type 1541 -console -binarymonitor]` exits with `Gtk-WARNING: cannot open display:` while `[-default -console -drive8type 1541 -binarymonitor]` is alive and bound — because `-console` is handled in the same `main.c` prefix scan as `-default` and `console_mode` gates GTK init at two call sites that both run before the late parser.
- **`-warp` and `-console` are additive, never an argv override.** `profile` maps to exactly two literal flag tokens and to nothing else: no `extraArgs`, no passthrough string, no argv element derived from a `profile` *value* (T-33-04). `VICE_ARGS` stays the single deliberate operator-only whole-argv override and still short-circuits ahead of both branches with a `profile` present — asserted.
- **The fork branch did not move, and now says so out loud.** Both pre-existing fork whole-argv assertions are byte-identical, each carries a new comment recording that fork argv byte-identity is a Validated v0.2.0 requirement rather than an ordinary expected-value-update site, and a third fork case proves `profile` has no path to that branch at all.
- **The stale warp sentence is re-grounded in the same commit as the table generated from it.** `vice_machine_config_set`'s reason no longer asserts, unqualified, that warp cannot be toggled while running — that was refuted live on 2026-08-27. It now states both true things: there is no runtime `WarpMode` resource at all (measured `err=0x01` OBJECT_MISSING over `RESOURCE_GET` (0x51) on VICE 3.9), and runtime warp toggling on stock exists only as a text-monitor command, a channel this project does not dial.
- **The generated host artifact was regenerated by its build step, not hand-edited**, and staged in the same commit as its `.mts` source. `HOST_BOUND_ARTIFACTS` is unchanged at eight entries — no new host-bound module appears in this phase.

## Decisions Made

1. **Where the four inherited assertions landed.** The plan assigned one whole-argv assertion to Task 1 and "the other four" to Task 2, while Task 1's own `<verify>` block demands `node --test broker-launch.test.ts` report `fail 0`. Both cannot hold: the determinism block is unconditional, so all five move the moment `buildViceArgs()` changes. The four expected arrays were therefore updated inside Task 1's commit as a mechanical necessity, and Task 2 delivered everything else it specifies. No commit in this plan is red at any point in its history.
2. **Which one-time note the idempotency test observes.** `warnedBinmonBindWidened` is module state consumed by the pre-existing note-once test earlier in the same file, so "exactly one binmon note" is unobservable from any later test. The new test drives the widened-bind branch with `binmonHost: "0.0.0.0"` three times exactly as the plan asks, and observes the second, genuinely-unconsumed `-remotemonitor` note for its "exactly one" assertion — additionally asserting **zero** further binmon notes, which is what proves the gate was not reset. A file-position comment records that this test must stay the only site widening the text-monitor bind.
3. **`Object.freeze` on the exported block.** `readonly string[]` is erased at runtime. A caller mutating the shared array would produce a launch whose argv silently stopped matching the seed a capture record cited, which is precisely the class of drift the export exists to prevent.
4. **No speedup number in the public capability table.** The measured ~1.97× is a fact about *this host*; publishing it in a generated capability table would present it as a fact about the tool. It lives in the code comment beside the `-warp` emission, where the reader deciding whether to request warp will see it, together with the two facts that matter more: `AUTOSTART` turns warp on by itself during the load whatever argv says, and warp is behaviour-neutral under a frame-anchored protocol but invalidates a wall-clock bracket by 1.76×.
