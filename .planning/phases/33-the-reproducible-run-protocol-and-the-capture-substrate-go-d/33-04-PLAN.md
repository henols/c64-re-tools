<objective>
Produce a flat 64K image by slicing a VICE `.vsf` snapshot's `C64MEM` module body,
with no transcription step anywhere — and make the slicer refuse a malformed
snapshot rather than returning a plausible 65536 bytes of garbage.

Purpose: `CAP-01` exists because the transcription route already lost data twice —
one 32 KB write truncated mid-payload, one 8 KB write dropping ten characters
localised to `$7871`. The snapshot route removes the transcription step entirely.
It also removes a 4096-address exclusion: the `.vsf` `C64MEM` array is `mem_ram[]`,
RAM *under* I/O rather than the register read view, so `$D000-$DFFF` is not
volatile on this route at all.

Every downstream number in this milestone is measured on this substrate, which is
why refusing beats guessing: an offset-based slicer, or a byte-by-byte resync
fallback that locks onto a false module-name string inside 64 KB of RAM data,
returns something 65536 bytes long that is not the machine's memory. That is the
worst available failure mode here and this plan's central acceptance criterion.

Output: `src/mcp/vice/vsf-slice.ts` plus its test and four synthetic fixtures, and
a skill-side CLI wrapper that reaches the same module rather than duplicating its
knowledge.

This plan is emulator-free. It runs concurrently with 33-03's live measurement and
33-05's argv work; none of the three share a file.
</objective>

**Named constants, computed not literal.** `SNAPSHOT_MAGIC` is the 19-byte
`"VICE Snapshot File"` plus `\x1a`; `SNAPSHOT_MACHINE_NAME_LEN` is 16;
`SNAPSHOT_VERSION_MAGIC` is the 13-byte `"VICE Version"` plus `\x1a`;
`MODULE_HEADER_LEN` is 22. Derive `FIRST_MODULE_OFFSET` as
`19 + 2 + 16 + 13 + 4 + 4`, which evaluates to 58 — write the arithmetic, not the
number, so the derivation is checkable. The two bytes after the magic are the
snapshot major and minor; the 16 after that are the NUL-padded machine name
(`"C64SC"` on this build); then the version magic, 4 VICE version bytes
(`03 09 00 00`), and a 4-byte SVN dword. Body constants: `RAM_OFFSET` 4,
`RAM_SIZE` 65536, `MIN_C64MEM_BODY_LEN` = `RAM_OFFSET + RAM_SIZE + 3` = 65543
(snapshot minor 0), `V01_C64MEM_BODY_LEN` = `MIN_C64MEM_BODY_LEN + 4 + 4 + 4` =
65555 (minor 1).

**`listSnapshotModules(bytes)`.** Verify the leading magic and refuse by name if
absent. Then walk strictly from `FIRST_MODULE_OFFSET`: at each offset read the
16-byte name as latin1 with trailing NULs stripped, the major and minor bytes, and
the size as **u32LE at header offset 18** — the size covers the module's own
22-byte header. Bounds-check before every read. If the size is below
`MODULE_HEADER_LEN`, or `offset + size` exceeds the file length, **throw** a
`VsfSliceError` naming the offset, the decoded name and the size, and stating that
it is refusing rather than rescanning. Advance by the module's size — never by one
byte. After the loop, assert the final offset equals the file length exactly and
throw naming both numbers if it does not; that terminal equality is the cheapest
whole-file integrity check available and it is what catches a future VICE adding a
third magic block loudly instead of silently. Return an array of
`{ name, major, minor, offset, size, bodyOffset, bodyLength }`.

**`sliceC64Mem(bytes)`.** Call `listSnapshotModules`, then select the entries
named exactly `C64MEM`. Zero matches: throw listing the names that WERE found, in
`extractEntry`'s register. Two or more: throw naming the count and both offsets —
a duplicated module name is a malformed snapshot, not a first-wins situation.
Then check the body length: below `MIN_C64MEM_BODY_LEN`, throw naming the observed
length and the minimum. Copy the RAM array out as a new 65536-byte buffer from
`bodyOffset + RAM_OFFSET`. Read the three suffix bytes immediately after the RAM
array: `dataOut` at `RAM_OFFSET + RAM_SIZE`, `dataRead` at `+ 1`, `dirRead` at
`+ 2`. Those two `*_read` fields are the **CPU-visible** values — the 4-byte
prefix is `(pport.data, pport.dir, EXROM, GAME)` and is deliberately NOT the
normalisation source, because on the measured snapshot the prefix reads
`[231,47,0,0]` while the suffix reads `[39,55,47]` and the live registers gave
`$00=47 $01=55`. Return
`{ ram, dataOut, dataRead, dirRead, snapshotMinor, bodyLength }` and record which
snapshot minor produced which body length in the returned record, so a caller can
tell 65543 from 65555 without re-deriving it.

Resolve the cross-package hazard deliberately, and record which of the two

**The constraint, restated so the choice is visible.** `anno-d64.ts`'s header
records it as measured: the MCP server ships as one npm package whose file list
covers only `src/mcp/vice/`, the skills ship in the other package, and no skill
script in this tree imports the MCP tree today. Two answers exist: (a) a
self-contained skill-side script that carries its own copy of the layout, on the
`d64-parse.mjs` / `anno-d64.ts` two-independent-copies precedent, or (b) an
MCP-side CLI entry point the skill invokes.

**Take (b).** Reason: `.vsf` layout knowledge is a single-seam concern in this
tree, and a second copy of a byte layout whose whole purpose is to be the one
authoritative reading of the snapshot format is exactly the anti-pattern the
project names. The `d64-parse.mjs` precedent is two copies of a *stable, published*
disk format; the `.vsf` layout is version-sensitive and this phase has already
found one stale copy of it. Record this choice and its reasoning in the wrapper's
header, citing `anno-d64.ts`'s constraint paragraph, so the next reader sees a
decision rather than an oversight.

**MCP-side CLI entry.** Give `vsf-slice.ts` a `#!/usr/bin/env node` shebang and a
`main()` guarded so it runs only when the module is the process entry point —
never on import, because the module must stay side-effect-free for the structural
census and for `capture-predicate.ts`'s use of it. `main()` does the file I/O the
module's own functions refuse to do: read the named `.vsf`, call `sliceC64Mem`,
and write the flat image. Verbs and flags: `slice <snapshot.vsf> --out <image.bin>`
writes the 65536-byte image and prints a one-line summary carrying the snapshot
minor, the body length and the three suffix values; `slice … --json` prints that
summary as JSON instead; `digest <snapshot.vsf>` prints the sha256 of the sliced
image without writing a file. A refusal from `sliceC64Mem` exits non-zero with the
module's own message on stderr — no message is rewritten or softened at the CLI
boundary.

**Skill-side wrapper.** `src/skills/c64-ram-capture/scripts/vsf-slice.mjs`, in
`compare.mjs`'s verb-dispatch shape, forwards its argv to the MCP-side entry
point. It resolves that entry point through a documented ladder and **refuses by
name** when every rung fails: (1) `$VICE_MCP_DIR/vsf-slice.ts` if the environment
variable is set; (2) the in-repo relative path from the script's own
`import.meta.url` (the plugin distribution keeps both trees in one checkout);
(3) `createRequire(import.meta.url).resolve("@henols/vice-mcp/vsf-slice.ts")` for
the npm-installer route. On total failure, exit non-zero with a message naming
