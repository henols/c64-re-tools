## The fixture question, answered plainly

Research emphasis #1 asked for an honest answer rather than a demonstration against a table
that does not exist. Both the researcher and the pattern mapper independently read the
committed bytes and reached the same finding: **no committed fixture currently carries a
store-typed data or graphics table ready for a `!binary` swap.**
`fixtures/ghidra/charset-phantom.annostore.json` types its `$1000..$17ff` range as `"code"`,
and Phase 37/45 tests depend on it staying that way.

**Decision, stated rather than worked around:** the demonstration uses the committed
`fixtures/ghidra/charset-phantom.prg`'s **own real bytes** for `$1000..$17ff`, with a store
this test builds for itself (through `buildStoreOverImage()`) that types that range
`external_file`. The committed `.annostore.json` is not touched.

This is a real character-set table and not a synthetic stand-in, and the fixture's own header
comment is the evidence: `$D018 = $04` and `$D011 = $1b` derive a character-set base of
`$1000` with a 2048-byte size, and the range is `$1000-$17ff` exactly — "matching
`CHARACTER_SET_SIZE`". The committed store types those bytes `code` because that fixture's
purpose is to show an analyser minting phantom function labels across a character set; the
bytes are a character set either way. Typing them as data in a test-local store is the honest
reading of what they are, not a convenient relabelling.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| image bytes -> a `.bin` file on disk | Whole ranges of a program's bytes are now written out as standalone files a person is expected to edit. |
| a hand-edited `.bin` -> the next export | The user's edit is durable work the tool did not create; a re-export is where it would be destroyed. |
