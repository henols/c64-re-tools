address-to-enum association, and take the `SCHEMA_VERSION` bump that comes with
it — deliberately, with the cost named.

manifest, so `MCP-01`'s mechanical derivation check requires a route for it, and
the Phase 28 store has no table that associates an enum with an address. D-15 is
the owner's decision to add the table and bump rather than to refuse by name or to
add a migration arm.
Output: `anno_enum_usage` in the DDL, `SCHEMA_VERSION = 3`, and three store
functions the `anno_apply_enum_usage` verb dispatches to.
</objective>

## Decisions and readings adopted by this plan

- **D-15 (locked, user decision, 2026-08-29):** add `anno_enum_usage` and bump
  `SCHEMA_VERSION` 2 → 3 **with no migration arm**. Every existing v2 `.annostore`
  becomes permanently unopenable, deliberately. The store shipped five days ago; a
  migration arm bought now would protect stores that may not exist. This
  supersedes D-07's note that a `SCHEMA_VERSION` bump is a one-way decision to be
  avoided this milestone — the bump is taken with the cost named.

  **single-witness** refusal. No migration arm is added to `openStore`, and the
  plan asserts that a v2 store still refuses **by name** rather than being
  silently upgraded.
- **F-6 (carried forward unchanged):** Phase 28's two `behavior_unverified` items
  are neither closable nor re-litigable by anything this phase does, and
  prohibition 28-18 P3 forbids closing, dropping, or re-filing them as done. They
  are restated verbatim in the summary, not re-assessed.

autoincrement `id`, a not-null `address`, a not-null `enum_id` referencing
`anno_enum(id)`, a nullable `bank`, and a uniqueness constraint over
`(address, bank)` so one address carries at most one enum usage. Add
`anno_enum_usage_address` as an index on `address`, matching the existing
`anno_label_address` / `anno_comment_address` naming. The association is by

Add an `EnumUsageRow` type in `anno-types.ts` beside the other row types, carrying
`id`, `address`, `enumId`, `enumName` and `bank`.

Add three exported functions to `anno-store.ts`. `applyEnumUsage(handle, args)`
validates `address` through `parseStoreAddress` and the enum name through
`assertEnumName`, resolves the enum to its `anno_enum.id` and refuses by name if
there is none, then copies `putXref`'s idempotency shape exactly: select the
existing row first and return `changed: false` without advancing the revision when
the same enum is already applied at the same address. `clearEnumUsage(handle, args)`
deletes the row for an address and returns `changed: false` when there was none —
this adds a **third** `delete from anno_` site to the module, where 28-REVIEW
recorded exactly two; record that count change explicitly in the function's doc
block so the next reader finds it as a stated fact rather than a surprise.
`listEnumUsage(handle)` joins `anno_enum_usage` to `anno_enum` and returns
`EnumUsageRow[]` sorted by address.

confinement of `node:sqlite` to this one module. Validate every argument before any
