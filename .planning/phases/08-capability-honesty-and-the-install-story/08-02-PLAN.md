Wire the registry into the one code path that actually fires, and prove it end to end.

`vice_sid_get_state` returns `{"content":[{"type":"text","text":"Unknown tool: vice_sid_get_state"}],"isError":true}`.

`readManifestTools()` reads the *active* backend's manifest only (**D-07**, the shipped design).

One `if`, one function call, in the same function that already does exactly this for `DENY_LIST`.

Purpose: criterion 1 -- never a generic unknown-tool error for a capability the other backend has.
Output: the refusal reaching a real MCP client over real stdio, proven by a spawned subprocess.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| MCP client (Claude) -> `tools/call` `request.params.name` -> `CallToolRequestSchema` override | The only untrusted input crossing into this change; it may be any string, including a deny-listed name or a nested-argument bypass attempt |
| the override's refusal branches -> the calling agent's next decision | A wrong refusal text misroutes an agent (e.g. toward a destructive `vice_recycle`), so the text is a behavioural surface, not cosmetic |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-08-02-01 | Elevation of Privilege | ordering of the new lookup vs the `DENY_LIST` check | mitigate | **The load-bearing control of this plan (D-G).** Task 1 places the lookup strictly inside the `tools[name]` miss branch, after `DENY_LIST`. Two independent tests pin it: Task 1's source-offset assertion (`DENY_LIST` before `capabilityRefusalMessage` before `Unknown tool`) and Task 2 test 4's wire-level assertion that a nested `tools_call` bypass attempt still gets the deny-list refusal and never a capability refusal. Structurally reinforced: deny-listed names are skipped by `if (DENY_LIST.includes(def.name)) continue;` in the registration loop, so they are never keys in `tools` and can never reach the new branch even if mis-ordered. |
| T-08-02-02 | Spoofing | a capability refusal impersonating a deny-list refusal (or the reverse) | mitigate | The two branches return distinct, non-overlapping text (`permanently forbidden` vs `VICE_BACKEND=`). Task 2 test 4 asserts both the positive and the negative on the same call. |
| T-08-02-03 | Information Disclosure | the refusal text revealing internals to a caller | accept | The refusal reveals only tool names and reasons already public in `docs/stock-vice-parity.md`, the two shipped manifests, and this public repo. Plan 08-01's registry-content rule is the upstream control; no host, port, path or secret is interpolated. |
| T-08-02-04 | Injection | `name` interpolated into the returned message | mitigate | `name` is placed only into a plain string that is returned as MCP text content. It never reaches a shell, a filesystem path, a `new Function`/`eval`, or a network request -- the refusal returns before any transport is touched, so `forwardToVice()` / `rewriteArguments()` / `call()` are all unreached. |
| T-08-02-05 | Denial of Service | the new lookup adding cost to the hot path | accept | It executes only on a `tools[name]` miss -- never on a successful call -- and is a linear scan over 26 in-memory entries with no I/O. |
| T-08-02-SC | Tampering | npm/pip/cargo installs | mitigate | No package installed. Task 1's acceptance runs `check-npm-packages.mjs`, which re-asserts the runtime dependency set is exactly `@mastra/mcp` + `@mastra/core` and that the newly-imported module is in the published tarball. |
</threat_model>
