`capabilityRefusalMessage()` contract, mirroring `denyListRefusalMessage()`'s keyed shape:
return `undefined` when there is no entry for `name`, **and also** when `entry.providedBy ===
activeBackend` (defensive: the active backend already advertises it, so a miss there is a genuine
unknown-tool case, not a capability gap). Otherwise render one of three wordings selected by
`entry.category`:

- `hardware` -> names the tool, states it is **unrecoverable** on the active backend, gives
  `entry.reason`, then names the providing backend with the actionable `Set VICE_BACKEND=fork` (or
  `=stock`). No "wait for a later phase" framing -- none is coming. The literal token
  `unrecoverable` must appear.
- `descoped` -> names the tool, states it is **not implemented** on the active backend, gives
  `entry.reason`, then the providing backend and `Set VICE_BACKEND=...`, then `entry.alternative`
  when present. The token `unrecoverable` must NOT appear in this wording -- research Pitfall 3:
  a reader told "not supported" for both cannot tell which one to file an issue about.
- `stock-only-gain` -> names the tool, states it is not implemented on the **fork** backend, gives
  `entry.reason`, then `Set VICE_BACKEND=stock`.
