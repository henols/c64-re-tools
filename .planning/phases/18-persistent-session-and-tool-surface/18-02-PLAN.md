<objective>
Add the one shared "ensure settings" function D18-32/D18-33 require: a
read-parse-force-rewrite pass over an **existing** `.regen2000proj`, callable
before a session spawns against it. This closes the ROADMAP note's gap — the
existing synthesiser forces `use_illegal_opcodes` only at creation, so a session
re-opening an older project would otherwise silently re-degrade every illegal
opcode to an opaque byte-directive fallback.

Purpose: `anno-project.ts` has **no** function today that touches an existing
project file. `synthesizeProject()` only ever builds a brand-new object from raw
bytes — there is no read-JSON-mutate-JSON-rewrite path anywhere in the module.
This function must be written new, sharing the forced-values *convention* with
`synthesizeProject()`, not lifted out of it.

Output: `ensureProjectSettings()` and `AnnoProjectSettingsError` in
`anno-project.ts`, with unit and planted-violation coverage in
`anno-project.test.ts`. This plan does not wire it to anything — plan 18-03's
tracer calls it, and plan 18-07 proves the half that only a live session can
prove (that a subsequent mutating call's own save does not revert it).
</objective>

  <action>
    Add to `src/mcp/vice/anno-project.ts`:

    `export class AnnoProjectSettingsError extends Error` — sets `this.name` to
    `"AnnoProjectSettingsError"` and carries a public `projectPath: string` field, following
    this module's existing named-error convention (a dedicated public field, never a value
    reachable only by parsing message text). Give it an options-object constructor in the
    same shape `anno-mcp-client.ts`'s error classes use.

    `export function ensureProjectSettings(projectPath: string, opts?: { system?: string }): { changed: boolean }`
    — the one shared "ensure settings" seam D18-33 names. It must:
    1. `readFileSync` the path as utf8; on any read failure throw `AnnoProjectSettingsError`
       naming the path and the underlying errno, with the original error as `cause`;
    2. `JSON.parse` it; on failure throw `AnnoProjectSettingsError` naming the path and the
       parse message. Refuse when the parsed value is not a plain object;
    3. read `settings.system`. When it is present and does not strictly equal the expected
       system (`opts.system ?? ANNO_SYSTEM_C64`), throw `AnnoProjectSettingsError` whose
       message embeds BOTH the found value and the expected value, and return without
       writing anything. When it is absent, write the expected value;
    4. force `settings.use_illegal_opcodes` to `true` **silently** — no throw, no warning, no
       option to skip. Reference `ANNO_SYSTEM_C64` for the system value rather than
       re-typing the literal, so the two callers of this convention share one constant;
    5. when nothing needed changing, return `{ changed: false }` without rewriting the file
       at all (so an idempotent open does not churn the file's mtime);
    6. when something changed, serialise with `JSON.stringify` and replace the file using the
       write-temp-then-`renameSync` idiom already used by `refresh-manifest.ts`, so a crash
       mid-write cannot leave a truncated project file. Return `{ changed: true }`.

    Give the function a doc comment stating WHY it exists (the ROADMAP note's gap: the
    synthesiser forces the setting only at creation, so a session re-opening an older project

    `system` half is a refusal while the `use_illegal_opcodes` half is silent (forcing
    illegal-opcode decoding only ever widens what decodes correctly and cannot invalidate an
    existing annotation; rewriting the machine type could reinterpret every block
    classification in an annotated project).

    Update `anno-project.ts`'s module header to say that this module now has two settings
    surfaces — the synthesiser for new projects and the ensure-pass for existing ones —
    sharing forced values through `ANNO_SYSTEM_C64` and nothing else.

    Do not modify `synthesizeProject()`'s body.
