<objective>
Close PKG-04 on the accepted-risk branch its own success criterion permits: record the
broker control-plane listener's `0.0.0.0` bind default in PROJECT.md's Key Decisions table
as a dated, reasoned, reversible acceptance — with the rationale checked against source
rather than inherited from research prose.

Purpose: PKG-04 inherits QUAL-03, whose v0.2.0 wording ("network exposure of the emulator
control plane is documented or restricted") predates the broker control plane in its current
form. Success criterion 4 permits either branch — narrowed with a live bind check, **or**
recorded in PROJECT.md as an accepted risk with rationale. Choosing acceptance is therefore
not a scope reduction; it is one of the two outcomes the criterion was written to allow.

**Decision D-16-05: accept, do not narrow.** Three reasons, in order of weight.
(1) The `0.0.0.0` bind exists specifically so a consumer running inside a devcontainer can
reach a broker on the host: `host.docker.internal` resolves on Linux to the Docker bridge
gateway address, and a listener bound to `127.0.0.1` accepts only traffic arriving on the
loopback interface, so a loopback-only default is structurally unreachable from the exact
topology this project's container-detection code exists to serve. Narrowing the default
without replacing that reachability is a regression dressed as a hardening.
(2) The listener is not unauthenticated. Every request is gated by a per-boot capability
token before any state read or write.
(3) The alternative worth building — bind loopback unless a container topology is detected —
is new behaviour, not a literal change, and this milestone's own Out of Scope table says no
new capability. It is recorded as a follow-on, not built here.

The narrow branch is recorded as considered-and-rejected in the entry itself, so a future
reader does not read acceptance as nobody having looked.

**Reversibility:** `reversible`. This plan writes a dated planning record with named
reversal criteria and changes no behaviour; reversing it means taking the smart-default
follow-on and superseding the row, exactly as FORK-01's row is written to be superseded.

Output: one Key Decisions row, one named follow-on item, and a verified correction to the
research draft's residual-risk wording.
