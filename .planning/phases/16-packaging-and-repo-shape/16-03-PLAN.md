<objective>
Give `wireMcp()` — the one function in this repository that reads, edits and rewrites a file
belonging to somebody else's project — the regression coverage it has never had, and stand up
the minimal test infrastructure the `installer/` package needs to run it.

Purpose: PKG-01 has two halves. The relocation half is plans 16-01 and 16-04. The merge half
is this: ".mcp.json merged into any consumer's existing config". The merge semantics already
exist and are already correct — the pending todo says so, and reading the function confirms
it — so the honest remaining work is not writing a merge, it is *asserting* the merge, which
nothing in this repository currently does. `scripts/package.sh` validates only that the vice
server's args mention the plugin-root variable; no check anywhere covers non-clobbering.

**Decision D-16-03, resolving the two open questions this plan owns.**
(a) The plugin install route needs no new merge code: a plugin declares its MCP servers
through a manifest pointer and the loader layers those definitions into the running session's
server set rather than rewriting the consuming project's file. The file-writing merge is the
npm-installer route only, and `wireMcp()` already implements it. So PKG-01's merge half is
verify-and-test, not build-new.
(b) Yes, build the `installer/` regression test, even though success criterion 1 speaks only
about tarball contents. Three reasons: the pending todo's own Solution step 4 asks for
exactly this test, in these words; the phase's security research names a malformed consumer
config as a tampering path whose only mitigation is this function's refuse-on-invalid branch,
and an unasserted mitigation is a claim; and `16-VALIDATION.md` lists it as a Wave 0 gap, so
declining it would have to be a recorded deferral rather than a silent omission.

**Reversibility:** `reversible`. A test file and a `test` script; deleting them restores the
prior state exactly.

Output: `installer/wire-mcp.test.mjs`, a `test` script in `installer/package.json`, and
whatever minimal export seam `cli.mjs` needs so the suite drives the shipped code rather than
a copy of it.
</objective>

|----------|-------------|
| installer process ↔ consumer project file | The installer reads, edits and rewrites a file it does not own; the consumer's other MCP servers and unrelated config live in that same file |
| untrusted file content ↔ JSON parser | A consumer config may be truncated, hostile, comment-bearing, or a non-object; the parser's behaviour on each decides whether the file survives |
| test suite ↔ repository working tree | A test that writes outside its scratch directory can leave residue in a published package or in a commit |
