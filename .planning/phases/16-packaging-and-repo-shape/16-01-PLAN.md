<objective>
This is the phase's tracer: relocate the smaller of the two payload trees — the six
skills — out of Claude Code's auto-discovery path and into `src/skills/`, wired
end-to-end through every layer the relocation will later have to satisfy for the much
larger vice-mcp move: the plugin manifest, the packaging validator, both skill-corpus CI
checks, the installer's skill-sync source, CI's own working paths, the three
skills-path literals living inside the vice-mcp test suite, and one skill script whose
sibling-directory scan would silently narrow.

Purpose: the vice-mcp move (plan 16-04) touches ~180 files and roughly thirty consumers.
If any layer of the relocation machinery is broken — a manifest path the loader rejects, a
CI check whose walk silently finds nothing, a packaging validator that fails closed — it is
far cheaper to discover that on six directories with ten consumers than on the whole tree.
Every layer this tracer crosses is a real production layer, verified with the same gates the
big move will use: `VICE_REQUIRE_ACME=1 npm test` (the full glob CI runs, never the narrower
`test:automated`), `scripts/package.sh`, and both `check-skill-*` scripts with their own
non-vacuity floors intact.

This is a tracer, not a prototype: nothing here is stubbed, provisional, or scheduled for
replacement. Every edit is the final edit for the file it touches.

**Decision D-16-01 (target layout), recorded here and used by plans 16-04/16-05:** the
target is `src/skills/` and `src/mcp/vice/`, both directly under the repository root. For
the skills half this is unconstrained. For the vice-mcp half it is load-bearing and
verified: `repoRoot()`'s branch-4 last resort climbs exactly three levels, and `src`/`mcp`/
`vice` is the same three segments as the current location — see plan 16-04, which owns that
verification and the `repo-root.test.ts` pin.

**Decision D-16-02 (the dev-time story), recorded here because this plan is where in-repo
autoload actually stops:** accept losing in-repo skill autoload (the pending todo's option
(c)), and document two real routes for exercising the payload as a consumer does — the
scriptable one (`node installer/bin/cli.mjs <scratch-dir>`, which agents and CI may run) and
the plugin one (`/plugin marketplace add ./` against this repo's existing
`marketplace.json` `"source": "./"`, performed by a human, never by an agent, because it
writes machine-global `~/.claude/plugins/` state shared with the live session). Losing
autoload is the *point* of the requirement, not a regression: the todo's problem statement
is that development-in-place and installed-consumer are indistinguishable, so "it works in
the repo" is never evidence that "it works when installed". Cost accepted: a Claude session
opened on this repo no longer auto-triggers the six skills; it can still read them under
`src/skills/`, and CLAUDE.md's Project Skills table (swept in plan 16-05) points there.

**Reversibility:** `costly`. Undoing the relocation is a mechanical `git mv` back plus the
same literal sweep, and the published npm tarballs are unaffected (their file lists are
package-relative — proven in plan 16-04). What is not free is the churn: the plugin zip's
internal layout and the marketplace path contract change once per direction, and consumers
who already installed the plugin absorb a layout change on update. Not `one-way`, so no
decision checkpoint is inserted.

Output: `src/skills/` with all six skills, every functional consumer updated, and the full
test glob plus all three packaging/corpus gates green against the relocated tree.
</objective>
