<objective>
Build the correlation and demultiplexing layer on top of plan 02-04's parser: the
pending-request map, request-id-first event routing, N+1 related-frame
accumulation, expected-response validation, and the socket-close rejection path.

Purpose: this is the correctness-critical half. Five unsolicited types arrive at
request id `0xffffffff`, and two of them — `CHECKPOINT_INFO` (`0x11`) and
`REGISTER_INFO` (`0x31`) — share a response type byte with a legitimate reply. A
client that demultiplexes on response type instead of request id resolves a
pending `CHECKPOINT_GET` with some other checkpoint's data: silently wrong, not a
crash. The vendor's ordering here is already correct and is preserved verbatim.

<decisions_implemented>
- **D-16** — add generalised `related[]` accumulation, the command→expected-response
  table, and a desync counter. The vendor's request-id-first demux ordering is
  already correct and is preserved verbatim.
- **D-17** — never mint request id `0xffffffff`; keep the id a full uint32. Five
  unsolicited types arrive at that id and two share a response type with a
  legitimate reply, so demux keys on request id and never resolves a pending
  request with an event.
- **D-11** — PROTO-06 rides the socket lifecycle. A TCP close or reset is
  unambiguous and immediate: every in-flight request rejects with a died-underneath
  error, and a timeout stays reserved for "connected but silent". No epoch polling
  on the stock path. (The "new machine, re-handshake" half is plan 02-08's.)

**Planner decision (RESEARCH.md's duplicate-reply question):** a duplicate reply on
an already-settled request id is **dropped and counted**, not emitted on the
`'event'` channel. Routing it to `'event'` — which is what the vendor's structure
does today by accident, because the pending entry is deleted before resolve —
would let a future consumer treat a duplicate reply as a second, spurious
`STOPPED`/`RESUMED` transition. Distinguishing "settled" from "never seen" needs
memory: keep a bounded ring of the last 256 settled request ids. An id in that ring
is a duplicate (drop, count `duplicateReplies`); an id not in it and not
`0xffffffff` and not pending is a genuine unsolicited frame at a non-broadcast id
(emit `'event'`).
</decisions_implemented>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| binmon socket → pending-request map | Frames from the socket decide which caller's promise is resolved and with what data |
| event stream → downstream consumers | An event consumer acts on emulator state transitions; a misrouted frame becomes a false state transition |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-20 | Spoofing | unsolicited frame resolving a pending request | mitigate | Request-id-first ordering preserved verbatim: the `0xffffffff` check runs before any pending lookup and never inspects the response type byte, so a `CHECKPOINT_INFO`/`REGISTER_INFO` event cannot be mistaken for the reply it shares a type with (PROTO-03) |
| T-02-21 | Tampering | wrong-typed reply on a matching request id | mitigate | `EXPECTED_RESPONSE` is consulted before `resolve()`; a mismatch rejects with `StockResponseMismatchError` naming expected and received, rather than handing the caller another command's payload |
| T-02-22 | Spoofing | duplicate reply on a settled id emitted as telemetry | mitigate | Bounded 256-entry settled-id ring distinguishes duplicate from never-seen; duplicates are dropped and counted, never emitted on `'event'`, so a consumer cannot read one as a spurious `STOPPED`/`RESUMED` |
| T-02-23 | Denial of Service | pending map leak on close | mitigate | The close/error path rejects and clears every pending entry, and the client refuses further sends — no promise is left unresolved and no unbounded pending growth survives a reconnect loop |
| T-02-24 | Denial of Service | settled-id ring growth | mitigate | Ring is bounded at 256 entries by construction, not by eviction policy chosen at runtime |
| T-02-SC | Tampering | npm/pip/cargo installs | accept | No package-manager installs in this plan |
