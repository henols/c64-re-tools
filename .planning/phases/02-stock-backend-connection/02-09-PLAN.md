<objective>
Lay the two foundations the stock tool surface stands on: a trimmed, separately
committed stock manifest with a tested selector, and the one seam that turns a
broker lease into a live stock session.

Purpose: D-07 makes the two backends expose genuinely different tool lists as the
shipped end state, so the surface is a second committed file rather than a runtime
filter. And `stockConnect()` requires an already-resolved
host/port/targetId/brokerControl — D-13 says nothing may reach a binmon
`connect()` without a broker-granted lease and a monitor claim, so the stock
module needs a single, injected way to obtain that lease before any handler
exists to want one.
Output: `tools-manifest.stock.json`, the first half of `stock-dispatch.ts`
(manifest selector plus `ensureStockSession`), and a `HeldLease` type on
`vice-broker-client.ts`. Plan 02-10 adds the dispatch table, `vice_ping`, and the
`vice-proxy.ts` wiring on top.
</objective>

**Scope note, not a reduction:** in Phase 2 the stock manifest carries `vice_ping`

subsequent phase adds its own entries to this same file and this same table.

**Planner decision (lease acquisition for stock handlers — fix (a), not fix (b)):**
`stockConnect()` requires an already-resolved `host`/`port`/`targetId`/
`brokerControl`. On the fork path those coordinates come from
`ensureBrokerLease()`, a private, non-exported function in `vice-proxy.ts` that
classifies broker liveness, opens the control session, acquires a grant, hands it
through `containerizeGrant()`/`adoptGrant()`, and stores the session and grant id
in that file's module state. Two ways to give the stock path the same coordinates
were considered:

(a) reuse `ensureBrokerLease()` as the single acquisition, widening what it
returns so its result can be threaded into `stockConnect()`, and injecting it into
`stock-dispatch.ts` from the one call site that already changes for the backend
switch; or

(b) give `stock-dispatch.ts` its own acquisition built directly on
`openBrokerControl()` / `session.acquire()`.

**(a) is chosen.** (b) is the "re-deriving a cross-cutting seam locally"
anti-pattern aimed squarely at the acquisition path: it would produce a second
liveness classification, a second grant adoption, and a second module holding a
control session — and `ensureBrokerLease()`'s body is precisely the kind of
accreted, incident-shaped logic (`readBrokerLiveness()` first, the
never-cache-a-negative-result invariant, `containerizeGrant()`'s host→container
inversion, the release-before-reacquire ordering that closed the plan-14 grant
leak) that a parallel copy silently loses. A second acquisition would also let one
session hold two grants at once, which is exactly the leak that ordering comment
exists to prevent. Worse for D-13 specifically: a locally-built control session
would send `monitor_claim` on one connection while a different connection held the
grant, so the claim would not actually govern the dial it precedes.

The injection direction is forced by cycle avoidance, which this codebase treats
as deliberate (`repo-root.ts`'s header): `vice-proxy.ts` imports
`stock-dispatch.ts`, so `stock-dispatch.ts` must not import back. Therefore
`stock-dispatch.ts` declares the provider type it needs and `vice-proxy.ts`
supplies `ensureBrokerLease` itself (plan 02-10, task 2) at the one call site that
already changes. No adapter function, no registry, no second copy — the provider
*is* the existing seam.
