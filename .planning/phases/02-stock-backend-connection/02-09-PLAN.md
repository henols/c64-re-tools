- **D-01/BACK-01** — one config value switches backends; the resolved value is read
  through `backend-detect.mts`'s single seam.

only, because Phase 2's boundary explicitly excludes the tools themselves — the
1:1 opcode tools are Phase 3, the client-side seam and disassembler Phase 4, the
reimplemented tools Phase 5, the stock-only gains Phase 6, timing Phase 7. Every
subsequent phase adds its own entries to this same file and this same table. What
must be complete *here* is the seam and its no-fall-through guarantee, and
`vice_ping` as its first real entry.

**Planner decision (testability of `vice-proxy.ts`):** `vice-proxy.test.ts` is one
of the three files excluded from the automated gate, so any logic added inside
`vice-proxy.ts` would be effectively untested. Therefore the manifest selection and
the dispatch choice are implemented as pure exported functions in
`stock-dispatch.ts` and unit-tested there; `vice-proxy.ts`'s own diff is reduced to
calling them. This keeps the untestable file's change surface to two call sites,
which is also exactly what D-09 and PATTERNS.md require ("do not add a third
dispatch site").

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| MCP client → tool dispatch | Tool names arrive from the model and select a handler |
| manifest file → advertised surface | A committed JSON file decides what capabilities are offered |
| stock handler → emulator | A dispatched handler drives full memory read/write over the emulated machine |
