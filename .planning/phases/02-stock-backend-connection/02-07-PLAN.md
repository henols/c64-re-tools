<objective>
Make the backend a detected fact with an explicit override, cached once per
binary under `.vice-supervisor/`, and give the connect handshake somewhere to
record what it learns about that binary's version-gated capabilities.

Purpose: BACK-01 is satisfied by the override; D-01 makes the common case need no
config at all, which is what actually serves "install stock VICE and go". BACK-04
needs a place to record capability answers determined at connect rather than at
first use, and that place is the same cache.
Output: `backend-detect.mts`, its compiled host artifact, and the replacement of
plan 02-03's temporary `backendFromEnv()` reader.
</objective>

<decisions_implemented>
- **D-01** — the backend is DETECTED, not defaulted. The broker works out what the
  `x64sc` binary is once, when it first starts, and remembers it. `VICE_BACKEND` is
  an explicit override, not a required setting. BACK-01 still holds: one config
  value still switches backends, it just is not mandatory.
- **D-02** — the discriminator is `-mcpserver`, not `-binarymonitor`. The fork is
  built on a 3.10 tree and accepts both; stock accepts only `-binarymonitor`.
- **D-03** — the probe runs once at broker first-start, is cached under
  `.vice-supervisor/`, is keyed so a binary replaced in place is noticed, and must
  not sit inside `broker-launch.mts`'s `inFlight` critical section.
- **D-04** — one broker only ever launches one kind of binary.
- **D-06** — a one-time stderr note when `VICE_BACKEND` is unset, naming the
  detected backend and how to override it, following `repo-root.ts`'s existing
  one-time-warning gates.
- **D-10** — version-gated capabilities fold into the same cached record;
  `CPUHISTORY_GET` returns `0x83` on stock 3.9 and `OK` on the 3.10 fork, with
  `0x8f` the distinct not-compiled-in case.

**Planner decision (RESEARCH.md Open Question 2 — probe mechanism, D-03 left this
to the planner):** `--help` output introspection. Not a trial launch. Three
reasons: it runs entirely outside `broker-launch.mts`'s `inFlight` critical section
*by construction* rather than by careful serialisation, which is what D-03 asks
for; it does not depend on RESEARCH.md's `[ASSUMED]` A1 (that stock's argument
parser rejects an unknown flag with a non-zero exit — unverified against a real
stock binary); and it costs one short-lived spawn instead of two, one of which
would be a throwaway emulator launch. Trial launch is explicitly not used.

**Planner decision (cache key composition, D-03 left this to the planner):**
`{ resolvedPath, mtimeMs, sizeBytes }` for the backend verdict, plus `versionQuad`
once a connect has produced one. Path alone fails D-03's replaced-in-place
requirement outright. The version quad cannot key the *initial* verdict because it
is only readable over `VICE_INFO` after a launch and a connect, and the verdict is
needed before the launch — so it joins the record later and invalidates it on
mismatch. `mtimeMs` plus `sizeBytes` catches every realistic in-place replacement
(`apt upgrade`, a manual `cp`); a content hash was rejected because it costs a full
read of a multi-megabyte binary on every broker start, and this is not an
adversarial-attacker scenario (RESEARCH.md assumption A2, accepted knowingly).
</decisions_implemented>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| configured binary path → process spawn | An operator-supplied path is executed to read its `--help` output |
| `.vice-supervisor/backend.json` → launch-flag selection | A cache file decides which flags a binary is launched with and which protocol the client speaks to it |
| `VICE_BACKEND` env → whole-server behaviour | One env var overrides the detected verdict |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-03 | Elevation of Privilege | `probeBackend()` spawn | mitigate | `spawnSync` with an argv array and `shell: false`; the binary path is never interpolated into a command string; `execSync`/`exec` are grep-gated to zero occurrences; 5000 ms timeout with kill-on-timeout so a hostile or hung binary cannot stall broker startup |
| T-02-02 | Tampering | `.vice-supervisor/backend.json` cache poisoning | mitigate | A cache hit requires `resolvedPath` + `mtimeMs` + `sizeBytes` to all match the binary currently on disk, so an edited verdict for a binary that has since changed is rejected; the file is written `chmod 0600` via tmp-sibling → rename; a malformed or unexpected-shape file is a miss, not a trusted value. Residual: an attacker with write access to `.vice-supervisor/` and no ability to change the binary can flip the verdict — accepted, since that same write access already reaches the epoch and grant records this project has always trusted |
| T-02-25 | Denial of Service | probe inside the `inFlight` guard | mitigate | The probe resolves once at startup, before the control listener binds and before any launch is possible; grep and reading gates confirm no probe call inside `tryLaunchOne()`. This is the 2026-08-01 triple-launch outage's exact failure class (D-03) |
| T-02-26 | Denial of Service | detection failure killing the stdio server | mitigate | `resolvedBackend()` never throws; an indeterminate outcome returns a defined shape and the broker continues with the fork shape. A dead stdio server is never restarted by Claude Code for the session |
| T-02-27 | Information Disclosure | cache file permissions | mitigate | `chmod 0600` on the tmp sibling before content is written, matching `refresh-manifest.ts`'s established sequence |
| T-02-SC | Tampering | npm/pip/cargo installs | accept | No package-manager installs in this plan |
</threat_model>
