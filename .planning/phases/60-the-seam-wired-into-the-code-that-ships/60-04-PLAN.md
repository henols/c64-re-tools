## Planner decisions recorded for this phase

There is no Phase 60 CONTEXT.md. The decisions below are the planner's, recorded visibly.
Phase 59's `D-06` (no dedicated environment variables for these two ids) and `D-12` (bare
string values in `tools.json`) are binding and are not reopened.

- **PD-08 — a deliberate divergence from `60-PATTERNS.md`, resolved in favour of the
  requirement text. The `tools.json` layer goes AHEAD of the sibling-of-`x64sc` candidate,
  not between it and the `$PATH` fallback.** `60-PATTERNS.md` and the orchestrator's own
  notes both say "insert the `tools.json` check between the sibling-of-`x64sc` check and the
  `$PATH` fallback". Taken literally, a sibling that happens to exist would silently beat a
  path the user explicitly wrote in the file, which contradicts two requirement texts at
  once: `LOC-02` states the order as "environment variable, then `tools.json`, then `$PATH`
  or sibling probe", placing the sibling probe in the THIRD tier; and `LOC-01` requires every
  code path to honour a recorded path. ROADMAP criterion 4 settles it in the same direction —
  these two tools still resolve as siblings "**when the file says nothing about them**". The
  resulting order is: `tools.json` (via the seam; these ids have no environment layer), then
  the sibling-of-`x64sc` candidate, then the `$PATH` walk. "Widened, not replaced" is
  preserved exactly: neither existing branch is removed, reordered relative to each other, or
  weakened.
  Reversibility: costly — this is user-visible precedence; changing it later changes which
  binary an existing setup resolves.

- **PD-09 (answers the orchestrator's explicit question): `spawn-seam.test.ts` is NOT
  revived, and the four comments citing it are corrected to state the convention as
  voluntary.** Reviving a guard deleted by a 43-test cleanup is not in this phase's scope and
  no requirement asks for it. What this phase DOES close mechanically is the half that
  matters to this milestone — the closed consumer set for the four environment-variable
  names, delivered by plan 60-05 — so the corrected comments point at that test by name for
  the part that is enforced, and say plainly that the local-variable naming rule is kept by
  convention with no test behind it.
