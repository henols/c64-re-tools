<objective>
Make the emulator binary the broker actually spawns come from the tool-location seam, once
per process, outside the `inFlight` guard.

Purpose: `LOC-01` is a claim about the code that runs. Today the real `spawn()` reads a
`VICE_BIN` expression duplicated in `src/mcp/vice/broker-launch.mts` at two sites and never
consults the seam at all, so a `tools.json` entry for the single most important tool in the
project would change nothing a user can see. This plan closes that, and in doing so removes
the emulator-binary ordering from every module except the seam (`LOC-02`).

Output: `resolvedBackend()` resolves through `resolveTool("x64sc", ...)`; `vice-broker.mts`
threads the one resolved string down the already-plumbed `viceBin` parameter chain;
`broker-launch.mts` becomes a pure consumer; the three compiled host-bound artifacts are
regenerated and committed.
</objective>

## Planner decisions recorded for this phase

Phase 60 has **no CONTEXT.md** — no discuss-phase was run. Phase 59's `59-CONTEXT.md`
deferred two design questions to this phase by name. They are answered here, visibly, as
planner decisions rather than left implicit. Phase 59's `D-01`, `D-02`, `D-03`, `D-08`,
`D-09` and `D-12` are treated as binding and are not reopened.

- **PD-01 (answers Phase 59 `D-01`'s deferred question — `resolvedBackend()`'s final role):
  `resolvedBackend()` gains the `tools.json` layer internally by calling the seam; it keeps
  no ordering of its own.** `src/mcp/vice/backend-detect.mts` stops naming the emulator
  environment variable, and its private `$PATH` walk is reduced to a call into the seam's
  exported `resolveOnPath()` — the first of the three coexisting copies Phase 59 `D-02` said
  would collapse here. Chosen over "the caller resolves separately and picks between two
  answers" because three downstream consumers read `resolvedBackend()`'s `binPath` without
  passing anything (`vice_ping`'s reported path, and `host-tool.mts`'s two sibling-probe
  seeds); making the caller choose would leave those three reading an un-seamed answer and
  create exactly the second opinion Phase 61's `DOCTOR-05` forbids.
  Reversibility: costly — Phase 61's doctor and `vice_ping` both read this result.
- **PD-02: `deps.viceBin` and `deps.resolveBinPath` on `ResolvedBackendDeps` survive
  unchanged as explicit injection overrides that bypass the seam.** This is what keeps
  `backend-detect.test.ts`'s existing cases passing untouched, which is `LOC-03`'s own
  criterion, and it matches this repo's destructured-options injection convention.
- **PD-03: when a caller supplies neither `toolsDir`/`projectRoot` nor `supervisorDir`,
  `resolvedBackend()` derives them from `process.cwd()`.** Documented as a last resort, not
  a guess: a working directory with no `.c64-re-tools/tools.json` makes the file layer a
  silent no-op, so the fallback can only ever widen resolution where a real project root is
  already the working directory.

<assumption_delta_decision>
- **Noun now primary:** the seam's resolution of a declared tool id — `resolveTool(id)`'s
  answer, carrying `layer` and `mechanism` — is the primary identity for "where a tool is".
- **Decision: `promote`.** Each individual probe (the environment variable, `tools.json`,
  the `$PATH` walk, the sibling-of-`x64sc` candidate, the fixed-prefix list, the vendored
  path) is demoted to a `mechanism` inside one ordered resolution, rather than added
  alongside the environment variable as a second peer source of truth. `LOC-02` states the
  criterion in as many words: the precedence order exists in exactly one place.
- **Not `add-alongside`,** and the distinction is load-bearing: `tools.json` is not a second
  place to look, it is the second layer of one order whose result reports which layer
  answered — which is what leaves Phase 61's `DOCTOR-05` with nothing to reimplement.
- **What would force a further promote later:** two probe-layer mechanisms
  (`sibling-of-x64sc` in `host-tool.mts`, and ACME's fixed-prefix list) still live outside
  `resolveTool()` after this phase (plan 60-03's PD-07 keeps ACME's fixed-prefix list, plan
  60-04's PD-08 keeps the sibling candidate, each with its reason). If Phase 61's
  differential check ever shows the doctor and live dispatch disagreeing for `c1541`,
  `petcat` or `acme-lib`, that is the signal to move those two mechanisms inside the seam.
</assumption_delta_decision>

## Prohibition recall — canon-referral breadcrumbs (surfaced, deliberately not minted)

The two-stage must-NOT recall was run over this phase's five requirements. The survivors are
authored into each plan's `must_haves.prohibitions`, descriptor-less. Four kept candidates

  `/gsd-secure-phase` and threat `T-60-01`; not minted here.

  `/gsd-secure-phase` and threat `T-60-02`; not minted here.
- A relative or `~`-prefixed path escaping the project tree is canon path traversal —
  covered by `/gsd-secure-phase` and threat `T-60-03`; not minted here.
- A host-absolute path leaking across the container boundary in a refusal message is canon
  information disclosure — covered by `/gsd-secure-phase` and threat `T-60-04`; not minted
  here.

Candidates DROPPED at the precision stage as routine engineering rather than values or
safety: must not mutate its input, must not throw on an empty list, must not cache a stale
answer, must not fall through silently after a bad file entry, must not mutate `$PATH`. Those
belong to the edge probe and to ordinary code review.
