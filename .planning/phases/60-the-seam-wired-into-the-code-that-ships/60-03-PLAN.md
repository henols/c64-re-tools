Route ACME, ACME's standard library and Ghidra through the seam inside the one host-tool
executor, and make every refusal in that module quote the declaration instead of a literal.

Purpose: `LOC-01` is a claim about every code path. `host-tool.mts` is where `acme`,

`buildHostToolArgv()`; `acme`/`acme-lib`/`ghidra` resolved through `resolveTool()`; every
refusal in the module carrying `remedyTextsFor()`'s declared prose; the compiled artifact
regenerated and committed.

## Planner decisions recorded for this phase

There is no Phase 60 CONTEXT.md. The decisions below are the planner's, recorded visibly.
Phase 59's `D-05` (the `location` block), `D-07` (`kind` and `marker`, and that the seam
returns the directory itself and never the marker-joined path), `D-08` (validation applies
to the file layer only), `D-09` (one bad entry refuses one tool) and `D-16`/`LOC-05` (dxa
stays un-overridable) are binding and are not reopened.

- **PD-06: `buildHostToolArgv()` gains an OPTIONAL fourth parameter, a
  `HostToolLocator` — `{ toolsDir, projectRoot }`.** It is optional because this function
  has more than forty direct call sites across four test files that exercise argv shape and
  nothing else; making it required would rewrite all of them, which is precisely the churn
  `LOC-03` exists to prevent. The one production caller, `runHostTool()`, always supplies
  it. When it is absent the locator is derived from `process.cwd()` — documented as a last
  resort, not a guess: a working directory with no `.c64-re-tools/tools.json` makes the file
  layer a silent no-op, so the fallback can only widen resolution where a real project root
  is already the working directory. This mirrors plan 60-01's PD-03 for `resolvedBackend()`
  so there is one rule, not two.

- **PD-07 (a correction to `60-PATTERNS.md`): `findAcmeLib()` is WIDENED, not replaced.**
  The pattern map states that `resolveTool("acme-lib", ...)` is "a drop-in for this whole
  function's body". It is not, and taking it literally would break existing setups: the
  seam's probe layer is a `$PATH` walk for `kind: "executable"` ids ONLY, so a
  `directory`-kind id gets no probe layer at all — and ACME's standard library is resolved
  today by a fixed list of four documented prefixes (`/usr/local/share/acme`,
  `/usr/share/acme`, `/usr/lib/acme`, and `.acme` under the home directory). Replacing the
  function outright would delete that list and start refusing every developer who installed
  ACME from a distribution package and never set the environment variable, which is a direct
  `LOC-03` violation. The seam answers the environment and file layers; the existing
  fixed-prefix list stays as the probe layer beneath them.

<assumption_delta_decision>
- **Noun now primary:** the seam's resolution of a declared tool id — `resolveTool(id)`'s
  answer carrying `layer` and `mechanism`.
- **Decision: `promote`** — each individual probe becomes a `mechanism` inside one ordered
  resolution rather than a peer source of truth beside the environment variable, because
  `LOC-02` requires the precedence order in exactly one place. Full rationale and the
  "what would force a further promote" note are recorded in `60-01-PLAN.md`; PD-07 above is
  the one mechanism this plan deliberately leaves outside the seam, and says why.
</assumption_delta_decision>
