<objective>
Close the one failed truth of Phase 60: make a slash-free environment override resolve the
binary the developer actually named, and make the case where it cannot be resolved a named
refusal instead of a silent substitution — at the seam and at the real spawn call.

Purpose: `LOC-03` promises that a developer whose setup, test invocation or CI step sets
`VICE_BIN`, `ACME_BIN`, `ACME` or `GHIDRA_HOME` notices nothing whatsoever. For the class of
value that names a bare executable resolved by `$PATH` — which worked before this phase,
through `spawn()`'s own search and through `backend-detect.mts`'s former explicit `$PATH`
walk — the promise is currently false: the value is dropped, and resolution falls through to a
`$PATH` search for the *declared tool id*, which can start a different binary with no
diagnostic at all.

Output: a widened, terminal environment layer in `tool-location.mts`; the developer's own
candidate carried out of the seam so a consumer never has to re-read the variable; the refusal
surfaced through `resolvedBackend()` to the broker's startup log; and regenerated, committed
compiled artifacts.
</objective>

## Planner decisions recorded for this gap-closure pass

There is no Phase 60 CONTEXT.md. The decisions below are the planner's, recorded visibly,
continuing the `PD-` numbering the shipped plans 60-01..60-05 already use.

- **PD-13: widen first, then refuse — and the refusal is terminal only with respect to the
  declared-id `$PATH` probe.** The verification offered two fixes: widen the environment layer
  to walk `$PATH` for the value itself, or make a non-match a terminal refusal. Read against
  `LOC-03`'s own wording — "no current developer setup, test invocation or CI step changes
  behaviour" — only widening preserves the setup that actually worked before this phase: a bare
  `VICE_BIN=x64sc-custom` on `$PATH` was handed straight to `spawn()`, and
  `backend-detect.mts`'s former `defaultResolveBinPath()` walked `$PATH` for exactly that
  string. A refusal-only fix would newly break that developer, so it is rejected as the primary
  fix. Widening alone, however, leaves the dangerous half of the defect intact: a value that
  resolves nowhere still falls through to a `$PATH` search for the declared id and can start a
  different binary. So both halves ship: widen, and then — when the variable was set non-empty
  and nothing resolved it — stop, with a refusal, before the declared-id probe.
- **PD-14: the file layer is still consulted after an unresolvable environment value; only the
  declared-id `$PATH` probe is cut off.** A `tools.json` entry is a path the developer wrote
  down, not a guess, and cutting it off would weaken `LOC-01` for the combination of a stale
  variable plus a recorded path — a combination that works today. The hazard this gap is about
  is the *guess*: `$PATH` searched for a string the developer never typed. That is the single
  fall-through removed. This is also exactly what the verification's own `missing` item asks
  for, in its own words: never fall through "to Layer 3's literal-id `$PATH` probe".
- **PD-15: `findAcmeLib()`'s fall-through to its four fixed prefixes is deliberately left
  alone.** With `ACME` set to a directory that does not exist, the seam will now return a
  refusal; `findAcmeLib()` folds a refusal into "not found" and continues to
  `/usr/local/share/acme`, `/usr/share/acme`, `/usr/lib/acme` and `~/.acme`. That is
  pre-phase behaviour for that variable and plan 60-03's own verified truth, so preserving it
  is what `LOC-03` requires. It is recorded here so a verifier sees it was decided, not missed.
- **PD-16: this amends Phase 59's `D-08` posture for the environment layer, deliberately.**
  `D-08` scoped the environment layer to existence-only and coded a non-match as "not found,
  not refused, fall through". That posture is precisely what produces this gap. The executable-bit
  half of `D-08` is untouched: the `accessSync`/`X_OK` check stays scoped to the file layer
  alone, and the shipped test proving an environment override with no executable bit still
  resolves stays green, unchanged.

## What breaks, stated plainly

- **One shipped test's intent changes deliberately.** `tool-location.test.ts`'s "nothing
  answers: path/layer/mechanism are null and tried lists the environment candidate first, PATH
  candidates last" sets `VICE_BIN` to a nonexistent path and asserts that resolution walks on to
  the declared-id `$PATH` candidates with `refusal` null. That is the defective behaviour,
  pinned. It is rewritten in place — never deleted — to assert the refusal, with the reason
  recorded beside it. Task 2 owns that rewrite.
- **A developer who sets one of the four variables to a value that resolves nowhere, and has no
  `tools.json` entry for that id, now gets a named refusal** where today they silently get
  whatever same-named binary `$PATH` supplies. Before this phase that developer got a failed
  spawn naming their own value. The refusal is the honest form of the same outcome, and no setup
  that worked before this phase is affected.
- **Nothing changes for an unset variable, an empty-string variable, or a variable naming a real
  path.** Those are every case CI and every existing fixture in this tree actually exercise.

<assumption_delta_decision>
- **Noun now primary:** an **environment-supplied tool candidate** — a string a developer put in
  a declared variable, which may be either a path to resolve directly or a bare name to resolve
  on `$PATH`. The seam previously modelled that string as a literal path and nothing else, which
  is the identity error underneath this gap: `statSync()` on a bare name asks the wrong question
  of the right string.
- **Decision: `promote`.** "Environment value" is promoted from *a path* to *a candidate with two
  resolution mechanisms*, reusing the exact distinction `resolveOnPath()` already draws with its
  own `bin.includes("/")` branch rather than inventing a second one. The candidate is surfaced on
  the result as `envCandidate`, so the one true statement about what the developer asked for
  travels with the answer instead of being re-derived by each consumer.
- **Not `add-alongside`:** adding a second, environment-only probe beside the existing layers
  would put a fourth ordering into the tree and break `LOC-02`'s "the precedence order exists in
  exactly one place". The promotion keeps one order and changes what one layer of it understands.
- **What would force a further promote later:** if a declared variable ever needs to hold
  something that is neither a path nor a `$PATH`-resolvable name — a version selector, a URL, a
  list — then `envCandidate` stops being a string and becomes a parsed shape, and that is the
  signal to promote again rather than to special-case a prefix inside this layer.
- **Optional contract test encoding the generalized intent** (not required by this plan, proposed
  for a later phase): for every declared record carrying an `envVar`, resolving with that variable
  set to a value that resolves nowhere must never return a path, for any id — a property over the
  declaration rather than a case per variable.
</assumption_delta_decision>
