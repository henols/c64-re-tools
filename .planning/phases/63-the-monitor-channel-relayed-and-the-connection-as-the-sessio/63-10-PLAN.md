<planner_findings>
Facts established by direct read of the working tree and of the installed emulator during
planning. Re-confirm each before writing code — especially fact 2, which is a live probe.

1. **The project already measured `-jamaction 2`.** `stock-live-triage.test.ts`'s header and
   its `attemptJamMechanism()` inline comment both record, from that plan's own live probe on
   genuine 3.9 AND 3.10: `-jamaction 2` (Monitor) "routes a JAM through the STOPPED path
   instead of emitting the bare, zero-length-body JAM (0x61) event". `stock-live-relay.test.ts`'s
   own header carries a matching "Never use -jamaction 2" prohibition for that reason. So `2`
   is a known-negative for a bare JAM, not an untried candidate — probe it anyway as a control,
   but do not expect it to answer the question.
2. **`-jamaction` exists on the installed binary and its value set is documented by the binary
   itself.** `/usr/bin/x64sc --help` prints: `-jamaction <Type>  Set action on CPU JAM:
   (0: Ask, 1: continue, 2: Monitor, 3: Reset, 4: Power cycle, 5: Quit Emulator)`. Re-run that
   command and quote its output in the evidence file rather than trusting this line.
3. **`4` and `5` are forbidden by a standing project rule** (`stock-live-triage.test.ts`'s
   "WHAT NOT TO DO", T-07-17-05): power-cycling destroys all emulation state and quitting races
   the harness's own teardown. `0` (Ask) raises a modal dialog and must also be avoided. The
   probeable set is therefore: **no override (the production default, 1), `2`, and `3`.**
4. **No production launch-argv change is available or needed.** `broker-control.mts`'s
   `normaliseLaunchProfile()` carries an explicit T-33-04 prohibition on any profile key whose
   VALUE reaches argv, and `VICE_ARGS` replaces the WHOLE argv including the broker's own
   dynamically allocated ports. This plan therefore spawns the emulator DIRECTLY from the test
   file for the probe — exactly as `stock-live-triage.test.ts` already does with its
   `spawnOnPort(port, extraArgs)` helper — and touches no shipped module.
5. **The direct-dial-versus-relay discriminator has never been run.** 63-06's isolation
   experiment for id 69 compared two sequential DIRECT dials to each other (both got their own
   dump) but did not reproduce the production readiness probe's exact shape as the first
   connection. That precise shape — `probeReady()`'s `defaultBinmonProbe()`: a real PING, read
   the reply, resume with EXIT, close GRACEFULLY with `socket.end()` — is what the hypothesis
   names, and is what the probe must use.
6. **A bare TCP connect-and-destroy probe is measured-poisonous on this build** and must never
   be used here: `stock-live-relay.test.ts`'s `waitForPortOpen()` header records that an
   abruptly destroyed connection sat in the accept backlog until VICE retrieved it, dead, and
   treated it as its ONE serviced client, starving every later connection. Use a real
   PING/EXIT round trip closed with `socket.end()`.
</planner_findings>
