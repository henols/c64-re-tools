## Plan-level decisions (RESEARCH Open Questions, decided here rather than deferred)

- **OQ1 — `vice-proxy.ts`'s control connection stays on `openBrokerControl()`/`broker.json`
  for this phase.** Only the NEW relay connections use the fixed endpoint. Rationale: the
  ROADMAP's convergence note keeps `vice-proxy.ts` on legacy imports until Phase 66 and
  `SEAM-01` (Phase 65) owns that migration; the narrower reading is more atomic. The seam
  this leaves — control reached one way, relay another — is not left unchecked: the
  per-claim handle below is minted over the control connection and presented over the relay
  connection, so a relay that landed on a *different* broker is refused by name rather than
  splicing to the wrong machine.
- **No runtime development flag.** The ROADMAP permits a short-lived rollback flag. This plan
  declines it: `StockConnectDeps.dialMonitorSocket` is an injectable seam in this project's
  standing register and gives tests and a manual bisect the same lever without leaving a
  runtime branch behind as carried debt.
- **Attach authority: a per-claim handle, never a bare target id.** A relay connection is a
  *different socket* from the control connection that holds the grant, so
  `broker-control.mts`'s `ownsTarget()` closure variable is null on it and cannot gate the
  attach. `monitor_claim` therefore mints a 16-byte random handle, returns it on its reply and
  stores it on the claim record; `attach` requires the per-boot control token AND a
  constant-time match on that handle. This is the concrete form of the ROADMAP's "ownership is
  checked per operation, never by bare target id" for a socket that holds no grant.

## Upstream settled decisions this phase implements

`REQUIREMENTS.md`'s project-wide settled decisions stand in for the missing CONTEXT.md and
are honoured literally:

- **Decision 3 (session model).** Skill calls stateless, the MCP connection is the session.
  Implemented by the relay's lifetime being the session's lifetime (this plan and 63-04) and
  confirmed by observation for the stateless shape (63-05, Task 3).
- **Decision 6 (wire shape).** One endpoint, multiple tagged connections; no new envelope
  format; the protocol module's socket-consumption contract is not touched. Implemented as one
  dedicated physical connection per claimed channel, distinguished by the handshake tag, with
  raw bytes past the handshake and **no envelope of any kind** around them. The one place this
  phase does touch the protocol module needs stating plainly rather than glossed: `connect()`
  creates its own socket internally and there is no injection seam anywhere in either client
  class, so relaying at all requires a narrow new entry point. `attach()` adds a socket
  *source* and reuses the existing data, close and error wiring byte for byte; it parses
  nothing new and changes no frame the module already parses. That is the narrowest reading of
  Decision 6 that is actually implementable, and it is recorded here rather than left as an
  unstated liberty.

## Canon-referral breadcrumb (prohibition probe)

- "A relay connection attaching to a target id it never claimed" is canon OWASP A01 broken
  access control. Per the canon-referral rule it is **not** minted as a prohibition; it is
  carried as threat `T-63-01` below and mitigated by the per-claim handle.

<assumption_delta_decision>
**Signal:** `pluralization` — the scope introduces a *second* project's session against one
broker ("a second `connect()` sits unserviced…", "must not be able to reach another's
instance"). One broker has lost its single-tenant monopoly.

**Primary noun:** the **session** — a client-declared identity owning a grant, its monitor
claims and its relay connections — is now the thing a human names, not the port number.

**Decision: `promote`, for identification only.** The session becomes the primary user-facing
identity (Plan 63-05 puts it on `status`); the port number is demoted to a detail of one
session. **Authorisation is deliberately NOT generalised:** the grant the connection itself
holds, and the per-claim handle minted from it, remain the only credentials. A caller-declared
session label must never become an authorisation input — that is prohibition P2 in Plan 63-05.

**Invariant test suggested and accepted:** Plan 63-05's `status` cases assert that two grants
from two different declared sessions are each identifiable by their own label, and that a
request naming another session's label is refused with the same wording as a request naming a
bare target id.
</assumption_delta_decision>
