<objective>
Give the broker the two things it needs to leave evidence behind when a relay dies: a
name for the operation that was in flight, and a writer that can put a record on disk
from the host side.

Purpose: SESS-05 requires an incident record carrying a broker-supplied reason that
names the operation in flight. The broker cannot observe that name — the channel lock
that knows it is in-process, container-side state — and it cannot reuse the existing
incident writer, which is a container-side module rooted at a per-project directory.
Both halves are new plumbing, and both have to exist before Plan 63-04 can order a
write ahead of a reclaim.

Output: an eleventh control op that carries the operation name, the grant field that
holds it, a new host-bound incident writer rooted at the machine-level incidents
directory, and the two client call sites that declare and clear the name.
</objective>

## Plan-level decisions (RESEARCH Open Questions 3 and 4, decided here)

- **OQ3 — the broker gets its own host-bound writer; `incident-record.ts` is NOT
  parameterised.** RESEARCH recommends threading a directory parameter through the existing
  writer. That recommendation does not survive contact with the boundary: the blocker is not
  the hardcoded default path, it is that `incident-record.ts` is a container-side `.ts` module
  and the broker runs from a compiled `.mjs` artifact that has no such sibling — the same
  reason `broker-home.mts`'s own header gives for not importing the project-root resolver.
  Parameterising the existing writer would change every existing call site and still leave the
  broker unable to call it. So: a small, purpose-built `broker-incident.mts`, **mirroring**
  the field vocabulary rather than importing it — the same mirror-with-a-sync-test discipline
  this codebase already uses for the handshake magic string and the dev-version placeholder.
  Task 2 adds the sync test so the two vocabularies cannot silently drift.
- **OQ4 — "the operation in flight" needs new wire-level bookkeeping, and it is a client
  declaration over the control connection.** The broker cannot derive it: the channel-lock
  holder that knows it is per-process container-side state, and deriving it from the relayed
  bytes would mean parsing binmon frames, which Success Criterion 1 forbids outright. It is
  declared with a new `operation` op sent from the two wrappers that already know the tool
  name and already hold the control session. The declaration is **written but not awaited** by
  the caller — a pending entry is registered so the response-ordering discipline of the
  control reader is preserved, while the tool call itself never waits on it. This same
  declaration is what Plan 63-04 uses to tell a legitimately silent channel (a checkpoint
  wait) from a dead one, so one mechanism serves both SESS-05 and SESS-04 rather than two.
