<objective>
Make the connection the session: when a relay socket dies — cleanly, abruptly, or by
going silent past a bound the broker owns — the broker notices from socket events
alone, leaves evidence, and then lets go of exactly as much as died.

Purpose: SESS-03 and SESS-04 are the two halves of "a client that dies badly is still
cleaned up", and SESS-05 is the rule that makes the cleanup accountable. This is the
plan where the relay stops being a pipe and becomes a session.

Output: a bounded, broker-owned idle deadline that can tell a legitimately silent
channel from a dead one; keepalive on both the relay and control connections; a
channel-scoped teardown that writes its record before it releases anything; and the
same evidence step ahead of the existing identity-verified instance kill.
</objective>

## Plan-level decision: what a bounded deadline can and cannot mean

RESEARCH proposes an idle timeout as the direct mitigation for a relay that attaches and
goes silent. Taken alone that is wrong in a way worth writing down: a held session is
legitimately silent for minutes while an agent thinks, and a checkpoint armed on a cold
address is legitimately silent for longer still. An idle timeout that reclaimed the instance
would destroy a user's emulator state as a routine consequence of thinking.

So the deadline is kept, and two things are changed about it.

- **It is suspended while the grant has a declared operation.** Plan 63-03's declaration is
  what separates "legitimately waiting" from "gone". A channel with something declared is
  never torn down by the clock; a channel with nothing declared and nothing moving is.
- **Firing is channel-scoped, never an instance kill.** The deadline releases the monitor
  claim and destroys the two relay legs, freeing the scarce single-client monitor slot, and
  leaves the instance running and the grant standing. The client's next tool call re-attaches
  through the existing identity-proved reconnect, so a user loses nothing but the relay.

The keepalive setting is kept too, as a **secondary** signal and labelled as one. Node can set
the delay before the first probe; the probe interval and count past that delay remain the
host's own kernel settings, which this broker cannot change. That is stated in the code
comment and in the README so nobody later mistakes it for the bounded mechanism.
