<objective>
Close the caller half of 63-VERIFICATION.md's remaining gap (truth #5, ROADMAP Success
Criterion 4, SESS-05). `text-connect.ts`'s `textDisconnect()` and `stock-connect.ts`'s
`stockDisconnect()` both close their end of the relay socket FIRST and send
`releaseMonitor()` second. Because of that order the broker sees the socket die before it
ever learns the teardown was deliberate, so plan 63-11's per-channel teardown runs too late
to prevent the spurious incident record.

Purpose: neither half of this fix works alone. 63-11 makes `monitor_release` remove and
close the channel's live relay session; this plan makes both production callers send that
release before they close, so the broker's early-return guard is the thing the close lands
on. `text-tools.ts`'s `withTextTool()` runs this exact open/run/close sequence on EVERY
text-channel tool call, which is why the defect shows up once per successful call.

Output: two reordered teardown functions, each with the disconnect guaranteed regardless of
what the release returns, and six regression cases proving the order behaviourally rather
than by reading the source — plus the full-suite gate over the composed fix.
</objective>

<planner_findings>
Four facts were established by direct read of the current working tree during planning.
Re-confirm each before writing code.

1. **Both functions are two statements today, in the wrong order.** `textDisconnect()`
   (`text-connect.ts`, roughly line 216) awaits `safeDisconnect(session.client)` and then
   awaits `session.brokerControl.releaseMonitor({ targetId, channel: "text" })`.
   `stockDisconnect()` (`stock-connect.ts`, roughly line 577) is the identical pair with
   `channel: "binary"`. Both discard the release outcome entirely on this success path.

2. **A real `releaseMonitor()` never rejects.** `BrokerControlSession`'s own header in
   `vice-broker-client.ts` (roughly line 862) states that each method "resolves against its
   own deadline; none of them ever reject", and `ReleaseMonitorOutcome` models `timeout`,
   `unauthorized`, `bad_request`, `denied` and `internal` as outcomes rather than throws. So
   the reorder cannot make a real production release hang unboundedly ahead of the
   disconnect — it is bounded by that deadline. A `finally`-shaped disconnect is still
   required, because a stub or a future implementation could throw and because a throw must
   not leave the socket open.

3. **Both existing consumers already tolerate a throw from these functions.**
   `stock-dispatch.ts`'s `ensureStockSession()` (roughly line 375) wraps its stale-session
   `stockDisconnect(stale)` in a try/catch that logs; `stock-recycle.ts` (roughly line 564)
   calls it inside a try whose catch returns a well-formed `isError` result; `text-tools.ts`
   (roughly line 210) wraps `textDisconnect(session)` in a try/catch that logs. So preserving
   the current throw-propagation semantics is safe, and swallowing a throw would be a silent
   behaviour change. Use `try { release } finally { disconnect }` — the release's throw still
   propagates, and the disconnect still happens.

4. **The `catch` blocks inside `textConnect()`/`stockConnect()` are a DIFFERENT path and stay
   as they are.** Both already do `safeDisconnect(client)` and then a release wrapped to
   report but never displace the original error (the WR-07 precedent both files' comments
   describe). A handshake that fails after the relay attached is a genuine abnormal event and
   its incident record is correct evidence — reordering those would suppress a record that
   should exist.
</planner_findings>
