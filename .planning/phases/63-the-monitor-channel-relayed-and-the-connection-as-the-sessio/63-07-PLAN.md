<planner_findings>
Three facts were established by direct read of the current working tree during planning.
They correct the gap prose in places; implement against these, and re-confirm each before
writing code.

1. **`handleRecycleForRealBroker()` does NOT delete the grant or the instance.**
   63-VERIFICATION.md's gap `reason` says both paths "delete the grant/instance records".
   That is true of `handleRelease()` only. `handleRecycleForRealBroker()`'s body calls
   `markDeliberateDeath(instance, true)`, `clearMonitorClient(instance)` and
   `await verifiedKill(...)`, and its own header states plainly that neither record is
   deleted because the exit handler needs both to carry out the respawn. So the two paths
   have DIFFERENT symptoms, and 63-REVIEW.md CR-01 (not the verification prose) describes
   them correctly:
   - **release:** the async close finds grant and instance already gone, so the record is
     content-empty — `operation: null`, `port: null`, `epoch_before: null`.
   - **recycle:** the async close finds the grant still present, resolves the instance
     through `grant.port`, and after a fast respawn that is the **new** post-recycle
     `InstanceRecord` — so `port`/`epoch_before` describe the replacement, misattributing
     the very evidence the mechanism exists to produce.
   Both are wrong; they are wrong in different ways, and the SUMMARY must say so.

2. **`RelayDeathTrigger` genuinely does not carry `"control_close"`, and that is correct.**
   `broker-relay.mts:133` declares `"relay_close" | "relay_error" | "relay_idle_expiry"`.
   `broker-incident.mts:55` declares `BrokerIncidentTrigger` as those three **plus**
   `"control_close"`. `broker-relay.mts`'s header prose says `control_close` "never
   originates here ... vice-broker.mts's own release path, Task 3, is what produces that
   fourth value" — which is accurate: `handleRelease()` passes `trigger: "control_close"`
   to `writeIncident`, an incident trigger, never to `RelaySession.close()`. **Resolution:
   do NOT widen `RelayDeathTrigger`.** The deliberate teardown calls
   `session.close("relay_close")` — the graceful shape — and `close()` ignores its argument
   entirely past the first call anyway (`RelaySession.close`'s own documented contract).

3. **`close()` is safe to call from a teardown path.** `spliceRelay()` keeps two separate
   latches: `deathReported` (guards `onDeath`) and `closed` (guards the socket destroy).
   Destroying the sockets fires their `"close"` events, which call `reportDeath()` →
   `onDeath` → `handleRelayDeath()`. Deleting the map entry BEFORE calling `close()` is
   what makes that re-entry a no-op — this is exactly the order `handleRelayDeath()` itself
   already uses at `vice-broker.mts:1139-1141`. Preserve it.
</planner_findings>

**Noun now primary:** the **grant** (`GrantRecord`, keyed by target id) — unchanged.
`relaySessionKey(grantId, channel)` keys the relay-session map per channel, and
`GrantRecord.operation` remains a single field per grant.

**Decision:** `no-change`.

**Rationale:** the detector's two `pluralization` signals ("a second `connect()` sits
unserviced…", "must not be able to reach another's instance") are both verbatim quotations of
ROADMAP cross-cutting constraints that predate this round; neither is a generalization this
gap closure introduces. The teardown helper this plan adds is keyed by grant and enumerates
the frozen two-value `MONITOR_CHANNELS` tuple, which preserves the existing model exactly —
a grant owns N channels, and a channel is a detail of its grant, never a peer identity.
Plan 63-08's WR-01 fix likewise narrows the window in which `GrantRecord.operation` can be
written rather than pluralizing the field, so the "one in-flight operation per grant"
assumption `handleOperationNote()` documents is preserved rather than contradicted.

generalized intent — it goes red the instant a third channel exists and the teardown path
still handles only two.
