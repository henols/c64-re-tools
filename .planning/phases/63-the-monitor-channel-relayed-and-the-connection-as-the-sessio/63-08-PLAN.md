<objective>
Close 63-VERIFICATION.md's GAP 1 third `missing:` item (63-REVIEW.md WR-01, VERIFICATION
Key-Link row "⚠️ PARTIAL (ordering)", SESS-05): `text-tools.ts`'s `withTextTool()` declares
its operation on the grant BEFORE `withTextChannelLock()` has granted the shared
cross-channel mutex, while `stock-dispatch.ts`'s `withChannelLockHeld()` declares only AFTER
`acquireChannelLock()` has returned.

Purpose: `handleOperationNote()` (`vice-broker.mts`) stores exactly one `operation` value per
grant, on its own stated assumption that `channel-lock.ts`'s single cross-channel mutex
already guarantees only one logical operation runs per grant at a time. That assumption only
holds if every caller declares after it holds the mutex. Today a text tool queued behind a
running binary tool overwrites `grant.operation` with its own name while it is still queued —
so a relay death at that instant attributes the incident to an operation that never ran, and
the text call's own `finally` can erase a declaration belonging to the other channel.

Output: symmetric declare ordering in both wrappers, and a concurrency test that contends the
shared mutex from the binary channel — the only shape in which the defect is observable.
</objective>

<planner_findings>
Facts established by direct read of the current working tree during planning. Re-confirm
before editing.

1. **Both orderings are present exactly as the review describes.** `text-tools.ts`'s
   `withTextTool()` has `void lease.brokerControl.noteOperation({ targetId, channel: "text",
   name: toolName }).catch(() => {});` immediately before `try { return await
   withTextChannelLock(toolName, () => fn(session.client), { timeoutMs:
   deps.channelLockTimeoutMs }); }`, and clears the field with a second `noteOperation({...
   name: null })` in the outer `finally` beside `textDisconnect(session)`.
   `stock-dispatch.ts`'s `withChannelLockHeld()` has `handle = await acquireChannelLock({
   channel: "binary", operation: toolName, timeoutMs })` and only then
   `declareOperation(session, toolName)`, with `declareOperation(session, null)` and
   `handle.release()` in its own `finally`.

2. **The mutex genuinely is shared across both channels.** `withTextChannelLock()`
   (`text-protocol.ts:700`) is a thin wrapper over the same `acquireChannelLock()` the binary
   side calls, differing only in `channel: "text"`; `channel-lock.ts` holds one
   `currentHolder` for both. So holding the binary lock in a test blocks the text handler's
   acquisition, which is what makes the defect observable.

3. **The test harness is already wired for this.** `text-tools.test.ts` already imports
   `acquireChannelLock`, `currentChannelLockHolder`, `channelLockRefusalMessage` and
   `resetChannelLockForTests` from `channel-lock.ts`, and already builds
   `makeStubBrokerControl()` whose `noteOperation()` is a stub returning `{ ok: true }`.
   No new harness is needed — extend the existing stub to record its calls.

4. **`handleOperationNote()`'s one-field-per-grant model is deliberate and must not change.**
   Its header states that a grant has exactly one in-flight operation regardless of which
   channel runs it, and it explicitly discards the `channel` argument (`void channel;`). The
   reorder makes that assumption true; do not pluralize the field or key it by channel.
</planner_findings>
