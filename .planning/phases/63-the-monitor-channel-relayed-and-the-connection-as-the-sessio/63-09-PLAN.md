<objective>
Close the relay's half of 63-VERIFICATION.md truth #2 (`⚠️ PRESENT_BEHAVIOR_UNVERIFIED`,
ROADMAP Success Criterion 1, SESS-02, WINDOWS id 70): prove — automatically, deterministically
and in CI — that a JAM frame is byte-transparent over the relay and demuxes by request id, the
same as the three wire shapes already proven.

Purpose: Success Criterion 1's own wording is about the relay, not about the emulator —
"`stock-protocol.ts` is handed a different socket and frames, parses and demuxes identically,
with its own content unchanged." That property is testable without an emulator, and today it
has **zero** coverage for the JAM shape: `grep -c jam src/mcp/vice/broker-relay.test.ts`
returns 0 (measured during planning). Plan 63-06's live run attempted to prove the same claim
through a real emulator and could not, because real stock VICE 3.9 did not emit a JAM at all
under its default JamAction — an emulator-behaviour question, separate from the relay, which
plan 63-10 measures and ledgers honestly.

CLAUDE.md's own protocol constraint makes this shape the highest-value one to cover: `JAM`
(0x61) has a **zero-length body** — `monitor_binary.c:384-394` computes the PC then passes
`length = 0` — and "every client surveyed assumes 2 bytes and breaks on it."

Output: three cases in `broker-relay.test.ts`, all driven through the real `spliceRelay()`,
the real `dialMonitorRelay()` and the real `stock-protocol.ts` parser over real loopback
sockets.
</objective>

Facts established by direct read of the working tree during planning. Re-confirm before
writing code.

1. **The fixture already exists.** `src/mcp/vice/binmon-fixtures.ts` exports
   `syntheticJamFrame()`, which builds exactly the documented shape: `responseType: 0x61`,
   `errorCode: 0x00`, `requestId: VICE_BROADCAST_REQUEST_ID`, `body: Buffer.alloc(0)`. Its own
   doc comment cites `monitor_binary.c:384-394`. Use it; do not hand-build a second JAM frame.
2. **The harness already exists.** `broker-relay.test.ts` already imports `ViceMonitorClient`,
   `ResponseType`, `VICE_BROADCAST_REQUEST_ID`, `encodeResponseFrame` and `dialMonitorRelay`,
   and already has `withStubEmulatorServer()`, `setupBrokerState()`, `withRelayTestBroker()`
   and `claimAndDialRelay()`. No new harness is needed.
3. **The parser's JAM arm tolerates both body lengths by design.**
   `stock-protocol.ts:1478` returns `programCounter: body.length >= 2 ? body.readUInt16LE(0) :
   null`, so a zero-length body must decode to `null`. Asserting `null` is what distinguishes
   a correct decode from a fabricated PC.
4. **Zero existing JAM coverage in this file.** `grep -c jam broker-relay.test.ts` returns 0.
   These are genuinely new cases, not duplicates of something 63-01…63-06 already wrote.
5. **A launch-argv route for `-jamaction` is blocked by a recorded project prohibition.**
   `broker-control.mts`'s `normaliseLaunchProfile()` carries an explicit, requirement-tagged
   rule (T-33-04): "WHAT MUST NEVER BE ADDED HERE: a passthrough string, an `extraArgs`, or
   any key whose VALUE reaches argv. `profile` maps to exactly two literal flag tokens
   (`-console`, `-warp`) and to nothing else." `-jamaction <n>` is precisely a key whose value
   reaches argv. This plan therefore adds **no** launch-argv change; plan 63-10 measures the
   emulator question by a route that needs none.
</planner_findings>
