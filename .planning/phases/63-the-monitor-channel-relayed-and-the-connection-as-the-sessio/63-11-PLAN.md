<planner_findings>
Five facts were established by direct read of the current working tree during planning. Two
of them CORRECT the gap prose. Implement against these, and re-confirm each before writing
code.

1. **In production today the socket close happens BEFORE the release, not after.**
   `text-connect.ts`'s `textDisconnect()` (line 216) is two statements: `await
   safeDisconnect(session.client)` and then `await
   session.brokerControl.releaseMonitor(...)`. `stock-connect.ts`'s `stockDisconnect()`
   (line 577) is the identical pair for the binary channel. So the client destroys its end
   of the relay socket first, and the broker writes the junk record from
   `handleRelayDeath()` before `monitor_release` ever arrives on the control connection.
   63-VERIFICATION.md's `missing[0]` describes the fix as making "the client-side socket
   close that FOLLOWS" a no-op, and its `missing[2]` says "both existing production callers"
   follow a release with a close — both of those describe the TARGET order, not today's.
   **Consequence: this plan's broker-side teardown is necessary but NOT sufficient on its
   own.** Plan 63-12 reorders both callers to release-then-close. Neither plan alone removes
   the spurious record; together they do. Say so in the SUMMARY rather than claiming this
   plan closes the gap by itself.

2. **`tearDownRelaySessionsForGrant()` cannot be reused unchanged**, exactly as the gap
   says. It iterates `MONITOR_CHANNELS` and tears down the WHOLE grant, which would destroy
   the other channel's live session on a single-channel release. The fix is to extract its
   per-channel body into a new helper and have the grant-level function call that helper in
   its loop, so there is ONE delete-before-close implementation and not two.

3. **`handleMonitorRelease()` has four exit paths and only three of them may tear down.**
   Its body resolves the instance (absent -> `bad_request`), reads
   `instance.monitorClients[channel]` (absent -> `ok: true`, the documented tolerance for
   releasing an already-cleared record), compares `existing.grantId !== targetId` (->
   `denied`), and otherwise calls `clearMonitorClient(instance, channel)` and returns
   `ok: true`. The teardown belongs on the two `ok: true` paths and on neither refusal —
   a refusal that destroyed a live socket would turn a spoofed release into a working
   denial-of-service against another grant.

4. **`handleRelayDeath()` already has the early-return guard this fix depends on**
   (`vice-broker.mts:1112-1113`): an absent `state.relaySessions` entry means "a teardown
   already ran", and it returns having written nothing. Deleting the map entry before
   calling `close()` is what routes the re-entry into that guard. `spliceRelay()` keeps two
   independent latches (`deathReported`, `closed`), so calling `close()` from a teardown
   path is safe and idempotent.

5. **`broker-state.mts`'s `relaySessions` doc comment currently names exactly TWO removers**
   (`handleRelayDeath()` and `tearDownRelaySessionsForGrant()`, added by plan 63-07). This
   plan adds a third entry point. Because the new helper is what `tearDownRelaySessionsForGrant()`
   itself now delegates to, the honest correction is to name the new helper as the single
   deliberate-teardown primitive, with `tearDownRelaySessionsForGrant()` described as its
   whole-grant caller. Leave the "SINGLE WRITER ... is handleRelayAttach()" sentence alone —
   it is still true.
</planner_findings>
