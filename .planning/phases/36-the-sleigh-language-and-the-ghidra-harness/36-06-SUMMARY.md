## Accomplishments

- Derived the 105-byte undocumented-opcode set mechanically from the committed `6502_undocumented.sinc` (`op=0x[0-9a-fA-F]{2}` extraction, lowercased, de-duplicated) -- MEASURED and asserted at exactly 105, independently re-derivable at the shell.
- Built `generateOpcodeSweep()`, ONE synthetic-sweep generator reused unmodified by all three tasks: one byte per 4-byte slot (opcode + NOP filler + a documented RTS terminator), generated fresh into a scratch workspace and never committed. MEASURED that a terminator is not optional: without one, `DecompInterface` reports every seeded function `DECOMPILE_FAILED` (fall-through NOP disassembly runs each "function" off the end of the image with no discovered exit) -- recorded in `fixtures/ghidra/README.md` and evidence Part 1.
- `assertSweepFullyDecodes()` refuses (throws) on a zero-length sweep and on a sweep containing none of the required bytes, rather than trivially passing either -- covered by two pure unit tests.

A disclosed, MEASURED anomaly (byte `$89` decodes under the stock language too, reproduced across two independent runs) is recorded rather than hidden or smoothed into a rounder number.
- Derived the six unstable/page-crossing-dependent representative bytes from the committed `.sinc`'s own `define pcodeop` declarations and their referencing constructors (never typed); `unstableAHXStore`'s two constructors ($93, $9f) resolve to the first one found ($93). Live: all six decompile to a form naming their own opaque operation by name, with that operation's own result flowing DIRECTLY to the destination register or store (a bare `return uVar1;` or `... = uVar1;`), never a computed expression -- the actual content OPC-02 requires, not merely that the byte decoded.
- Derived the 15-byte overlap between the extension and the stock 65C02 source from both real files -- MEASURED, asserted as both a set and a size (15), with its own non-empty-overlap assertion. `extractLanguageElementIds()` reads only `<language ...>` elements' own `id` attribute (a naive whole-file scan double-counted a nested `<compiler ... id="default"/>` child on the first attempt -- caught and fixed before commit). Confirmed the stock `6502.ldefs` still declares only its own two original ids and the extension's `6502_nmos.ldefs` is a physically separate file under a separate, non-colliding id; confirmed `65c02.slaspec`'s own first line includes only the base 6502 source, never this extension.
- Live: all 15 shared bytes decode as code under `65C02:LE:16:default` in the same installation, with none of the extension's six pcodeop names appearing anywhere in the decompiled text; the two bytes also in the eight-constructor compile-failure set ($9c, $9e) decompile to a real store-of-zero statement (STZ's own signature), never this extension's own SHY/SHX userop.
- Recorded all three parts in `evidence/36-06-opcode-decode.md`: the 105-row per-byte table under both languages (Part 1), all six unstable decoded forms verbatim (Part 2), and the 15-byte overlap set, per-byte 65C02 table, and structural non-collision reason (Part 3) -- closing with what remains unproven (the sweep is synthetic; plan 36-07 is the real-code check).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug, measurement-driven] Sweep slots needed an explicit RTS terminator, not just NOP padding**
- **Found during:** Task 2's own first live probe (before any assertion was written)
- **Issue:** The plan's own action text said to pad each slot "so a multi-byte instruction cannot run into its neighbour" but did not specify a terminator. A first probe with NOP-only padding across the whole 64K image let `analyzeAll()`'s fall-through disassembly run every seeded function off the end of the image with no discovered exit; `DecompInterface` reported `DECOMPILE_FAILED` for all six unstable-byte functions (0 decompiled of 6 attempted), so Task 2's own check (reading decompiled text) had nothing to check.
- **Fix:** Added a documented RTS ($60) at the last byte of every 4-byte slot, bounding each slot's own function without ever overlapping the longest undocumented instruction (3 bytes). Re-probed live: all six (and later, all 105, and all 15) decompiled cleanly (0 failed, 0 timed out).
- **Files modified:** `src/mcp/vice/ghidra-opcode-live.test.ts`, `src/mcp/vice/fixtures/ghidra/README.md`
- **Verification:** Live re-run against the real installation; `DECOMPILE_FAILED 0` across all three sweeps.
- **Committed in:** `65e7c780` (Task 1 commit -- the shared sweep generator, used by all three tasks, was authored with the terminator from the start once this was found during early probing)

**2. [Rule 1 - Bug] A naive `id="..."` regex double-counted a nested `<compiler>` element's own id**
- **Found during:** Task 3's own LDEFS case, first run
- **Issue:** `extractLanguageElementIds()`'s first draft matched `id="..."` anywhere in the file, which also matched each stock language's own nested `<compiler name="default" spec="6502.cspec" id="default"/>` child element -- a completely different id (the compiler-spec id, not the language id). The stock `6502.ldefs` case failed, reporting four ids instead of two.
- **Fix:** Matched `<language ...>` opening tags first (a `[^>]*` scan, which matches embedded newlines since the tag spans multiple lines), then extracted the `id` attribute from within each matched tag's own text only -- mirroring `ghidra-project.mts`'s own `LANGUAGE_ELEMENT_PATTERN`/`ID_ATTR_PATTERN` two-step.
- **Files modified:** `src/mcp/vice/ghidra-opcode-live.test.ts`
- **Verification:** Re-run live; the stock `6502.ldefs` case now reports exactly its own two ids.
- **Committed in:** `230b91b3` (Task 3 commit)

**3. [Rule 1 - plan premise adjusted by measurement] Task 3's per-byte mnemonic proof could not use a raw disassembly mnemonic string**
- **Found during:** Task 3's own planning, before any live run
- **Issue:** The plan's action text asked to "assert the decoded mnemonic is the 65C02's own documented meaning for that byte." `GhidraStructExport.java`'s committed export format (which this plan deliberately does not modify -- it is a file plan 36-05 touches, in the same wave) has no section printing a raw per-address disassembly mnemonic; only `## CLASSIFICATION` (code/data/undef) and `## DECOMPILED_TEXT` (decompiled C) are available.
- **Fix:** Used the AVAILABLE signals instead: classification (decodes as code under 65C02), a checked ABSENCE of all six of this extension's own pcodeop names in the decompiled text (a real collision check, not merely "it decoded"), and for the two compile-failure bytes specifically, a checked PRESENCE of the real STZ signature (a literal `= 0;` store, the opposite of this extension's own opaque SHY/SHX userop) -- combined with the structural non-inheritance proof (separate `.ldefs` id, separate compiled language file, `65c02.slaspec`'s own first line including only the base source). The plan's own `must_haves.truths` explicitly permits this: "asserted unchanged against a reading taken before the extension was installed, OR against the 65C02's own documented mnemonics per byte" -- the second half of that OR is what this plan's design satisfies, via the strongest signal the committed export format actually provides.
- **Files modified:** none beyond the test file itself; documented in `key-decisions` and evidence Part 3 rather than silently substituted.
- **Verification:** Live re-run confirms all 15 bytes classify as code, none contain any extension pcodeop name, and the two compile-failure bytes both show the STZ store-of-zero signature.
- **Committed in:** `230b91b3` (Task 3 commit)
