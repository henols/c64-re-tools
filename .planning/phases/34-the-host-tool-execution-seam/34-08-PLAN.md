`runOracleProbe()` spawns as the EXECUTABLE after only an existence check. Then make
"no argv passthrough anywhere" a mechanism rather than three point fixes, by declaring every

a trust-boundary regression introduced by the migration itself: before Phase 34 the same

migration it is honoured as a host-absolute path and executed by the host broker.

script migrated, and a data-driven census that catches the next unresolved path key.

## Why the review's first offered fix is the wrong one here, and what is delivered instead

`34-REVIEW.md` § CR-01 offers two fixes: (a) require the override to resolve INSIDE the
workspace via `resolveWorkspacePath()`, or (b) restrict it to a basename allowlist. Its own
code sketch uses (b).

Option (a) must not be taken. The untrusted principal is the container-side caller, and that
caller can write files into the shared bind-mounted workspace — the review says so itself
("a container-side actor that can write a file into the shared bind-mounted workspace ... can
set the variable to it and have the host broker execute it"). Requiring the executable to
live inside the workspace therefore *guarantees* the caller can choose it: it would hand out
a host-execution primitive by design rather than closing one.

Option (b) narrows the primitive but does not close it: any file named as the expected binary,
anywhere the broker can reach — including inside the caller-writable workspace — would still
be spawned.

This plan delivers the closure that strictly subsumes both: **the wire key is removed** and
the oracle's location comes from the broker process's own environment on the host, with
option (b)'s basename check retained as a second layer on that host-resolved value. That is
the literal form of the criterion ("no argv passthrough anywhere") and of the module's own
invariant, and it is the same shape `34-04` already chose when it moved `findAcmeLib()`'s
five host candidate paths server-side.

**Version-skew consequence, stated rather than discovered.** The two sides of this seam ship
in different npm packages (`@henols/c64-re-tools` holds the skill scripts,
`@henols/vice-mcp` holds the executor), so an older script can meet a newer server. That
pairing now gets a refusal naming the retired key, which `probeUnp64()` already reports as
oracle-absent with the refusal text as its reason — absence of the oracle is a documented,
expected state in that module, so this degrades diagnosably. Accepting-and-ignoring the key
instead would violate the module's own never-drop-a-key-silently discipline, which is why
refusal is the right behaviour and is asserted as a case.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| container-side caller → broker control socket | The untrusted principal: it supplies every wire value AND can write files into the shared bind-mounted workspace |
| broker control op → host EXECUTABLE selection | The boundary CR-01 crosses: which host binary runs, not merely which arguments it gets |
| host broker process environment → oracle location | The replacement boundary: configuration that the container-side caller cannot write |
