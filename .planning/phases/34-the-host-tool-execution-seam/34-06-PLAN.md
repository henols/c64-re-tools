<assumption_delta_decision>
**Detected:** `pluralization` — the phase scope introduces "a second floor pinned over its
own prefix", where there was one.

**The noun that is now primary:** *a module family prefix*, not *the annotation module
family*. The non-vacuity floor was written for one family and is now one instance of a
per-family obligation.

**Decision: `add-alongside`, deliberately.** A second, independently hand-pinned floor sits
beside the first rather than both being promoted into one parameterised mechanism.

**Rationale:** the promote move here would be a shared helper taking a prefix list and
returning a count to compare against — and that is precisely the shape
`hostpath-consumers.test.ts`'s own header forbids in terms: "THE FLOOR MUST NEVER BE DERIVED
FROM DISK... A floor computed from `readdirSync` at test time can never fail." A generalized
floor mechanism whose per-family threshold came from anywhere but a hand-written literal
would convert two proven guards into two unfailable ones, over a suite that still reads
green — the exact decay the project's Standing Constraint on repaired guards describes. So
the correct primary noun changes while the mechanism deliberately does not.

**Accepted debt:** N families means N hand-pinned floors, each needing a deliberate raise
when its family grows, and each capable of drifting out of date independently.

**What would force a promote:** a fourth family prefix, or the first observed instance of a
floor silently drifting from its measured count for more than one milestone. The promote
would then be a shared helper that still takes a hand-pinned integer literal PER CALL —
never a derived total — so the non-vacuity survives the generalization.
</assumption_delta_decision>
