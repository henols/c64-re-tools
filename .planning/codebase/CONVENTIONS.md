# Coding Conventions

**Analysis Date:** 2026-08-11

## Scope Note

This repository has no `src/` application code in the traditional sense. It is a Claude Code
plugin: a collection of **skills** (`.claude/skills/*`, each with Node `.mjs` scripts), an **MCP
server** (`.claude/mcp/vice/*`, TypeScript run directly via Node's native type-stripping, no build
step for dev/test), and an **npm installer** (`installer/bin/cli.mjs`). Conventions below are
drawn primarily from `.claude/mcp/vice/` (the largest, most rigorously maintained code, ~24k lines
across `.ts`/`.mts` files) and cross-checked against the skill scripts and installer, which follow
the same style in plain JS.

## Naming Patterns

**Files:**
- Lowercase, hyphen-separated: `repo-root.ts`, `container-guard.mts`, `broker-launch.mts`,
  `vice-broker-client.ts`, `d64-parse.mjs`, `project-paths.mjs`.
- Test files are co-located, same basename plus `.test.ts` / `.test.mjs`:
  `repo-root.ts` -> `repo-root.test.ts`; `d64-parse.mjs` -> `d64-parse.test.mjs`.
- `.mts` is used specifically for modules that get compiled to a build artifact under
  `resources/` (see `.claude/mcp/vice/tsconfig.build.json`'s `include` list: `vice-broker.mts`,
  `container-guard.mts`, `broker-state.mts`, `broker-launch.mts`, `broker-kill.mts`,
  `broker-epoch.mts`, `broker-control.mts`). Plain `.ts` files are consumed as source directly
  (type-stripped at runtime by Node >=22.18, never compiled) — do not rename a `.ts` file to
  `.mts` (or vice versa) without checking whether it is in that build `include` list.
- Compiled/deployed output lives under `.claude/mcp/vice/resources/*.mjs` — generated by
  `build.ts`, never hand-edited.

**Functions:**
- `camelCase`, verb-first, descriptive of the single thing they do: `repoRoot()`, `containerPath()`,
  `containerizeRecord()`, `ensureResourcesInstalled()`, `isInsideContainer()`, `denyListRefusalMessage()`.
- Boolean-returning functions read as predicates: `isInside()`, `isLoopbackHostname()`,
  `isValidRequestId()`, `isLaunchInFlight()`.
- Internal/private helpers are declared `function` (not exported); public API is `export function`.

**Variables:**
- `camelCase` for locals and mutable module state (`warnedEnvOutsideFrom`, `reqId`).
- `SCREAMING_SNAKE_CASE` for module-level constants, especially ones with an env-var or
  protocol-contract flavor: `HERE`, `WORKSPACE_ROOT`, `CONTAINER_WS`, `DEFAULT_ENDPOINT`,
  `DENY_LIST`, `ACQUIRE_TIMEOUT_MS`, `REQUEST_ID_PATTERN`, `HOST_BOUND_ARTIFACTS`.
- `HERE` is the idiomatic name for `dirname(fileURLToPath(import.meta.url))` — used consistently
  across nearly every module and test file in `.claude/mcp/vice/` and the skills scripts.

**Types (TypeScript):**
- `PascalCase` for interfaces and classes: `RepoRootOptions`, `ContainerizeRecordResult`,
  `ViceError`, `MachineRestartedError`, `BrokerState`, `InstanceRecord`.
- Options objects follow the pattern `<FunctionName>Options` (`RepoRootOptions`,
  `ContainerizeRecordOptions`, `ViceErrorOptions`) and are destructured directly in the function
  signature with defaults: `function repoRoot({ from = HERE, env = process.env }: RepoRootOptions = {})`.
- Result/return shapes follow `<FunctionName>Result` (`HostRootCandidatesResult`,
  `ContainerPathCandidatesResult`, `ContainerizeRecordResult`).
- Custom error subclasses end in `Error`: `ViceError`, `MachineRestartedError`,
  `PathOutOfWorkspaceError`, `PathTranslationError`.

## Code Style

**Formatting (no formatter config committed — conventions are enforced by consistency, not tooling):**
- No `.eslintrc*`, `.prettierrc*`, `biome.json`, or equivalent config file exists anywhere in the
  repo. Style is maintained by hand; match the surrounding file exactly rather than assuming a
  tool will normalize it.
- 2-space indentation throughout (`.ts`, `.mts`, `.mjs`).
- Double quotes for strings (`"like this"`), not single quotes.
- Semicolons are used consistently (not an ASI-reliant style).
- Line width is generous (~100-120 cols is common, some lines exceed that inside dense comments)
  — do not aggressively wrap; prefer wrapping at logical operators/`&&`/ternary boundaries.
- Template literals for interpolation, always: `` `${toolName} is permanently forbidden...` ``.
- `#!/usr/bin/env node` shebang on every standalone script (`.mjs`, and CLI-capable `.ts` files).

**Linting:** Not configured. `npm run typecheck` (`tsc --noEmit -p tsconfig.json`, strict mode) is
the only static check enforced in CI (`.github/workflows/ci.yml`) — treat TypeScript's `strict`
compiler as the linter for `.claude/mcp/vice/`.

## Import Organization

**Order (observed consistently in `.claude/mcp/vice/*.ts`):**
1. Node built-ins first, `node:` protocol prefix always used: `import { existsSync } from "node:fs";`
2. Blank line, then local/relative imports, using explicit `.ts`/`.mts` extensions:
   `import { ensureResourcesInstalled } from "./install-resources.ts";`
3. `type`-only imports use `import type { ... }` or an inline `type` keyword within a named
   import list: `import { spawn, type ChildProcessWithoutNullStreams } from "node:child_process";`

**Path style:**
- No path aliases (no `tsconfig` `paths` remapping). All imports are explicit relative paths.
- Every relative import to a local TS/MTS module includes its real extension
  (`allowImportingTsExtensions: true`, `verbatimModuleSyntax: true` in `tsconfig.json`) — never a
  bare specifier or extensionless import for local files.
- One documented cross-extension constraint: same-module-to-sibling-module imports inside files
  destined for the `resources/` build (`.mts` -> `.mjs`) have their own extension rule — see the
  header comment in `broker-launch.mts` before changing an import extension in that build set.

## Error Handling

**Custom error hierarchy:**
- Base: `class ViceError extends Error` (`.claude/mcp/vice/vice.ts:250`) carries an optional
  `code`/`data` payload, mirroring JSON-RPC error shape.
- Specialized subclasses extend `ViceError` and add domain fields as plain public properties
  (not getters): `class MachineRestartedError extends ViceError { baselineEpoch, currentEpoch,
  where, lastToolCall }` (`.claude/mcp/vice/vice.ts:277`).
- Other one-off error classes are declared minimally, `class PathOutOfWorkspaceError extends
  Error {}` (`.claude/mcp/vice/vice-proxy.ts:1690`), when no extra payload is needed.
- Constructor pattern: `constructor(message: string, { ...fields }: XOptions = {}) { super(message);
  this.name = "ClassName"; ...assign fields... }` — always sets `this.name` explicitly so
  `error.name` is stable across minification/renaming.

**Throwing:**
- Functions that cannot produce a valid result throw `new Error("<message>")` with a message that
  names the exact input and the exact remedy, e.g. `containerpath.ts`'s `containerPath()`:
  ``throw new Error(`${reason || ...}\n  Or ${SET_ENV_HINT}`)``.
- Range/validation errors embed the offending value and the valid range directly in the message
  (`d64-parse.mjs`'s `tsToOffset()`: `` `track ${t} out of range` ``) so `assert.throws(fn, /regex/)`
  in tests can match on message content, not just error type.

**Never-throw contracts are explicit and load-bearing:**
- Some functions are documented as deliberately swallowing all errors — e.g.
  `ensureResourcesInstalled()` "never throws (D-3)" — and callers add a defensive `try { ... }
  catch { /* comment explaining this is belt-and-suspenders */ }` around them anyway, with a
  comment stating this is not evidence the contract is expected to change.
- Pure/never-throwing transforms return a `{ result, changes, untranslated }`-shaped record
  instead of throwing on partial failure (`containerizeRecord()` in `containerpath.ts`) — prefer
  this shape over throwing when a caller needs to know WHICH fields succeeded/failed, not just
  pass/fail.

**Silent-but-observable failure is treated as a bug class to actively design against.** Multiple
files (`repo-root.ts`, `vice.ts`) have long header comments describing a prior incident where a
wrong-but-non-throwing path resolution caused silent data loss, and explicitly forbid
reintroducing that shape (fixed relative hop counts instead of marker-based resolution). When
adding a fallback branch, prefer a one-time `console.error()` warning (see the
`warnedEnvOutsideFrom` / `warnedNoMarkerFound` guards in `repo-root.ts`) over silent success on a
guessed value.

**CLI error convention:** scripts with a CLI entry point catch at the top level and print
`` `error: ${(e as Error).message}` `` to stderr, then `process.exit(1)` — see the bottom of
`containerpath.ts` and `installer/bin/cli.mjs`.

## Comments

**Extremely thorough, decision-record-style header comments are the house style**, not an
exception. Non-trivial modules open with a multi-paragraph comment explaining:
- WHY the file exists (what problem/incident motivated it, often referencing a specific dated
  plan ID, e.g. `quick-260731-p8a`, or a decision label like `D-2`, `D-3`, `D-7`).
- What it is the ONE authoritative place for (the "single seam" pattern — see below).
- What NOT to do, with the specific past mistake named (e.g. "Do not reintroduce a fixed `".."`").

Inline decision labels (`D-1`, `D-2`, `D-17`, `D-1.2-H`, etc.) are used as stable cross-reference
anchors between code comments, test comments, and planning docs — when modifying logic tied to a
`D-N` label, check whether the comment's reasoning still holds rather than deleting the label.

**JSDoc** (`/** ... */`) is used on every exported function/type, describing purpose, parameter
semantics, and edge-case behavior in prose — not terse `@param`/`@returns` tags. Example style
from `repo-root.ts`:
```ts
/** Options accepted by repoRoot()/supervisorDir(): `from` overrides the
 * caller location the ladder resolves relative to (defaults to this file's
 * own location, HERE), and `env` overrides the environment it reads
 * CONTAINER_WORKSPACE_PATH from (defaults to process.env) -- both exist so
 * the ladder is deterministically testable without mutating real process
 * state, per repo-root.test.ts's own injection idiom. */
export interface RepoRootOptions { ... }
```

**Section divider comments** using a long `-----` or `====` rule with a short label are used to
break long files into named regions, e.g. in `vice-proxy.test.ts` and `containerpath.test.ts`:
```ts
// ---------------------------------------------------------------- round-trip
// ============================================================================
// repoRoot() ladder (D-2) and the last-resort path-anchor hop count ...
// ============================================================================
```

## Function Design

**Size:** Functions are kept single-purpose but comments are long relative to code — a 15-line
function may carry 30+ lines of surrounding rationale. Do not shorten the comments to "clean up"
without preserving the WHY.

**Parameters:** Multi-field inputs are destructured options objects with inline defaults, not
positional booleans: `function containerizeRecord(record, { pathFields = [], urlFields = [], alias
}: ContainerizeRecordOptions)`. Required vs. optional fields are deliberate in the type (see
`ContainerizeRecordOptions.alias` being mandatory while `pathFields`/`urlFields` default to `[]`).

**Return values:** Prefer structured result objects (`{ candidates, exact?, reason? }`,
`{ record, changes, untranslated }`) over throwing or returning `null`/sentinel values, especially
when a caller needs to report WHY a value could not be produced. `reason` fields are always
human-readable prose meant to be surfaced directly, not error codes to be mapped later.

## Module Design

**Exports:** Named exports only — no default exports observed in `.claude/mcp/vice/` or the skill
scripts. Every file exports a focused, named set of functions/types.

**One authoritative seam per concern ("D-N" single-source-of-truth pattern):** the codebase
strongly favors exactly one module owning a given piece of derived knowledge (e.g. `repo-root.ts`
is "the ONE shared place every module... resolves the repo root through"; `vice.ts`'s `call()` is
the only file that speaks MCP JSON-RPC to the host VICE endpoint). When adding new functionality
that needs an existing derived value (repo root, container path mapping, deny-list message),
import the existing function rather than recomputing it inline — duplicating that logic is
treated as the primary defect class this codebase's comments warn against.

**Barrel files:** Not used. Every module is imported directly by its own filename; there is no
`index.ts` re-export layer in `.claude/mcp/vice/`.

**Dependency injection for testability:** functions that depend on environment, time, or I/O
accept an optional override parameter defaulting to the real thing, e.g. `repoRoot({ from = HERE,
env = process.env })`. This is the standard way to make a function unit-testable in this codebase
— prefer adding an injectable parameter over reaching for a mocking library.
