# Phase 28 review, IN-02 — disposition: accepted, not fixed

## Why this file exists

`docs-review-disposition.test.ts` reported `IN-02` undispositioned immediately after
`28-VERIFICATION.md` was regenerated by the phase-28 re-verification:

```
finding(s) with no disposition anywhere -- fix them and cite the plan/SUMMARY, or file a todo naming the reason:
  28-REVIEW.md (28-the-store-core): IN-02
```

The id had been dispositioned only by the **previous** round's `28-VERIFICATION.md`. When the
verifier overwrote that file with the post-gap-closure report, the mention went with it — the
finding did not change, its only disposition source did. `IN-01` and `IN-03` survived because
`28-08-SUMMARY.md` names them; `IN-02` was named nowhere else.

Filing it here rather than re-adding a line to a verifier-authored report: `VERIFICATION.md` is
evidence written by the agent that did the verifying, and editing it from the orchestrator seat
to turn a guard green is exactly the kind of fact-laundering this project's workflow forbids. A
todo is the guard's own documented alternative, and unlike a VERIFICATION.md mention it will
survive the next re-verification too.

## What IN-02 is

`anno-store.ts:299-306` — `fsyncPath` opens with `"r"`, and calls `openSync` on a *directory*.
Neither is portable: both fail on Windows.

## Disposition: accepted, not fixed

Correct for the hosts this tree targets. The project's platform requirements are Linux and
macOS — the MCP server, the broker and the host launcher are all built against POSIX
behaviour, and no Windows host is supported today. The reviewer's own verdict is "no fix
required today"; this is a note for a future port, not a defect in shipped behaviour.

Directory `fsync` is also the whole point of the call: it is what makes a rename durable, and
dropping it to gain portability the project does not need would weaken the durability
guarantee `STORE-04` rests on.

## What would reopen it

Adding Windows to the supported platform set. At that point, guard the call with
`process.platform === "win32"` and **document that the directory fsync is skipped there** —
silently skipping it converts a durability guarantee into a silent durability loss, which is
the failure mode this finding exists to flag.
