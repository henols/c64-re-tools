# Quick 260823-kf6 — Correct STATE.md's carried-forward ledger (QUAL-01..03 closed by PKG-02..04)

## Why

`.planning/v0.4.0-MILESTONE-AUDIT.md`'s round-1 verdict is `status: tech_debt`, and its
**cluster 1** — the one the audit itself calls *"the one worth fixing before close"* — is this:

> `STATE.md:855-857` still lists `QUAL-01`, `QUAL-02` and `QUAL-03` as `Deferred`. This
> milestone closed all three: `PKG-02` discharges QUAL-01, `PKG-03` discharges QUAL-02,
> `PKG-04` discharges QUAL-03.

The pairings are not inferred — REQUIREMENTS.md names each one in the requirement text itself:

- `REQUIREMENTS.md:262` — `- [x] **PKG-02**: acme.mjs, driver.mjs and derive.mjs have tests (QUAL-01)`
- `REQUIREMENTS.md:263` — `- [x] **PKG-03**: Orphaned planning references in source comments are removed or repointed (QUAL-02), guarded against reintroduction`
- `REQUIREMENTS.md:264` — `- [x] **PKG-04**: The emulator control-plane network exposure (QUAL-03) is either narrowed or recorded as accepted with rationale`

and the Traceability table (`REQUIREMENTS.md:421-423`) carries all three as `| 16 | Complete |`.

Two prose sites then repeat the now-false claim about how many carried rows are still open:
`STATE.md:801-806` and REQUIREMENTS.md's DEBT-04 closure note at `REQUIREMENTS.md:212-216`.

**Why it matters more than ordinary bookkeeping.** The error direction is safe — it *overstates*
remaining debt rather than hiding it — but the location is pointed. `docs-deferred-ledger.test.ts:22`
records in its own header that the "Carried forward from earlier closes" table is **NOT checked**,
so no guard can catch this. A milestone whose thesis is *"the ledger must be derived and guarded"*
would otherwise close with a neighbouring hand-maintained ledger carrying three rows its own work
falsified, one heading away from the ledger it fixed.

## The shape to copy already exists in the same table

The `Drive8Type=0` row directly above the QUAL rows (`STATE.md:853`) is the house style for a
closed carried row — a bolded verdict, the phase and plans that closed it, and a `Deferred At`
cell that keeps the original provenance *and* adds the close:

```
| Defect | `Drive8Type=0` default ... | **Fixed** — Phase 8.2 plans 02-04 landed the fix, proved it live, and re-ran the walkthrough to a recorded `pass` | v0.2.0 Phase 8.1 (2026-08-19), fixed in Phase 8.2 (2026-08-19) |
```

Follow that. Do not invent a new column, a new marker vocabulary, or a fourth column.

## Two things that must NOT change

1. **The derived `0 items` count** in `## Deferred Items` (`STATE.md:783-795`) is *correct*. It
   counts pending todo files plus open UAT-gap rows and never counted the carried-forward table.
   This task corrects the carried table's *status* accounting and the prose describing it.
2. **`PKG-04` is a recorded accepted risk, not a fix.** Its closure note
   (`REQUIREMENTS.md:266-272`) reads *"Disposition: `accept`, not `narrow`"* and ends
   *"The `Control-Plane Bind Follow-on` section below remains open owned follow-on work — this
   completion does not close it."* The QUAL-03 row must say the same. Wording that implies the
   network exposure was narrowed away would trade a stale-status defect for a false-safety one.
