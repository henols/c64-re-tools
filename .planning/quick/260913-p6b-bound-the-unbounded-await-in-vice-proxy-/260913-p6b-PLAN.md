<design_decision>
**The bound goes in the HELPER, not at the one call site.** Reasoning, from
observations made at planning time:

1. `waitForCall()` has ELEVEN call sites (4384, 4431, 4471, 4613, 4671, 4796,
   4857, 4901, 4947, 5000, 5047), every one of them the identical idiom: send a
   `vice_recycle` request, then `await recycle.waitForCall()`. The whole
   `vice_recycle` family shares the one product path that drifted, so it is
   likely that MORE THAN ONE of these eleven is unsatisfiable. `node:test` runs
   top-level tests in a file sequentially, so hang #2 would kill the run exactly
   as hang #1 does. A call-site-only fix could need up to eleven
   discover-then-fix rounds to yield ONE census. The helper fix makes the file
   finish in one run — which is the entire deliverable.
2. A helper-level deadline cannot silently change any healthy caller. All eleven
   call sites are bare `await` expressions: none passes the promise to
   `Promise.race`, none asserts that it stays pending, none stores it for later.
   A healthy wait resolves in milliseconds and never reaches the deadline. Only
   an unsatisfiable wait changes behaviour — from "hang forever" to "fail with a
   message naming the cause".
3. `makeControllableRecycleSequence().next()` (call sites 5094, 5113) has the
   identical resolve-later-or-never shape, in a test that has NEVER RUN. Bounding
   it in the same pass costs three lines and removes a second candidate hang from
   the same family. It is in scope for the same stated reason as #1: the plan's
   deliverable is a file that finishes.

Anything beyond these two helpers is NOT authorized up front. If the full run in
Task 2 still fails to complete, see `<mutable_scope_authority>`.
</design_decision>
