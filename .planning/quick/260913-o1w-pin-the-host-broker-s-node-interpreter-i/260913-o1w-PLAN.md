## F1 — `vice-launcher.sh` is HAND-AUTHORED, not generated. Editing it is correct.

`build.ts`'s `HOST_BOUND_ARTIFACTS` (build.ts:42-53) lists ten `.mjs` names and
no `.sh` at all, and `tsconfig.build.json`'s `include` is ten `.mts` files. The
launcher's own header says it outright: "HAND-AUTHORED -- not generated. It
lives beside the generated vice-broker.mjs purely because install-resources.mjs
deploys the whole resources/ directory as a unit; this is the one file in this
directory a maintainer edits directly."

`install-resources.ts` encodes the same split structurally: `isGeneratedEntry()`
splits the deployed set in two, and the hand-authored half keeps a
refuse-on-divergence posture (install-resources.ts:438-450) while the generated
half is auto-refreshed. So the edit is safe from `build.ts`, and the file is the
ONE place in `resources/` a human is supposed to change.

**Operational consequence you must handle (F1a):** because it is hand-authored,
`installResources()` will REFUSE to refresh the already-deployed copy at
`.c64-re-tools/bin/vice-launcher.sh` once it diverges — it warns and deploys
nothing for that entry. Measured: that deployed copy is byte-identical to the
source right now, so it WILL diverge the moment you edit. Task 1 therefore
refreshes it explicitly (the deliberate overwrite the installer will never
perform on its own). Do not delete it instead: `repo-root.test.ts:191` asserts
that path exists.

Note what that existing assertion does NOT do: it checks existence only, never

run. That gate is guarded on existence (the file is legitimately absent anywhere

## F2 — The MCP server's `process.execPath` CANNOT be threaded to the launcher.

The prompt asked this to be verified rather than assumed. Verified, and the
answer is no:

- Nothing in the shipped tree spawns `vice-launcher.sh`. Every non-test
  reference is a path used in a MESSAGE, never in a spawn: `vice-proxy.ts`'s
  `brokerHostPath()` (vice-proxy.ts:732-744) computes an absolute HOST path so
  `brokerNeverStartedMessage()` can print "Start it on the host with: <path>",
  and `install-resources.ts`'s `hostLaunchInstructions()` prints "start the
  on-demand broker from the HOST workspace, e.g.: <path>". The only spawns of
  the launcher anywhere are in `repo-root.test.ts`, `vice-broker-launch.test.ts`
  and `host-scripts.test.ts`.
- So there is no parent/child relationship at all. `execPath` can be neither
  inherited nor passed as an argument, because nothing hands the launcher
  arguments — a HUMAN types the path.
- And in the devcontainer shape it would be actively wrong: the server's
  `execPath` is a CONTAINER path with no host counterpart (the container's node
  is not bind-mounted), and this project requires every host-facing path to go
  through `hostpath.ts`, which would have nothing to translate.

**Therefore the ladder collapses to two rungs plus a refusal:**

1. `VICE_BROKER_NODE`, an explicit absolute-path override. This is the rung that
   fixes the concrete trap the defect names: a systemd unit whose
   `Environment=PATH=` carries no nvm entry (the shape
   `~/.config/systemd/user/nanoclaw.service` already uses, which pins an
   absolute interpreter in `ExecStart` precisely because its own PATH cannot).
2. `node` as found on PATH.
3. Refuse.

There is no third rung to invent. Write the WHY of the missing rung into the
launcher as a reason a reader can act on — that the server never spawns this
script, so there is no channel — never as a pointer to this document.

## F3 — The floor is major 24, and the justification is NOT "package.json says so".

Measured: the deployed compiled artifact loads and runs its guard-report path
under all five installed interpreters — `/usr/bin/node` v20.19.2, nvm v20.20.0,
v22.13.0, v22.22.0, v24.20.0 — all exit 0. So today's artifact does not itself
demand 24.

That tolerance is a property of the compile step, not of the project. Pinning
the floor to what `tsc` currently emits would make the gate certify exactly the
configuration the project intends to be able to remove, and would leave the real
question ("which Node is this supposed to be?") still unanswered.

The decisive argument is the drift one. This repository already declares one
number for this code: `src/mcp/vice/package.json`'s `engines.node: ">=24.0.0"`,
and the broker artifact ships inside that package. A second, lower number
hardcoded in bash would be a second source of truth for a single question,
free to drift silently — which is the same failure class as the bare
interpreter itself. So: floor = the major from `engines.node`, held to one value
by a test.

**Accepted consequence, state it in the SUMMARY:** a host whose PATH `node` is
22.22 works today and gets a named refusal after this change. That is the point.
The override exists to point at a DIFFERENT conforming binary, never to lower
the floor — do not add a floor-override env var.

**Explicitly out of bounds:** do NOT touch `installer/package.json`'s
`engines.node`. That floor governs a different package (the plain-`.mjs`
installer, which has no interpreter-pinning problem), it is a separate open
question, and that question is blocked on THIS work rather than the reverse.
`installer/` appears nowhere in `files_modified` and must appear nowhere in the
diff.

| T-o1w-01 | Elevation of Privilege | `VICE_BROKER_NODE` in vice-launcher.sh | low | accept | An actor who can set this launcher's environment can already run any binary directly as that user, so the variable grants no new capability. The ACCIDENTAL case is still mitigated: the override is accepted only when it is an executable file, and a bad value is refused by name rather than silently falling back to PATH. |
| T-o1w-02 | Spoofing | the `--version` probe | low | accept | The version string comes from the candidate binary's own output, so a hostile binary can lie. This gate exists to catch misconfiguration, not to establish trust in the interpreter; treating `--version` as authenticated would be false assurance. Unparseable output is refused rather than passed. |
| T-o1w-03 | Information Disclosure | `node_exec_path` in broker.json | low | accept | The record is written mode 0600 and already carries the pid and a control token; an interpreter path is strictly less sensitive than what is already there. |
| T-o1w-04 | Denial of Service | the new exit-4 refusal path | low | mitigate | A refusal must never read as a wedge: it exits non-zero BEFORE exec with a message naming the binary, its version, the floor and both remedies, so the operator gets an action instead of a hang. |
| T-o1w-SC | Tampering | npm/pip/cargo installs | n/a | accept | This plan installs no packages — no package-manager invocation appears in either task, and the standing project rule forbids adding one. The package-legitimacy gate has no subject here. |
