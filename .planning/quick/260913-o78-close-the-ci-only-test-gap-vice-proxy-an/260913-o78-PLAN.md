<objective>
Fix the single deterministic failure in `src/mcp/vice/broker-e2e.test.ts` — the
`wired warm-hit (plan 41-05)` case, which times out at line 478 on
`the respawned instance must reach recorded state "ready" within the deadline`.

**This is a TEST-FIXTURE fix. The product is correct.** Stated plainly because
the failure presents as a broker regression and is not one:

`writeProbeAnsweringStub()` (line 190) generates a stand-in emulator that reads
its listen port out of its own argv via `args.indexOf("-mcpserverport")` — the
**fork** backend's flag. Commit `d54d98a1` ("collapse backend detection")
narrowed `ViceBackend` to the single literal `"stock"`, so `buildViceArgs()`
(broker-launch.mts:155) now emits `-binarymonitor -binarymonitoraddress
ip4://<host>:<port>` and the fork tail at broker-launch.mts:383 is unreachable.
The stub therefore gets `idx === -1`, computes `Number(args[0])` → `NaN`, and
calls `server.listen(NaN)` — which binds a **random OS-assigned port**. Nothing
ever listens on `record.port`. `probeReady()` with `backend: "stock"` routes to
`defaultBinmonProbe()`, a raw binary-monitor TCP round trip at `record.port`,
which can never succeed. `promoteLaunchingInstances()`
(broker-launch.mts:1133) only promotes a record whose probe passes, so the
respawned record stays `launching` forever and the test's 10s `ready` wait
expires.

The crash-respawn itself works (the test's own `epoch_file` poll proves the
respawn lands on the SAME port). `promoteLaunchingInstances()` is correct.
Timing is not the cause and the 10s deadline must not move.

**Explicitly out of scope, do not touch:** `broker-launch.mts`,
`vice-broker.mts`, `broker-state.mts`, `resources/*.mjs`, and
`vice-proxy.test.ts` (its far larger drift is being run as a separate phase —
do not plan or fix any of it here).
