## Root cause — MEASURED at planning time, not inferred

Read this before touching anything. The naive framings of this task are all wrong, and
the measurements below are what rule them out.

**What actually breaks.** `.github/workflows/ci.yml:21-23` sets, for the whole job:

```
env:
  CONTAINER_WORKSPACE_PATH: ${{ github.workspace }}
  HOST_WORKSPACE_PATH: /host${{ github.workspace }}
```

Its own comment says why: *"Path translation in the MCP tests reads these."* But
`container-guard.mts`'s THIRD container-detection signal is, verbatim,
`CONTAINER_WORKSPACE_PATH is set (this devcontainer sets it)`. One variable carries two
meanings — "here is the devcontainer's workspace path" for path translation, and "you
are inside a container" for the guard. On a real devcontainer both are true. On a
GitHub runner only the first is being simulated, so the job tells every process in it
that it is inside a container when it is not.

`host-tool-client.ts:342` selects its transport on exactly that signal
(`if (isInsideContainer())`), so every host-side seam invocation in the job dials a
control plane that has no broker behind it.

**The four observations that establish this** (all made on this host, 2026-09-13):

1. The exact CI shell body, run unmodified here, **SUCCEEDS**: it scaffolds, assembles
   through the real seam, and writes a 55-byte program loading at `$0801-$0836`. The
   code is not broken.
2. The same shell with only `CONTAINER_WORKSPACE_PATH` added to the environment
   **FAILS**, printing `error: hostToolOverControlPlane: broker.json not present or
   unreadable` — character-for-character the message CI printed.
3. `skill-acme-build-cli.test.ts` alone: **15 pass / 0 fail** clean;
   **11 pass / 4 fail** with that variable set.
4. Whole narrowed suite (`npm run test:automated`) under CI's two variables plus
   `VICE_REQUIRE_ACME=1`: **4399 tests, 4379 pass, 11 fail, 9 skipped**. The eleven
   split across exactly three files — 4 in `skill-acme-build-cli.test.ts`, 6 in
   `host-tool.test.ts`, 1 in `host-tool-transport.test.ts`. The latter seven all fail
   with `getaddrinfo ENOTFOUND host.docker.internal`: same cause, different symptom, as
   the container verdict also picks the container-side dial host.

**Why this matters for scope.** Fixing only the scaffold step moves the red one step
later. The Test step would then fail on those same eleven. The pipeline stays blocked
and nothing publishes. All eleven are in scope.

## The two rules, and why the collision dissolves

The brief framed this as a collision between two absolute rules:

- **`acme.mjs`'s header:** never add a local assembler spawn as a fallback when the seam
  is unreachable.
- **`host-tool.mts`'s header:** no second copy of a tool's argv construction —
  `buildHostToolArgv()` is the single owner.

Both stand, untouched, and neither has to bend. That is because the defect is in
**neither** place. The seam is correct; `buildHostToolArgv()` is correct; `acme.mjs` is
correct. What is wrong is that CI lies to the container detector about the machine it is
running on. Fix the lie's blast radius and the shipped seam works exactly as designed.

Concretely, this plan adds **zero** assembler spawns and **zero** argv construction. The
command line still comes from `buildHostToolArgv()` and nowhere else.

## Two routes evaluated and REJECTED, with the measurement that killed each

**Rejected — express the check through `verifyAcmeAssemblesTree()`.** The brief flagged
this as promising. It does not fit. `AcmeVerifyTreeOptions` requires `expectedBytes` AND
`expectedSegments`, and `acme-verify.ts`'s own contract states those must be derived by
the caller *from the image*, never from the source — *"deriving these from the exported
text would make the whole verdict a self-check wearing an oracle's clothes."* A freshly
scaffolded template has no image and no independently-derived byte oracle; supplying one
would mean pinning golden bytes of the scaffold, which is both a self-check and against
the direction the project is currently moving. That module answers "do these bytes match
the image"; the scaffold check asks "does this assemble at all". Different question.

**Rejected — delete the job-wide `env:` block so the runner stops lying.** Tempting, and
the narrowed suite would not notice (test count and skip count are identical, 4399/9,
with the variables set and unset). But `broker-e2e.test.ts:32`,
`vice-broker-launch.test.ts:37` and `vice-proxy.test.ts:79` each gate their real
in-container cases on both variables being set and SKIP without them — and all three cite
this workflow's own line numbers as the reason they can rely on it. They are
`MANUAL_ONLY_TESTS` entries, so they reach CI only through the Test step's full glob and
never appear in a `test:automated` count. Deleting the job env would convert three files'
container coverage into silent skips while CI reported green — the precise failure this
project refuses everywhere else. **Do not delete or relocate the job-wide `env:` block.**
