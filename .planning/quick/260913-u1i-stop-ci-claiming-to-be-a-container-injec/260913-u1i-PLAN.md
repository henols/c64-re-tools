<objective>
CI's `build` job declares itself to be inside a container. It is not: a GitHub runner is
a host. The workflow sets `CONTAINER_WORKSPACE_PATH` workflow-wide as a path-translation
fixture, and the five-signal container detector reads that same variable as signal 3 —
proof of being inside a container. The consequence was measured, not theoretical: every
host-side invocation in the job routed to a control plane with no broker behind it, which
broke the job's first substantive step, skipped every step behind it including the test
run and all three release jobs, and stayed broken for roughly five phases because only CI
ran that step and CI was already red. The previous quick task pinned individual tests back
to the host route, leaving the job itself globally mislabelled.

This plan removes the lie at its source and pays for it by injecting the container
environment where container behaviour is actually under test.

Purpose: make the job's environment match the machine it runs on, without converting any
real coverage into a silent skip, and without touching a single line of production code.

Output: two broker test files whose container-guard cases source their container signal
from the test itself and therefore run everywhere; a workflow file that declares no
container-workspace environment at all; and a guard that fails if the block returns or if
a new file starts depending on one.
</objective>

## The measurement that settles the scope question

The prompt asked for a deliberate decision on `vice-proxy.test.ts`, whose 4 gated cases
sit in a file scheduled for a wholesale re-baseline. It was settled by running the file
under CI's own environment values at planning time, which nobody had done:

| environment | tests | pass | fail | skipped |
|---|---|---|---|---|
| both variables UNSET (a developer's host today) | 122 | 45 | 73 | 4 |
| both variables SET (CI today) | 122 | 45 | **77** | 0 |

All four gated cases are in the +4. **Under the only environment that runs them, they
fail.** The workflow block is not buying coverage from that file — it is buying four
failures. So the "deleting the block launders coverage into silence" hazard, which is real
and decisive for the two broker files, does not apply to this one: there is no green
signal there to lose.

**Decision: convert the two broker files (5 cases). Leave `vice-proxy.test.ts`'s gate.**

Three reasons, in order of weight:

1. **Nothing is lost.** Those 4 cases are red right now under the only condition that runs
   them, in a file that is 77/122 red because a large phase deleted most of the module
   beneath it. After this change they become named skips instead of unattributed failures
   — which is, if anything, more honest about their state.
2. **A conversion could not be verified.** The two broker files convert by handing a CHILD
   process one environment variable — no in-process `process.env` mutation at all, so the
   change is deterministic and provable locally in seconds. `vice-proxy.test.ts`'s cases
   call `hostPath()` and `repoRoot()` in-process (and `containerpath.ts` caches its
   workspace root at MODULE scope, so an in-test mutation cannot reach it), and a failure
   after conversion would be indistinguishable from the 73 pre-existing ones. That is the
   opposite of gaining confidence.
3. **The work would be discarded.** The re-baseline owns that file wholesale.

**How that file's container coverage is accounted for rather than silently lost** — three
things, all in this plan:

- The gate STAYS, but its skip reason is rewritten. It currently cites the workflow file's
  line numbers as the thing that satisfies it; after this change nothing satisfies it
  ambiently, so the reason names the exact local command that does.
- Task 2 adds a test asserting that the set of test files still gating on an inherited
  container-workspace signal is **exactly** `["vice-proxy.test.ts"]`, failing in BOTH
  directions. An extra member means someone added a new gate depending on an environment
  no job supplies any more; a missing member means the re-baseline resolved this one and
  the ledger must move with it. The exception becomes an enumerated, greppable fact.
- The unit-level behaviour those cases wrap end-to-end is separately covered by tests that
  already inject the environment as a parameter or set-and-restore it around the call:
  `container-guard.test.ts`, `repo-root.test.ts`, `install-resources.test.ts`,
  `stock-paths.test.ts`, `stock-derived.test.ts`, `stock-dispatch.test.ts`. The loss is
  confined to the end-to-end wire path through the proxy child, in a file that cannot
  currently prove anything at all.
