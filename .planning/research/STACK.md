# Stack Research

**Domain:** v0.9.0 — text-monitor channel client, VICE text-output parsers, a runtime-evidence table in `.annostore`, and `c1541`/`petcat`/`cartconv` over the existing `host_tool` seam
**Researched:** 2026-09-06
**Confidence:** HIGH — every claim below is either read from this repo's committed source, or measured live this session against the two VICE builds actually installed on this host (genuine stock `/usr/bin/x64sc` 3.9 and the fork's `/usr/local/bin/x64sc` 3.10, which shadows PATH). No manual-only claims are presented as fact where they weren't cross-checked; two are flagged MEDIUM/LOW below where that happened.

## The one-line answer to the headline question

**No new npm runtime dependency is needed for any of the four target features.** `node:net` (already imported in `vice-broker-client.ts` and `broker-control.mts`), `node:sqlite` (already the store's one seam, `anno-store.ts`), and `node:child_process`'s `spawn` (already imported in `host-tool.mts`) cover the text-monitor client, the parser layer, the evidence table, and the three new host tools in full. The project's "zero new npm runtime dependency for several milestones" property is a `package.json` fact, not a target to hit by construction — `src/mcp/vice/package.json`'s `dependencies` block is two entries (`@mastra/mcp@1.15.0`, `@mastra/core@1.55.0`) and stays two entries after this milestone.

## Recommended Stack

### Core Technologies

| Technology | Version | Purpose | Why Recommended |
|------------|---------|---------|-----------------|
| `node:net` | builtin, Node ≥24 (already required) | Text-monitor TCP client (`connect()` to the `-remotemonitor` port) | Already the transport for both existing VICE clients — `vice-broker-client.ts:31` (`import { connect, type Socket } from "node:net"`) and `broker-control.mts:27` (`createServer`). No framing library exists anywhere in this tree; `broker-control.mts` hand-rolls its own newline-delimited buffer with a `MAX_LINE_BYTES` cap (`:285`) rather than importing one. The text-monitor client should do the same: a raw `Socket`, a manually-grown string/Buffer accumulator, and a regex match on the prompt (see below) rather than a readline-per-line abstraction, because "end of response" here is a *pattern*, not a line boundary. |
| `node:sqlite` (`DatabaseSync`) | builtin, Node ≥24 (already required, RC-stability) | Runtime-evidence table(s) inside the existing `.annostore` file | `anno-store.ts` is already, by a scanned-and-tested rule (`anno-seam.test.ts`'s `THE_ONE_SEAM = "anno-store.ts"`), the **only** module in the shipped set permitted to name `node:sqlite` — through any of its four working access routes (static import, dynamic import, `process.getBuiltinModule`, `createRequire(...)("node:sqlite")`). This is a hard integration constraint, not a preference: the evidence table's DDL, its insert/query functions, and its schema-version bump all belong **inside `anno-store.ts`**, not a new module, or the seam test goes red on a planted violation exactly as designed. |
| `node:child_process` (`spawn`, never `spawnSync`) | builtin | Invoking `c1541`, `petcat`, `cartconv` host-side | Already the mechanism for every existing host tool — `host-tool.mts:1464`: `spawn(toolPath, argv, { stdio: ["ignore", "pipe", "pipe"], ... })`. The three new binaries slot in as three more `HostToolId` union members (`host-tool.mts:139`) with their own `HOST_TOOL_ARG_KEYS` / `HOST_TOOL_PATH_ARG_KEYS` entries and a typed `buildHostToolArgv()` branch — the exact shape `acme.build`, `ghidra.analyze`, `dxa.disassemble` already use. No new spawn primitive, no shell, no argv passthrough (the existing "typed allowlist, never a shell" rule in `host-tool-executor.md` §5 applies unchanged). |

### Supporting Libraries

**None.** There is no supporting library to add. Below is why the three plausible candidates are each unnecessary, not merely undiscussed:

| Candidate | Purpose it would serve | Why it is not needed |
|-----------|------------------------|----------------------|
| A "TCP line protocol" package (e.g. a length-prefix or newline-framing library) | Framing the text-monitor's responses | The house style is to hand-roll this (see `broker-control.mts`'s `MAX_LINE_BYTES` buffer). More importantly, the text monitor is **not** line-framed the way the binary monitor or the broker control channel are — the terminator is a prompt *pattern* (`(C:$xxxx) `), not a fixed-length header or a bare newline, so a generic line-framing library would solve the wrong problem. |
| A parser-combinator / grammar library (e.g. a PEG or parsimmon-style parser) | Parsing `memmapshow`/`prof flat`/`chis`/`bt`/`io` text | Every one of these five formats is a fixed-column, fixed-keyword text table (see the measured samples below) — the same shape `binmon-fixtures.ts` and `dxa`'s listing parser already handle by hand with pinned fixtures, per-format ownership, and a "refuse by name, never by exit code" discipline. A grammar library is real overhead (a new dependency, a new failure mode when a VICE build's whitespace differs by one column) for a problem five `String.prototype.split`/regex modules already solve elsewhere in this tree. |
| A migration/ORM library (e.g. `knex`, `drizzle`) for the `.annostore` schema bump | Adding the runtime-evidence table(s) | `node:sqlite`'s `DatabaseSync.exec()` already runs arbitrary DDL and `.prepare().run()` already runs parameterised DML inside `begin immediate` / `commit` — exactly the two primitives `anno-store.ts` already uses for its `SCHEMA_VERSION` 1→2→3 history. A migration library would duplicate transaction handling `anno-store.ts` already owns and would be a second file naming `node:sqlite`'s cousin problem (a second query surface) even if it never imported the module directly. |

## Alternatives Considered

| Recommended | Alternative | When to Use Alternative |
|-------------|-------------|--------------------------|
| Hand-rolled `node:net` buffer + prompt-regex terminator | `node:readline` wrapping the socket | `readline.createInterface({ input: socket })` is tempting because every text-monitor line is genuinely newline-terminated. Reasonable **inside a parser** that already has a complete response string and wants to iterate its lines (e.g. splitting a `memmapshow` dump row-by-row) — not as the framing layer, because `readline`'s natural unit is "one line," and the thing that must be detected here is "the response is complete," which is a multi-line pattern match, not a line count. Use `readline` for the second job, not the first. |
| Refuse-by-schema-version, as `anno-store.ts` already does at every prior bump | An actual `ALTER TABLE`/upgrade-in-place migration arm | See "`node:sqlite` schema/migration mechanics" below — this is the one place this research recommends *reconsidering* the established precedent rather than just continuing it, and says why. |
| Three new `HostToolId` members on the existing seam | A second, parallel "disk/basic tool" control op family | `host-tool-executor.md` is explicit that a second seam is the anti-pattern this milestone's prerequisite work (v0.8.0 Phase 34) was built to prevent — one `host_tool` namespace, one allowlist, one argv builder. Do not special-case c1541/petcat/cartconv into their own op. |
| Probe-and-classify capability detection for `prof`/`chis` (attempt the command, read VICE's own literal refusal string) | A static entry in `capability-registry.ts` | `capability-registry.ts`'s own header scopes it explicitly to **backend-selection** data (fork-vs-stock tool-name divergence, 26 entries, "no credential, no secret ... no tool name that is not already present in one of the two shipped manifests"). Whether *this specific connected binary* was compiled `--enable-cpuhistory` is a **per-connection runtime fact**, not a per-backend-name fact — it is the same shape of problem `stock-diagnose.ts`'s `classifyDiagnoseUnavailable()` already solves for `CPUHISTORY_GET` (attempt the opcode, classify the failure into a named reason, never guess ahead of time). Model the text-channel probe the same way; do not add a 27th `capability-registry.ts` row for it. |

## What NOT to Use

| Avoid | Why | Use Instead |
|-------|-----|--------------|
| Any new npm runtime dependency (a TCP framing lib, a parser-combinator lib, a migration/ORM lib, a second SQLite driver such as `better-sqlite3`) | The project's own `PROJECT.md` already names `better-sqlite3` specifically as an out-of-scope addition (v0.7.0 decision, still binding), and the pattern generalises: every one of this milestone's needs is already covered by a builtin this tree already imports. Zero new deps has been true for several milestones running and nothing here breaks that. | `node:net`, `node:sqlite`, `node:child_process` |
| A second module naming `node:sqlite` (e.g. a standalone `runtime-evidence.ts` with its own `DatabaseSync` import) | `anno-seam.test.ts` scans the shipped module set and fails on exactly this — it is a tested, not documented, confinement. | New exported functions inside `anno-store.ts` itself |
| `PRAGMA user_version` as the schema-version mechanism | The store already has its own answer to this question — an `anno_meta` table with an explicit `schema_version integer not null` column, checked by exact-equality read (`anno-store.ts:518-540`) — chosen deliberately alongside the store's own `pragma integrity_check` and non-empty-row checks, because `PRAGMA user_version` alone cannot distinguish "corrupt" from "version 0" the way the store's three-part refusal already does (see the module header's "zero-length file opens" finding). Introducing `PRAGMA user_version` now would create a second, competing version signal in the same file. | Keep incrementing `SCHEMA_VERSION` in `anno-types.ts` and writing the new value into the existing `anno_meta.schema_version` column, exactly as the 1→2→3 history already does |
| `ATTACH DATABASE` to keep runtime-evidence rows in a second file | `node:sqlite`'s `DatabaseSync` supports `ATTACH` as plain SQL (nothing special in the driver), so it is *technically* available — which is exactly why it needs saying no to explicitly. A second attached file reintroduces the durability problem `anno-store.ts`'s header already solved once (single-file, `delete`-journal-mode, fsync-on-rename) for a second file with none of that discipline, and it fragments the "one seam, one file" model the SIGKILL-durability proof depends on. | New tables in the same `.annostore` file, added to the existing `DDL` string |
| A generic "run any host command" op, or reusing `acme.build`'s or `dxa.disassemble`'s argv shape for the new tools by loosely typing an `args: string[]` passthrough | `host-tool-executor.md`'s rule 5 — "a typed allowlist of named tools, never a shell or argv passthrough" — and this is enforced today by `HOST_TOOL_ARG_KEYS`/`HOST_TOOL_PATH_ARG_KEYS` being explicit per-tool key lists, not a generic bag. | `c1541.<verb>` / `petcat.decode` / `cartconv.<verb>`-shaped `HostToolId` members, each with its own explicit typed argument object and its own `buildHostToolArgv()` branch |
| Treating any of `c1541`/`petcat`/`cartconv`'s **exit code** as the success signal | Measured this session (see below): the three tools do not share one convention. `c1541` and `cartconv` both return exit **0** on a file-not-found error (`c1541`: `Error - Cannot open file ...`, exit 0; `cartconv -f` on a missing file: `Error: Can't open ...`, exit 0); `petcat` returns exit **1** on the equivalent error. A single "exit 0 = ok" wrapper across all three would silently swallow every `c1541`/`cartconv` failure. | Parse each tool's own stdout/stderr text for its own literal success/error markers, per tool, the same way `acme-verify.ts`'s test-only oracle keys strictly on ACME's own result line rather than its exit code |
| VICE's text-monitor assembler/disassembler (`a`/`d`) or `x64`↔`x64sc` mode switching, reached as a side effect of building the text client | Explicitly declined by owner decision 2026-09-06 (`PROJECT.md`, Current Milestone section) — both become reachable the moment the channel opens, and both were declined on the spot as adding a fourth, unowned classifier alongside dxa and Ghidra. | Nothing; leave both uncalled. Reverses only on a named consumer, per that decision. |
| VICE event record/replay as "reproducible run identity" | Falsified by measurement, not merely undesirable: `event.c` carries six event options, none `-record`, and `x64sc -record` exits 255. `PROJECT.md`'s Current Milestone section names this as a corrected false premise carried over from v0.8.0. | Whatever mechanism v0.9.0's phase planning settles on for "run identity" (out of this research's scope — a v0.9.0 architecture question, not a stack question) — just not event replay |

## Stack Patterns by Variant

**If the connected VICE build was compiled with `--disable-cpuhistory` (non-default, but possible — e.g. a stripped-down embedded build):**
- The literal string `"Not compiled with CPU tracing."` is what both `chis` and `prof` reply with — confirmed present verbatim in `/usr/bin/x64sc`'s (this host's genuine stock 3.9) string table alongside the build's own recorded configure line, which shows `--enable-cpuhistory` was explicitly passed. `--enable-cpuhistory` is VICE's own default (`VICE_ARG_ENABLE_LIST(cpuhistory, [ --disable-cpuhistory ...])` in `configure.ac` — opt-out, not opt-in), so most distro builds will have it, but "most" is not "all."
- Probe for this the same way `stock-diagnose.ts` already probes `CPUHISTORY_GET`: attempt the command once (lazily, on first use, or once at monitor-claim time), classify the literal refusal string into a named unavailable reason, cache the result on the connection/instance record for the life of that VICE process. Do **not** add a static `capability-registry.ts` row — this is a per-connection fact, not a per-backend fact.

**If the roadmap wants the evidence layer to survive an existing project's `.annostore` file (i.e., a real store already exists on disk from v0.7.0/v0.8.0 use):**
- Continuing the established precedent (bump `SCHEMA_VERSION`, refuse mismatched stores by exact equality, write no migration arm) means every existing store on every consuming project's disk becomes **permanently unopenable** the moment this ships — see the dedicated section below. This is a genuinely open decision this research surfaces rather than resolves; do not let it default silently to "no migration arm" a second time without re-running the same cost/benefit check `anno-types.ts`'s `SCHEMA_VERSION` doc comment ran at version 3, because the basis that check measured ("no store file is tracked... none exists... no tagged release has ever shipped a store") is very likely **false** by now — v0.7.0 and v0.8.0 both shipped with the store as the substrate, and Phase 37's auto-import (`AUTO-01..08`) exists specifically to *fill* stores from real analysis runs.

**If the phase planner needs the text and binary monitors to coexist on one running instance:**
- This is squarely the milestone's own stated gate ("Bind-time coexistence is confirmed against stock 3.9; interleaved command behaviour is Unverified") and an architecture question, not a stack question — no library choice here changes that answer. Noted only so a reader of this stack research does not look here for it.

A parser keying on content, not on which line the prompt shares, is unaffected either way. |

Observed as the terminal token of every synchronous command's response on both builds this session. This is the reliable end-of-response signal the question asked about: match `/\(\w+:\$[0-9a-fA-F]{4}\)\s$/` against the tail of the accumulated buffer. ## `node:sqlite` schema/migration mechanics, specifically

This subsection answers the question in full because the downstream planner needs the mechanics, not just a library name.

**What exists today (`anno-store.ts`, `anno-types.ts`).** A single `anno_meta` table holds one row: `id integer primary key check(id = 1)`, `schema_version integer not null`, `revision integer not null`. `openStore()` reads that row and requires **exact equality** against the module's `SCHEMA_VERSION` constant (currently `3`); any mismatch throws `AnnoStoreCorruptError`-shaped refusal naming both numbers. There is no `PRAGMA user_version` use anywhere in the module — the application-level `anno_meta` row is the version signal, deliberately, because it can be joined with the store's own "zero-length file opens" and `pragma integrity_check` checks in one place (the module header explains why `PRAGMA user_version` alone cannot tell "corrupt" from "genuinely version 0"). This is `node:sqlite` used exactly as documented: `DatabaseSync.exec()` for DDL and transaction control (`"begin immediate"`, `"commit"`, `"rollback"`), `DatabaseSync.prepare().run()`/`.get()`/`.all()` for parameterised DML/queries. Both `ATTACH DATABASE` and `PRAGMA user_version` are supported by the underlying SQLite `node:sqlite` embeds (as plain SQL, nothing special in the driver surface) — but this project uses neither, by choice, for the reasons above.

**The existing precedent for "add a table."** Version 3 (D-15, 2026-08-29) added `anno_enum_usage` and its index to the `DDL` string with **zero other changes** to any existing table, bumped `SCHEMA_VERSION` from 2 to 3, and wrote **no migration arm** — a version-2 store is refused outright, not upgraded. `anno-types.ts`'s own doc comment names the accepted cost explicitly and, critically, names the *basis* it was measured against: "no store file is tracked in this repository and none exists in its working tree... no tagged release has ever shipped a store at all." That basis is what made "just refuse" cheap at the time.

**What a runtime-evidence table needs, mechanically.** Purely additive DDL — one or more new `CREATE TABLE` statements for observation rows (run-keyed, per the seed: image identity, scenario/bracket identity, address, observed-EXEC bit or equivalent, accumulated monotonically) plus whatever index the join-against-`anno_range` query needs — appended to the existing `DDL` string inside `anno-store.ts`, a `SCHEMA_VERSION` bump to `4`, and new exported functions (an insert path and the agree/disagree join query the seed specifies) in the same file. No `ALTER TABLE` is needed for a pure addition; the entire migration, mechanically, is "create the new table(s) if opening version 3, or just create everything fresh if opening nothing." `node:sqlite`'s transaction primitives (already in use) are sufficient for this — no new API surface is required from the module.

**Where this research recommends *not* repeating the precedent unexamined.** The version-3 doc comment's own words are worth re-quoting: "Stating the difference is the point: this one is a choice, not an impossibility." Unlike version 1 (genuinely unmigratable — the snapshot ring's ownership was unrecoverable), a version-3→4 bump **could** ship a migration arm — literally just running the new `CREATE TABLE` statements against an opened version-3 database before rewriting its `anno_meta.schema_version` to 4, inside the same `begin immediate`/`commit` pair `openStore()` already uses — and whether that's worth doing now turns on a fact this research did not verify: whether any real project's `.annostore` file, populated by two shipped milestones' worth of auto-import and manual annotation, would be stranded by a hard refusal. That is a roadmap/phase-planning decision, explicitly flagged here rather than defaulted.

## Line-protocol client mechanics, specifically

**Transport.** `node:net`'s `connect({ host, port })` returns a `Socket` exactly as `vice-broker-client.ts:412` and `:1148` already do for the binary monitor and the broker control channel respectively — same primitive, third use.

**Framing is not length-prefixed and not per-line.** Unlike the binary monitor (11-byte request / 12-byte response headers) and the broker control channel (newline-delimited JSON, capped at `MAX_LINE_BYTES`), the text monitor's `monitor_network.c` speaks free-form text terminated, per command, by its own prompt string. The measured, reliable signal (see Version Compatibility above) is the prompt pattern `(<memspace>:$<hex4>) ` at the tail of the accumulated response. A client should: accumulate incoming bytes in a buffer, on every `data` event check whether the buffer's tail matches the prompt regex, and if so treat everything before the prompt as the completed response body and hand it to the relevant parser. A byte cap analogous to `MAX_LINE_BYTES` is worth keeping given `memmapshow`'s measured size (a full, unfiltered dump is **65,536 rows**, one per address — several megabytes of text) — this is a real bulk-output case the phase should size for explicitly, not assume away.

**A quiescence/timeout fallback remains prudent**, not because the prompt signal is unreliable in the steady state (it measured reliably in both builds this session) but because the milestone's own stated Unverified item is exactly whether an unsolicited notice can arrive on this channel while a response is in flight — the binary monitor has five such unsolicited types arriving at `0xffffffff`, and nothing in this research rules out an analogous case here. Treat a prompt-match as authoritative when it arrives; treat a long silence with no prompt as the "prove it, don't assume it" signal `stock-diagnose.ts` already uses on the binary side.
