# Stack Research: v1.0.0 "The Rebuild Half"

**Domain:** Static reverse-engineering rebuild pipeline (annotated 6502/6510 binary → multi-file ACME source → reassembled `.prg` → VICE-verified behavioural equivalence), layered on an existing 209k-line TypeScript/Node MCP server with zero build step.

**Researched:** 2026-09-10
**Confidence:** HIGH on ACME directive semantics and on "no prior art exists" findings (each independently searched and cross-checked); MEDIUM on the exact shape of the hazard-detector algorithms this project should write itself (design guidance, not an external claim); HIGH on the zero-new-dependency recommendation (verified against the existing `anno-export-asm.ts` architecture and the project's own Out-of-Scope ledger).

## Headline Answer

**Zero new npm runtime dependencies, zero new host prerequisites.** Every one of the four new capabilities (multi-file ACME generation, swappable data tables, movement-hazard detection, behavioural-equivalence comparison) is reachable by extending code this project already owns: `anno-export-asm.ts` (the ACME emitter), `disasm-decoder.ts`/`disasm-renderer.ts` (the 6510 decoder), `.annostore`'s existing `anno_scope`/`anno_range` tables, the `acme-verify.ts` byte-diff oracle, `capture-pair.mjs`/`compare.mjs` (frame-exact capture + classification), and the already-shipped `vice_cpu_history` (`chis`) text-monitor tool. Nothing in this milestone's four questions requires a library ACME/dxa/Ghidra/`.annostore` don't already give you. Where genuine prior art was searched for (movement-hazard detection especially), it does not exist as a reusable tool or library, on any measured search pass, and that is stated as a finding rather than papered over with a plausible-sounding name.

## 1. ACME Multi-File Source Generation

### Core Directives (verified against ACME's own shipped documentation — `docs/QuickRef.txt` and `docs/AllPOs.txt`, the same texts this project's `acme-build` skill is dated against, "ACME release 0.97 'Zem', 31 Jan 2021")

| Directive | Syntax | Semantics | Relevance to per-scope multi-file export |
|---|---|---|---|
| `!source` (alias `!src`) | `!source "file.a"` | Assembles another file inline, at the point of the directive, then resumes the including file. `"..."` searches the current directory first; `<...>` searches library paths (`-I`). | This is the wiring mechanism: one top-level file `!source`s one file per scope, in address order. |
| `!to` | `!to "out.prg", cbm` | Sets the single final output file and format (`cbm` = 2-byte load address prefix, `plain` = none). Settable once, normally in the top-level file only. | Per-scope files must **never** carry their own `!to` — ACME errors `Output file already chosen` if two files try to set it (already a documented gotcha in this project's own `acme-build/SKILL.md` troubleshooting table). One `!to` in the top-level wiring file only. |
| `*=` | `*= $0801` | Sets the program counter and opens a new segment at that address. | Each scope file opens with its own `*= <scope.start>`, exactly what `anno-export-asm.ts` already does per block today — this generalizes per-block to per-file. |
| `!pseudopc` | `!pseudopc <expr> { ... }` | Assembles as if PC were `<expr>` while the *real* output position is wherever `*=`/prior code left it — i.e. decouples "where bytes land in the file" from "what address the code believes it's at." Measured (already recorded in `anno-export-asm.ts`'s own doc comments): `!pseudopc` **errors** with `Program counter undefined.` unless `*` is already set beforehand. | Only needed if a scope's *load* address differs from its *link* address (e.g. a routine relocated at runtime, or code copied under I/O). Not needed for the common case (scope stays where it was found). Do not reach for it unless a specific relocation case is found. |
| `!zone` (alias `!zn`) | `!zone <title> { ... }` or `!zone <title>` (unclosed, extending to next `!zone`) | Opens a **local-label scope**. Labels beginning with `.` are visible only inside the current zone; a name with no leading `.` is global across the whole assembly regardless of zone. Zones do **not** nest — the manual states "Multiple zones allow reusing local label names" as the entire purpose. | **Load-bearing for per-scope files.** Every generated scope file should open with `!zone <scopeId>` and close it (or let the next `!source`'d file's own `!zone` end it) so that any dotted local labels the exporter emits for that scope (see below) don't collide with another scope's local labels of the same spelling. |
| Local labels (`.name`) | `.loop`, `.exit` | Zone-scoped; cannot be defined a second way (`LABEL=VALUE` form is for globals only). | Use for genuinely intra-routine labels the exporter can identify as never referenced outside their own scope's address range (e.g. a loop-back branch target). Everything cross-scope-referenced must be a **global** (undotted) label — which is what `anno-export-asm.ts` already emits today (it emits every store label as a plain undotted symbol; see `formatSymbolDefinition()`). |
| `!if` / `!ifdef` | `!ifdef LABEL { ... } else { ... }` | Standard conditional assembly, resolved at first pass, condition must be solvable in pass 1. | Not required for the core multi-file split. Becomes relevant only if BUILD-02's "data tables swap without touching code" needs a build-time selector between table variants (see §2) — and even then, the existing `acme.mjs` `-D` flag (already used for `game.asm -DBORDER=2`) is the simpler, already-integrated mechanism; prefer it over introducing `!ifdef` unless a variant needs to change which *file* is included, not just a value. |
| `!sl` (alias `!symbollist`) / `!svl` | `!sl "out.sym"` | Dumps every **global** label to a file after assembly completes; `!svl` writes VICE-monitor-compatible label syntax. | Not new: `acme.mjs build` already produces a `.sym`/`.vs` pair via CLI flags rather than an in-source `!sl`/`!svl` directive, and `acme-build/SKILL.md` documents loading `.vs` via `vice_symbols_load`. No change needed — keep using the CLI route, do not add `!sl` lines to generated source, since it would duplicate a capability the driver script already owns and the two could drift on which labels are "used." |
| `!byte`/`!08`, `!word`/`!16`, `!text`/`!tx`, `!scr` | as documented | Exactly what `anno-export-asm.ts`'s `emitDataLines()` already emits today, unchanged by the multi-file split. | No change — these stay exactly as `disasm-renderer.ts`/`emitDataLines()` produce them; the split only changes *which file* a block's lines land in, never how a block is rendered. |

### What breaks when generated source is split across files (verified against ACME's own multi-pass behaviour and a documented forum report)

1. **Forward references across files are fine — ACME is multi-pass.** ACME resolves an assembly in multiple passes specifically to allow forward references; a symbol defined in a scope file that assembles *later* in the `!source` chain is resolvable from an earlier one. This is not a hazard by itself.

2. **The real hazard is symbol collision from an *unwrapped* local label, not forward reference.** A documented 6502.org report (`"[solved] Symbol already defined" error with ACME assembler`) traces exactly this failure mode: including a file with `!src` re-triggers a re-pass over that file's contents, and a label defined without an enclosing `!zone` is **global by default** — so two `!source`d scope files that both happen to define, say, a bare `loop` label collide with `Symbol already defined.`, while the identical code inlined into one file does not (because ACME's own re-pass semantics for included files interact with global-vs-local resolution differently than for a single file). **Concretely: never emit an undotted local-looking label (`loop`, `exit`, `done`) into a per-scope file without either (a) wrapping the whole file in `!zone <scopeId>` and dotting every label that isn't a cross-scope reference, or (b) giving every intra-scope label a scope-qualified global name** (this project's existing auto-name prefixes — `s_`, `p_`, `l_`, etc. — already guarantee uniqueness project-wide, which sidesteps this hazard for free as long as those prefixes are kept; a human-renamed label that collides across two scopes is the one case a generator must check for before emitting).

3. **Zone boundaries and macro visibility.** ACME zones are **flat, not nested** — a `!zone` inside another `!zone` is simply a second, sibling scope, not a child. This matches `.annostore`'s own `anno_scope` table, which the code already refuses to store as nested or overlapping (`AnnoRangeShapeError`, enforced in `addScope()`). **This is a genuine structural alignment worth calling out to the roadmapper: the store's scope model and ACME's zone model are both flat-and-disjoint by construction, so no translation layer is needed between "annotation-store scope" and "ACME zone" — a 1:1 mapping is correct, not a simplification that will need revisiting.** Macros (`!macro`) are **not currently used** by `anno-export-asm.ts` at all (it emits raw `!byte`/`!word`/decoded mnemonics only), so macro-visibility-across-files is not a hazard this milestone introduces.

4. **`!to` and top-level wiring must live in exactly one file**, per the `!to` row above — this is already a documented failure mode in this project's own `acme-build/SKILL.md` (`Output file already chosen`), just not yet hit in the multi-file context. The generated top-level "wiring" file is new work: `anno-export-asm.ts` today emits one flat file with no `!source` wiring at all, so this is a genuinely new output shape, not a variation on an existing one.

### Integration point

`anno-export-asm.ts`'s block-emission loop (the `for (const block of blocks)` loop building `blockLines`) already groups blocks by contiguous address ranges. The multi-file feature is: (a) join blocks against `listScopes()` instead of (or in addition to) `listRanges()`'s block boundaries, (b) route each scope's `emitBlock()` output into its own generated string keyed by a **filename derived deterministically from `scope.start`** (e.g. `scope_0801.a`) rather than a stored name — **`ScopeRow` has no name column today** (`{ id, start, endInclusive }` only, confirmed by reading `anno-types.ts`), so either (i) derive filenames from the address, which needs zero schema change and is the recommended default, or (ii) add a `name` column, which is a `SCHEMA_VERSION` bump the project's own v0.7.0-era Out-of-Scope ledger already treats as a real, non-trivial cost (`.annostore`'s strict-equality schema check with no migration arm — see the v4 bump discussion in `PROJECT.md`). Recommend (i) for this milestone; a name column is a legitimate follow-on if a human wants readable filenames, not a blocker for BUILD-01.

The existing `acme-verify.ts` byte-diff oracle needs **no change in kind** — it already assembles output and diffs bytes against the image; pointed at the new top-level wiring file instead of a flat single file, the same "assemble with real ACME, diff the bytes" contract holds unchanged. This is the load-bearing reason multi-file export is cheap: the verification oracle is file-shape-agnostic already.

## 2. Data-Table Extraction to Separate, Swappable Files

### The two real choices, and which one wins

| Approach | Mechanism | Byte-identity | Swappability | Readability |
|---|---|---|---|---|
| **`!binary` include** (`!binary "table.bin", size, skip`) | ACME reads a raw binary file directly into the output at assembly time. Verified parameters (from `docs/AllPOs.txt`): filename, optional `SIZE` (pads/truncates), optional `SKIP` offset, optional `INTERLEAVE` step. | Exact — the bytes are read verbatim from disk. | **Best.** A charset, sprite sheet, level layout or music binary can be replaced by overwriting the `.bin` file with zero source-code changes, which is precisely `BUILD-02`'s stated goal ("data tables extracted to their own files so graphics, levels and music swap without touching code"). | Worst for a human reading the `.a` file — the bytes are invisible. Mitigate by keeping the store's own type/comment metadata as a **sidecar comment block** immediately above the `!binary` line, generated the same way `anno-export-asm.ts` already emits block comments today. |
| **Inline `!byte`/`!word` runs** (current behaviour) | The exact mechanism `anno-export-asm.ts`'s `emitDataLines()` already produces. | Exact — proven by the existing real-ACME byte-diff oracle. | Poor — swapping a table means editing hundreds of hex literals inside the `.a` file, which is what `BUILD-02` exists to eliminate. | Best — every byte is visible and commented in place, which is why the exporter currently does this for *everything*, code and data alike. |

**Recommendation: `!binary` for extracted data tables, keeping `!byte`/`!word` for everything else (code and small/one-off constants).** This is not an either/or across the whole export — it's a per-block decision keyed on the store's existing `dataType` column: any block whose `dataType` is one of the twelve typed data members (not `code`) *and* which a human or a later BUILD-02 heuristic marks as "extractable" becomes a `!binary`-included sibling file; blocks left inline stay exactly as `anno-export-asm.ts` renders them today. This requires **no new directive semantics** beyond what's in the table above, and reuses the exact byte-source-of-truth (`expectedBytes` sliced from the image) the existing byte-diff oracle already trusts.

**Trade-off made explicit for the roadmapper:** `!binary` loses ACME's own `!if * != $XXXX` end-of-block drift assertion in the same textual form — the assertion still works (it's driven by ACME's `*` after the include, unaffected by whether the bytes came from `!byte` or `!binary`), but a human reading only the `.a` file no longer sees the byte values that would make a wrong table length obvious at a glance; the drift assertion is now the *only* signal. This is an acceptable trade for swappability and should be stated as such rather than silently accepted.

**File naming and format:** a raw flat `.bin` per table (no header, no length prefix — the `SIZE`/`SKIP` parameters on `!binary` already handle offset/length, so the file itself should be the simplest possible artifact a non-programmer could regenerate from a graphics tool). Do **not** invent a custom container format (e.g. a JSON-wrapped byte array) — that would be a second data model competing with the store's own typed-range vocabulary for no benefit, and it's explicitly the kind of "own the substrate" complexity this project's Out-of-Scope ledger already declines (`bank-qualified addressing as a modelled feature`, `a persisted program.json as a parallel model` — same shape of decision, same reasoning applies to a table wrapper format).

## 3. Movement-Hazard Detection

This is the section where the honest answer is mostly **"nothing exists,"** verified by direct, repeated search rather than assumed. Each of the four hazard classes is treated separately below because the prior-art picture differs meaningfully between them.

### (a) Indexed jump tables, including the RTS-trick idiom

- **The idiom itself is extremely well-documented** — NESdev's own "RTS Trick" wiki page and multiple 6502.org forum threads describe it precisely: an address-minus-one is pushed (`PHA`/`PHA` of high/low bytes, or a `JSR` to a fixed pusher routine) and an `RTS` is then executed, which pops the two bytes, adds one, and jumps there — turning `RTS` into an unconditional computed jump. This is universal 6502-scene knowledge, not obscure.
- **No disassembler surveyed detects it automatically.** `6502bench SourceGen` (`github.com/fadden/6502bench`, actively maintained, MIT-style — a genuine, real, currently-shipping 6502 disassembly workbench) has an **explicit, named feature for RTS-trick tables** ("Adjusted for RTS/RTL" checkbox in its Format Address Table dialog, confirmed against its own tutorial text), which is the single strongest piece of concrete prior art found — but it is **manual**: the user must first recognize the pattern, tag the code entry point, and explicitly check the "adjusted for RTS/RTL" box before the tool applies the +1 offset arithmetic across a batch of entries the user has already delimited. It does not scan a binary and propose "this looks like an RTS-trick table" on its own.
- **Ghidra and IDA** (this project already owns Ghidra 12.1.3) have generic "switch/jump table" analyzers for architectures where the compiler emits a recognizable pattern (a bounds check, an indexed load, an indirect jump) — this is a compiler-output pattern, not a hand-written 6502 idiom, and neither tool's stock analyzer looks for the "push, then RTS" shape at all; this project's own NMOS 6502 SLEIGH extension (Phase 36) does not add such an analyzer and nothing in the codebase claims otherwise.
- **Verdict: no reusable library or tool exists.** The detectable signature this project *can* build cheaply, using data it already has: (1) the runtime evidence layer (`anno_evid_exec`, shipped v0.9.0) already distinguishes observed-executing addresses from unobserved ones — an `RTS` whose *target* varies across recorded runs (multiple distinct `(PC-before, PC-after)` pairs at the same `RTS` address in `anno_evid_exec`) is direct, measured evidence of a computed jump via `RTS`, stronger than any static pattern-match; (2) statically, a plain byte-pattern scan for `PHA ... PHA ... RTS` or `LDA #hi / PHA / LDA #lo / PHA / RTS` immediately preceded by an indexed load from a table region is a legitimate first-pass heuristic **this project must write itself** — there is no existing library to call. Both signals should feed the same hazard report rather than either standing alone, consistent with `EVID-06`'s "disagreement first" pattern already proven in this codebase.

### (b) Self-modifying code

- **6502bench SourceGen** again is the closest named prior art: its manual states it "will always place the label at the instruction start" when an operand target falls mid-instruction, which is the same mid-instruction-label mechanism `anno-export-asm.ts` **already implements today** (`midInstructionLabelLine()`, `MID_INSTRUCTION_LABEL_FLOOR`, the `smc_operand`/`smc_alias` fixture cited in its own doc comments). **This capability is not new for v1.0.0 — it already exists and already has a committed fixture (`fixtures/export-asm/smc.prg`).** What's genuinely new is *detecting and reporting* SMC as a hazard for a human decision, not merely rendering it correctly once found (rendering is solved; flagging is not).
- **No academic or open-source tool statically detects SMC on 6502 code in general** — the closest research found (`arxiv.org/abs/1909.12626`, "Reachability Analysis of Self Modifying Code") targets x86 malware unpackers with a fundamentally different threat model (adversarial obfuscation, not a game routine tweaking its own operand for speed) and is not adaptable as a tool, only as a general idea (trace forward from every store instruction and check whether its target address later gets fetched as an opcode).
- **Verdict: detectable directly and cheaply from what this project already stores**, with no external tool needed. `.annostore` already knows, per label, whether it sits **strictly inside** a decoded instruction (`midInstructionLabelLine()`'s exact criterion). The hazard detector is: enumerate every label at such an address, cross-reference against `anno_evid_exec` for a `STA`/`STX`/`STY`/`INC`/`DEC` instruction whose write target resolves to that same address (a static operand match is sufficient here — no execution trace needed to *find* the write, only to confirm it fires), and report the pair. This is new code, not a new dependency, and it slots directly into the existing mid-instruction-label machinery rather than duplicating it.

### (c) Page-alignment dependence

- **Two distinct sub-hazards exist and were conflated in the question — worth separating for the roadmapper:**
  1. **Correctness-affecting page alignment**: a table or routine that must not cross a page boundary because code reads it with an 8-bit index that wraps (e.g. `LDA table,X` where the author assumed `table` starts at `$xx00` and never checked a carry into the high byte) — a genuine bug class if the table moves during rebuild.
  2. **Timing-affecting page-crossing**: the well-documented 6502 hardware fact that absolute-indexed addressing (`LDA abs,X` / `abs,Y`) costs one extra cycle when the index addition carries into the high byte — this is a **cycle-count** hazard, not a correctness hazard, and only matters where cycle-exact code exists (raster effects — see (d)).
- **No dedicated static-analysis tool for either sub-hazard was found**, on a direct, repeated search. What exists is manual-calculation reference material only (6502.org forum threads explaining the carry mechanism) and per-instruction cycle tables (widely published, e.g. on 6502.org and c64-wiki, already the kind of reference `c64-memory-mapping` already curates for register semantics — no reason not to do the same for opcode timing if needed).
- **Verdict: this project must compute both from data it already has, and the second sub-hazard reuses machinery this milestone already plans to lean on.** For (1), a rebuild that **relocates** a table is the only scenario where this bites — if `BUILD-*`'s stated design keeps every scope at its original address (which the multi-file design in §1 does by default, via `*= <scope.start>`), sub-hazard (1) is largely moot for a same-address rebuild and only becomes live if a human deliberately relocates a table, at which point a purely mechanical check ("does `(table.start & 0xFF00) !== ((table.start + table.length - 1) & 0xFF00)` for any table an indexed instruction reads with an 8-bit index" ) is cheap arithmetic over data the store and decoder already expose — no tool, just a predicate. For (2), the **decoder already classifies addressing modes** (`disasm-decoder.ts`) and 6502 per-opcode base-cycle counts are a fixed, public, unchanging table (part of the CPU's documented behaviour, not something requiring a library) — a page-crossing-cost report is "for every absolute-indexed instruction, is the indexed operand's page fixed or could it vary" cross-referenced against `vice_cpu_history`'s now-shipped per-entry cycle counts (`chis`, `EQUIV-*`'s own planned instrument) for the *measured* answer on a real run, which is strictly stronger evidence than a static guess.

### (d) Cycle-exact raster code

- **No static-analysis tool exists for this**, confirmed by direct search across demoscene, academic and emulator-tooling sources. What the demoscene actually uses, universally, is **manual cycle counting against a published per-opcode cycle table**, plus **empirical verification on real or emulated hardware with a raster-bar / border-color visual probe** — there is no "cycle-exact code verifier" tool named anywhere in the sources found, only calculators and reference tables (e.g. the c64-wiki "raster time" page, forum-posted spreadsheets). This is the one hazard class where the honest answer is closest to "nobody has built this, including outside this project's own domain."
- **What this project already has that gets partway there, without a new tool:** `chis` (`vice_cpu_history`, shipped and parsed in v0.9.0) returns per-entry cycle counts from a real, running stock VICE. That is a genuine, measured cycle-exact record — **but it is an execution trace, not a static verdict**, and it only tells you what cycle count a routine *took on one run*, not whether the code is *designed* to be cycle-exact (i.e., whether small future edits would break timing that currently happens to work). Detecting "this code cares about exact cycle count" statically, from bytes alone, has no known algorithm: it is fundamentally a question about programmer intent (is this IRQ handler positioned to land a raster split at a specific line, or does it just happen not to matter) that no tool infers from a disassembly.
- **Verdict, stated plainly per the quality gate: there is no prior art to point to for this hazard class, and this project should not invent a name for one.** The pragmatic scope for `BUILD-04` here is a **weak, honestly-labelled heuristic**: flag any routine that (i) is entered from a raster/CIA-timer IRQ vector (already resolvable — `.annostore` and the recon skills already identify IRQ handlers) **and** (ii) contains a branch, loop or `NOP`-padding pattern whose cycle count a static per-opcode sum can compute exactly for **one** path through the code (branches with data-dependent outcomes make this only a lower/upper bound, not an exact count) — report it as "IRQ-reached code with a computable cycle count on the traced path; verify against real hardware timing before assuming it can move," never as "verified cycle-exact." This is consistent with the milestone's own stated principle — "the tool reports, the end-user decides" — applied to a hazard class where the tool genuinely cannot know more than that.

### Summary table for §3

| Hazard | Existing tool/library? | What this project should build |
|---|---|---|
| RTS-trick jump table | No (SourceGen has a manual-tagging assist only; not automatic) | Static byte-pattern scan **plus** cross-check against `anno_evid_exec`'s observed multi-target `RTS` sites — the runtime signal is the strong one |
| Self-modifying code | No general tool; academic work targets unrelated x86 malware unpacking | Cross-reference the store's existing mid-instruction-label machinery against write-instruction operand targets — mostly already-owned data, new query only |
| Page-alignment (correctness) | No | Cheap arithmetic predicate over table bounds vs. index width, gated on whether a rebuild relocates the table at all |
| Page-alignment (timing) | No dedicated tool; public cycle tables only | Static addressing-mode classification (already in `disasm-decoder.ts`) cross-checked against `chis`/`vice_cpu_history`'s measured counts |
| Cycle-exact raster code | **None found anywhere, in or out of this domain** | A weak, explicitly-labelled heuristic (IRQ-reached + computable-path cycle sum), reported as a caution, never a verified fact |

## 4. Behavioural-Equivalence Comparison (original vs. a *different* rebuilt binary)

### What was searched for and not found

No tool — inside the VICE project or outside it — is built to compare **two different binaries'** runtime behaviour. VICE's own `Testbench` (`vice-emu.pokefinder.org/wiki/Testbench`, confirmed by direct fetch) is explicitly a **regression-testing framework for the emulator itself** against reference screenshots and pass/fail test programs — it validates that *one* emulator behaves like a reference emulator, never that two different C64 programs behave alike. No TAS/speedrun tooling, no demoscene tool, and no academic paper surfaced anything closer.

### What this project already owns that answers the question without a new tool

This milestone's own `EQUIV-*` requirements already name the right instrument, and it needs extension, not replacement:

1. **`capture-pair.mjs` / the frame-exact stop protocol (Phase 33, `REPRO-*`)** — already proven to stop two *same*-binary runs at the same frame and capture byte-identical 64K RAM. Running it once against the **original** image and once against the **rebuilt** image, to the **same** external checkpoint (an address or frame count meaningful in both, e.g. "just after the title screen routine returns"), is the correct anchor point — this is a mode the code has never been run in (stated explicitly in this milestone's scope: "`compare.mjs` driven in original-versus-different-binary mode, a mode it has never been run in"), not a new capability to build.

2. **`compare.mjs`'s existing three-way classification (volatile / drift / divergence)** is the right shape of answer but the wrong **mask** for this use case as currently configured: its volatile list (`$0000-$0001`, `$0100-$01FF`, `$0200-$03FF`, `$D000-$DFFF`) was tuned for *reproducibility* of the *same* binary, where every differing byte outside those spans is a bug. Comparing a rebuild that is deliberately allowed to differ byte-for-byte (per the milestone's own stated bar: *"byte identical is nothing I care about but the function of it be identical"*) needs the mask **narrowed to the addresses that constitute observable behaviour** — specifically the milestone text already names `$D020`/`$D015`/`$D018` (border colour, sprite enable, screen/charset pointers) as exactly the addresses a real behavioural regression must not be allowed to hide inside a widened volatile mask. This is a parameter change to an existing script, not new tooling: `compare.mjs`'s `VOLATILE` array becomes caller-configurable (or a second named mask) rather than the current single hardcoded reproducibility mask.

3. **Screen-content comparison** for "does it look the same," beyond raw memory bytes: `DISPLAY_GET` (0x84, already a supported binary-monitor opcode per this project's own `vice.ts`) returns an INDEXED8 framebuffer this project's transport already decodes client-side (per the existing constraint that "RGB conversion and PNG encoding move client-side"). A pixel-level diff of two `DISPLAY_GET` captures at the same checkpoint is a legitimate second signal alongside the memory-based one, and needs no new dependency — it's the same INDEXED8 buffer this project already has a client-side decoder for, diffed byte-for-byte the same way `compare.mjs` already diffs RAM.

4. **The committed transcript as the artifact of record** (the milestone's own stated bar for `EQUIV-02`) is a documentation practice, not a tool choice — record the two checkpoints' `compare.mjs` output and, if used, the `DISPLAY_GET` diff summary, verbatim, the same way this project already commits real-ACME transcripts as evidence elsewhere (`acme-verify.test.ts`'s pattern).

**Nothing here calls for a new library.** The behavioural-equivalence question is answered by (a) running the existing frame-exact-stop capture twice, against two different images, to a shared checkpoint — a mode-of-use change, not new code in the stopping mechanism itself — and (b) parameterising `compare.mjs`'s volatile mask rather than widening the reproducibility-tuned default, plus optionally diffing two `DISPLAY_GET` framebuffers as a second, independent signal.

## What NOT to Add

| Avoid | Why | Use instead |
|---|---|---|
| `better-sqlite3` or any other SQLite binding | Already explicitly out of scope since v0.7.0 for `.annostore`; the store already runs on `node:sqlite`. Nothing in this milestone's four questions touches the store engine at all. | `node:sqlite`, unchanged. |
| An interval-tree npm library, for scope/range lookups | Already explicitly out of scope since v0.7.0; `.annostore`'s own narrowest-range-wins paint index already solves range lookup and is proven exact at all 65,536 addresses against an independent linear-scan oracle. | The existing paint index. |
| A `da65`/`ca65`/`ld65` rebuild route, or any second assembler | Already proven an anti-feature at the v0.8.0 close — measured, not theorized: five of six evaluated grounds failed and the rebuild assembled cleanly to a **wrong binary**. This milestone's whole premise (`BUILD-01` wiring `!source` files) is built on ACME, which this project already owns and has a working byte-diff oracle for. | ACME 0.97 "Zem", already integrated. |
| Any npm 6502 disassembler package (`6502-reasm`, `js6502`, `disawsm`, `Dis64`) | Surveyed directly: none has automatic RTS-trick or SMC detection beyond narrow, hardcoded write-opcode heuristics (`js6502`'s SMC support, for instance, is explicitly limited to `STA`/`STX`/`STY`/`INC`/`DEC` only and has no jump-table logic at all); all are small, largely unmaintained, browser-oriented projects with no advantage over this project's own owned `disasm-decoder.ts`/dxa/Ghidra stack, and adopting one would be a second, competing decoder — the exact failure mode `disasm-opcodes.ts`'s own header comments already warn against for a different reason (drift between two copies of the same table). | The existing decoder/dxa/Ghidra trio; write hazard detectors as pure TypeScript over their output and over `.annostore`. |
| `6502bench SourceGen` itself, as a dependency or subprocess | It's a real, useful, actively-maintained tool (cited above as the strongest concrete prior art for RTS-trick tagging) — but it is a Windows-hosted, C#/.NET, interactive GUI application with no CLI/headless/library mode documented anywhere searched. It cannot be shelled out to from a Node host-tool seam the way `acme`/`dxa`/`analyzeHeadless` are, and doing so would also violate this project's "detect, never auto-install" rule for a tool most CI/Linux hosts don't have. | Read its manual for algorithm/UX inspiration only (as this document does); do not integrate it. |
| A custom JSON/binary container format for extracted data tables | Would be a second data model next to the store's own typed-range vocabulary, for a problem `!binary`'s existing `SIZE`/`SKIP`/`INTERLEAVE` parameters already solve. Same reasoning this project already applied to reject `program.json` as a parallel model at the v0.8.0 close. | Raw flat `.bin` files, one per extracted table, read by `!binary`. |
| A general-purpose x86-style SMC/obfuscation-detection framework or academic tool | Domain mismatch — every result found targets adversarial x86 malware unpacking, not a game routine that legitimately overwrites one operand byte for speed. Bringing in that framing would import threat-model assumptions (adversarial evasion, polymorphism) this domain does not have. | The mid-instruction-label + write-target cross-reference approach in §3(b), built directly on already-shipped store data. |
| Building a "cycle-exact code verifier" as a named, confident-sounding feature | No such tool or algorithm exists anywhere surveyed, in this domain or any adjacent one; inventing a plausible name for one here would be exactly the failure mode this research was told to avoid. | The explicitly weak, labelled heuristic in §3(d) — report a computable-path cycle count as a caution, never as a verified guarantee. |
