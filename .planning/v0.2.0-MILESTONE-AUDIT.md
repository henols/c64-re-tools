# Milestone v0.2.0 — Switchable stock-VICE backend — Audit Report

**Audited:** 2026-08-19
**Status:** `tech_debt` — no unsatisfied requirements, no critical blockers, substantial accumulated debt
**Definition of done (ROADMAP.md):** *"a user with an apt-installed VICE can run the six shipped
skills, and is told plainly where they must reach for the fork instead"* — explicitly **not** parity
with the fork.

---

## 1. Verdict

Every in-scope requirement is satisfied with evidence. Cross-phase wiring is genuinely connected —
backend selection through broker launch, protocol client, dispatch, and capability refusal all trace
in source, and the manifest / dispatch table / capability registry / generated docs agree exactly.
Typecheck is clean; `npm test` is 1780 passed / 0 failed / 27 correctly-gated skips / 5 todo.

Two things keep this from `passed`:

1. **The milestone's own finish line has not been observed.** The end-to-end walkthrough — a person
   installs stock VICE and the plugin from the README alone, sets `VICE_BACKEND=stock`, and drives
   `c64-ram-capture` to a full RAM capture — is recorded `pending` in `08-HUMAN-UAT.md`. Everything
   underneath it is proven; the claim itself is not. The human reviewed and approved closing Phase 8
   on that basis, so this is an accepted partial, not a hidden gap — but it is the one sentence the
   milestone exists to make true, and it is still unwitnessed.
2. **Accumulated debt is real and unusually well-documented.** ~20 warning-level findings across five
   phases, 6 pending todos, one non-Nyquist-compliant phase, and four stale planning documents.
   Nothing breaks a success criterion; collectively it is more than a rounding error.

The project's verification discipline is notably strong: gaps were found and closed by re-verification
in Phases 3, 5 and 7 rather than waved through, live proofs were re-run independently by verifiers
rather than cited from SUMMARYs, and two false "live-confirmed" claims were caught and corrected in
07-18. This audit found no case of a requirement marked complete without evidence behind it.

### 4.2 I-1 — Production stock launches apply no config isolation (WARNING, not a blocker)

**Affected:** BROK-01, DIST-03 · **Severity: warning** (downgraded from the integration checker's
initial `critical` after live testing)

`buildViceArgs()`'s stock branch (`broker-launch.mts:173`) emits
`["-binarymonitor", "-binarymonitoraddress", "ip4://<host>:<port>"]` and never `-default`.
`spawnFn(viceBin, viceArgs)` (`broker-launch.mts:255`, via `vice-broker.mts:831`) takes no options
argument at all, so no `XDG_CONFIG_HOME` is set — the emulator inherits the broker's environment and
reads the user's real `~/.config/vice/vicerc`.

Every live test in the milestone isolates both. `stock-live.test.ts:204-208` states `-default` as a
hard requirement citing the recorded flag-order finding; all four live-spawn sites use a scratch
`XDG_CONFIG_HOME`. Most tellingly, `stock-live-broker-monitor.test.ts:255-261` — the one test that
drives the **real** broker daemon — injects a scratch `XDG_CONFIG_HOME` into the broker's env with
the comment *"safe here even though this broker's own stock argv (buildViceArgs()) carries no
-default flag itself."* The production launch path has consequently never been exercised against a
populated `vicerc`.

**Live-tested during this audit, and the alarming reading does not hold.** This machine's
`~/.config/vice/vicerc` carries `MCPServerEnabled=1` (fork residue) and `ConfigVersion=3.10` — the
exact contamination the isolation exists for. Spawning with the *production* argv against the real
config:

| Binary | Args | vicerc | Monitor bound? |
|---|---|---|---|
| `/usr/bin/x64sc` (3.9) | production (no `-default`) | real, 3.10-written | **yes** |
| `/usr/local/bin/x64sc` (3.10) | production (no `-default`) | real | **yes** |
| `/usr/local/bin/x64sc` (3.10) | `-default` first | real | yes |

The recorded flag-order finding is about **ordering** — `-default` *after* `-binarymonitor` clobbers
the monitor enable. Production passes no `-default` at all, which is the safe case, and the 3.9-vs-3.10
config-version modal did not appear. So this is **not** a broken flow, and the same correction applies
to Phase 8's WR-02: the README's published command binds correctly on both binaries against a real
config.

What remains genuinely true, and worth fixing: production has **no** defence against a persisted
`vicerc` leaking a resource into a broker-launched instance (`jamaction` is the case the project's own
test headers name), and this path has never been exercised under one. `spawnFn`'s two-argument
signature means adding isolation is a small refactor, not a one-line change. Fix shape: give `spawnFn`
an options parameter and set a scratch `XDG_CONFIG_HOME` for stock launches, mirroring what the test
harness already does.
