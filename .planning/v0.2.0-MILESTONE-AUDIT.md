### 4.3 NEW-1 — the "same argument shape" claim is not literally true (warning)

The D-07 standing constraint (`ROADMAP.md:61-62`, echoed verbatim at `docs/tool-support.md:5`) says a
tool advertised on both backends keeps *"the same name and the same argument shape"*. Diffing every
shared tool's `inputSchema` programmatically: **17 of 34 differ.** Stock adds optional properties the
fork does not have — `vice_memory_read`'s `sideEffects`, `vice_checkpoint_add`'s
`acknowledgeTraceRisk`, `vice_run_until`'s `timeout_ms`, and so on — each labelled "Stock-only" in its
own description.

**Why this is a warning and not a gap.** A breaking-change diff — properties *removed*, properties
*retyped*, or fields *newly required* — was run separately and returns exactly one hit:
`vice_checkpoint_set_condition`, whose stock schema **omits** `type` where the fork declares
`"type": "string"`, deliberately and with the reason stated inline in the manifest ("the checker's
supported subset has no union keyword to express 'string or object'"). That is a widening, not a
narrowing. Every divergence is permissive: the fork's required-field set is an unmodified subset of
stock's schema, so a call shaped for the fork manifest remains valid against stock. The failure mode
D-07 exists to prevent — a skill silently misbehaving because the two shapes disagree — does not
occur. The two skill docs that reference a diverging field (`c64-program-recon`'s
`tool-selection.md`, `vice-wedge-triage/SKILL.md` on `vice_run_until`) already caveat it as
backend-qualified.

**Recommended fix (not a tag blocker):** either loosen the wording at both sites to *"the same name
and a backward-compatible argument shape — stock may add optional, clearly-labelled parameters"*, or
add a structural test asserting the intended invariant (fork's required-field set ⊆ stock's schema)
rather than exact equality. Worth doing before someone writes a schema-equality test against the
current prose and finds it red.
