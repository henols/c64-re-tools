# Working plan

The step-by-step plan for building c64-re-tools from the frozen design in
[`redesign/`](redesign/README.md). Milestones follow
[`19-implementation-plan.md`](redesign/19-implementation-plan.md); this file
turns them into small steps with a status each.

Rules:

- One step is pushed straight to `main`, no PR. It ends with `pnpm typecheck && pnpm test` green (no build since D17).
- Only the current milestone is expanded into steps. Expand the next one when you start it.
- Everything is built new. Nothing from the deleted implementation is ported.
- Open design points are decided once, in [Decisions](#decisions). Change a decision here first, then the code.

Status: `[ ]` todo · `[~]` in progress · `[x]` done

## M6 — Disk and BASIC tooling

Acceptance (19 §8): with real fixture media, inspect a D64 directory, extract a PRG, decode its BASIC loader, find its machine-code handoff, and load the extracted program in VICE.

- [x] M6.1 **c1541 adapter** — `c1541.inspect` on the wire (image bytes as the attachment, `d64`/`d71`/`d81`/`g64`), `src/host/tools/c1541.ts`: c1541 does the image work (`info`, `dir` free count, `bam`, `chain t s`, `bread` raw blocks); the adapter parses the raw header and directory blocks, so file names keep their exact PETSCII bytes (c1541's own `dir` and name arguments lose case). c1541 exits 0 on errors, so failures come from its output and from missing output files. A damaged structure (chain loop, block out of range) is `media-error`; a missing name is `found: false`.
- [x] M6.2 **petcat adapter** — `petcat.decode`, `src/host/tools/petcat.ts`: `petcat -2` for the listing; the adapter parses the tokenized lines itself (end marker at a zero link high byte, as BASIC relinks), checks that petcat's line numbers match, and finds SYS/USR handoffs in the tokens outside strings, REM and DATA. A constant SYS expression gives an address; anything else is `computed`. Bytes that are no BASIC program give `decoded: false`.
- [x] M6.3 **Host client** — `inspectDisk` and `decodeBasic` in `src/host-client/tools.ts`, reading project files through `transfer.ts`.
- [x] M6.4 **c64-disk skill** — `skills/c64-disk/scripts/disk.ts` (directory, bam, entry, chain, read with `--out`) and `SKILL.md` (ASD-STE100).
- [x] M6.5 **c64-basic skill** — `skills/c64-basic/scripts/basic.ts` and `SKILL.md` (ASD-STE100).
- [x] M6.6 **Acceptance** — a D64 made by real c1541 with a BASIC loader and its machine code: directory → read → decode → handoff → `c64_autostart` of the extracted program, run until BASIC reaches the handoff in VICE (live part opt-in).

## M7 — DXA + normalized-findings importer

Acceptance (19 §9): a fixture PRG goes through DXA, normalized findings and the importer into knowledge.db; a second DXA run with changed results retires obsolete DXA facts, keeps history, protects semantic knowledge, and a malformed result imports nothing.

- [x] M7.1 **Importer** — `src/knowledge/import.ts`: normalized findings (analyzer, coverage, authoritative categories, symbols, regions, references), complete validation before any write, one revision per import, same-analyzer retirement in authoritative coverage, coverage-aware region splits, semantic and other-analyzer rows kept. Only code against data is a conflict (12 §12, §19); unchanged facts keep their rows, so a repeated run makes no revision.
- [x] M7.2 **DXA adapter** — `dxa.analyze`, `src/host/tools/dxa.ts`: dxa 0.1.5 with `-a dump -p all-nmos6502 -d skip-scanning` (`-U` for a PRG, `-g 0000` for 64 KiB), seeds as routine, data-block and xa label files (only when they have lines: dxa refuses an empty file). The listing is checked line by line (address order, from the load address to the end, each line as long as its bytes or data items) before regions, labels and the listing attachment leave the host. Regions are authoritative, labels are not (16 §9).
- [x] M7.3 **c64-static-analysis DXA path** — `analyze.ts --analyzer dxa [--listing <file>]`: the same knowledge seeds, DXA → normalized findings (labels as non-authoritative label symbols, regions authoritative), the same importer; the SKILL.md makes DXA the first pass and Ghidra the deeper one.
- [x] M7.4 **Acceptance** — `test/integration/dxa/findings-import.test.ts` with the real scripts, host and dxa: a first pass into knowledge, a semantic rename and classification, a changed program whose second pass retires three DXA regions in one revision (history kept, semantic rows kept, echoed seed not owned), and a truncated listing that imports nothing. ## M8 — Ghidra deeper analysis

Acceptance (19 §10): the NMOS language compiles, decodes all 105 undocumented opcodes with the right lengths, has tested p-code for the deterministic families, stops flow at JAM, keeps unstable instructions opaque and models NMOS decimal mode; then Ghidra findings go through the same importer, a semantic rename seeds the next run, and an echoed seed does not become Ghidra's.

- [x] M8.1 **NMOS language** — `src/host/tools/ghidra/language/`: a complete 256-opcode NMOS 6502/6510 SLEIGH language with its own id (Ghidra's 6502 decodes only the 151 documented opcodes, has no decimal mode, and its STA pattern takes $89, so a layer over it would clash). Deterministic undocumented instructions get real p-code; XAA/LXA/AHX/TAS/SHX/SHY use opaque pcodeops that keep their inputs; JAM does not fall through; ADC/SBC and the decimal-sensitive undocumented instructions follow NMOS decimal mode. Build copies the Ghidra assets into `dist/`.
- [x] M8.2 **Headless runner** — `src/host/tools/ghidra/index.ts`: find Ghidra (`C64RT_GHIDRA` install directory, or `analyzeHeadless` on PATH), run it with a per-request settings directory (`XDG_CONFIG_HOME`/`XDG_CACHE_HOME`) that holds the language as an extension, a disposable project, our script directory and a bound; the user's Ghidra install and settings stay untouched.
- [x] M8.3 **Language acceptance** — real-Ghidra tests (skipped without Ghidra): compile, the 105-opcode sweep, p-code emulation of SLO/RLA/SRE/RRA, SAX/LAX, DCP/ISC and the immediate family, JAM flow, opaque unstable instructions, decimal arithmetic.
- [x] M8.4 **ghidra.analyze** — wire types and bounds (16 §10), a Java export script (functions with name source, code/data regions, references, bounded decompilation), seeds (entry points, data ranges, labels), complete validation before the result leaves the host.
- [x] M8.5 **c64-static-analysis skill** — `skills/c64-static-analysis/scripts/analyze.ts`: seeds from current knowledge, `ghidra.analyze`, Ghidra → normalized findings (seed names stay semantic), `importFindings`, a compact result; `SKILL.md` (ASD-STE100).

- [x] M12.10 **TypeScript only, through npx (D17)** — no build and no `dist/`: the bins are `src/*/main.ts` with a `#!/usr/bin/env tsx` shebang and tsx is a runtime dependency; `tsc` only typechecks; esbuild and `distribution/bundle.ts` are gone. - [x] M12.11 **Heartbeat (D18)** — protocol version 2: after `ready` the client pings every 10 s and the host answers `pong`; either side closes a connection that sent nothing for 30 s, the host with its session and emulator. TCP keepalive on both ends. The ping never reaches the VICE session, and the host never probes VICE: any monitor command stops the CPU, so VICE liveness stays passive (process exit, monitor socket close).
- [x] M12.12 **A held VICE (D19)** — VICE's own pause (Alt+P) or a dialog makes it take no monitor commands, and every command sent meanwhile runs once it goes on. A monitor timeout on an open connection is now its own error: the operation fails with a message that names the pause or dialog, later operations fail at once and send nothing, and the session waits with no limit for VICE to answer a ping and a text command, then puts the machine back as it was before (running again unless a breakpoint hit). - [x] M22.4 **Switches in the source (D72)** — a patch is written as `!if SWITCH { code, NOP fill } else { original }` in a `!zone`, with a size guard that stops ACME with `!error`; the names inside the range are written once before it as `name = * + n`, so both builds define them. `constants.asm` sets each switch to 0 unless the build defines it. c64-source builds each switch on, and reports `fits`, `overflow`, `changes outside` or `does not assemble`; a failure gives exit 1.
- [x] M22.5 **Macros in the source (D73)** — `macros.asm` with the definitions, included by `main.asm` and `loader.asm`; a use is one `+name args` line. A use falls back to the instructions, with the reason, when a name points inside it, it lies in a patch, ACME refuses it, or its bytes differ from the image.
- [x] M22.6 **Macro candidates** — c64-static-analysis finds a fixed list of idioms (`inc16`, `dec16`, `add16_8`, `add16`, `sub16`, `set16`, `mov16`, `wait_line`) in code regions and reports them as candidates; `--macro-batch` writes an `apply` batch with the definitions and uses. It writes no knowledge (D51).
- [x] M22.7 **Texts** — c64-knowledge, c64-source, c64-static-analysis and c64-assembler SKILL.md; 06 §4 and 11. ASD-STE100, ste-lint at 0 hard.
- [x] M22.8 **Acceptance** — `test/e2e/switches-macros.test.ts`: a switch with three patches and one with only NOP, a macro with two uses of which one falls back; the source is `check.identical`, the switch `fits`, a build with the switch on differs only in the patched ranges, and the analyzer batch applied keeps the source identical (with ACME and Ghidra).

## Decisions

Points the design leaves open, decided for M1. Revisit a row before changing the behavior it describes.

| # | Point | Decision |
|---|---|---|
| D1 | Framing | Each frame: 4-byte big-endian length, then UTF-8 JSON. Max frame 1 MiB. Binary attachments (M5) travel as raw length-prefixed frames announced by a JSON header. |
| D2 | Handshake | Client sends `hello {protocol: "c64-re-tools-host", version: 1, role: "vice-session" \| "tool"}`. Host replies `ready` once VICE is up, or an `installation-incomplete` error on mismatch. The connection is the session; no open/close messages. |
| D3 | Correlation | Each request carries a client-chosen id. The host replies in completion order and serializes VICE work per session. A disconnect drops queued work. |
| D4 | Wire errors | `{code, message}` using the 15 §5 codes, chosen by the host. host-client passes them through; MCP returns them as `isError` results. |
| D5 | Endpoint | TCP port 6464 on every address (`0.0.0.0`, D35). Client tries `127.0.0.1`, `host.docker.internal`, `host.containers.internal`; `C64RT_HOST=host:port` overrides. |
| D6 | Auth | None (D35). |
| D7 | Orphans | Process groups cover normal exit and signals; the exit guard also removes owned scratch paths. A watchdog process per Host Runtime (M12.1), and per skill script or CLI run that starts native tools, runs in the temporary directory, notices its owner's end through an inherited pipe (a pid poll is only the fallback), and stops every registered group and removes every owned path when the runtime dies by SIGKILL or a crash. |
| D8 | Finding VICE | `C64RT_VICE`, else `x64sc` on `PATH`. If missing, refuse by name with the install remedy. Never auto-install. |
| D9 | MCP SDK | `@modelcontextprotocol/sdk`, stdio transport, plus its schema library. No other runtime dependency in M1. |
| D10 | Video standard | PAL by default; `C64RT_VIDEO=ntsc` at MCP start. Fixed for the session. |
| D11 | VICE crash | Fail the operation with `machine-state-lost`. No automatic restart in M1. |
| D12 | DXA order | DXA was not installed during the first pass, so M8 (Ghidra) went first through the same importer; M7.2–M7.4 were built once Henrik installed dxa 0.1.5. |
| D13 | Test execution | Decided by Henrik: c64-testing scenarios (and the c64-unpacker capture) run in a skill script that opens its own VICE session through the host client, with the same operations the MCP uses. 19 §11 asks for scenarios and A/B runs in code and an automated acceptance. A test run starts a VICE of its own beside the MCP's. |
| D14 | Host start and status | Decided by Henrik: the Host Runtime is only started by hand, in the foreground. Before it listens it starts VICE once with the session arguments and stops it again; it refuses to start when VICE is missing or does not start, for example without its ROM files, and prints VICE's own error lines (VICE writes a log file, because its piped output is lost when it exits early). No autostart, no service files, no `diagnose`. `c64-re-tools status` shows the version, the programs on PATH, the tools that skill scripts run here, whether the Host Runtime answers, and VICE and its tools on the host (`host.status`), each found and run once. |
| D15 | Analyzer seeds | Seeds come only from semantic knowledge (user and LLM): their routines as entry points, their non-code regions as data, their names as labels. 12 §18 says "current" symbols and regions, but an analyzer's own facts fed back as seeds force the same answer again, so a re-analysis could never retire them (12 §7); found live with DXA in M7.4. |
| D16 | Tool placement | Decided by Henrik: the Host Runtime handles only VICE and the tools that come with it (c1541, petcat). Skill scripts run ACME, DXA and Ghidra themselves, on the machine of the agent, through `src/native/` (one supervisor with an exit guard, staging, bounded runs); 18 §8 placed them on the host. Their parameter and result types left the wire protocol, and the Ghidra assets ship inside the c64-static-analysis bundle. |
| D17 | TypeScript only, through npx | Decided by Henrik: everything that runs is TypeScript, also when installed; nothing is built and nothing is linked. Users run the programs with `npx -y …@latest`, and the MCP declaration does too, so they update themselves. Node 24 runs `.ts` by type stripping, but never under `node_modules` (`ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING`), where npx installs; so the bins run with tsx (a runtime dependency, by shebang). Installed skills hold `.ts` files in the project, where Node runs them. Replaces the JavaScript artifacts of 08 §6, 09 §1 and 18 §11–13, and the global binary of M11.2. |
| D18 | Heartbeat | Henrik asked how the host finds an MCP that went away without a clean close. A close (also after kill -9) was already enough; a half-open connection (container network, sleep) or a hung client was not. After `ready` the client pings every 10 s; the host closes a connection, its session and its emulator after 30 s without any frame; the client fails a host that sends nothing for 30 s like a closed one. Protocol version 2, so a host and a client from different releases fail the handshake with "restart the host runtime" (likely with npx @latest). VICE itself is never pinged: a monitor command stops the CPU. |
| D19 | A held VICE | Henrik asked that a paused machine is not released and that a timeout does not end in a vague "not responding". Found live: monitor commands never resume a stopped CPU, and VICE's window keeps answering while the monitor holds it; only VICE's own pause or a dialog stops it taking commands, and those commands run later. So a timeout holds the session (operations fail at once with the cause and the remedy, nothing is sent), and when VICE answers again the session restores the run state from before the failed operation. The first detection still takes the 10 s request limit. |
| D20 | Headless VICE, a window on demand | Henrik asked that VICE always starts headless and that the agent can show the same machine in a window when it needs the user's input, and hide it again; breakpoints must survive, and it must work the same on Linux, Windows and macOS. Found live and in VICE's source: `-console` (common startup code: no UI) runs VICE with no window and no display, and it is a start option only, so a mode change is a new VICE process. A snapshot holds RAM, registers, the cycle clock and the disk in drive 8 (as GCR data, so writes go along), but no checkpoints; attaching the image file on top of a restore makes VICE write the restored disk into that file. So the session moves the machine by snapshot into a new VICE and sets the session state again (M12.13); the image is never attached again. A request for the current mode does nothing and succeeds. A held VICE (D19) can only happen with the window open. When the window VICE ends without `close`, the session goes back headless from the state of when the window opened instead of losing the machine (D11 stays for crashes). Adds `c64_window` to the 15 §37 tool list and `window` to `c64_status`. |
| D21 | Results after a live run | Henrik asked to fix what a hand-driven live run found. 15 §12/§13 listed points without their conditions, so an agent could not see a condition after it set one; the session already keeps it (D20), so every point result now carries it, in the input form. 15 §8 gave no pc for a reset that stops, although the stop is at the reset vector; the result now gives it. AP SDK writes Windsurf's MCP declaration to the home directory in project scope (Windsurf has no project file) and records it in the project manifest; the CLI puts the home file back and drops that item, so a project install never changes the home directory and a project uninstall never removes a global declaration. After uninstall the CLI removes the directories AP SDK leaves empty and MCP configuration files that hold only an empty server list. The phantom keys of the joyport simulation device stay: Henrik decided that this is how a C64 works (corrected by D56: they are VICE bug #2202, not C64 behaviour). |
| D23 | Oldest VICE | Found in CI: VICE 3.7.1 (Ubuntu 24.04) has no monitor profiler and answers CPU history, until-return and c1541 chains differently. 3.9 and 3.10 pass every live suite; 3.8 was never tested. So the minimum is VICE 3.9, for x64sc, c1541 and petcat. The Host Runtime refuses an older x64sc when it starts (VICE_INFO), the adapters refuse an older c1541 or petcat at first use, both by name with the remedy (D8). Replaces the "3.6 or later" of the remedy text. |
| D24 | MCP declaration on Windows | On native Windows `npx` is a `.cmd` shim, which a harness starts only through `cmd /c` (Claude Code documents this). The plugin is evaluated on the machine where `install` runs, so an install there declares `{"command": "cmd", "args": ["/c", "npx", "-y", "--package=@henols/c64-re-tools@latest", "c64-re-tools-mcp"]}`; elsewhere the declaration stays `npx …`. |
| D22 | Drive stops | Found live: a drive 8 checkpoint makes VICE enter the monitor from inside the drive CPU, while the computer's CPU is between two cycles of an instruction, and VICE makes drive 8 the text monitor's default device. A computer register write was then lost or applied later, the first frame count ended one frame early, and load, d, hunt, mmsh and stopwatch acted on the drive. The session completes such a stop before its next command, before an observation or a pause that first sees it reports registers, and inside a run that it ends: a computer exec checkpoint over all memory and a resume, so VICE enters the monitor from the computer's CPU at its next instruction. The drive runs those few cycles too, which 15 §11 already allows for drive targets. Every text command that acts on the default device first selects the computer (`dev c:`). |
| D25 | Marketplace plugin | The Claude Code marketplace route (`.claude-plugin/plugin.json`) installs the repository as a plugin. | D27 | Kept after the strict review | The review asked for these; Henrik's "in order" left the call to the lead, who kept them: `src/c64.ts` keeps the BASIC and VIC-II helpers, because host, VICE, native and skill code use them (its address type is a plain number, not a brand); `host.status` keeps each tool's path for `c64-re-tools status`, which a person reads, while refusals that reach an agent name the tool only; `c64_memory_find` keeps `end` optional with default `$ffff`; the static-analysis script keeps Ghidra as its default analyzer, while SKILL.md and the README lead with a DXA pass; petcat results keep `loadAddress`, `basicEnd` and `reason` beyond 16 §13; the CLI keeps its human-readable output instead of the skill scripts' JSON envelope. |
