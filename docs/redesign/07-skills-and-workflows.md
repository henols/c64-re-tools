# 07 — Skills and workflows

## 1. Role of skills

Skills are the workflow/intelligence layer for an LLM harness.

They explain:

- what capability to use;
- when to use it;
- why it is useful;
- useful sequencing;
- how to interpret results;
- when evidence is insufficient.

They do not implement the underlying capability.

## 2. Binding rule

```text
Skill:
  HOW / WHEN / WHY

Application/tooling:
  WHAT actually happens
```

A skill must not contain its own:

- PRG/D64 parser;
- memory-diff engine;
- annotation/knowledge store implementation;
- VICE monitor client;
- host-tool launcher;
- filesystem staging protocol;
- duplicated project-root resolver when the integration already has one.

## 3. Reverse-engineering workflow

A reverse-engineering skill may guide an agent through steps such as:

```text
identify/load subject
  ↓
inspect BASIC/entry path
  ↓
trace execution in VICE
  ↓
DXA first-pass disassembly / structural discovery
  ↓
automatic import of compatible structural findings
  ↓
inspect current knowledge + runtime evidence
  ↓
LLM/user add semantic names, classifications and comments
  ↓
Ghidra deeper analysis seeded by current knowledge
  ↓
automatic import of compatible structural findings
  ↓
review conflicts/history and refine semantic knowledge
  ↓
reconstruct source
  ↓
build
  ↓
compare behavior
```

DXA and Ghidra are complementary rather than competing analyzers:

- **DXA normally comes first** for an unfamiliar program because it is the fast 6502 disassembly/structural pass.
- **Ghidra normally comes later** when established entry points, known data regions or a deeper control-flow/data-flow question justify the heavier analysis.
- Analyzer processes never open `knowledge.db`; the Application API deterministically imports durable findings.
- Automatic imports fill gaps and add compatible structure but do not silently overwrite conflicting semantic knowledge.
- Current accepted knowledge is fed back into later Ghidra runs as entry points, data ranges and labels where supported.
- LLM/user semantic edits may replace generated analyzer names with application-specific names while preserving the generated values in database history.

The skill invokes deterministic MCP operations for each concrete action.

## 4. Working with project knowledge

Skills should normally ask for current context before reasoning about an address:

```text
knowledge.at(address)
```

This returns the symbol, region, comments and references already known there.

When something appears wrong or surprising, skills can inspect:

```text
knowledge.history(address)
knowledge.revision(id)
```

to see how the project arrived at its current knowledge.

Examples of useful review questions:

- Was this routine name generated by Ghidra or chosen semantically by the LLM/user?
- When did this region change from code to sprite data?
- Which Ghidra/DXA import introduced a questionable reference?
- What explanation accompanied an LLM rename?
- Was an earlier conclusion later reverted?

The database's revision history is the authoritative knowledge history; Git is not used as a substitute for these queries.

## 5. Development workflow

Development skills may guide:

```text
edit source
  ↓
assemble
  ↓
autostart/load
  ↓
set breakpoints/watchpoints
  ↓
inspect memory/registers/screen
  ↓
run tests/scenarios
```

The same machine/debug/build tools are shared with reverse engineering.

## 6. Skill composition

Prefer focused skills with clear responsibilities rather than one enormous C64 skill. A high-level reverse-engineering skill may reference focused skills/capabilities, but the implementation logic remains in the tool layer.

The exact skill catalogue can evolve during implementation. The architecture does not bind the project to the current twelve-skill split.

## 7. Long repetitive work

Skills should request higher-level deterministic operations when repetition would otherwise force the LLM to perform large loops of tiny calls.

Bad pattern:

```text
LLM: step → read → step → read → step → read ... thousands of times
```

Preferred pattern:

```text
LLM: request bounded trace/compare operation
Tool: performs deterministic loop
Tool: returns compact result
LLM: reasons about result
```

## 8. Refuse rather than invent

Skills should preserve uncertainty. If evidence does not establish what a routine/data region does, the workflow records only what is justified rather than manufacturing a confident label or explanation.
